## P1 Problem

At runtime a member is declared server-side-only in one of **three** ways:

1. `[ServerSideOnly]` (`Source/LinqToDB/Mapping/ServerSideOnlyAttribute.cs`);
2. an `Sql.ExpressionAttribute`-derived attribute whose `ServerSideOnly` is true — **including by constructor default**: every `Sql.ExtensionAttribute` ctor chains to `Sql/Sql.ExtensionAttribute.cs:454-460`, which sets `ServerSideOnly = true`, so a bare `[Sql.Extension("…")]` is marked with nothing written;
3. any `Sql.TableFunctionAttribute`-derived attribute — `Internal/Linq/Builder/ExpressionTreeOptimizationContext.cs:85-90` flags it server-side-only on a path that never calls `IsServerSideOnly`.

Against a member's body, only two of the four combinations are defects:

| | real body | throw-only stub |
|---|---|---|
| **marker present** | valid — mapped SQL in-query, body serves callers outside one | **defect** unless the stub throws `ServerSideOnlyException` |
| **marker absent** | valid — an ordinary client-evaluable member | **defect** — the member can be client-evaluated and will throw |

Nothing in the build checks either. Today they are violated in 19 places:

**Marker missing (6).** `Sql/Sql.GroupBy.cs:8-10` — `IGroupBy.Rollup<T>`/`Cube<T>`/`GroupingSets<T>` throw `ServerSideOnlyException` from `GroupByImpl` with no marker of any form, while `Sql.Grouping` at `:29` carries one. `Sql/Sql.cs:158` `Sql.Property<T>`. `Sql/Sql.Strings.cs:88-91` and `:103-107` — `StringAggregate` ×2, whose doc comments say *"will always throw. Use only inside an `IQueryable` expression tree"*.

**Wrong exception in a marked stub (13).** `Sql/Sql.Row.generated.cs:970-1006` — ten `Overlaps<T1..T10>` marked `ServerSideOnly = true` and stubbed with `throw new NotImplementedException()`; emitted by `Sql/Sql.Row.tt:201`. `Sql/Sql.Window.cs:2989-2995` and `:3049-3054` — group-form `PercentileCont`/`PercentileDisc` throw `InvalidOperationException` while their own windowed siblings at `:3014-3016`/`:3073-3075` throw `ServerSideOnlyException`. `Sql/Sql.cs:65-69` — `Sql.Spread<T>` throws a bare `InvalidOperationException()` with no message.

The failure this produces is #5782: `Sql.Window`'s 104 methods were unmarked, the build was green before and after #5783 hand-applied the marker, and the omission surfaced only as a runtime exception in user code.

## P3 Constraints & anti-goals

- **No public-API surface change.** `ServerSideOnlyException` already ships both constructors (`PublicAPI.Shipped.txt:7724-7726`) and **must not gain a third** — see D-7.
- **No generated SQL change and no baseline movement.** Any baseline diff is a defect in this change.
- **Do not reshape the client-evaluation pipeline.** `ExpressionTreeOptimizationContext`, `ExpressionBuildVisitor`, `ExposeExpressionVisitor` and `GroupByBuilder` are **read-only** for this branch.
- **`Source/CodeGenerators` ships in no package** (`IsPackable=false`) and must stay that way.
- **The user-facing rules must not require a linq2db version floor** — resolve every symbol by metadata name; absence means silence.
- **Anti-goal: a marked member with a real body is valid** and must never be reported (D-9).
- **Anti-goal: do not add markers to the `[ExpressionMethod]` stubs.** D-8 form 4 makes them silent by classification instead.
- **Anti-goal: no new `.editorconfig` per-rule severity lines.** `.editorconfig:140` bulk + the `[Source/CodeGenerators/**.cs]` RS1015 waiver at `:686-691` already cover new ids.
- **Anti-goal: no `Tests/Linq` production changes.** New fixtures go in `Tests/Tests.Analyzers`; `Tests/Linq` is read-only and serves only as the dogfooding corpus.
- **Anti-goal: no code fix and no options for the internal rules** — D-10, D-11.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — The stub test is "the whole body is one throw", any exception type

- **chosen:** classify a member as a stub when its body is a single `IThrowOperation`, accepting both the expression-bodied and block-bodied shapes (U-7). Which exception types *matter* is decided per-arm by D-12.
- **rejected:** key on the *syntax* `=> throw …` — misses the block-bodied form, where `Sql.Spread` (`Sql.cs:68`), `ConvertRemover` (`:201`) and `Stuff` (`:664`) live. Measured: 75 block-bodied throw-only stubs in `Source/LinqToDB`, and an expression-bodied-only scan missed the `Sql.Spread` defect entirely.
- **why this:** the operation-shaped test is what makes a broad trigger affordable. A naive text search for `=> throw new <X>` over `Source/LinqToDB` returns **328** non-`ServerSideOnlyException` hits, almost all `switch`-arm defaults, ternaries and guard clauses, which an operation block never confuses with a body.
- **failure mode of the choice:** a member whose body is one throw *by coincidence* is a stub by this test. D-12's arm-B exception list is what keeps those out of the report.

### D-8 — The analyzer's marker set: the three runtime forms plus `[ExpressionMethod]`

- **chosen:** a marker is present when **any** of: (1) `[ServerSideOnly]`; (2) an `Sql.ExpressionAttribute`-derived attribute whose *effective* `ServerSideOnly` is true — explicit `= true`, **or** the attribute type derives from `Sql.ExtensionAttribute` and no explicit `= false` is written; (3) any `Sql.TableFunctionAttribute`-derived attribute; (4) `LinqToDB.ExpressionMethodAttribute`.
- **rejected:** read only the attribute's named arguments. `Sql.ExtensionAttribute.cs:454-460` sets `ServerSideOnly = true` in the ctor every other ctor chains to, so a bare `[Sql.Extension("…")]` is marked with nothing written; the rejected design reported *correct* user code and offered a no-op fix (`Tests/Linq/UserTests/Issue2562Tests.cs:14-20`, `Issue773Tests.cs:31-34`, `Linq/FunctionTests.cs:764-767`).
- **rejected:** the two forms `MappingExtensions.IsServerSideOnly` reads. Misses form 3, so `SqlFn.OpenJson` (`:1515`, `:1528`) — correctly declared — would be falsely reported and "fixed" with a redundant `[ServerSideOnly]`.
- **rejected:** treating `[ExpressionMethod]` as *marker-capable but unset*. `ExpressionMethodAttribute : MappingAttribute` (`Source/LinqToDB/ExpressionMethodAttribute.cs:38`) has no `ServerSideOnly` property, so its implied value is a choice — and "unset" puts all 20 in-repo stubs into arm A as false positives.
- **rejected:** exempting `[ExpressionMethod]` from the exception rule while keeping it a marker for the missing-marker rule. That would silence the convention exactly where nobody follows it — measured, **35** `[ExpressionMethod]` stubs in `Tests/Linq` across 15 files throw `InvalidOperationException` ×20, `NotImplementedException` ×11, `System.NotImplementedException` ×3 and `NotSupportedException` ×1, and **none** throws `ServerSideOnlyException`. Adjudicated by the maintainer as *impose the convention anyway*: `ServerSideOnlyException(nameof(X))` names the API a caller reached for, which is strictly more useful than "the method or operation is not implemented", the rule ships at `Info`, and `allowed_exception_types` is the opt-out.
- **why this:** `[ExpressionMethod]` is a declaration of translation — the member is rewritten to its expression before evaluation, so a stub body is correct by design, exactly as with `[Sql.Function]`. Measured: all 20 in-repo `[ExpressionMethod]` stubs already throw `ServerSideOnlyException`, so form 4 is free in `Source/LinqToDB` and SC-3 holds. Forms 1–3 are decidable from `AttributeData.AttributeClass` (base-type walk) plus `NamedArguments`, without reading ctor bodies.
- **failure mode of the choice:** form 4 makes the analyzer's model deliberately **broader than the runtime's** — `IsServerSideOnly` does not read `[ExpressionMethod]` — justified by substitution making the body unreachable in a query. Recorded in P10 as a considered departure from "mirror the runtime".

### D-12 — Two arms for the missing-marker rule; arm B's list defaults to `ServerSideOnlyException` alone

- **chosen:** report a missing marker when a stub has no D-8 marker **and** either (**arm A**) the member carries a marker-capable attribute — `Sql.ExpressionAttribute`-derived or `TableFunctionAttribute`-derived — whose `ServerSideOnly` is explicitly false or unset, in which case **any** exception type counts; or (**arm B**) the member carries no marker-capable attribute, in which case it counts only if the thrown type is in a configured list, defaulting to **`LinqToDB.ServerSideOnlyException` only**. Additionally the rule considers only `OwningSymbol`s that are ordinary methods, explicit interface implementations, or property **getters** — never constructors, operators or indexers.
- **rejected:** a default list of `ServerSideOnlyException` + `NotImplementedException` + `InvalidOperationException`. Measured and withdrawn: `Tests/Linq` alone carries ≈176 unattributed whole-body throws of the latter two across 61 files — IDE-generated stubs, `IConvertible` implementations, `FakeQueryProvider` doubles, DTO constructors — and `throw new NotImplementedException()` is the default IDE stub in every consumer project, so SC-4 could not hold. The trim costs **zero** detections: all 6 wanted arm-B hits throw `ServerSideOnlyException`, and every in-repo whole-body `NotImplementedException`/`InvalidOperationException` stub is *marked* and therefore handled by the exception rule instead.
- **rejected:** arm A alone (attribute-scoped only). Cannot see the six real defects — the `IGroupBy` trio, `Sql.Property`, `StringAggregate` ×2 — which carry no attribute; nor would it have caught #5782.
- **rejected:** one list gating both arms. An attribute is already a positive declaration of intent, so requiring a particular exception type on top of it would silence a genuine `[Sql.Function]`-with-a-throwing-body defect for no gain.
- **rejected:** an anchor gate ("the declaring type or a containing type declares a marker") as arm B's filter. It admits any exception type inside an anchored type, so an ordinary `NotImplementedException` TODO beside an `Sql.*` member is reported; and it does not silence the `[ExpressionMethod]` stubs, which sit in anchored types.
- **why this:** each arm rests on evidence the member itself carries — arm A's is the attribute, arm B's is the thrown type. `ServerSideOnlyException` is a linq2db type whose sole meaning is "server-side API called on the client", which is why it discriminates where the general-purpose exceptions do not: 5 whole-body uses across all of `Tests/Linq`, against 176 for the other two.
- **failure mode of the choice:** a wholly-unmarked member stubbed with a *different* exception is missed — that is #5782 plus a second mistake, and the user-facing option exists to widen the list for a codebase with its own convention. The symbol-kind restriction is not cosmetic: `[ServerSideOnly]` is `AttributeTargets.Property | Method` (`Mapping/ServerSideOnlyAttribute.cs:8`), so on a constructor the code fix would emit uncompilable code.

### D-9 — "Marker present with a real body" is not a rule

- **chosen:** do not report it at all.
- **rejected:** report it with structural exemption families. Measured: ≈54 such members in `Source/LinqToDB` and **zero** defects; the families failed to cover ≥6 (`Sql.cs:936` `CurrentTzTimestamp`, `Linq/Expressions.cs:1214-1219`, three `Sql.Expressions.cs` sites), and any predicate loose enough to admit `Convert` ×2 / `Lower` / `Upper` admits every pure client body.
- **rejected:** narrow it to standalone `[ServerSideOnly]` + non-stub body — violated legitimately by `Sql/Sql.cs:311-316`.
- **why this:** adjudicated as a property of the design: a marked member generates mapped SQL inside a query and its body serves callers outside one. Confirmed by probe (U-2).
- **failure mode of the choice:** a marked member whose body silently disagrees with its SQL is undetectable. That was never statically decidable.

### D-2 — Two rules, one diagnostic id each

- **chosen:** `LINQ2DB0002`/`L2DB1003` = missing marker; `LINQ2DB0003`/`L2DB1004` = wrong exception in a marked stub.
- **rejected:** one id for both — different remedies, different fixes, different options.
- **rejected:** the earlier three-rule shape sharing an id — moot once D-9 removed the second direction.
- **why this:** one rule per remedy. `L2DB1002` is reserved by open issue #5779.
- **failure mode of the choice:** two ids to document and keep in `AnalyzerReleases`. Splitting later would break consumer `.editorconfig`s, so it is done now.

### D-11 — Options are a user-facing concern; internal rules are fixed

- **chosen:** internal rules take no options; user-facing rules take `linq2db.L2DB1004.allowed_exception_types` and `linq2db.L2DB1003.unmarked_stub_exception_types`, **both additive** to their defaults. Comma-separated fully-qualified metadata names, matched **exactly**, subclasses excluded.
- **rejected:** making `unmarked_stub_exception_types` *replace* arm B's default. A consumer listing only their own exception type would silently drop `ServerSideOnlyException` — the one type that discriminates — and the fixture would pass under either reading, so the ambiguity would ship.
- **rejected:** options on the internal rules — a knob there lets a future contributor silence a deliberate decision.
- **rejected:** subclass-inclusive matching — listing a base type would re-admit its hierarchy, and `Exception` is one keystroke from doing that.
- **why this:** a shipped rule's audience writes code the maintainers never see; an internal rule has no such audience. Recorded in [`authoring-analyzers.md`](../../docs/authoring-analyzers.md).
- **failure mode of the choice:** the shared core (D-5) takes an options struct rather than reading `.editorconfig` itself — `CodeGenerators` passes the fixed defaults, `LinqToDB.Analyzers` passes what it read. Option keys are looked up **lower-cased**.

### D-4 — Generated code is analyzed by the internal rules and skipped by the user-facing ones

- **chosen:** `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` in `Source/CodeGenerators`; `None` in `Source/LinqToDB.Analyzers`. (There is no `All` member on that enum — the first draft used one and failed to compile with `CS0117`; both flags are needed, since `Analyze` alone would examine generated code without reporting on it.)
- **rejected:** `None` in both — Roslyn treats `*.generated.cs` as generated, silently dropping the ten `Sql.Row.generated.cs` hits, the largest confirmed cluster. Measured: `Sql.Row.generated.cs` is the only `*.generated.cs` under `Source/LinqToDB` containing any `throw new`.
- **rejected:** `All` in both — a consumer cannot edit their generated code.
- **why this:** linq2db's generated files are checked in and maintained through their `.tt`; a consumer's are not.
- **failure mode of the choice:** the hosts diverge on one line and a future reader may "harmonize" them. Mitigated by a comment at both sites naming the other. Also unverified until G-05: whether Meziantou.Polyfill's generated members contain listed-type throw-only bodies on the portable TFMs.

### D-5 — Shared detection code lives in `Source/LinqToDB.Analyzers` and is `Compile`-linked by `CodeGenerators`

- **chosen:** the core is an ordinary file of `Source/LinqToDB.Analyzers`, borrowed by `CodeGenerators.csproj` with `<Compile Include="..\LinqToDB.Analyzers\ServerSideOnlyContract.cs" Link="ServerSideOnlyContract.cs" />`.
- **rejected:** a new `Source/Analyzers.Shared/` folder — a new mechanism needing `<File Path>` entries in `linq2db.slnx` to be visible.
- **rejected:** a shared project (`.shproj`/`.projitems`) — measured: the repo uses none.
- **rejected:** duplicating the logic — the two rule sets must agree by construction.
- **why this:** the established in-repo idiom (`Source/LinqToDB.Compat/LinqToDB.Compat.csproj:25-29`, `Tests/Linq/Tests.csproj:66`). `CodeGenerators` needs no `Compile Remove` counterpart because its `Directory.Build.props` has no `<Import>`.
- **failure mode of the choice:** the file compiles against **two Roslyn versions** (`4.8.0` vs CPM `5.6.0`), so only building both proves it (G-01).

### D-6 — `Sql.Row.generated.cs` is hand-edited in lockstep with `Sql.Row.tt`

- **chosen:** change `Sql.Row.tt:201` and apply the identical change to the ten emitted sites.
- **rejected:** regenerate — measured: no MSBuild target, no `TextTransform`, no script, no `dotnet-t4`; regeneration is Visual-Studio-only.
- **rejected:** install `dotnet-t4` — risks different headers or line endings for one repeated token.
- **why this:** the template's `foreach` emits byte-identical text per iteration apart from type arguments, and the exception rule verifies the output independently.
- **failure mode of the choice:** drift if someone edits one and not the other. Bounded: the analyzer catches drift in the output.

### D-7 — The `Percentile*` guidance moves into `<remarks>`, the exception does not grow a constructor

- **chosen:** change the two group-form stubs to `throw new ServerSideOnlyException(nameof(X))` and fold the "use `AggregateExecute`" sentence into the adjacent `<remarks>`.
- **rejected:** add a `(string apiName, string hint)` ctor — new public API on a shipped type for two call sites.
- **rejected:** exempt the two sites — their windowed siblings ten lines below already throw `ServerSideOnlyException`.
- **rejected:** pass the whole sentence as `apiName` — produces a nested, wrong message.
- **why this:** measured — no test asserts on the message, and `<remarks>` shows in IntelliSense before the throw happens.
- **failure mode of the choice:** a caller catching `InvalidOperationException` sees a different type. Accepted: catching it is not a supported pattern.

### D-10 — The internal rules ship no code fix

- **chosen:** internal rules report only; fixes exist for `L2DB1003`/`L2DB1004` alone.
- **rejected:** a fixer-only `CodeGenerators.CodeFixes` project. RS1038 is **not** the obstacle — it fires only for an assembly *containing* a `DiagnosticAnalyzer`, which is why `LinqToDB.Analyzers.CodeFixes` references `Workspaces` under the same `EnforceExtendedAnalyzerRules` (`Analyzers.Common.props:16`, `LinqToDB.Analyzers.CodeFixes.csproj:30`). The cost is the extra project.
- **why this:** the maintainer's standing rule, recorded in [`authoring-analyzers.md`](../../docs/authoring-analyzers.md): an internal rule's own PR fixes every existing violation as a precondition for merging, and later violations are build errors inside the change that introduces them.
- **failure mode of the choice:** the 19 sites are fixed by hand; TO-2 and TO-3 catch a slip.

## P10 Adjudicated (M/L)

Free in `Source/LinqToDB` (all 20 stubs already throw `ServerSideOnlyException`) but **not** free downstream: measured, all 35 `[ExpressionMethod]` stubs in `Tests/Linq` throw something else and will report the exception rule, and a consumer writing `throw new NotImplementedException()` in such a stub gets the same.
