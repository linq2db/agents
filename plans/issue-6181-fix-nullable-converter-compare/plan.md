## P1 Problem

[#6181](https://github.com/linq2db/linq2db/issues/6181) (regression since 6.5.1, [#5902](https://github.com/linq2db/linq2db/pull/5902)): an operator or comparison between a plain `DateTime` column and a `DateTime?` column that carry *the same* conversion is refused with `Error_ValueConverter_DivergentOperands`. The reporter (linq2db.EntityFrameworkCore 10.7.0, EF Core 10) declares `ValueConverter<DateTime,DateTime>` for every `DateTime` property and a `ValueConverter<DateTime?,DateTime?>` for every `DateTime?` property that delegates to it: `v => v != null ? (DateTime?)dateTimeConverter.ConvertToProvider(v.Value) : (DateTime?)null`.

Measured red on `12bc7fe14` (SQLite.MS, net10.0):
- core, native fluent mapping `Plain: v => F(v)` / `Date: v => v != null ? (DateTime?)F(v.Value) : null`: `t.Where(r => r.Plain == r.Date)` throws `The LINQ expression '(DateTime?)r.Plain == r.Date' could not be converted to SQL. Additional details: 'Cannot combine 'Plain' and 'Date' in the database: their value converters do not agree …'` (`ValueConversionTests.PlainAndNullableSpellingsOfOneConversionCompare`).
- EF, issue case 2: `where t2.FromDate >= t1.MinCreatedOn` throws the same `DivergentOperands` naming `FromDate` / `CreatedOn` (`IssueTests.Issue6181_CompareGroupedDateWithNullableDate`).
- EF, issue case 1: a window function ordered by `CalculatedBoolProperty = t1.CreatedOn <= t2.ToDate ? false : true`, then filtered `RowNumValidity == 1` and grouped, throws `The LINQ expression 'q.RowNumValidity == 1' could not be converted to SQL.` with no details (`IssueTests.Issue6181_WindowFunctionOrderedByDateComparison`). Attribution measured: with `CombinesDivergentStorage` short-circuited to `false` (temporary probe, reverted) both EF tests pass on SQLite.MS EF10, so case 1 is the same refusal and nothing else in its chain fails.

Mechanism (code read, `SequenceHelper.cs:61-187`): `ConvertTheSameWay` → `ConversionsMatch` rebuilds both lambda bodies around a shared non-nullable parameter. Two things defeat it for the reporter's pair:
1. **Null guard.** Rebuilding `$v != null` around a non-nullable `p` throws (no `NotEqual(DateTime, DateTime?)` operator), `TryCanonicalize` falls back to `AsWrittenIn` (both sides keep their own nullability), and a conditional body can never equal the plain `F(p)`. This hits the *natural* nullable spelling in native linq2db and EF alike.
2. **Opaque delegate (EF only).** measured (probe `.build/.agents/issue6181-probe/probe.cs`, EF Core 10.0.0): the delegating body is `Convert(Invoke(MemberAccess(MemberAccess(Constant(<closure>), plain), ValueConverter.ConvertToProvider), Convert($v.Value, object)), DateTime?)`. The invoked `Func<object,object>` has no structure to compare, so even with the guard removed the bodies differ from `Call H.ToStore($v)`.

## P3 Constraints & anti-goals (M/L)

- Do not weaken #5902: a pair `ConversionsMatch` cannot prove equal stays refused ("cannot tell" = "different"). Rejected below as D-4.
- No public API change outside `LinqToDB.Internal.*`; `SequenceHelper` is `internal`, the EF adapter is `private`. One new public member in the Internal namespace (A-2): `ExpressionEvaluator.TryEvaluateCapturedValue`, listed in `PublicAPI.Unshipped.txt`.
- No change to `ConvertTheSameWay`'s `HandlesNulls` equality or to `StoredConversion`.
- Generated SQL may change only where a pair flips from "different" to "same": `SetOperationOverNullableAndPlainConversions` (UNION ALL now one column instead of two). Every other baseline unchanged.
- B changes the lambdas the EF bridge hands to linq2db for execution (read, write, UPDATE inlining), not only for comparison: the rewritten lambda must compute the same value as the original for every non-null input.
- User-visible delta of B beyond the fix: `UpdateBuilder.cs:516-533` inlines a converter body into SQL when it is translatable. A delegating EF converter whose target *is* SQL-translatable (e.g. `v => v.AddHours(1)`) was opaque on master, so a server-side `UPDATE SET col = <server expression>` stored the raw value; after B the conversion runs in SQL. That is the behaviour a non-delegating converter already has, so it is a correction, but it changes stored values and goes in the PR body / release note.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Fix the nullable-spelling half in core `ConversionsMatch`

- **chosen:** before canonicalising, reduce a lambda whose parameter is `Nullable<T>` and whose body is a null guard — `p != null ? X : null`, `null != p ? X : null`, `p.HasValue ? X : null`, `p == null ? null : X`, `!p.HasValue ? null : X` (null arm: what `InternalExtensions.cs:227-230` `IsNullValue` accepts — null constant, `Default` of a nullable type — plus a parameterless `new T?()`, each through any `Convert`) — to `X`; and in `Canonicalize`, map `p.Value` / `p.GetValueOrDefault()` on the parameter to the shared non-nullable parameter. Only when both converters report `HandlesNulls == false` (`ConvertTheSameWay` already requires equal `HandlesNulls`; pass the flag into `ConversionsMatch`). Each admitted spelling is one TO-1 cell.
- **rejected:** fix only in the EF bridge — the native fluent spelling (`ValueConversionTests` `Issue5975MappingSchema`, measured red) has the same defect and no bridge in the way.
- **rejected:** strip the guard regardless of `HandlesNulls` — a converter that handles nulls *is* handed null (`ConvertFromDataReaderExpression.cs:138-143` feeds `default`), so its null arm is part of what it stores.
- **why this:** with `HandlesNulls == false` the guard never executes (U-1), so `X` is exactly what the converter does to every value it receives; the plain lambda is `X` over `p`. On EF the flag is not the user's declaration: the adapter hard-codes `HandlesNulls = false` (`EFCoreMetadataReader.cs:457`) whatever `ConvertsNulls` says, so the EF half rests on that constant plus the chokepoints in U-1.
- **failure mode of the choice:** a recogniser too wide could strip a conditional whose "null arm" is not null (e.g. `p != null ? X : someDefault`), or one with its arms reversed, equating two conversions that store values differently. Bounded by requiring the other arm to be null and the test's polarity to select `X` for a non-null value; TO-4 pins a guarded body with a different `X`, TO-4b a reversed-arms body, both staying refused.

### D-2 — Fix the delegation half in the EF bridge, at adaptation

- **chosen:** in `EFCoreMetadataReader` (the `ValueConverterAttribute` site `:451-461`), rewrite each EF lambda before wrapping it: a node `Convert(Invoke(Member(instance, ValueConverter.ConvertToProvider|ConvertFromProvider), Convert(x, object)), T)` whose `instance` evaluates (closure/constant member chain) to an EF `ValueConverter` is replaced by that converter's `ConvertToProviderExpression` / `ConvertFromProviderExpression` applied to `x` (`LambdaExpression.GetBody`), converted to `T` when the types differ; the target lambda is itself rewritten first (recursive delegation).
- **rejected:** a core recogniser for EF delegates — core cannot reference EF types (layering), and `Invoke` of an opaque constant is exactly what `ConvertTheSameWay`'s remark says must stay "different".
- **rejected:** rewrite only a comparison-time copy, keep executing the original lambdas — two representations of one converter (one compared, another executed) is the divergence #5902 guards against; and the inlined form is what `UpdateBuilder.cs:526` already inlines elsewhere.
- **why this:** the bridge is the one place that knows the delegate is EF's compiled form of an expression it can read.
- **failure mode of the choice:** the executed lambda changes; if EF's delegate ever does something its expression does not (sanitising nulls, type coercion) results could shift. Bounded by applying only on an exact parameter-type match (D-3) and by TO-7 (the existing #5975/#5976 EF tests, which use this converter for insert, update, concat).

### D-3 — Inline only on an exact, evaluable match

- **chosen:** inline when (a) the invoked member is `ConvertToProvider` / `ConvertFromProvider` declared on `Microsoft.EntityFrameworkCore.Storage.ValueConversion.ValueConverter`; (b) the instance expression evaluates without parameters (`ExpressionEvaluator.EvaluateExpression`, public — `PublicAPI.Shipped.txt:14609` — guarded by "contains no `ParameterExpression`") to a non-null `ValueConverter`; (c) the single argument is `Convert(x, object)` with `x.Type` equal to the target lambda's parameter type **and that type a non-nullable value type** — so `x` cannot be null and EF's delegate (which returns null for a null input when `ConvertsNulls` is false, without calling the expression) and the inlined expression agree on every input. Otherwise leave the node as written.
- **rejected:** inline any `ValueConverter` delegate call with a loose type (e.g. unwrap `Nullable` on the argument) — widens what changes in executed code for no case the issue needs.
- **why this:** any unmatched shape keeps today's behaviour (opaque, refused), which is the #5902-safe direction.
- **failure mode of the choice:** a delegating converter written differently (a helper method, `Func` captured separately) stays refused; acceptable, documented in P10.

### D-4 — Do not treat an undecidable pair as equal

- **chosen:** keep "cannot prove equal" ⇒ different.
- **rejected:** waive the guard for comparisons, or for any pair that contains an opaque node — reintroduces #5798's silent wrong result (ticks vs seconds, both transparent and both "different").
- **why this:** #5902's contract; the fix widens what can be *proven*, not what is assumed.
- **failure mode of the choice:** other undecidable-but-equivalent spellings keep failing after this fix; they need their own recognition.
