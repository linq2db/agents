## P1 Problem

A `TimeSpan` column declared `[Duration(DurationUnit.Second)]` compared with `==` to a duration the unit cannot represent silently returns nothing, with no signal anywhere.

```csharp
[Column, Duration(DurationUnit.Second)] public TimeSpan InSeconds { get; set; }

q.Where(r => r.InSeconds == TimeSpan.FromSeconds(1.5))   // -> zero rows, always
```

The generated SQL is `InSeconds >= @p1 AND InSeconds <= @p2` with `@p1 = 2`, `@p2 = 1` — an ordinary-looking range over two parameters. Nothing in the log, the exception surface or the translation says the predicate is unsatisfiable by construction.

The lowering is **correct and must not change**: `DateFunctionsTranslatorBase.InDeclaredUnit` (`Source/LinqToDB/Internal/DataProvider/Translation/DateFunctionsTranslatorBase.cs:878`) asks equality as the two comparisons it is made of, each rounding the bound the way its operator needs (`ValueIn(..., roundUp: true)` / `roundUp: false`). The two bounds meet exactly when the value is representable and cross when it is not — the empty range *is* the right answer.

The translator also cannot refuse it. `BoundIn` (`:686`) builds the rounding as an **expression** (`Expression.Divide` → `Math.Ceiling`/`Floor` → convert, `:710`–`:716`) evaluated per execution while the parameter value is produced — the comment at `:782` states this explicitly. So the value is unknown at translation time and `== TimeSpan.FromSeconds(1.5)` shares a cached query shape with `== someVariable`. Refusing there would be either a data-dependent runtime throw on an already-cached query, or refusing literals while an identical variable stays silent.

Where the `TimeSpan` operand is a **constant**, the mistake is statically decidable. That is analyzer work, and no rule exists.

## P4 Unknowns (M/L)

- U-1 Does .NET Core's `TimeSpan.From*(double)` round the product to whole milliseconds the way .NET Framework's does? — **resolved-by probe** (BCL sources fetched and read, not recalled): **no, and they diverge in two ways rather than one.** .NET Framework's `Interval(double value, int scale)` takes `scale` in *milliseconds* and computes `millis = value*scale ± 0.5`, then `(long)millis * TicksPerMillisecond` — round half-away-from-zero to a whole millisecond (`microsoft/referencesource`, `mscorlib/system/timespan.cs:228-237`). Modern .NET's `Interval(double value, double scale)` takes `scale` in *ticks* and hands the product to `IntervalFromDoubleTicks`, which does `new TimeSpan((long)ticks)` — a **truncation toward zero**, with no millisecond rounding (`dotnet/runtime`, `System.Private.CoreLib/src/System/TimeSpan.cs:636-656`). A two-reading guard would therefore have been unsound on modern .NET for any value whose double tick product is not exactly representable. Corrected in D-4.
- U-2 Can more than one `[Duration]` reach a single member, with different units? — **resolved-by probe**: `DurationAttribute` declares `AllowMultiple = true` (`Source/LinqToDB/Mapping/DurationAttribute.cs:25-27`) and inherits `MappingAttribute.Configuration` (`Source/LinqToDB/Mapping/MappingAttribute.cs:17`); `ColumnDescriptor` picks one per mapping-schema configuration via `mappingSchema.GetAttribute<DurationAttribute>` (`ColumnDescriptor.cs:144`). Yes — hence D-5.
- U-3 Is `L2DB1002` actually free? — **resolved-by probe**: `AnalyzerReleases.Unshipped.md` is header-only on `origin/master`; `Shipped.md:10` carries only `L2DB1001`; the in-flight #5788 branch reserves `L2DB1003`/`L2DB1004`. A `rg --no-ignore --hidden` sweep of the whole tree found nothing claiming 1002.
- U-4 Would the new rule redden the repo's own build (`Tests/Linq` has 15 `[Duration]` members)? — **resolved-by probe**: `Source/LinqToDB/LinqToDB.csproj:52` deliberately omits `OutputItemType="Analyzer"` on the user-facing analyzer reference, so the shipped rules never run on this repo's build. No `.editorconfig` severity line and no in-repo suppression is needed. Dogfooding must attach the analyzer explicitly, which `/dogfood-analyzer` does.
- U-5 Does a lambda **nested inside** an expression tree (`q.Where(r => r.Items.Any(i => …))`) still count as expression-tree context? The inner lambda is converted to `Func<>`, not `Expression<>`. — **resolved-by design**: the gate tests *every* enclosing `IAnonymousFunctionOperation`, not the nearest one. Pinned by a test (TO-1).
- U-6 Is the analyzer's private ticks-per-unit table the only such table, and can a unit be declared by a route an analyzer cannot see? — **resolved-by scout**: exactly one ratio table exists (P7 row 1); six declaration routes exist and only the attribute is analyzer-visible (P7 row 4).
- U-7 A `foreach` bound yields **several** candidate constants for one syntax node, some representable and some not. Is that a report? — **resolved-by user answer**: yes, report it. Semantics and wording in D-8 — "can never match" is asserted only when *every* candidate is non-representable; a mixed set gets *"…can never match for that value"* and names the offending duration.
- U-8 Can a LINQ **range variable** (`from d in wanted … x.InSeconds == d`) be resolved without real dataflow? — **resolved-by design**: yes for the direct shape. The range variable is a lambda parameter, so walk parameter → enclosing `IAnonymousFunctionOperation` → `IDelegateCreationOperation` → `IArgumentOperation` → `IInvocationOperation`, and resolve that invocation's source sequence with the *same* constant-collection helper `foreach` uses. Anything else bails silently. See D-8.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Diagnose in an analyzer, not in the translator

- **chosen:** a new `DiagnosticAnalyzer` in `Source/LinqToDB.Analyzers`.
- **rejected:** refusing the comparison inside `InDeclaredUnit` — the value is not known at translation time (`BoundIn` emits the rounding as an expression evaluated per execution, `DateFunctionsTranslatorBase.cs:686`,`:782`), so a refusal is either a data-dependent runtime throw on an already-cached query shape, or a rule that refuses a literal while an identical variable stays silent.
- **why this:** the constant case — the one actually mistyped — is statically decidable and nothing else is.
- **failure mode of the choice:** the analyzer only sees attribute-declared units, so the five fluent/metadata routes (P7 row 4) stay undiagnosed forever. Accepted and stated (P10); the issue mandates it be documented on the wiki page.

### D-2 — Fire only inside expression-tree lambdas

- **chosen:** report only when some enclosing `IAnonymousFunctionOperation` has a **parent whose `Type` is `System.Linq.Expressions.Expression<T>`** — tested on the parent's type, **not** on the parent's node kind.
- **rejected:** testing for an `IDelegateCreationOperation` parent (this decision's first draft). The critic's objection: `CSharpOperationFactory.CreateBoundConversionOperation` emits a `DelegateCreationOperation` only when the conversion's type `IsDelegateType()`, and `Expression<T>` is a class — so an expression-tree lambda sits under an `IConversionOperation` instead, and a kind-based gate never fires. **Not probed** (neither of us could execute Roslyn here, and the 4.8 `Microsoft.CodeAnalysis.xml` does not settle it), but the objection is *made moot rather than adjudicated*: the type-based test above is correct under either node shape, so the cheaper move is to write the version that cannot be wrong than to spend a build deciding which shape it is.
- **rejected:** flagging any `==`/`!=` against a `[Duration]` member — simpler, and catches a predicate factored into a plain `bool` helper, but fires on legitimate in-memory comparisons against objects that never came from the database.
- **why this:** the failure this rule exists for — a query that silently returns nothing — happens only in translated code. Confirmed as the user's choice at planning time.
- **failure mode of the choice:** a predicate written as `static bool Match(E e) => e.InSeconds == TimeSpan.FromSeconds(1.5);` and used through a linq2db expression-method is not diagnosed. A false negative, not a false positive. Should the parent chain interpose a node the walk does not expect, the rule degrades to **silence**, not to a wrong report — TO-1's expression-tree positives are what prove it fires at all.

### D-3 — Recognize every statically-evaluable `TimeSpan` shape

- **chosen:** `new TimeSpan(...)` (all ctor overloads), `TimeSpan.FromTicks`, the `From*(double)` factories, `TimeSpan.Parse`/`ParseExact` over constant arguments, the `Zero`/`MinValue`/`MaxValue` static fields, and **`+` / `-` / unary `-` between operands that each resolve** (checked arithmetic, bail on overflow) — all leaf args constant, `IConversionOperation` unwrapped for the `TimeSpan` → `TimeSpan?` lift.
- **rejected:** factories only — leaves `new TimeSpan(0, 0, 1, 500)` and `FromTicks` silent, which are ordinary ways to write the same mistake.
- **why this:** Roslyn has no `ConstantValue` for a `TimeSpan`, so every shape is hand-evaluated regardless; the marginal cost of each additional shape is one `switch` arm. Operator folding is **load-bearing, not a nicety** — the corpus's clearest real instance is `TimeSpan.FromMinutes(15) + TimeSpan.FromMilliseconds(500)` (`IntervalTranslationTests.Queries.cs:841`), which no factory-only reader can evaluate. Widest recognition confirmed as the user's choice at planning time.
- **failure mode of the choice:** `Parse` is culture-sensitive in its fraction separator, so a string parsing under the consumer's culture but not under invariant would be evaluated wrongly — mitigated by **bailing** when the invariant parse fails rather than guessing. `TimeSpan.MaxValue`/`MinValue` are multiples of no unit above a tick, so `col == TimeSpan.MaxValue` is flagged on every such column; correct (it genuinely cannot match) but may read as pedantic.

### D-4 — Report a `double`-factory constant only when all **three** runtime readings agree

- **chosen:** for the `double`-argument `From*` factories, compute **three** tick values and report only when every one is non-representable in the declared unit:
  1. **exact** — the product in `decimal` (never `double`: a tick count reaches 19 digits and a double stops distinguishing at 16);
  2. **.NET Framework** — `(long)(value * scaleInMilliseconds ± 0.5) * TimeSpan.TicksPerMillisecond`;
  3. **modern .NET** — `(long)(value * scaleInTicks)` evaluated in `double`, i.e. truncation toward zero.
  Readings 2 and 3 are simulated literally, so this is exact rather than approximate. Bail on overflow in any of them.
- **rejected:** trusting the exact decimal value alone — netfx rounds to a whole millisecond, so `FromSeconds(0.9999999)` is exactly 1 second there while the exact reading is 9 999 999 ticks. A **false positive** on netfx.
- **rejected:** intersecting only the exact and millisecond-rounded readings (this decision's first draft, written from recall). Reading the two BCL sources showed modern .NET **truncates the double tick product** instead of rounding to milliseconds (U-1), so a value whose product is not exactly representable in `double` lands a tick below the exact value — unsound on the runtime most consumers target. The correction came from the probe, not from review.
- **why this:** the analyzer cannot know the consumer's target runtime, and the intersection of all three readings is sound on every one. Not applied to `FromTicks`, the integer-argument `From*` overloads, `FromMicroseconds`/`FromNanoseconds`, constructors, `Parse` or the static fields — all exact on every runtime by construction.
- **failure mode of the choice:** sub-millisecond `double`-factory constants (`FromMilliseconds(0.5)` against a `Millisecond` column) are not diagnosed, because the netfx reading rounds them to a representable value. A false-negative class, deliberately traded for soundness.

### D-5 — Multiple `[Duration]` attributes: all must agree, and one must be unconfigured

- **chosen:** report only when **every** `[Duration]` on the member finds the value non-representable **and** at least one of them has no `Configuration` (the all-configurations fallback). Unit read from the `Unit` named argument when present, else `ConstructorArguments[0]` — `[Duration(DurationUnit.Second, Unit = DurationUnit.Hour)]` is legal syntax (`Unit` is `{ get; set; }`, `DurationAttribute.cs:42`) and the named assignment runs after the ctor, so the named argument wins. Walk `IPropertySymbol.OverriddenProperty` so an attribute on a base declaration is seen (`Inherited = true`); the declaring syntax may be in another file or another assembly.
- **rejected:** taking the first attribute's unit — the effective unit is chosen per mapping-schema configuration (`ColumnDescriptor.cs:144`), so a `[Duration(Second)]` + `[Duration(Millisecond, Configuration = "SqlServer")]` pair against 1.5 s genuinely matches under SqlServer and reporting it would be a false positive.
- **rejected:** ignoring members with more than one attribute — loses the common case where every configuration agrees.
- **why this:** the report is then true under every configuration the mapping can resolve to.
- **failure mode of the choice:** a member declared *only* with configuration-scoped attributes is never diagnosed even when every one of them agrees, because a configuration matching none of them leaves the column with no duration semantics at all.

### D-6 — Private ticks-per-unit table, keyed by enum **member name**

- **chosen:** the analyzer carries its own map and resolves the attribute's enum argument to a `DurationUnit` **field name** off the `INamedTypeSymbol`, then looks the name up: `Microsecond` 10, `Millisecond` 10 000, `Second` 10 000 000, `Minute` 600 000 000, `Hour` 36 000 000 000, `Day` 864 000 000 000. `Tick`, `Nanosecond` and any unrecognized name never report. **Eight entries, not eleven** — `DurationUnit` deliberately omits `Week` and the calendar units that `SqlIntervalUnit` carries (`SqlIntervalType.ToIntervalUnit`, `Source/LinqToDB/Internal/SqlQuery/SqlIntervalType.cs:46`, is total over exactly eight members).
- **rejected:** using the raw underlying `int` — the package has no linq2db version floor, so it can analyze a linq2db whose enum members sit at different ordinals; a numeric key would silently mis-attribute the unit.
- **why this:** the name is the stable contract across versions, and an unknown name degrades to silence rather than to a wrong answer. Reuses the exact `IFieldSymbol { HasConstantValue: true }` scan already in the tree at `Source/LinqToDB.Analyzers.CodeFixes/LegacyWindowChainRewriter.cs:529-540` (note its deliberate `Equals(...)` rather than `==`, because both sides are boxed underlying integers).
- **failure mode of the choice:** a `DurationUnit` member added later (`Week` is the obvious candidate — `SqlIntervalUnits.TryGetTicksRatio` already carries its ratio at `Source/LinqToDB/Internal/SqlQuery/SqlIntervalUnits.cs:41`, it is simply not a `DurationUnit` today) is not diagnosed until the analyzer's table learns it. Silent under-reporting, never a wrong report.

### D-7 — No code fix

- **chosen:** report only; register no `CodeFixProvider`.
- **rejected:** offering to round the literal to the nearest representable value — the analyzer cannot know whether the author meant 1 s, 2 s, or to change the column's unit.
- **why this:** the issue says so, and a fix that guesses the intended value would silently change a predicate's meaning.
- **failure mode of the choice:** no bulk remediation path; each site is fixed by hand.

### D-8 — Resolve the operand to a **candidate set**, not a single value

- **chosen:** one recursive `TryResolveCandidates(IOperation) → ImmutableArray<TimeSpan>?` with a bounded rule set, returning `null` (bail) on anything unrecognized:
  - a recognized constant shape (D-3) → one candidate;
  - an `ILocalReferenceOperation` for a local declared with an initializer, where **every** reference to that `ILocalSymbol` in the containing method is a plain read in a recognized position → recurse into the initializer;
  - an `ILocalReferenceOperation` that is an `IForEachLoopOperation.LoopControlVariable` → resolve the loop's `Collection` as a **constant collection** and recurse into every element, requiring all to resolve;
  - an `IParameterReferenceOperation` that is a LINQ element parameter → walk parameter → enclosing `IAnonymousFunctionOperation` → its parent chain → `IArgumentOperation` → `IInvocationOperation`, and resolve that invocation's source sequence with the **same** constant-collection helper — **only** when the lambda has exactly one parameter, that parameter is ordinal 0, and the invoked method is on an allowlist of `System.Linq.Enumerable`/`Queryable` sequence operators whose first argument *is* the element source.
  
  **Constant collection** means an inline `IArrayCreationOperation` (or collection-expression literal) with an element initializer, or a local holding one that passes the same all-references-are-reads sweep. Nothing else — in particular no `List<T>` initializer, since a list can be mutated after construction.
  
  Report when **any** candidate is non-representable; assert *"can never match"* / *"always matches"* only when **every** candidate is, and use the *"…for that value"* variants — naming the offending duration — for a mixed set.
- **rejected:** operand-expression only. The corpus census (P7 rows 15–16) is decisive: **not one** of the tree's `==`/`!=` sites against a `[Duration]` member writes its constant inline, so an operand-only rule fires zero times on the whole repo and SC-6 could not discriminate a working rule from a broken one. The inline constants that do exist sit on ordering operators, which must not be flagged.
- **rejected:** reporting only when every candidate is non-representable. That silently drops the `foreach` sites, which are exactly where the corpus expresses the defect.
- **rejected:** enumerating the *writes* that disqualify a local (this decision's first draft: "no `ISimpleAssignmentOperation`/`ICompoundAssignmentOperation` target, no `ref`/`out` use"). The critic's objection stands and is not reachability-bounded: `IDeconstructionAssignmentOperation`, `IAddressOfOperation`, an `ILocalSymbol.IsRef` local, and mutation *through* the local (`bounds[0] = …`, `Array.Sort(bounds)`) all escape that match list, and P3 says no false positive at any cost in recall. Inverting the sweep to an allowlist of read positions costs the same code and cannot be outflanked by a write shape nobody enumerated.
- **rejected:** an unqualified "LINQ lambda's element parameter". Also the critic's, also accepted: in `Zip((a, b) => …)`, a `Join` key selector, `Aggregate(seed, (acc, d) => …)` or a `SelectMany` result selector the parameter is **not** drawn from the receiver, so walking to `Arguments[0]` resolves a different sequence and reports a value the code never compares — a false positive that names a duration appearing nowhere in the predicate. The single-parameter / ordinal-0 / allowlist restriction above is what makes the walk sound; the corpus's only instance (`Queries.cs:1294`/`:1301`) happens to be the safe shape, so the corpus alone would never have caught this.
- **why this:** widest reach confirmed as the user's choice at planning time, and it is what makes the dogfood gate a measurement rather than a formality.
- **failure mode of the choice:** still the biggest false-positive surface in the rule. A mixed candidate set reports a site that is fine on some iterations — mitigated by wording that says exactly that rather than overclaiming. Every resolution step bails rather than guessing, so the residual risk is a *shape* that resolves soundly but that a reader would not expect to be folded at all.

## P11 Amendments (M/L)

Both entries are implementation corrections inside E-1 — no new edit-point, no widened surface, so no approval is voided. Recorded because each replaces a mechanism the plan named.

- A-1 **The range-variable walk keys on an operator allowlist, not on an argument ordinal.** D-8 said "single-parameter lambda, ordinal 0, allowlisted operators"; the first implementation additionally required the *lambda argument* to sit at parameter ordinal 1, which is wrong for a **reduced extension method** — `bounds.Select(d => …)` binds the reduced symbol whose only parameter is the selector, so the lambda is ordinal 0 and the walk bailed. `ReportsRangeVariable` failed red for exactly that reason. The ordinal is not merely mis-numbered but the wrong test: `Join`'s *inner* key selector is also a one-parameter lambda in a later argument, yet its parameter ranges over the **second** sequence, so any position-based rule would resolve the first argument and report a duration the predicate never compares. Replaced by an explicit `IsElementSelector` name allowlist (`Where`/`Select`/`SelectMany`/`Any`/… — `Zip`, `Join`, `GroupJoin` and `Aggregate` deliberately absent) plus "the lambda is not argument zero". `DoesNotReportInnerKeySelectorParameter` was added to pin it, and it is the control the corpus could never have supplied.
- A-2 **The array-local guard admits the same pure operators, not `foreach` alone.** D-8's "constant collection … or a local passing the same all-references-are-reads sweep" was first implemented as *foreach-only*, which is stricter than the plan and rejected the very shape the range-variable rule exists for — `bounds.Select(…)` is not a `foreach`. Widened to "a `foreach` collection, or argument zero of an allowlisted element-selector operator", which is the plan's intent: those operators read the sequence and cannot write it, while `Array.Sort`, an element assignment or a call that keeps a reference still disqualify. This is why `ReportsRangeVariable` needed two fixes rather than one.
