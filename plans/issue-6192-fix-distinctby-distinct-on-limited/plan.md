## P1 Problem

[#6192](https://github.com/linq2db/linq2db/issues/6192). On providers with `SqlProviderFlags.IsDistinctOnSupported` (PostgreSQL `PostgreSQLDataProvider.cs:58`, DuckDB `DuckDBDataProvider.cs:40`; no other setter), `DistinctBy` lowers to `DISTINCT ON` by mutating the `SelectQuery` of the sequence it receives (`DistinctByBuilder.cs:124-141` → `ApplyDistinctOn` `:250-269`): the ON keys go to the front of *that query's* ORDER BY and `DistinctOn` is set on *that query*. The preceding ordering captured at `:113` is not used on this path. Measured on master `7fd98eda5e` over the shared `Parent` data (`ParentID:Value1` = `1:1, 2:null, 3:3, 4:null, 5:5, 6:6, 7:1`), result sets (order ignored), logs `.build/.agents/probe6192-master*.log` in the worktree:

1. **LIMIT/OFFSET applied after DISTINCT ON** — the sequence is the limited query itself, so DISTINCT ON, ORDER BY and LIMIT/OFFSET share one query:
   - `Parent.OrderByDescending(p => p.ParentID).Take(3).DistinctBy(p => p.Value1)` → PostgreSQL.16 / DuckDB `{7, 3, 5}`, C# `{7, 6, 5}`. SQL: `SELECT DISTINCT ON (t1."Value1") … ORDER BY t1."Value1", t1."ParentID" DESC LIMIT :take`.
   - `….Skip(2).DistinctBy(p => p.Value1)` → `{5, 6, 4}`, C# `{5, 4, 3, 1}`.
2. **Tie-break lost when the ordering sits below the DISTINCT ON query** — the limited query keeps its ORDER BY (`SqlQueryOrderByOptimizer.cs:244`), the DISTINCT ON query's ORDER BY holds only the key, each group keeps an arbitrary row:
   - `….Take(7).Select(p => new { p.ParentID, p.Value1 }).DistinctBy(x => x.Value1)` → PostgreSQL.16 `{1, 3, 5, 6, 4}`, C# `{7, 6, 5, 4, 3}` (DuckDB happened to be right).
   - `….Take(7).AsSubQuery().Select(…).DistinctBy(…)` → PostgreSQL.16 `{1, 3, 5, 6, 4}`; `….Take(7).AsSubQuery().DistinctBy(…)` → PostgreSQL.16 `{1, …}`; NULLS variant (P8 TO-9) → PostgreSQL.16 `{4, 5}`, C# `{2, 1}`.

Widened by the user (P12 → *Design pivot*): the captured ordering (`ExpressionBuilder._currentOrderBy`, `ExpressionBuilder.cs:67-165`), which the ROW_NUMBER and OUTER APPLY lowerings of `DistinctBy` and the CteUnion eager-load strategy consume, is not a faithful record of the sequence's row order:

3. **An `OrderBy` on the inner side of a join / SelectMany replaces the outer ordering** (`OrderByBuilder.cs:184` resets the list; no builder isolates the inner build although `ExpressionBuilder.cs:139-141` says isolation covers "join inner, SelectMany collection"):
   - `from p in Parent.OrderByDescending(p => p.ParentID) join c in Child.OrderBy(c => c.ChildID) on p.ParentID equals c.ParentID select new { p.ParentID, p.Value1, c.ChildID }` then `.DistinctBy(x => x.Value1)` → SQLite.MS `{1, 2, 3, 6}` (`ROW_NUMBER() OVER (PARTITION BY Value1 ORDER BY ChildID)`), PostgreSQL.16 `{1, 3, 6, 2}` (`ORDER BY p."Value1", c_1."ChildID", p."ParentID" DESC`), C# `{7, 6, 4, 3}`. The `from … from c in Child.Where(…).OrderBy(…)` form: same values.
4. **A pre-`GroupBy` ordering survives the grouping** (`GroupByBuilder.cs:109`, no isolation): `OrderByDescending(p => p.ParentID).GroupBy(p => p.Value1).Select(g => new { g.Key, C = g.Count() }).DistinctBy(x => x.C)` → the ROW_NUMBER path orders by the pre-group column inside the grouped query (SQLite.MS SQL: `[g_1].[ParentID]` in a `GROUP BY [g_1].[Value1]` select list), instead of reporting that the sequence has no ordering.

Widened again by the user on 2026-10-29 (A-3), after the DISTINCT ON path's result order was shown to them:

5. **The DISTINCT ON path neither orders its result nor publishes the captured ordering.** It returns the DISTINCT ON context as is (`DistinctByBuilder.cs:150-151`): its ORDER BY must lead with the ON keys, so the result comes back ordered by the key, and the captured list, held only in the local `captured` after the `IsolateOrderBy` scope restored the pre-`DistinctBy` state (`ExpressionBuilder.cs:206`), never reaches the consumers above. The ROW_NUMBER path re-applies it as `OrderBy`/`ThenBy` built outside the scope (`DistinctByBuilder.cs:176-184`), which both orders the result and registers the list again (`OrderByBuilder.cs:185`). Measured on master (P3, unchanged by E-1 … E-9, which leave this return as it was): `Parent.OrderByDescending(p => p.ParentID).DistinctBy(p => p.Value1).Take(2)` → PostgreSQL.16 / DuckDB `{7, 3}`, SQLite and C# `{7, 6}`; `….DistinctBy(p => p.Value1).DistinctBy(p => p.ParentID % 2)` → PostgreSQL.16 / DuckDB throw `DistinctBy requires at least one ordering key`, SQLite `{7, 6}`. Re-measured on the branch in the A-3 red run (G-01).

## P2 Success criteria

- SC-1 On PostgreSQL and DuckDB, `DistinctBy` over a sequence that carries LIMIT (Take) or OFFSET (Skip) returns, per key, the first row of the limited rows in their order, and still lowers to DISTINCT ON.  → TO-1, TO-2
- SC-2 On PostgreSQL and DuckDB, when the DISTINCT ON query does not itself carry the sequence's ordering (it wraps a limited query, one or more levels down), the captured ordering is re-translated after the ON keys, keeping direction and NULLS position, for member and computed ordering keys alike, so each key keeps its first row.  → TO-3, TO-4, TO-9, TO-15
- SC-3 After a join (`join` / `Join` / `LeftJoin`, the `InnerJoin`-family) or a `SelectMany`, the captured ordering is the outer sequence's ordering followed by the inner side's — the inner side's first for a right join, which `Enumerable.RightJoin` enumerates inner-major — so `DistinctBy` keeps the first row in LINQ order on every provider, and the CteUnion root row order follows the same list.  → TO-10, TO-11, TO-12, TO-16, TO-17
- SC-4 (re-derived by A-4) An ordering applied before `GroupBy` survives it when it reads only grouping keys — a key itself, or a function of the keys, including one projected below the GroupBy and one reached through a join (the groups are then ordered by it, as in LINQ); a pre-group ordering list that does not order the groups (a non-key entry not preceded by key entries covering every grouping key) is dropped as a whole, so `DistinctBy` that has nothing else reports `Error_DistinctByRequiresOrderBy` on every provider; an `OrderBy` after `GroupBy` still counts.  → TO-5, TO-8, TO-18, TO-34 … TO-37, TO-42, TO-48
- SC-5 (re-derived by A-4) A captured entry anchored inside a CTE body below the DISTINCT ON query makes `DistinctBy` report `Error_DistinctByRequiresOrderBy` instead of keeping an arbitrary row per key; an outer-correlated entry is still skipped (constant per row).  → TO-38, TO-41, TO-47
- SC-6 The CteUnion eager-load strategy keeps its child ordering and SQL: the eager-loading suites pass with no baseline change.  → TO-14
- SC-7 Untouched shapes are unchanged: the existing `DistinctByMethodTests` stay green on SQLite, PostgreSQL, DuckDB; the new limited-shape tests return the same rows on SQLite before and after.  → TO-6, TO-7
- SC-8 (A-3) On PostgreSQL and DuckDB, `DistinctBy` returns the surviving rows in the captured ordering (LINQ's first-occurrence order), so a following `Take` keeps the first rows in that order, and the captured ordering reaches the consumers above (a stacked `DistinctBy`, the CteUnion root row number) as on the ROW_NUMBER path, except entries the DISTINCT ON path could not lift.  → TO-23 … TO-31

## P3 Constraints & anti-goals (M/L)

- No public API change: everything edited is internal (`DistinctByBuilder`, `JoinBuilder`, `AllJoinsLinqBuilder`, `SelectManyBuilder`, `GroupByBuilder`, `ExpressionBuilder` internal members). No SQL AST, optimizer or provider change.
- The ROW_NUMBER (`DistinctByBuilder.cs:144-173`) and OUTER APPLY (`:179-193`) lowerings are not edited; they change behaviour only through the captured list they read (SC-3, SC-4).
- Generated SQL changes only where a captured-ordering consumer reads a list that D-4 changes, and on the DISTINCT ON path for D-1 / D-2 shapes.
- **Result order of the DISTINCT ON path — in scope since A-3 (D-5).** Was out of scope under D-3, now superseded; the measurements moved to P1 item 5.
- **Out of scope — CTE-anchored captured entries.** `CteContext.InitQuery` rewrites every captured entry through the CTE's inner context (`CteContext.cs:89-94`); such an entry cannot be lifted through `SqlCteTable` (`CteTableContext.cs:22,39`), and its CTE body is built lazily, so its registration can fall outside the scope that should own it. Measured: `Parent.OrderByDescending(p => p.ParentID).AsCte().Where(p => p.ParentID > 0).DistinctBy(p => p.Value1)` → SQLite.MS throws `no such column: t1.ParentID` (ROW_NUMBER path), PostgreSQL.16 `{1, 3, 5, 6, 4}` (arbitrary), DuckDB right by luck; `….AsCte().DistinctBy(…)` → `Error_DistinctByRequiresOrderBy` on all three. This branch only keeps the DISTINCT ON path from emitting a dangling reference (SC-5); follow-up issue proposed.
- **Narrowing vs the issue text:** none. The issue's expected SQL (DISTINCT ON above the limited query, ORDER BY = key then the captured ordering) is met.
- **User-visible deltas vs master:**
  - PostgreSQL / DuckDB: `OrderBy…Take/Skip…DistinctBy` returns the correct rows; SQL gains a derived table (DISTINCT ON over the limited query).
  - PostgreSQL / DuckDB: `OrderBy…Take…(Select | AsSubQuery | Where)…DistinctBy` keeps the first row per key; the DISTINCT ON ORDER BY gains the tail keys.
  - PostgreSQL / DuckDB: an unlimited shape whose ordering sits one query below the DISTINCT ON query at build time gets its full tail; known instance `DistinctByAfterJoin` (`orderby c.Id, r.Id` then `select`) — master emits `ORDER BY c_1."Country", c_1."Id"` (baseline `PostgreSQL.16/…DistinctByAfterJoin(PostgreSQL.16).sql`), after the change also `r."Id"`, which LINQ requires (country UK: `c.Id = 1` joins tags `a`/`b`).
  - All providers: `DistinctBy` after a join / SelectMany whose inner side has an `OrderBy` now ranks by the outer ordering first (correct rows; ROW_NUMBER `OVER (… ORDER BY outer…, inner…)`); a query whose only `OrderBy` was on the inner side keeps working (the inner ordering is still captured).
  - All providers: `OrderBy(<not a grouping key>)…GroupBy(…)…DistinctBy(…)` with no `OrderBy` after the `GroupBy` now throws `DistinctBy requires at least one ordering key.` (master: PostgreSQL / DuckDB ran with an arbitrary row per key; the ROW_NUMBER path built SQL ordering a grouped query by a non-grouped column). `OrderBy(<grouping key>)…GroupBy(<same key>)…DistinctBy(…)` keeps working as on master (TO-18).
  - All providers, CteUnion eager loading: the root row number of a main query whose last `OrderBy` sat on a join / SelectMany inner side now orders by the outer ordering first (TO-17); after a `GroupBy`, a pre-group ordering by the grouping key drives the root row number through the key itself (TO-21), and any other pre-group ordering falls back to the key columns (`ExpressionBuilder.EagerLoadUnion.cs:180-188`, TO-22). No committed test had any of these shapes (scout, P7).
  - All providers: a captured entry kept by the GroupBy pruning is the grouping key's placeholder, so a `Distinct()` that projects that key (`OrderBy(k).GroupBy(k).Select(g => g.Key).Distinct()`) now keeps it (`DistinctBuilder.cs:76-95`) where master dropped the pre-group body as unprojected; consumers after such a `Distinct` see the key ordering (critic delta round). Reasoned, not separately tested.
  - PostgreSQL / DuckDB, SQL text only: when the DISTINCT ON key is also a captured ordering key that sits below the DISTINCT ON query (`OrderByDescending(x => x.Group)…Select(…)…DistinctBy(x => x.Group)`), the key's ORDER BY item now carries the captured direction / NULLS position (`… "Group" DESC`) where master synthesized `"Group"` ASC and the optimizer dropped the lifted duplicate (`SqlQueryOrderByOptimizer.cs:202`); the surviving row per key is the same. No fixture test has the shape (critic round 3).
  - All providers, right joins: `Queryable.RightJoin` (net10) keeps the inner ordering as the major key (master: inner only) and adds the outer one after it.
  - PostgreSQL / DuckDB (A-3): the DISTINCT ON query becomes a derived table ordered by the captured ordering (`SELECT … FROM (SELECT DISTINCT ON (k) … ORDER BY k, <captured>) ORDER BY <captured>`), when its ORDER BY does not already lead with the ON keys (a query that does, `OrderBy(k).ThenBy(…).DistinctBy(k)`, keeps master's SQL); `DistinctBy().Take(n)` returns the first n rows in LINQ order, the result is ordered as in LINQ, and a stacked `DistinctBy` works instead of throwing. A query whose captured entries are all CTE-anchored keeps master's SQL.
  - PostgreSQL / DuckDB (A-3): every captured-ordering consumer above a DISTINCT ON `DistinctBy` now reads the captured list instead of the pre-`DistinctBy` state (usually empty): a stacked `DistinctBy`, `Distinct` pruning, the GroupBy pruning (E-7), the join append (E-3 … E-6), and the CteUnion root row number, which used to fall back to the key columns (`ExpressionBuilder.EagerLoadUnion.cs:180-188`).
  - No shipped prose states master's behaviour for these shapes — searched `DISTINCT ON|DistinctOn|captured|CurrentOrderBy` in `Source/**/*.cs` doc comments: `BasicSqlBuilder.cs:860` (stays true) and the internal `ExpressionBuilder.cs:139-141` summary, which E-3 corrects.
  - (A-4) `OrderBy(<function of the grouping keys>)…GroupBy…DistinctBy` works again on every provider (as on master for `ROW_NUMBER`; PostgreSQL / DuckDB now rank by the ordering instead of an arbitrary row). All three go in the PR body's behaviour-change section.

### D-6 — GroupBy keeps orderings computed from the grouping keys, and drops a prefix that does not cover them (A-4; review MAJ001, MIN001)
