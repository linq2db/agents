# Work plan: issue-6192-fix-distinctby-distinct-on-limited — DistinctBy after a limited ordered sequence returns wrong rows on DISTINCT ON providers

**Tier:** L  ·  **Status:** approved  ·  **Approved-at:** 2026-10-28 (user, in session; edit set E-1 … E-9 as of P12 → *User review after round 3*)  ·  **Branch:** issue/6192-fix-distinctby-distinct-on-limited
**Schema:** `.claude/docs/work-plan.md`  ·  **Gates:** `.claude/docs/definition-of-done.md`

Tier L: the change edits the builders' shared captured-ordering state (`ExpressionBuilder._currentOrderBy`) from six builders, and that state is also read by the CteUnion eager-load strategy. Escalated from M on 2026-10-28 when the user widened the scope (see P12 → *Design pivot*).

## P1 Problem

[#6192](https://github.com/linq2db/linq2db/issues/6192). On providers with `SqlProviderFlags.IsDistinctOnSupported` (PostgreSQL `PostgreSQLDataProvider.cs:58`, DuckDB `DuckDBDataProvider.cs:40`; no other setter), `DistinctBy` lowers to `DISTINCT ON` by mutating the `SelectQuery` of the sequence it receives (`DistinctByBuilder.cs:124-141` → `ApplyDistinctOn` `:250-269`): the ON keys go to the front of *that query's* ORDER BY and `DistinctOn` is set on *that query*. The preceding ordering captured at `:113` is not used on this path. Measured on master `7fd98eda5e` over the shared `Parent` data (`ParentID:Value1` = `1:1, 2:null, 3:3, 4:null, 5:5, 6:6, 7:1`), result sets (order ignored), logs `.build/.agents/probe6192-master*.log` in the worktree:

1. **LIMIT/OFFSET applied after DISTINCT ON** — the sequence is the limited query itself, so DISTINCT ON, ORDER BY and LIMIT/OFFSET share one query:
   - `Parent.OrderByDescending(p => p.ParentID).Take(3).DistinctBy(p => p.Value1)` → PostgreSQL.16 / DuckDB `{7, 3, 5}`, C# `{7, 6, 5}`. SQL: `SELECT DISTINCT ON (t1."Value1") … ORDER BY t1."Value1", t1."ParentID" DESC LIMIT :take`.
   - `….Skip(2).DistinctBy(p => p.Value1)` → `{5, 6, 4}`, C# `{5, 4, 3, 1}`.
2. **Tie-break lost when the ordering sits below the DISTINCT ON query** — the limited query keeps its ORDER BY (`SqlQueryOrderByOptimizer.cs:244`), the DISTINCT ON query's ORDER BY holds only the key, each group keeps an arbitrary row:
   - `….Take(7).Select(p => new { p.ParentID, p.Value1 }).DistinctBy(x => x.Value1)` → PostgreSQL.16 `{1, 3, 5, 6, 4}`, C# `{7, 6, 5, 4, 3}` (DuckDB happened to be right).
   - `….Take(7).AsSubQuery().Select(…).DistinctBy(…)` → PostgreSQL.16 `{1, 3, 5, 6, 4}`; `….Take(7).AsSubQuery().DistinctBy(…)` → PostgreSQL.16 `{1, …}`; NULLS variant (P8 TO-9) → PostgreSQL.16 `{4, 5}`, C# `{2, 1}`.

Widened by the user (P12 → *Design pivot*): the captured ordering (`ExpressionBuilder._currentOrderBy`, `ExpressionBuilder.cs:67-165`), which the ROW_NUMBER and OUTER APPLY lowerings of `DistinctBy` and the CteUnion eager-load strategy consume, is not a faithful record of the sequence's row order:

3. **An `OrderBy` on the inner side of a join / SelectMany replaces the outer ordering** (`OrderByBuilder.cs:184` resets the list; no builder isolates the inner build although `ExpressionBuilder.cs:139-141` says isolation covers "join inner, SelectMany collection"):
   - `from p in Parent.OrderByDescending(p => p.ParentID) join c in Child.OrderBy(c => c.ChildID) on p.ParentID equals c.ParentID select new { p.ParentID, p.Value1, c.ChildID }` then `.DistinctBy(x => x.Value1)` → SQLite.MS `{1, 2, 3, 6}` (`ROW_NUMBER() OVER (PARTITION BY Value1 ORDER BY ChildID)`), PostgreSQL.16 `{1, 3, 6, 2}` (`ORDER BY p."Value1", c_1."ChildID", p."ParentID" DESC`), C# `{7, 6, 4, 3}`. The `from … from c in Child.Where(…).OrderBy(…)` form: same values.
4. **A pre-`GroupBy` ordering survives the grouping** (`GroupByBuilder.cs:109`, no isolation): `OrderByDescending(p => p.ParentID).GroupBy(p => p.Value1).Select(g => new { g.Key, C = g.Count() }).DistinctBy(x => x.C)` → the ROW_NUMBER path orders by the pre-group column inside the grouped query (SQLite.MS SQL: `[g_1].[ParentID]` in a `GROUP BY [g_1].[Value1]` select list), instead of reporting that the sequence has no ordering.

## P2 Success criteria

- SC-1 On PostgreSQL and DuckDB, `DistinctBy` over a sequence that carries LIMIT (Take) or OFFSET (Skip) returns, per key, the first row of the limited rows in their order, and still lowers to DISTINCT ON.  → TO-1, TO-2
- SC-2 On PostgreSQL and DuckDB, when the DISTINCT ON query does not itself carry the sequence's ordering (it wraps a limited query, one or more levels down), the captured ordering is re-translated after the ON keys, keeping direction and NULLS position, for member and computed ordering keys alike, so each key keeps its first row.  → TO-3, TO-4, TO-9, TO-15
- SC-3 After a join (`join` / `Join` / `LeftJoin`, the `InnerJoin`-family) or a `SelectMany`, the captured ordering is the outer sequence's ordering followed by the inner side's — the inner side's first for a right join, which `Enumerable.RightJoin` enumerates inner-major — so `DistinctBy` keeps the first row in LINQ order on every provider, and the CteUnion root row order follows the same list.  → TO-10, TO-11, TO-12, TO-16, TO-17
- SC-4 An ordering applied before `GroupBy` survives it only when it orders by a grouping key (then the groups are ordered by that key, as in LINQ); any other pre-group ordering is dropped, so `DistinctBy` that has nothing else reports `Error_DistinctByRequiresOrderBy` on every provider; an `OrderBy` after `GroupBy` still counts.  → TO-5, TO-8, TO-18
- SC-5 A captured entry that cannot be lifted to the DISTINCT ON query (a body anchored inside a CTE, `CteContext.cs:94`) is skipped, so the query keeps master's valid SQL.  → TO-13
- SC-6 The CteUnion eager-load strategy keeps its child ordering and SQL: the eager-loading suites pass with no baseline change.  → TO-14
- SC-7 Untouched shapes are unchanged: the existing `DistinctByMethodTests` stay green on SQLite, PostgreSQL, DuckDB; the new limited-shape tests return the same rows on SQLite before and after.  → TO-6, TO-7

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Wrap a limited sequence before applying DISTINCT ON

- **chosen:** on the DISTINCT ON path, after the key produced a non-empty ON list against `sequence`, if `sequence.SelectQuery.IsLimited` (`SelectQueryExtensions.cs:56-57`), apply DISTINCT ON to `new SubQueryContext(sequence)`, lifting the key placeholders with `builder.UpdateNesting(wrapper, keySql)`, and return the wrapper.
- **rejected:** wrap before building the key — the wrapper sets `sequence.Parent` (`SubQueryContext.cs:23`); on the constant-key fall-through (`DistinctByConstantKeyFallsBackToRowNumber`) the sequence would stay parented to an orphan.
- **rejected:** send a limited sequence to the ROW_NUMBER path — right rows, but drops the DISTINCT ON lowering of #5630; TO-2's SQL arm guards it.
- **why this:** DISTINCT ON runs before its query's ORDER BY and LIMIT/OFFSET; wrapping a limited sequence before a modifier is the builder idiom (`DistinctBuilder.cs:27-30`, `WhereBuilder.cs:25-30`, `AllAnyBuilder.cs:43-47`).
- **failure mode of the choice:** the wrapper's ORDER BY starts empty, so alone it reproduces failure mode 2 — D-2 completes it. TO-1 / TO-2 separate D-1 only (TO-1's limited rows have distinct keys; TO-2's duplicated `null` key is left to an arbitrary pick without D-2); TO-3 / TO-4 / TO-9 separate D-2.

### D-2 — Tie-break from the captured ordering when the DISTINCT ON query has none of its own

- **chosen:** when the DISTINCT ON query's ORDER BY is empty (after D-1's wrap, or when the sequence wraps the query that carries the ordering), re-translate each captured body against the DISTINCT ON context with `builder.BuildSqlExpression(context, body, BuildPurpose.Sql, BuildFlags.ForKeys)` (as `OrderByBuilder.cs:114`), and add every non-constant placeholder whose `SelectQuery` is the DISTINCT ON query as an ORDER BY item with the captured direction and NULLS position; placeholders `UpdateNesting` could not lift (U-9) are skipped. When the query already has an ORDER BY, the existing in-place reorder runs unchanged. `ApplyDistinctOn` then moves the ON keys to the front as today.
  - Discriminating inputs: a Select wrapper over the limited query (TO-3), two levels down (TO-4), an explicit NULLS position (TO-9), a CTE-anchored entry (TO-13), the unlimited one-level-down `DistinctByAfterJoin` (TO-7 baseline).
- **rejected:** walk the SQL FROM chain down to the nearest non-empty ORDER BY and lift its items with `Select.AddColumn` (rounds 1–2 of this plan) — exact for the limited shapes and independent of the captured list, but a second, structural record of "where the ordering lives" beside the one the ROW_NUMBER / OUTER APPLY lowerings and CteUnion already use, with its own stop rules (GROUP BY, aggregation level). Once D-4 makes the captured list faithful, the SQL walk only duplicates it; separating input: none observable for the limited shapes (both produce `ORDER BY key, ParentID DESC`), so this rejection stands on single-source-of-truth grounds, not on a test.
- **rejected:** always rebuild the ORDER BY from the captured list, even when the DISTINCT ON query has one — drops tie-breaks that are not registered (`Sql.Ordinal`, constant-position orderings, `OrderByBuilder.cs:180`) and rewrites SQL for every existing DISTINCT ON shape.
- **why this:** the captured list is the sequence's ordering as the builder understood it, the ROW_NUMBER path already ranks by it (`DistinctByBuilder.cs:162`), and re-translation through `BuildSqlExpression` lifts it through any number of wrapper levels with the builder's own column cache.
- **failure mode of the choice:** correctness now depends on the captured list being right; D-4 fixes the join / SelectMany / GroupBy leaks, the CTE leak stays (P3, SC-5 makes it skip instead of dangle). A skipped entry leaves that tie-break to the database (master behaviour for that shape).

### D-3 — Result order of the DISTINCT ON path stays out of scope

- **chosen:** do not re-apply or publish the ordering after DISTINCT ON here; propose a follow-up issue with the P3 measurements.
- **rejected:** fix it here — wraps every DISTINCT ON query and moves every DISTINCT ON baseline; separable defect with its own repro.
- **why this:** keeps the PR to wrong rows from captured / DISTINCT ON ordering; after D-4 the follow-up can reuse the faithful list.
- **failure mode of the choice:** `OrderBy…DistinctBy…Take` without a re-ordering `OrderBy` keeps returning wrong rows on PostgreSQL / DuckDB until the follow-up.

### D-4 — Make the captured ordering follow LINQ row order across joins, SelectMany and GroupBy

- **chosen:**
  - Join inner side (`JoinBuilder.cs:39`), `InnerJoin`-family inner side (`AllJoinsLinqBuilder.cs:32`) and SelectMany collection (`SelectManyBuilder.cs:55`) are built under the existing `IsolateOrderBy()`, keeping the inner side's captured list; once the join type is known (`JoinBuilder.cs:59-93`, `AllJoinsLinqBuilder.cs:46-65`, `collectionInfo.JoinType` after `SelectManyBuilder.cs:55`) a new `ExpressionBuilder.AppendJoinedOrderBy(inner, joinedFirst)` merges it with the restored outer list into a new list: `[.. outer, .. inner]`, or `[.. inner, .. outer]` for `JoinType.Right`; an empty inner list leaves the outer list as it was. This is LINQ's order: `Join` / `LeftJoin` / `SelectMany` enumerate the outer side and then each match in inner order; `Enumerable.RightJoin` enumerates the inner side (critic round 3). `FullJoin` keeps the outer-first rule — it approximates LINQ (matched rows outer-major, then unmatched inner rows), and `JoinBuilder`'s `FullJoin` arm is `#if NET11_0_OR_GREATER`, unreachable on the shipped TFMs. The linq2db `RightJoin` / `FullJoin` / `Join(SqlJoinType…)` extensions (`AllJoinsLinqBuilder`, and the SelectMany-collection form) have no LINQ-to-objects order and follow the same rule by analogy (P10 L-4). GroupJoin's lazy inner (`GroupJoinBuilder.cs:118`) needs no edit: its unisolated route is the SelectMany collection, now covered (U-3).
  - `GroupByBuilder.BuildMethodCall`, once the grouping keys are built (`:170`), keeps only the captured entries whose SQL, built against the data sequence, consists of the grouping key's placeholders, and removes the rest with `RemoveOrderByEntries` — the `DistinctBuilder.cs:59-99` pattern for `Distinct`, and the optimizer's rule for an ORDER BY above a GROUP BY (`SqlQueryOrderByOptimizer.cs:133-141`, #5626). LINQ orders groups by first occurrence, which for an ordering by the key itself is the key order; for any other ordering it is not expressible in SQL without an aggregate (user's question on the plan, 2026-10-28).
  - The `ExpressionBuilder.cs:139-141` summary is corrected to describe both scopes.
- **rejected:** always append outer-first regardless of join type (the first version of this decision) — makes the outer side the major key of a `RightJoin`, where master's `[inner]` had the right major key; separating input: TO-16.
- **rejected:** isolate (discard) the inner side's ordering, as the summary at `:139-141` describes — breaks the CteUnion branch row number, which relies on the child `OrderBy` inside a generated SelectMany (U-4; 3696 baselines would turn the branch row number into `0`, and `Select_Union_ChildOrderedEnumerable_PreservesDescendingOrder` loses child order). Separating input: TO-14 (mutation `discard instead of append` → that test red).
- **rejected:** fix the join ordering only inside `DistinctByBuilder` (pick the outer ordering from the SQL tree) — leaves the ROW_NUMBER path, OUTER APPLY path and CteUnion root row number reading the wrong list; the user asked for the captured list itself to be fixed.
- **rejected:** at GroupBy, discard every pre-group ordering (`IsolateOrderBy()` over the whole method — the first version of this decision) — turns `OrderBy(k).GroupBy(k)…DistinctBy` from a correct query on master into an error; separating input: TO-18.
- **rejected:** at GroupBy, keep the pre-group ordering and translate it to an aggregate (e.g. `MIN`/`MAX` of the key per group) to emulate LINQ's first-occurrence group order — a new semantic with no precedent here; the error `Error_DistinctByRequiresOrderBy` is the existing contract for "no ordering".
- **why this:** fixes the record at its source, so every consumer (three `DistinctBy` lowerings, `Distinct` pruning, CteUnion) reads the same, correct list; the append keeps every shape that works on master working.
- **failure mode of the choice:** (a) a consumer that relied on the inner ordering *replacing* the outer one now sees both — the only such consumer found is the CteUnion branch, where the outer list is empty (U-5, measured by TO-14). (b) The GroupBy pruning turns `OrderBy(<non-key>)…GroupBy…DistinctBy` into an error on every provider (P3 delta); an ordering by an expression *of* the key (`OrderBy(p => p.Value1 + 1).GroupBy(p => p.Value1)`) is not a key placeholder and is dropped too — conservative, as `DistinctBuilder` drops a computed ordering not in the projection (P10 L-6). The placeholder comparison (two builds of the same member through different paths can yield different `SqlColumn` objects, `ExpressionBuildVisitor.cs:6262`) is settled when implementing, by TO-18 going green. (c) The lazy CTE body and the association / fallback builds at `ExpressionBuildVisitor.cs:1898,1474` are not covered (P7 deferred rows).
