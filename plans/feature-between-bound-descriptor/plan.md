## P1 Problem

Reported by Igor Tkachev in his approving review of PR #6349 (FYI, pre-existing on master). `Sql.Between` / `Sql.NotBetween` translate `value`, `low` and `high` with no column descriptor (`SqlFunctionsMemberTranslatorBase.TranslateBetween`, `UsingColumnDescriptor(null)` around all three), while `x >= a` / `x <= b` type a value written beside a column by that column (`ExpressionBuildVisitor.ConvertCompareExpression`: `UsingSuggestedDescriptor(SuggestColumnDescriptor(left, right))`). Measured on the base:

```
-- an int stored as a 5-digit zero-padded string through a column ValueConverter (FunctionTests.BetweenOfConvertedColumn)
where Sql.Between(r.Padded, 5, 50) || Sql.Between(42, r.Low, r.High)
PostgreSQL.16: Npgsql.PostgresException 42883: operator does not exist: text >= integer
SQLite.MS:     [r].[Padded] BETWEEN 5 AND 50 OR 42 BETWEEN [r].[Low] AND [r].[High]  -> 0 rows, expected 2

-- a Guid? stored as text by its declared type, no converter (SQLite.MS)
Sql.Between(r.Value, low, high)  -> DECLARE @low Blob(16) ... BETWEEN @low AND @high  -> wrong rows; r.Value == low writes VarChar(36) text

-- a DataType.Date column, captured DateTime bounds with a time part (FunctionTests.BetweenOfDateColumn, between-pair-base-red.log)
PostgreSQL.16: r."Day" BETWEEN :low AND :high (Timestamp)  vs  r."Day" >= :low_1 AND r."Day" <= :high_1 (Date)  -> different rows
```

A second, SQLite-specific divergence (measured, `between-pair.log`): `SQLiteSqlExpressionConvertVisitor.ConvertExprExprPredicate` brings both sides of a date comparison to one form (`Date(...)` / `strftime(...)`, mandatory casts) and `VisitInListPredicate` does it for `IN`, but nothing does it for `BETWEEN`, so `[r].[Day] BETWEEN @low AND @high` compares the date text `'2020-01-01'` with `'2020-01-01 00:30:00.000'` where `Date([r].[Day]) >= Date(@low)` compares two dates. Pre-existing on the base for parameter bounds.

## P2 Success criteria

- SC-1 Beside a column with a `ValueConverter`, constant and parameter bounds, and a parameter value between column bounds, are written in the stored form; `Between` / `NotBetween` return the C# answer in a filter and a projection, including over a grouping's aggregate. → TO-1
- SC-2 Same for a `TimeSpan` column with `Duration(DurationUnit.Second)`. → TO-2
- SC-3 Beside a column whose stored form is chosen by its declared `DataType` (a `Guid?` stored as `VarChar`), the bounds take that form; with the conversion such a mapping needs registered, on every provider. → TO-3, TO-4
- SC-4 Beside a `DataType.Date` column, `Between` / `NotBetween` answer as `>=` / `<=` (`<` / `>`) answer in the same query — stored column, a value computed from one, an optional row's column, constant and parameter bounds — on every provider, SQLite included. → TO-5
- SC-5 The column the `Between` result is assigned to still does not type the operands (#6349 D-3). → TO-6
- SC-6 Every other `Between` test passes unchanged; the full SQLite.MS run changes no existing baseline other than by D-1 / D-3. → TO-7

## P3 Constraints & anti-goals (M/L)

- Public API (A-3, D-2): one new member `ITranslationContext.UsingComparisonDescriptor(Expression, Expression)` with an XML doc, a `PublicAPI.Unshipped.txt` line, and a `CP0006` suppression per TFM regenerated by `/api-baselines` (never hand-edited) — as #5468 did for `ProviderFlags`; D-5's builder is a public static method of `QueryHelper` with an XML doc and an `Unshipped` line (provider visitors call it — `code-design.md` → *Provider-called core methods are public*; critic round 4); the SQLite / Sybase `VisitBetweenPredicate` overrides take `PublicAPI.Unshipped.txt` lines (A-1); D-6 is private to `FirebirdSqlOptimizer`; A-5: D-7 is private to `DuckDBSqlOptimizer` (its `FinalizeStatement` override exists) and adds a `SapHanaSqlOptimizer.FinalizeStatement` override, which takes a `PublicAPI.Unshipped.txt` line (an added override, not a break). No other public surface.
- The column a `Between` result is assigned to does not type the operands — #6349 D-3, pinned by `FunctionTests.BetweenProjectedIntoConvertedColumn` / `BetweenSetIntoConvertedColumn`; the outer `UsingColumnDescriptor(null)` stays.
- `BETWEEN` stays the emitted predicate everywhere except SQLite over dates (D-3) and Sybase over a date beside a timestamp (A-1), which lower it without an enclosing `NOT` (D-5); NULL semantics unchanged except delta 8 (L-15); #6349's placement unchanged.
- Anti-goal: other translators that type operands (`Like` / string functions / YDB through `UsingTypeFromExpression`).
- Anti-goal: the comparison's refusal of operands stored differently (`ExpressionBuildVisitor.CombinesDivergentStorage`) — `Between` keeps the base's silence (P10 L-1).
- Anti-goal: a default `Guid` → text conversion for `DataType.VarChar` columns (U-7 — a mapping requirement, not a defect).
- Anti-goal: the row form `Sql.Row(...).Between(...)` — `QueryHelper.GetColumnDescriptorCore` has no arm for `SqlRowExpression`.

User-visible deltas vs the base (and master):

1. Fixed — the operands of `Between` / `NotBetween` beside a column with a `ValueConverter` / `Duration` unit or a declared `DataType` that changes the stored form are written in that form (SC-1..3).
2. Changed — beside a stored `DataType.Date` column (and any column coarser than the bound's own type), a constant or parameter bound takes the column's type as with `>=` / `<=`: SQLite, SQL Server and PostgreSQL (parameters) compare at date precision, so `Sql.Between(r.Day, noon, …)` includes the day of `noon` where the base excluded it (SC-4; user decision 2026-11-20, option b).
3. Parameters and constants of a `Between` beside any column take that column's declared type (size, Unicode, precision), as with `>=`.
4. Changed (SQLite) — a `BETWEEN` / `NOT BETWEEN` with any operand of a date or timestamp type (`Date`, `DateTime`, `DateTime2`, `DateTimeOffset`, `SmallDateTime`, `Timestamp`, or an undefined `DataType` over a CLR `DateTime` / `DateTimeOffset`; not `Time` — A-2) is written as its two comparisons (`x >= a AND x <= b`; `NOT BETWEEN` as `x < a OR x > b` — A-3, D-5), each side wrapped in `Date(...)` / `strftime(...)` as a comparison's is — the value is written twice and a column is no longer a bare operand (D-3; user decision 2026-11-20, "Фіксай тут").
5. Changed (SQL Server) — a `Guid` mapped with `DataType.VarChar` and no registered conversion: `Between` compared through SQL Server's implicit `uniqueidentifier` conversion on the base and now fails as `==` and `UPDATE` already do for that mapping (L-2).
6. Changed — a client value that its two pairs would type differently (one bound a column with a `ValueConverter`, a `Duration` unit or a declared type that changes the parameter and the other not, or two column bounds of different declared types) is written once: in the converted bound's form when a bound is converted, the other client bound with it (A-2, D-4 arm 2), otherwise untyped as on #6349 (D-4 arm 3). It is always one `BETWEEN`.
7. Fixed (Firebird) — a parameter value of `BETWEEN` whose low bound is a parameter too is cast to its type; Firebird rejected it with `-804 Data type unknown` (`Sql.Between(value, low, r.Id)`; three client values only as far as TO-12 measures them), and on Firebird 2.5 a parameter value of `NOT BETWEEN` whose high bound is a parameter (A-4) — pre-existing on master (A-3, D-6).
8. Changed (SQLite, Sybase) — D-3 / A-1 lower a `BETWEEN` to its comparisons, and a comparison of two client values folds where parameter values are at hand (U-11; A-4: on the direct side only once E-12 / E-13 make the statement parameter-dependent), a NULL to FALSE: inside a `NOT` the optimizer keeps outside a compound condition (`!(Sql.Between(none, r.Day, high) && x)`), a NULL client operand answers TRUE where master's `NOT (… BETWEEN …)` is unknown (P10 L-15). D-5 removes the `NOT` the lowering itself added, so `NotBetween`, `!Sql.Between(...)` and a projected negation keep SQL's answer (U-12 measured them TRUE on this branch before D-5).
9. Fixed (SAP HANA, DuckDB; A-5) — a timestamp parameter value of a `BETWEEN` with a date bound that is not a parameter is cast to its own type, so the server no longer types it as a date: `Sql.Between(value, r.Day, high)` with a time in `value` and `high` answered TRUE where `value >= r.Day && value <= high` is FALSE (both), and on DuckDB a parameter used in such a `BETWEEN` and beside a timestamp elsewhere in the statement failed to bind (`invalid date field format`) — pre-existing on master and #6349 (the same SQL, U-19; D-7).
10. Changed (DuckDB; A-5 round 10) — in a statement with such a `BETWEEN`, every other use of the same value parameter is cast to its type too (D-7's DuckDB arm): `value <= r.Stamp.Date` there compares the value as a timestamp, where DuckDB typed it as a date and dropped its time (master; U-22: [2] → [], C#'s rows) — and `Sql.Between(value, r.Day, high) || value >= r.Stamp.Date` no longer fails to bind with D-7 (U-21). Statements without such a `BETWEEN` are unchanged.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Type each bound as its comparison with the value types it

- **chosen:** `value` and `low` are translated in the scope of the comparison `value >= low`, `high` in the scope of `value <= high` — each scope is `ExpressionBuildVisitor.UsingComparisonDescriptor(context, left, right)`: `SuggestColumnDescriptor(left, right)` under `BuildPurpose.Sql`, then `UsingSuggestedDescriptor` — the lookup, coarse date/time exception and pair combination `>=` / `<=` use. User decision 2026-11-20 ("Відкочуй і роби b").
- **rejected:** converter / unit only — left a declared-`DataType` storage form wrong; implemented, withdrawn.
- **rejected:** a converted operand → emit the two comparisons, otherwise `BETWEEN` (user's proposal, prototyped green) — rolled back by the user for b.
- **rejected:** first operand with a descriptor lends it to all three through `UsingColumnDescriptorBeside`, found through `ITranslationContext.Translate` — critic round 2 refuted it (U-4): a bound typed by its sibling bound, and an optional row's stored column seen as computed.
- **rejected:** `UsingTypeFromExpression(value, low, high)` as `Like` uses — no coarse exception (U-1).
- **why this:** one rule for `BETWEEN` and `>=` / `<=` by construction; only the value's single occurrence is a choice (typed as in `value >= low`).
- **failure mode of the choice:** a constant value between bounds typed differently is written once, typed by `low`; the comparison's divergent-storage refusal is not reproduced (L-1).

### D-2 — Reach the visitor through a member of `ITranslationContext` (A-3; was an internal interface)

- **chosen (A-3):** `IDisposable UsingComparisonDescriptor(Expression left, Expression right)` on the public `ITranslationContext`, beside `UsingColumnDescriptor`, with an XML doc; `ExpressionBuildVisitor.TranslationContext` forwards to the internal `ExpressionBuildVisitor.UsingComparisonDescriptor(IBuildContext?, Expression, Expression)`; `IComparedValueTranslationContext` is deleted and the translator calls the member directly. User decision 2026-11-26 (MaceWindu MIN001, option a); the rule is `code-design.md` → *Count the implementors before adding a parallel interface beside a shipped one* (`ITranslationContext` has one implementor, `ExpressionBuildVisitor.cs:5906`, scout).
- **rejected (A-3):** the internal side interface (D-2 as approved) — the maintainer rule above, and a failed cast silently turned the typing off.
- **rejected:** re-deriving the comparison's lookup in the translator — a second copy of `SuggestColumnDescriptor`.
- **why this:** the one implementor already carries the sibling scope helpers; precedent #5468 (`ProviderFlags`: doc, `Unshipped` line, `CP0006` per TFM).
- **failure mode of the choice:** a binary-breaking addition for a third-party implementer (`CP0006`) — classified `added`, allowed at a minor (`api-surface-classification.md`); a release-notes line.
