## P1 Problem

Split out of the concat branch (its P3 / P10 L-4). On SQL Server (SqlServer.2019.MS, `Latin1_General` collation), a closure parameter or literal passed to a string function over a column mapped `DataType.VarChar` / `DataType.Char` is sent as non-Unicode, so non-Latin text comes back as `?`. Measured on master and on the stacked base (`7e10e0bd13`) with the new tests in `Tests/Linq/Linq/StringFunctionTests.cs` (`StringTypesTable`: `CharColumn Char(50)`, `NCharColumn NChar(50)`, `VarCharColumn VarChar(50)`, `NVarCharColumn NVarChar(50)`; logs `.build/.agents/unicode-args-{master,sibling}.log`, `strargs-red-base*.log`, `ab-base.log`):

- computed arguments — projection over `VarCharColumn = "A-100"` / `"B?200"`: `Replace("A", suffix = "Жук")` → `???-100`; `Sql.Replace(col, "A", suffix)` → `???-100`; `Replace(search = "Ж", "-")` over `"B?200"` → `B-200` (the `?`-typed search value replaces a real `?`); `Replace('A', 'Ж')` / `Sql.Replace(col, 'A', 'Ж')` → `?-100`; `PadLeft(8, 'Ж')` → `???A-100` (`REPLICATE('Ж', …)`); over `CharColumn`: `Replace("A", suffix).TrimEnd()` → `???-100` (`DECLARE @suffix Char(3) -- AnsiStringFixedLength`).
- compared values over a concat or a cast object — `(col + suffix).CompareTo(NVarCharColumn)` → `-1` (expected `0`), `(col + suffix).TrimEnd()` → `A-100???`, `Sql.Like(col + suffix, NVarCharColumn)` → no rows (expected row 1); `Sql.Like(Sql.Convert(Sql.Types.NVarChar(50), col), "%Ж%")` → row 2 (expected none: the pattern is typed `VarChar(50)`, `'%?%'` matches the real `?`). The concat shapes are red on master through the concat itself and still red on the stacked base.

Three mechanisms, each probed:

1. **Translator scope, read path.** `TranslationContextExtensions.UsingTypeFromExpression` (`TranslationContextExtensions.cs:88-114`) makes the first argument's column descriptor current for everything translated next, and finds it through `QueryHelper.GetColumnDescriptor` — the read path, which passes through a concat to its first column and through a cast that changed the database type. Callers: `StringMemberTranslatorBase` `TranslateLike :279`, `TranslateSqlReplace :303`, `TranslateStringReplace :330`, `TranslateCompareTo :357`, `TranslateStringPadLeft :383/:396`, `TranslateStringIsNullOrWhiteSpace :425`, `TranslateStringTrim :450`, `YdbMemberTranslator.TranslateLike :132`. `==` already types through `GetColumnDescriptorForTyping` (`ExpressionBuildVisitor.SuggestColumnDescriptor :3354`), so the string translators disagree with it.
2. **Computed arguments take the object column's type unconditionally** — the same scope, at Replace and the PadLeft padding char (`:396` re-lends `translatedField`'s descriptor), even for a plain VarChar column that a typing lookup also returns.
3. **`SqlExpressionFactoryExtensions.Replace` casts both arguments to the value's type** (`SqlExpressionFactoryExtensions.cs:391-395`, `EnsureType`, which compares through `EqualsDbOnly` including `Length`; from #4868 `19c112f46d`). On master it is a no-op in the common case — the argument already carries the column's type through mechanism 2. With mechanism 2 removed the parameter became `NVarChar(4000)` and was rendered `CAST(@suffix AS VarChar(50))`, literals `'Ж'` (`.build/.agents/unicode-args-fix.log:5742-5746`).

## P2 Success criteria

- SC-1 A projected Replace (`string.Replace(string,string)`, `Sql.Replace(string,string,string)`) over a VarChar column returns the C# answer for a non-Latin parameter, including a non-Latin search value over a row holding a real `?` → TO-1
- SC-1c A projected Replace with char literals (`string.Replace(char,char)`, `Sql.Replace(string,char?,char?)`) and `PadLeft(n, char)` with a non-Latin char literal over a VarChar column returns the C# answer → TO-1c
- SC-1d The same over a Char column, for a parameter and a char literal → TO-1d
- SC-2 `CompareTo`, `TrimEnd` and `Sql.Like` whose object/first argument is `varcharCol + p` return the C# answer for a non-Latin `p` → TO-2
- SC-3 `Sql.Like` over a cast of a VarChar column to NVarChar types its pattern from the cast, not the column → TO-2b
- SC-4 A computed argument under a comparison with a VarChar column keeps the comparison's VarChar type (index use), for Replace and the PadLeft char → TO-3
- SC-4b A Replace argument beside a Char column under a comparison with a VarChar column is not padded to the Char column's length → TO-3d
- SC-5 A computed argument beside an NVarChar or NChar column keeps that column's type, as on master → TO-4, TO-4b
- SC-6 A value compared with a plain VarChar column through `CompareTo` / `Sql.Like` keeps the column's VarChar type, as on master → TO-5, TO-5b
- SC-7 A Replace argument longer than (or of unknown length beside) the value's declared length is not cut — on SQL Server (Unicode argument) and on PostgreSQL (`Text` argument beside `VarChar(50)`) → TO-6
- SC-8 No SQL change on SQL Server / SQLite outside the declared type / `N` prefix / cast of string-function arguments beside a Char/VarChar column and the values D-1 retypes (beside a type-changing cast or a concat) → TO-7

## P3 Constraints & anti-goals (M/L)

- No public API change: `UsingTypeFromExpression` (both overloads) and `SqlExpressionFactoryExtensions.Replace` keep their signatures; new helpers are private static. No AST change.
- The read path of `QueryHelper.GetColumnDescriptor` (value converters when reading) is unchanged.
- `Trim(chars)` typing (`StringMemberTranslatorBase.cs:469/477`, `factory.Value(GetDbDataType(field), …)`) is not touched — user's choice 2026-10-27 (deferred, separate mechanism).
- Compared sites (`Sql.Like`, `CompareTo`, YDB `Sql.Like`) keep lending a plain column's type, VarChar included — pinned by master's `LikeWithDataType1`.
- Not fixed here: the Access concat convert loop (P10 L-4) — pre-existing on master.
- User-visible deltas vs master (cumulative with the concat branch's P3):
  - `UsingTypeFromExpression` (public, `LinqToDB.Internal.*`) now lends the *typing* descriptor: nothing from a concat without a Unicode column operand, nothing through a cast that changed the database type/precision/scale — D-1. Third-party translators calling it see the same change. A value beside a type-changing cast of an NVarChar column now takes the enclosing type (`NVarChar(4000)` on SQL Server) instead of the column's `NVarChar(n)`.
  - Replace (four registrations) arguments and the PadLeft padding char take the object column's descriptor only when it is NChar/NVarChar/NText; otherwise the enclosing descriptor — the projected member's (default `NVarChar(4000)` on SQL Server, `VarChar(255)` on Oracle, `Text` on PostgreSQL), the comparison partner, the assignment target — D-2, D-3. A non-Unicode column's `ValueConverter` and `Length` no longer reach those arguments.
  - `SqlExpressionFactoryExtensions.Replace` casts an argument to the value's type only when the cast changes nothing it holds: never a Unicode argument beside a Char/VarChar/Text value, never an argument longer than the value or of unknown length, never to a fixed-length (Char/NChar) value — D-4. A differently typed argument beside a Char column, cast (and padded) to the column's type on master, is no longer padded. SQL Server renders `Replace([t].[VarCharColumn], N'A', @suffix)` where master rendered `Replace([t].[VarCharColumn], 'A', @suffix)` with `@suffix VarChar(50)`; a same-family argument longer than the value (`x.NVarChar50.Replace("A", y.NVarChar100)`), cast to the value's length on master, is no longer cut. The function's declared type stays the value's.
  - shipped prose stating the old contract: none — `Grep` `UsingTypeFromExpression|EnsureType|Replace\(` XML docs in `TranslationContextExtensions.cs` / `SqlExpressionFactoryExtensions.cs` (no `<summary>` on either) and `Sql.Replace` docs (no typing claim).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — `UsingTypeFromExpression` looks up the typing descriptor

- **chosen:** `UsingTypeFromExpression(ISqlExpression?)` (and so the `params Expression[]` overload, which delegates) calls `QueryHelper.GetColumnDescriptorForTyping`. User's choice "C" (altitude half), 2026-10-27.
- **rejected (per-site switch in each caller):** same effect over eight call sites, and a new caller of the public helper would get the read path back. No input separates it from the chosen form.
- **rejected (leave the read path):** `(col + p).CompareTo/TrimEnd`, `Sql.Like(col + p, …)` and `Sql.Like(CAST(col AS NVarChar), p)` stay red. Separating inputs: TO-2, TO-2b — mutation m1 reddens both.
- **why this:** one rule for every value typed beside an expression — the one `==` already uses.
- **failure mode of the choice:** the typing walk's coalesce / condition / case arms still lend the first branch (the concat plan's coalesce / condition / case limit), so `(cond ? col : p).TrimEnd()` still types `p` from a VarChar `col` (P10 L-1). A value beside a type-changing cast of a Unicode column also loses that column's length (P3).

### D-2 — computed arguments take the object column's type only when it is Unicode

- **chosen:** `TranslateSqlReplace`, `TranslateStringReplace` and `TranslateStringPadLeft` open their scope with the concat branch's `UsingUnicodeTypeFromOperand` (now `params`), which lends the first NChar/NVarChar/NText descriptor and otherwise leaves the enclosing one. User's choice "C" (computed half).
- **rejected (keep lending any column type):** the P1 repro. Mutations m2 / m3 / m4 redden TO-1 / TO-1c / TO-1d.
- **rejected (drop the scope: `UsingColumnDescriptor(null)` when not Unicode):** a computed argument compared with an indexed VarChar column becomes nvarchar (`CONVERT_IMPLICIT` on the column). Separating input: TO-3 — mutation m6 → `@dash NVarChar(4000)`.
- **why this:** the concat branch's D-1 rule, applied to the other functions that build a value out of a column.
- **failure mode of the choice:** under a comparison or assignment with a VarChar column a non-Latin argument is still VarChar (P10 L-2); a non-Unicode column's `ValueConverter` / `Length` no longer reach Replace / PadLeft arguments; on providers whose default string type is non-Unicode (Oracle, PostgreSQL) the argument's declared type moves from the column's to the default (`VarChar(255)` / `Text`) — baselines there change (G-02, CI).
- **set members:** NChar — TO-4b (mutation m14); NVarChar — TO-4 (m9); NText — unexercised (deprecated SQL Server type, no column in the model).

### D-3 — the PadLeft char is translated under the object's scope, the count under its own null scope

- **chosen:** the padding count keeps its `UsingColumnDescriptor(null)` scope, now a block around its own translation; the char is translated under D-2's scope (object's Unicode descriptor, else enclosing). Master re-lent `translatedField`'s descriptor to the char inside the count's null scope.
- **rejected (char under the null scope when the column is not Unicode):** `b.Code == a.Code.PadLeft(5, '0')` renders `REPLICATE(N'0', …)` — an nvarchar comparison. Separating input: TO-3 — mutation m5.
- **why this:** the char is part of the computed value, so it follows D-2; the count is an integer and never took a string type.
- **failure mode of the choice:** none beyond D-2's.

### D-4 — `factory.Replace` casts an argument to the value's type only when the cast loses nothing

- **chosen:** `SqlExpressionFactoryExtensions.Replace` routes each argument through a private `EnsureReplaceArgumentType`: the argument is returned uncast when it is NChar/NVarChar/NText beside a Char/VarChar/Text value (`losesCharacters`), when the value has a length and the argument's is unknown or longer (`losesTail`), or when the value is fixed-length Char/NChar (`padsTail`); otherwise `EnsureType(argument, valueType)` as on master (re-keyed in pass 2 after critic round 1; `padsTail` added after round 2). A value with no declared length (Text / CLOB, a computed value) still takes the cast: it widens and loses nothing.
- **rejected (pass 1: skip only a Unicode argument beside a non-Unicode value):** refuted — after D-2 a default-typed argument on Oracle (`VarChar(255)`) / PostgreSQL (`Text`) is cast to the column's `VarChar(50)`, a new cast that cuts it. Separating input: TO-6's PostgreSQL cell — mutation m12 (`losesTail = false`, exactly pass 1's form) → `:suffix::VarChar(50)`, red (measured).
- **rejected (keep the cast as master):** D-2 alone stays red (`CAST(@suffix AS VarChar(50))`). Mutation m7 reddens TO-1 and TO-6.
- **rejected (drop `EnsureType` from `factory.Replace`):** would also leave a shorter non-Unicode argument (a `Char(1)` char on a provider mapping `char` non-Unicode) uncast, which master cast; no local input separates it from the chosen form (SQL Server / SQLite / PostgreSQL map `char` to `NChar(1)`), so it rests on keeping master's behaviour where nothing is lost.
- **rejected (cast to the value's Unicode counterpart):** a short Unicode argument would gain the value's length and lose nothing — no input separates it from leaving it uncast; a long one is already left uncast by `losesTail`. Rejected for adding a cast that does nothing.
- **rejected (move the rule into `TranslateReplace`):** `factory.Replace` has no other caller (U-1), and the cast is what is wrong.
- **why this:** the cast exists to bring a `char` or a shorter argument to the value's terms; it must not narrow one.
- **failure mode of the choice:** the function's declared type stays the value's VarChar while SQL Server returns nvarchar — a later reader of the declared type (`BasicSqlOptimizer.CorrelateValueTypes :479-521` for set operations) sees VarChar, as on master (critic round 1: no regression found); a provider requiring one character set across REPLACE's arguments would now see two (none known; CI).
- **set members:** value Char — TO-1d `Chars` (mutation m15); value VarChar — TO-1c (m13); value Text — unexercised (no Text column in the model); argument NChar — TO-1c `Chars`/`FunctionChars` (m13); argument NVarChar — TO-1 / TO-6 SQL Server (m7); argument NText — unexercised; `losesTail` — TO-6 PostgreSQL (m12); `padsTail` Char — TO-3d (m16); `padsTail` NChar — unexercised separately (an NChar column lends its descriptor through D-2, so its arguments already carry its type).

### D-5 — compared sites keep lending a plain column's type

- **chosen:** `TranslateLike`, `TranslateCompareTo`, `YdbMemberTranslator.TranslateLike` keep `UsingTypeFromExpression` (typing lookup after D-1), VarChar included.
- **rejected (Unicode-only at these sites too):** `Sql.Like(varcharCol, p)` / `varcharCol.CompareTo(p)` become nvarchar comparisons; contradicts `LikeWithDataType1`. Separating inputs: TO-5 / TO-5b — mutations m10 / m11.
- **why this:** the value is compared with the column, the same as `==` (concat plan P10 L-1).
- **failure mode of the choice:** a non-Latin pattern / bound against a VarChar column is `?`-typed (matches stored `?`), as with `==`.
