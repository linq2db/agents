## P1 Problem

Absent capability, the half of [#1404](https://github.com/linq2db/linq2db/issues/1404) that #6111 left out: reads registered from several call sites and run together (`DeferValue` / `CompleteDefer` in the issue). #6111's `db.QueryBatch(...)` needs every read written in one expression at one call site, so a repository whose page count and page rows come from two methods, or whose set of reads is conditional, cannot use it without passing `Expression<Func<T>>`s up to one call of a statically known arity of at most 7. On `f798e94b51` the target shape does not compile: `db.CreateQueryBatch()` does not exist (searched `CreateQueryBatch|QueryBatchBuilder|QueryBatchResult` across `Source/` and `Tests/`: no hit). #6111's plan (P5 D-1) deferred an explicit batch object "until cross-method registration is asked for"; the user asked for it on 2026-11-11:

```csharp
var batch = db.CreateQueryBatch();
var total = batch.Add(() => query.Count());
var items = batch.Add(() => query.Skip(offset).Take(limit).ToList());
await batch.ExecuteAsync(cancellationToken);
return new Page<T> { Count = total.Value, Items = items.Value };
```

(A-5, 2026-11-13) The reviewer asked to rebuild the batch step by step: first `Set` for regular results, then the two streaming forms (per row and `IEnumerable<T>`), later others such as `new { }`. The mechanism should also serve linq2db itself — eager loading — which needs streaming. Step 1, by the user's calls, is query first and a setter:

```csharp
var page  = new Page<T>();
var batch = db.CreateQueryBatch();
batch.Set(() => query.Count(), v => page.Count = v);
batch.Set(() => query.Skip(offset).Take(limit).ToList(), v => page.Items = v);
await batch.ExecuteAsync(cancellationToken);
```

(A-6) The query takes no context parameter: it captures what it reads, the context included, as `db.QueryBatch(() => …)` does. A-5's `d => …` form is gone (D-9).

## P3 Constraints & anti-goals (M/L)

- Public API is additive: `LinqExtensions.CreateQueryBatch`, `QueryBatchBuilder`, `QueryBatchResult<T>`, and `ErrorHelper` constants (internal namespace). No existing member changes signature. None of them shipped (all are this PR's `Unshipped` lines). (A-6) The surface is `CreateQueryBatch(this IDataContext)` and the non-generic `QueryBatchBuilder` (`Set<T>(Expression<Func<T>>, Action<T>)`, `Execute`, `ExecuteAsync`); A-5's generic forms go, unshipped too.
- No engine change: no edit under `Source/LinqToDB/Internal/Linq/**` or `Source/LinqToDB/SqlQuery/**` beyond A-3's visibility change of two eager-load helpers (`private` → `internal`, no body change), A-4's `CreatesTask` extraction and A-5's one comment line in `ScalarSelectBuilder`; no SQL change and no query-cache key change for any existing query; `NewQueryBatchTuple`'s shape for arities 2…7 unchanged.

- Anti-goal (the user's calls, 2026-11-11): no `IQueryable` shortcut overloads, no interfaces, no re-executable or incremental batch, no Faulted state, no lazy `Value`, no snapshot of captured values at `Add`.
- Anti-goal (the user's call): one round trip on a remote context. Remote runs sequentially, as `db.QueryBatch` does, and the docs promise nothing about it.
- Anti-goal — #1404 still narrowed, disclosed in the PR body ("Part of #1404"): deferred writes, a value from one statement feeding the next, subset flushing ("groups").
- User-visible deltas vs the parent branch (#6111): one new API family; no existing call changes behaviour. Shipped prose restating a contract this changes: none (searched the `<summary>` / `<remarks>` of `LinqExtensions.QueryBatch*`, `LinqExtensions.QueryBatch.cs:23-107`; they describe the one-call form only).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — An explicit batch object the caller holds

- **chosen:** `db.CreateQueryBatch()` returns a `QueryBatchBuilder` that the caller holds and passes to any method. `Add` records a lambda and returns a `QueryBatchResult<T>`. `Execute` runs every part through one `QueryBatch` call. (A-5) `Add` and the handle are replaced by `Set(query, setter)` — D-9; the batch object and the one `QueryBatch` call stay.
- **rejected:**
  - Context-level futures (`DeferValue` / `CompleteDefer`) — they need pending state on the context, flush triggers and Dispose behaviour (#6111 P5 D-1 and P3, kept).
  - A lazy `Value` that runs the batch on the first read — hidden synchronous I/O in async code (the user's call).
  - `IQueryable` shortcut overloads and interface types — the user's call: minimal surface.
- **why this:** the object carries the registration across call sites without the context knowing about it. One `QueryBatch` call keeps one build and one `ParametersContext`, so the `AccessorId` collision of independent builds cannot occur. It also keeps the read transaction, the hints refusal and the strict element operators of the node.
- **failure mode of the choice:** a forgotten `Execute` surfaces at the first `Value` read, not at the batch. The batch is not thread-safe, like `DataContext`.

### D-2 — Parts fuse into one runtime-built `ValueTuple`

- **chosen:**
  - The tuple type is built from the parts' body types: `ValueTuple<T1…T7>`, nested through `Rest` beyond seven parts.
  - The body is a `New` of the tuple, in a `Func<TTuple>` lambda, under the node `Methods.LinqToDB.QueryBatch.MakeGenericMethod(tupleType)`. (A-3) The type and the `New` come from the eager-load helpers `ExpressionBuilder.BuildValueTupleType` / `BuildValueTupleNew`, which nest the same way; their `New` binds no members, which the projection does not need (measured, A-3).
  - It runs through `ExpressionQueryImpl.CreateQuery(tupleType, …)` and `Execute<object>` / `ExecuteAsync<object>`.
  - Each handle reads its field through a `FieldInfo` path computed at `Execute`. The closed tuple type depends on every part, so the path cannot exist at `Add`. A read through `Rest` boxes each nested tuple once per read.
- **rejected:**
  - One `object[]` body — every batch would be `QueryBatch<object[]>`, sharing one 16-entry cache bucket per context type (critic round 1, `QueryCache.cs:503-553`, refuted).
  - `object[]` plus a `ChainHash` that hashes the body — a change to cross-cutting core.

### D-3 — Lifecycle: single use, a failure leaves the batch un-run

- **chosen:** the states are Pending → Running → Executed.
  - `Add` works only in Pending.
  - `Execute` starts from Pending. Success moves the batch to Executed, so it is single-use.
  - Any exception, including one thrown before the first await, returns the batch to Pending with no value set, so it can be retried. (A-5) This holds up to the first setter; once setters run the batch is Executed — D-10.
  - An empty batch's `Execute` sends nothing and moves to Executed.
  - `Value` throws unless the batch is Executed — including while Running, so a part that reads a handle of its own batch fails every run (U-17). The remarks on `Value` say a handle is read after `Execute`, never inside a part. (A-5: there is no `Value`; a part that reads a setter's target sees its value before `Execute` — SC-17.)
  - Order of checks in `Execute` / `ExecuteAsync`: the state first (Running or Executed → `InvalidOperationException`), then the empty batch (no command, and no hints or token check), then the `QueryBatch` node with its inherited checks (hints, the cancelled token since A-4, the disposed context).
- **rejected:**
  - A Faulted state that rethrows the original exception (the user's call).
  - A re-executable or incremental batch (the user's call).
  - An empty `Execute` that stays Pending — then "run" would depend on the part count.
- **why this:** a batch is a list of expressions, and a failure consumes nothing (U-5).
- **failure mode of the choice:** a retry inside a user transaction that the error aborted fails again until the user rolls back (PostgreSQL, U-6). The remarks say the retry runs in the caller's transaction as it stands.

### D-4 — `Execute()` and `ExecuteAsync(token)`; the cancelled token is the node's check

- **chosen:** `Execute()` and `ExecuteAsync(CancellationToken token = default)`, with the parameter named as on #6111's overloads. (A-4) The cancelled-token check is the `QueryBatch` node's (`Query.ThrowIfQueryBatchIsCancelled`, #6111 f90e2edd15), which runs before the load transaction and any command; the batch's own `ThrowIfCancellationRequested`, the first cut of this decision, was removed as its duplicate. The node checks the token after it has built the query (`ExpressionQuery.cs:117-120`), so on a cache miss a translation error or the hints refusal is reported before the cancellation. An empty batch never reaches the node, so it does not check the token (TO-8). Everything else is inherited from the `QueryBatch` node: the hints refusal, the read transaction, combining, strict element operators and the sequential remote path.
- **rejected:**
  - Async only (the user's call).
  - Relying on the token to reach the provider — a command or a BEGIN goes out first, and the exception type differs per provider (U-7).
- **why this:** the pre-check makes "nothing sent" true on every provider, at one line's cost.
- **failure mode of the choice:** cancellation after the pre-check is the provider's (`TaskCanceledException` on SQL Server). The docs promise only `OperationCanceledException`, which `TaskCanceledException` derives from.

### D-5 — Captured values are read at `Execute`

- **chosen:** `Add` stores the lambda as written. Closures are read when `Execute` builds the parameters, which is C#'s and deferred LINQ's semantics (the user's call).
- **rejected:** a snapshot at `Add` — it needs partial evaluation of the tree and differs from the rest of LINQ.
- **why this:** no code; the behaviour every LINQ user expects.
- **failure mode of the choice:** a value changed between `Add` and `Execute` is read in its changed state — intended, documented in `Add`'s remarks, pinned by TO-14.

### D-6 — Remote contexts inherit the sequential path

- **chosen:** no code and no doc promise. On a remote context the parts run one by one, with no read transaction, as `db.QueryBatch` does (#6111 P10; the user's call).
- **rejected:** a `NotSupportedException` on remote — extra code and a test, and it would diverge from `db.QueryBatch`.
- **why this:** zero cost; the values are the same (U-1).
- **failure mode of the choice:** "one round trip" does not hold on remote; the remarks say only that a context which cannot combine runs the parts one after another.

### D-8 — `Add` refuses a part that holds a task

- **chosen:** (A-4) `Add` throws `ArgumentException` (`Error_QueryBatch_TaskPart`) and records nothing when the `QueryBatch` node would refuse the part. The rule is the node's `ScalarSelectBuilder.CreatesTask` (#6111 f90e2edd15, extracted as E-8): a node of type `Task`, `Task<>`, `ValueTask` or `ValueTask<>` that is not a read of a held task. A held task is reached through a constant, a parameter, a field chain ending in one or static, a conversion or `TypeAs`, or an element of a held array; reading one starts nothing. A call, a constructor, a property, or a field of a value the part computes, may start one. The node refuses the same part at build time with `LinqToDBException`; `Add` catches it first. The first cut's own walk (A-1) was stricter — it also refused a held task as the part's result — and was replaced by the node's rule.
- **rejected:**
  - Accept the part — it starts an unobserved query outside the batch, on the batch's connection (U-8).
  - Check `T` alone — misses `Add<object>(…)` and a task inside an anonymous member, both measured (U-8, critic round 2).
  - Refuse in the `QueryBatch` node — that widens #6111's surface; reported to the user as a #6111 finding instead.
- **why this:** a task created in a part is never translated; it runs as a separate, unobserved query. One rule shared with the node means `Add` never accepts a part that `Execute` would refuse, and never refuses one it would run. A walk per `Add` costs little beside the build.
- **failure mode of the choice:** some bodies that start nothing are refused, because their task comes through a node that could start one — `tcs.Task.Result`, an auto-property holding a task, `cond ? a : b`, `Task.FromResult(2).Result`. The workaround is to capture the task (or its result) into a local first; the `ArgumentException` doc says a captured variable is allowed. A custom awaitable and an `IAsyncEnumerable<T>` part are not refused (unmeasured). A part over another context's table also runs outside the batch (U-9), but it is awaited and correct, so it is not refused. (A-6: U-22 found it runs inside the batch on the batch's context.) (A-5) `Set` applies the rule to the body with `d` bound as `Execute` will bind it, so the two see the same tree (critic round 8, objection 3: under a root, a task field of the context passed the as-written check and was refused at every `Execute`, U-21 round 2). With D-9's constant the context is held, as a captured variable is, so a task field read through `d` is accepted by both and starts nothing. (A-6) With no parameter `Set` checks the body as written, as `Add` did before A-5. (critic round 9, objection 1) A task member of a captured context (`() => db.PendingTask.Result`) passes `Set` — a field chain ending in the closure — but expose re-roots a captured context of the executing configuration (`ExposeExpressionVisitor.cs:839-848`), and the node's `IsHeldTask` does not hold a root (`ScalarSelectBuilder.cs:99-135`, `default: return false`), so the node refuses it at every `Execute`: the TO-23 class, pinned there. `db.QueryBatch(() => db.PendingTask.Result)` is refused the same way (reasoned, not run), so it is #6111's rule: `IsHeldTask` lacks a `SqlQueryRootExpression` case, the expose-time form of the same captured context. The user's call (2026-11-13): fix it in #6111 (`case SqlQueryRootExpression: return true;` and a `HeldTaskIsRead` arm), sent to that session; fixed there as efa292c097 and merged here (521bf52cbd), so a task field of a captured context is held by both `Set` and the node, and TO-18 accepts it.

  - After the query returns — the load transaction already completed (`ExpressionQuery.cs:114-146`, `:296-327`) — every value is read from the tuple first, then the setters run in `Set` order. They run outside the `try` whose `catch` returns the batch to Pending, from a snapshot of the values and the setters taken before `Complete()` clears the lists (critic round 8).

### D-10 — (A-5) A failure before the first setter is retryable; after it the batch is final

- **chosen (the user's call, 2026-11-13):**
  - A failure before any setter runs — the database, pending hints, a cancelled token, a strict `First` / `Single`, the build — leaves the batch Pending with nothing assigned, and it can be executed again (D-3).
  - The values are read and `Complete()` moves the batch to Executed before the first setter runs. A setter that throws ends the run: the exception propagates, the setters before it have run, the rest do not, and the batch cannot be executed again.
- **rejected:** "any exception, a setter's too, leaves the batch Pending" (the first cut of the session plan): a retry re-sends every query for a failure that is not the database's, and applies the setters before the failing one twice (`v => list.AddRange(v)`); for the streaming forms of step 2 it cannot hold at all, because rows already delivered cannot be taken back (critic round 7).
- **why this:** the reads are all or nothing; the setters are delivery, which is not repeated.
- **failure mode of the choice:** after a throwing setter some targets are assigned and some are not, and the batch cannot fill the rest. Step 2 restates the rule for streams, whose rows are delivered before the main row is read (P10).
