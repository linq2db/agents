## P1 Problem

Absent capability, the half of [#1404](https://github.com/linq2db/linq2db/issues/1404) that #6111 left out: reads registered from several call sites and run together (`DeferValue` / `CompleteDefer` in the issue). #6111's `db.QueryBatch(...)` needs every read written in one expression at one call site, so a repository whose page count and page rows come from two methods, or whose set of reads is conditional, cannot use it without passing `Expression<Func<T>>`s up to one call of a statically known arity of at most 7. On `f798e94b51` the target shape does not compile: `db.CreateQueryBatch()` does not exist (searched `CreateQueryBatch|QueryBatchBuilder|QueryBatchResult` across `Source/` and `Tests/`: no hit). #6111's plan (P5 D-1) deferred an explicit batch object "until cross-method registration is asked for"; the user asked for it on 2026-11-11:

```csharp
var batch = db.CreateQueryBatch();
var total = batch.Add(() => query.Count());
var items = batch.Add(() => query.Skip(offset).Take(limit).ToList());
await batch.ExecuteAsync(cancellationToken);
return new Page<T> { Count = total.Value, Items = items.Value };
```

(A-5, 2026-11-13) The reviewer asked to rebuild the batch step by step: first `Set` for regular results, then the two streaming forms (per row and `IEnumerable<T>`), later others such as `new { }`. The mechanism should also serve linq2db itself — eager loading — which needs streaming. Step 1, by the user's calls, is query first and a setter:

```csharp
var page  = new Page<T>();
var batch = db.CreateQueryBatch();
batch.Set(() => query.Count(), v => page.Count = v);
batch.Set(() => query.Skip(offset).Take(limit).ToList(), v => page.Items = v);
await batch.ExecuteAsync(cancellationToken);
```

(A-6) The query takes no context parameter: it captures what it reads, the context included, as `db.QueryBatch(() => …)` does. A-5's `d => …` form is gone (D-9).

(A-9, the user's calls 2026-11-25) `Set` is renamed `AddRequest`, and the pre-A-5 result overload comes back beside it, so both shapes above are served:

```csharp
var batch = db.CreateQueryBatch();
var total = batch.AddRequest(() => query.Count());                                   // QueryBatchResult<int>
batch.AddRequest(() => query.Skip(offset).Take(limit).ToList(), v => page.Items = v); // setter
await batch.ExecuteAsync(cancellationToken);
page.Count = total.Value;
```

(A-10, step 2, the user's calls 2026-11-25) Streaming parts: a part's rows go to the caller one at a time instead of into a `List<T>`, either through a handle read after `Execute` or through a callback during it, in the same command:

```csharp
await using var batch = db.CreateQueryBatch();

var total = batch.AddRequest(() => q.Count());
var rows  = batch.AddStreamRequest(() => q.OrderBy(x => x.Id));             // QueryBatchStream<T>
batch.AddStreamRequest(() => log.Where(l => l.Day == day), row => Write(row)); // per-row callback

await batch.ExecuteAsync(cancellationToken);  // main row → results, setters → callback streams
await foreach (var row in rows)               // handle streams, after Execute
	…
```

- Anti-goal — #1404 still narrowed, disclosed in the PR body ("Part of #1404"): deferred writes, a value from one statement feeding the next, subset flushing ("groups").

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — An explicit batch object the caller holds

- **chosen:** `db.CreateQueryBatch()` returns a `QueryBatchBuilder` that the caller holds and passes to any method. `Add` records a lambda and returns a `QueryBatchResult<T>`. `Execute` runs every part through one `QueryBatch` call. (A-5) `Add` and the handle are replaced by `Set(query, setter)` — D-9; the batch object and the one `QueryBatch` call stay. (A-9) `Set` is `AddRequest`, and the handle comes back as its other overload — D-11.
- **rejected:**
  - Context-level futures (`DeferValue` / `CompleteDefer`) — they need pending state on the context, flush triggers and Dispose behaviour (#6111 P5 D-1 and P3, kept).
  - A lazy `Value` that runs the batch on the first read — hidden synchronous I/O in async code (the user's call).
  - `IQueryable` shortcut overloads and interface types — the user's call: minimal surface.
- **why this:** the object carries the registration across call sites without the context knowing about it. One `QueryBatch` call keeps one build and one `ParametersContext`, so the `AccessorId` collision of independent builds cannot occur. It also keeps the read transaction, the hints refusal and the strict element operators of the node.
- **failure mode of the choice:** a forgotten `Execute` surfaces at the first `Value` read, not at the batch. The batch is not thread-safe, like `DataContext`.

### D-2 — Parts fuse into one runtime-built `ValueTuple`

- **chosen:**
  - The tuple type is built from the parts' body types: `ValueTuple<T1…T7>`, nested through `Rest` beyond seven parts.
  - The body is a `New` of the tuple, in a `Func<TTuple>` lambda, under the node `Methods.LinqToDB.QueryBatch.MakeGenericMethod(tupleType)`. (A-3) The type and the `New` come from the eager-load helpers `ExpressionBuilder.BuildValueTupleType` / `BuildValueTupleNew`, which nest the same way; their `New` binds no members, which the projection does not need (measured, A-3).
  - It runs through `ExpressionQueryImpl.CreateQuery(tupleType, …)` and `Execute<object>` / `ExecuteAsync<object>`.
  - Each handle reads its field through a `FieldInfo` path computed at `Execute`. The closed tuple type depends on every part, so the path cannot exist at `Add`. A read through `Rest` boxes each nested tuple once per read.
- **rejected:**
  - One `object[]` body — every batch would be `QueryBatch<object[]>`, sharing one 16-entry cache bucket per context type (critic round 1, `QueryCache.cs:503-553`, refuted).
  - `object[]` plus a `ChainHash` that hashes the body — a change to cross-cutting core.
  - `NewQueryBatchTuple` as it is — it cannot nest: it looks up `Item8` on an eight-field tuple, which has `Rest` instead.
  - The eager-load `GenerateKeyExpression` (`ExpressionBuilder.EagerLoad.cs:90-123`) — it takes a member array and an offset, not a type. (A-3) Its siblings `BuildValueTupleType` / `BuildValueTupleNew` are used instead. The first cut rejected their member-less `New` unprobed; A-3 measured that the projection accepts it.
  - A compiled accessor per shape — one compilation per new shape, for a read done once per part per run.
- **why this:** the result type is the cache identity the engine already uses, and (A-3) the nesting is the one eager-load keys and carriers already build and read (`EagerLoadingWideKeyTests`: 9- and 15-field keys). No engine body edit (A-3: two helpers made `internal`). The batch is built on #6111's `QueryBatch`, as the user confirmed at approval: `Execute` builds the same node in its one-lambda form and runs it the way `QueryBatch<T>`'s body does (`LinqExtensions.QueryBatch.cs:76-79`), with the tuple type known only at run time. So every change to `QueryBatch` on #6111 reaches the batch.
- **failure mode of the choice:** batches with identical part types still share one bucket, as every root `db.Select` / `QueryBatch` of one result type does on master (U-12); a 17th live shape of the same types evicts the oldest. Separating input for the rejected `object[]`: batches of 1…17 `Count` parts, then the one-part batch again — 0 builds with the tuple, 1 with `object[]` (TO-16). Boxing: the tuple is boxed once per run and each field once per read.

### D-3 — Lifecycle: single use, a failure leaves the batch un-run

- **chosen:** the states are Pending → Running → Executed. (A-10) A run that leaves stream handles open passes through Streaming before Executed (D-14).
  - `Add` works only in Pending.
  - `Execute` starts from Pending. Success moves the batch to Executed, so it is single-use.
  - Any exception, including one thrown before the first await, returns the batch to Pending with no value set, so it can be retried. (A-5) This holds up to the first setter; once setters run the batch is Executed — D-10.
  - An empty batch's `Execute` sends nothing and moves to Executed.
  - `Value` throws unless the batch is Executed — including while Running, so a part that reads a handle of its own batch fails every run (U-17). The remarks on `Value` say a handle is read after `Execute`, never inside a part. (A-5: there is no `Value`; a part that reads a setter's target sees its value before `Execute` — SC-17.) (A-9: `Value` is back, keyed on the result's own has-value flag rather than the batch's state; it throws before a run, while Running and after a failed run, as this line says — D-11.)
  - Order of checks in `Execute` / `ExecuteAsync`: the state first (Running or Executed → `InvalidOperationException`), then the empty batch (no command, and no hints or token check), then the `QueryBatch` node with its inherited checks (hints, the cancelled token since A-4, the disposed context).
- **rejected:**
  - A Faulted state that rethrows the original exception (the user's call).
  - A re-executable or incremental batch (the user's call).
  - An empty `Execute` that stays Pending — then "run" would depend on the part count.
- **why this:** a batch is a list of expressions, and a failure consumes nothing (U-5).
- **failure mode of the choice:** a retry inside a user transaction that the error aborted fails again until the user rolls back (PostgreSQL, U-6). The remarks say the retry runs in the caller's transaction as it stands.

### D-4 — `Execute()` and `ExecuteAsync(token)`; the cancelled token is the node's check

- **chosen:** `Execute()` and `ExecuteAsync(CancellationToken token = default)`, with the parameter named as on #6111's overloads. (A-4) The cancelled-token check is the `QueryBatch` node's (`Query.ThrowIfQueryBatchIsCancelled`, #6111 f90e2edd15), which runs before the load transaction and any command; the batch's own `ThrowIfCancellationRequested`, the first cut of this decision, was removed as its duplicate. The node checks the token after it has built the query (`ExpressionQuery.cs:117-120`), so on a cache miss a translation error or the hints refusal is reported before the cancellation. An empty batch never reaches the node, so it does not check the token (TO-8). Everything else is inherited from the `QueryBatch` node: the hints refusal, the read transaction, combining, strict element operators and the sequential remote path.
- **rejected:**
  - Async only (the user's call).
  - Relying on the token to reach the provider — a command or a BEGIN goes out first, and the exception type differs per provider (U-7).
- **why this:** the pre-check makes "nothing sent" true on every provider, at one line's cost.
- **failure mode of the choice:** cancellation after the pre-check is the provider's (`TaskCanceledException` on SQL Server). The docs promise only `OperationCanceledException`, which `TaskCanceledException` derives from.

### D-5 — Captured values are read at `Execute`

- **chosen:** `Add` stores the lambda as written. Closures are read when `Execute` builds the parameters, which is C#'s and deferred LINQ's semantics (the user's call).
- **rejected:** a snapshot at `Add` — it needs partial evaluation of the tree and differs from the rest of LINQ.
- **why this:** no code; the behaviour every LINQ user expects.
- **failure mode of the choice:** a value changed between `Add` and `Execute` is read in its changed state — intended, documented in `Add`'s remarks, pinned by TO-14.

### D-6 — Remote contexts inherit the sequential path

- **chosen:** no code and no doc promise. On a remote context the parts run one by one, with no read transaction, as `db.QueryBatch` does (#6111 P10; the user's call).
- **rejected:** a `NotSupportedException` on remote — extra code and a test, and it would diverge from `db.QueryBatch`.
- **why this:** zero cost; the values are the same (U-1).
- **failure mode of the choice:** "one round trip" does not hold on remote; the remarks say only that a context which cannot combine runs the parts one after another.

### D-7 — Names and shape

- **chosen:**
  - `QueryBatchBuilder` and `QueryBatchResult<T>` (the user's call), created by `LinqExtensions.CreateQueryBatch(this IDataContext)`, which is `[Pure]`. (A-5) Now `QueryBatchBuilder<TContext>` from `CreateQueryBatch<TContext>(this TContext) where TContext : IDataContext`, still `[Pure]`; `QueryBatchResult<T>` and `Add` are gone (D-9). (A-6) Back to the non-generic `QueryBatchBuilder` from `[Pure] CreateQueryBatch(this IDataContext)`. (A-9) `QueryBatchResult<T>` is back (D-11).
  - `Add<T>(Expression<Func<T>> part)`, not `[Pure]`. (A-9) Both `AddRequest` overloads, neither `[Pure]`: each records a part.
  - Both classes are sealed; `QueryBatchResult<T>` has an internal constructor.
- **rejected:**
  - A class named `QueryBatch` — it collides with the method in docs and `cref`s.
  - `DeferredQueryBatch` / `Deferred<T>`.
  - `IQueryBatch` interfaces.
- **why this:** the name says what it builds; a sealed class adds the smallest surface.
- **failure mode of the choice:** `QueryBatchBuilder` sits in the root namespace next to the `QueryBatch` methods; the XML docs cross-reference both.

### D-8 — `Add` refuses a part that holds a task

- **chosen:** (A-4) `Add` throws `ArgumentException` (`Error_QueryBatch_TaskPart`) and records nothing when the `QueryBatch` node would refuse the part. The rule is the node's `ScalarSelectBuilder.CreatesTask` (#6111 f90e2edd15, extracted as E-8): a node of type `Task`, `Task<>`, `ValueTask` or `ValueTask<>` that is not a read of a held task. A held task is reached through a constant, a parameter, a field chain ending in one or static, a conversion or `TypeAs`, or an element of a held array; reading one starts nothing. A call, a constructor, a property, or a field of a value the part computes, may start one. The node refuses the same part at build time with `LinqToDBException`; `Add` catches it first. The first cut's own walk (A-1) was stricter — it also refused a held task as the part's result — and was replaced by the node's rule.
- **rejected:**
  - Accept the part — it starts an unobserved query outside the batch, on the batch's connection (U-8).
  - Check `T` alone — misses `Add<object>(…)` and a task inside an anonymous member, both measured (U-8, critic round 2).
  - Refuse in the `QueryBatch` node — that widens #6111's surface; reported to the user as a #6111 finding instead.
- **why this:** a task created in a part is never translated; it runs as a separate, unobserved query. One rule shared with the node means `Add` never accepts a part that `Execute` would refuse, and never refuses one it would run. A walk per `Add` costs little beside the build.
- **failure mode of the choice:** some bodies that start nothing are refused, because their task comes through a node that could start one — `tcs.Task.Result`, an auto-property holding a task, `cond ? a : b`, `Task.FromResult(2).Result`. The workaround is to capture the task (or its result) into a local first; the `ArgumentException` doc says a captured variable is allowed. A custom awaitable and an `IAsyncEnumerable<T>` part are not refused (unmeasured). A part over another context's table also runs outside the batch (U-9), but it is awaited and correct, so it is not refused. (A-6: U-22 found it runs inside the batch on the batch's context.) (A-5) `Set` applies the rule to the body with `d` bound as `Execute` will bind it, so the two see the same tree (critic round 8, objection 3: under a root, a task field of the context passed the as-written check and was refused at every `Execute`, U-21 round 2). With D-9's constant the context is held, as a captured variable is, so a task field read through `d` is accepted by both and starts nothing. (A-6) With no parameter `Set` checks the body as written, as `Add` did before A-5. (critic round 9, objection 1) A task member of a captured context (`() => db.PendingTask.Result`) passes `Set` — a field chain ending in the closure — but expose re-roots a captured context of the executing configuration (`ExposeExpressionVisitor.cs:839-848`), and the node's `IsHeldTask` does not hold a root (`ScalarSelectBuilder.cs:99-135`, `default: return false`), so the node refuses it at every `Execute`: the TO-23 class, pinned there. `db.QueryBatch(() => db.PendingTask.Result)` is refused the same way (reasoned, not run), so it is #6111's rule: `IsHeldTask` lacks a `SqlQueryRootExpression` case, the expose-time form of the same captured context. The user's call (2026-11-13): fix it in #6111 (`case SqlQueryRootExpression: return true;` and a `HeldTaskIsRead` arm), sent to that session; fixed there as efa292c097 and merged here (521bf52cbd), so a task field of a captured context is held by both `Set` and the node, and TO-18 accepts it.

  - `Set` checks its arguments and the state, applies D-8's rule to the body (A-6: as written, nothing to bind), and stores the lambda as written and `v => setter((T)v!)`.
  - (A-6: gone — no parameter to bind; `BuildQuery` takes the bodies as written, as before A-5.) ~~`BuildQuery` (at `Execute`) replaces `d` with `Expression.Constant(_dataContext, typeof(TContext))` and then fuses the bodies as D-2 does. - **rejected:**

  - `d` as a field of a constant holder (U-21's (c)): reads every cell too; the constant is the first candidate that passes, and the simpler tree.
  - One method name `Set` for the streaming forms of step 2: a lambda whose body fits both `Action<T>` and `Action<IEnumerable<T>>` is ambiguous (CS0121). Decided at step 2 (the user's call). (A-9) The same holds for `AddRequest`; the rename changes nothing here.
  - (A-6, the user's call 2026-11-13) A context parameter, `Set(d => d.Items.ToList(), …)` — A-5's form, from the reviewer's sketch (`db => db.Items.ToList()`). It enforces nothing: `d => otherDb.Items.Count()` and `_ => items.Count()` compile, and about five in six part lambdas in this branch's A-5 tests ignored it (15 used `d`, the tests of `d` itself; critic round 9 counted 76 of 91, the rewrite 74 of 89 — the fixture reads a `CreateLocalTable` local, so this measures the fixture's habit, not user code). - **why this:** the compiler checks the direction of each assignment (`List<T>` → `IList<T>`, `int` → `long` compile; `int?` → `int` does not), the IDE knows `T` from the query before the setter is written, and the shape (query, consumer) is the one the streaming forms of step 2 take. (A-6) The query captures the context as any LINQ query and `db.QueryBatch` do, so the batch binds nothing and every part takes #6111's path as written.

A setter is user code; what it does is not the batch's.

### D-10 — (A-5) A failure before the first setter is retryable; after it the batch is final (A-10: for a batch with streams, before / after `Complete()`)

- **chosen (the user's call, 2026-11-13):**
  - A failure before any setter runs — the database, pending hints, a cancelled token, a strict `First` / `Single`, the build — leaves the batch Pending with nothing assigned, and it can be executed again (D-3).
  - The values are read and `Complete()` moves the batch to Executed before the first setter runs. A setter that throws ends the run: the exception propagates, the setters before it have run, the rest do not, and the batch cannot be executed again.
- **rejected:** "any exception, a setter's too, leaves the batch Pending" (the first cut of the session plan): a retry re-sends every query for a failure that is not the database's, and applies the setters before the failing one twice (`v => list.AddRange(v)`); for the streaming forms of step 2 it cannot hold at all, because rows already delivered cannot be taken back (critic round 7).
- **why this:** the reads are all or nothing; the setters are delivery, which is not repeated.
- **failure mode of the choice:** after a throwing setter some targets are assigned and some are not, and the batch cannot fill the rest. Step 2 restates the rule for streams, whose rows are delivered before the main row is read (P10). (A-10, critic round 16 objection 2) Step 2's restatement: for a batch with streams the line between retryable and final is `Complete()`, not the first setter — a callback or a stream's SQL that fails after the results are set ends the run with no setter run; a batch without streams keeps this rule unchanged. The shipped remark "a batch that failed before its setters ran has set no result and assigned nothing, and can be executed again" (`QueryBatchBuilder.cs:43-45`) is rewritten to say so (E-9). (A-9) Results are not targets: D-11 sets every one of them before the first setter, so a throwing setter leaves them set.

### D-11 — (A-9) `AddRequest`, with a setter or returning a result

- **chosen (the user's calls, 2026-11-25):**
  - `Set<T>(Expression<Func<T>> query, Action<T> setter)` is renamed `AddRequest<T>`, behaviour unchanged.
  - The pre-A-5 result form comes back as an overload: `QueryBatchResult<T> AddRequest<T>(Expression<Func<T>> query)`. `QueryBatchResult<T>` is sealed with an internal constructor; `Value` throws `InvalidOperationException` (`Error_QueryBatch_NotExecuted`, restored) until the batch has read it.
  - Both overloads go through one private recorder: the null check, `ThrowIfNotPending`, D-8's `CreatesTask` rule, then the part and its sink are recorded. A result's sink sets the result; a setter's sink calls the setter. The sinks are one list in part order, each tagged as a result or a setter (critic round 12, objection 2), so the value index stays the part index.
  - Delivery (D-10's order, extended): every value is read from the tuple, `Complete()` moves the batch to Executed, **every result is set**, then the setters run in `AddRequest` order. A result's set cannot throw (the value has the part's type), so the results are all set before any user code runs.
  - A result holds its own "has value" flag, not a reference to its batch (the pre-A-5 result asked `_batch.IsExecuted`). Every result is set in the same step that makes the batch Executed, and nothing runs between the two, so `Value` answers as before: not-run before `Execute`, while Running and after a failed run (the result is unset in each). It no longer keeps the batch, and through it the context, alive.
- **rejected:**
  - Results set in `AddRequest` order among the setters (what a result-as-setter sink gives for free): a setter that throws leaves every later result unset on an Executed batch, and the pre-A-5 `Value` (keyed on the batch's state) would then return `default(T)` silently; with the own flag it would throw "not executed" on an executed batch. Either is wrong.
  - A separate name for the result form (`Add`, as before A-5) — the user's call: one name, two overloads.
  - The pre-A-5 `Value` keyed on the batch's state — pins the batch and the context for as long as a result is kept, and answers wrongly if a result is ever left unset.
- **why this:** a result is a value store, not user code, so it is filled with the read, and a setter — user code — sees a fully executed batch: its state Executed and every result readable. Overload resolution is by arity, so `AddRequest(q)` and `AddRequest(q, setter)` never compete; step 2's per-row and `IEnumerable<T>` setters will still compete with `Action<T>` (CS0121, D-9's rejected line, unchanged by the name).
- **failure mode of the choice:** a forgotten `Execute` surfaces at the first `Value` read (D-1's failure mode, back for results). A part that reads a result of its own batch fails every run with the not-run error (U-17, SC-13 restored), as before A-5. A result and a setter target in one part behave differently: the result fails the run, the target is read silently (SC-17). (A-10: D-14 delivers the main row before any stream row, so this rule now holds in step 2 as well — the step-2 caveat below is answered.) (critic round 12, objection 6) A forgotten setter compiles: `batch.AddRequest(() => q.Count());` is the result overload, so the part is read and its value dropped with the discarded result. Not annotated: `[Pure]` would misstate a method that records a part (critic round 1), and `MustUseReturnValue` is used nowhere in `Source/`; pre-A-5 `Add` had the same exposure. (critic round 12, objection 5) "Every result is set before the first setter" is step 1's rule: a step-2 stream delivers rows before the main row is read, so before any result is set; step 2 restates it, as D-10 says for setters.

- **chosen (the user's calls, 2026-11-25):**

### D-13 — (A-10) The run mode fixes the read mode

- **chosen (the user's call):** after `Execute()` a handle is read with `foreach` only; after `ExecuteAsync()` with `await foreach` only; the other mode throws `InvalidOperationException` (a new `ErrorHelper` constant) before reading anything. A callback is a sync `Action<T>`, legal under both.

### D-14 — (A-10) Order, lifetime and states

- **chosen (the user's calls):**
  - Command order: buffered collections, the main row, callback streams (add order), handle streams (add order). The main row comes first among the streams, so a strict `First` / `Single` of the main row fails before any stream row.
  - (the user's call after critic round 15, option a; critic round 16 objection 1 resolved as its reading (i)) Delivery order inside `Execute`, after the main row, on both routes: `Complete()`, every result, the callback streams, (sequential route) the handle streams buffered, then the setters — so `Execute` / `ExecuteAsync` still complete with every setter run, as their shipped contract says (`QueryBatchBuilder.cs:169`, `:39-40`). On the combined route the handle streams are read by the caller after `Execute`, so after the setters. Every stream query binds its values before any setter on both routes — the combined route in `BuildPlan`, the sequential route by running before the setters — so a part reading a setter's target sees its value from before `Execute` everywhere (SC-17). A callback can read the batch's results; a setter runs after every callback stream.
  - (critic round 15, objection 2; round 16 objections 2 and 4) A failure after `Complete()` — a callback, a stream's SQL, a setter — ends the run: the batch is final, the exception propagates, the setters not yet run never receive their values (the results are set), and every handle not yet finished or skipped is closed: reading it throws the closed text, buffered or not. `Dispose` before the handles end closes them the same way. Precedence of a handle's refusals: not ready (no successful run) → closed → wrong mode → already read or skipped.
  - Handles are read strictly forward: reading handle k skips what is left of handles before k (`NextResult`); a skipped or finished handle throws when read again; each handle is read once. (A-11, review MAJ002) The skip retires a handle still being enumerated too, and every enumeration checks its handle's state before each row: closed → the closed text, otherwise not reading → the already-read text. Without it a skipped enumeration went on over the moved reader (SQLite: the provider's "reader is closed") or over its buffer (SqlCe). (critic round 18) The check precedes every move, the one past the last row too, on both routes (objection 3: the buffered loop checked only before a row it yielded); and a handle starts at its enumerator's first move, inside the iterator — taking the enumerator only checks the refusals — so an enumerator disposed before it moves skips nothing and leaves its handle readable (objection 5: `Start` ran when the enumerator was taken, and disposing an unstarted iterator runs no `finally`, so the handle stayed Reading and the batch Streaming).
  - States: Pending → Running → Streaming (handles open, the reader held) → Executed. In Streaming, `AddRequest`, `AddStreamRequest` and `Execute` throw `Error_QueryBatch_Running`'s sibling (a new "streams are open" constant).
  - Lifetime: `QueryBatchBuilder : IDisposable, IAsyncDisposable`. The reader, the connection lock and the `CloseAfterUse` suppression are released when the last handle ends, or on `Dispose` / `DisposeAsync`; for a batch without open streams `Dispose` does nothing. (A-11, the review's observation, the user's call "release") A handle ends when its enumeration ends, read to its end or left before it: the enumeration's `finally` marks a handle still reading finished, and the batch releases once the last handle is not open — reading the last one skipped every one before it. The cursor's own release after the last stream's rows stays for a batch of callbacks only, which no handle ends. (A-10, after round 14) Only the combined route holds a reader past `Execute`; on the sequential route `Execute` ends Executed with the handles buffered (D-15).
  - No load transaction for a batch with a stream part. On the combined route the reader stays open across user code, which `Query.cs:266-270` forbids inside a transaction linq2db opened, and most providers cannot commit with a reader open; on the sequential route the callbacks are user code, and the stream queries run from the batch after `IQueryProvider.Execute` has returned, outside its transaction scope (`ExpressionQuery.cs:305-313`, critic round 15). A caller wanting one snapshot opens a transaction.
  - (critic round 13, objection 4) The kind (callback or handle) is part of the stream marker, so of the cached query; the command orders callback streams before handle streams whatever their add order.
  - (objection 6) On a batch with streams the setters, the callbacks and any code reading results before the handles run while the reader is open: a setter or callback that queries the same context fails where the provider allows one reader (P10). Any exception after the main row — a setter, a callback, a stream's SQL — releases the cursor (reader, lock, `CloseAfterUse`) before it propagates; the batch is final (D-10).
  - (objection 9) Every refusal has its own `ErrorHelper` text: a handle read before a successful run (before `Execute`, after a failed one), closed (critic round 17), read with the other mode, read again or after being skipped; streams open.
  - (A-12, the user's calls on critic round 18's open behaviours) A handle is Delivering from `Bind` until `EndDelivery` makes it Ready, so a stream callback or a setter that takes its enumerator gets `Error_QueryBatch_Running` — on the combined route the read would move the shared reader under a callback stream still reading; a failure during delivery closes a Delivering handle. Refusal precedence: not ready → being executed → closed → wrong mode → already read or skipped. A cancelled asynchronous handle read is a failure of the stream on both routes: the buffered loop checks its token before every move and takes `FailStreamsAsync`, as the reader's own cancellation does on the combined route. `Complete()` sets Executed before the results (`QueryBatchBuilder.Complete`, called first in `BeginDelivery`; critic round 19 corrected a stale line cite), so a re-entrant `AddRequest` / `AddStreamRequest` / `Execute` from a callback or a setter gets the already-executed text on both routes; after delivery a combined batch with unread handles is Streaming (the streams-open text) until they end or the batch is disposed, then Executed again.
  - (objection 7) Skipping a handle and disposing a batch before its handles end read the remaining rows through on SqlClient, Npgsql and MySQL (SqlClient's `Close` reads every pending result); no `DbCommand.Cancel()` is sent — its effect differs per provider and can leave the connection unusable (P10).
- **rejected:** reading handles in any order with buffering of the skipped ones (gives up streaming for them); throwing on out-of-order reads (the user's call: skip); a separate `ExecuteStream()` returning a disposable owner (the user's call: the batch disposes).
- **why this:** result sets are strictly sequential on every provider (U-26); the main row first gives the caller its scalars before the streams and keeps D-10 / D-11.
- **failure mode of the choice:** until the handles are read or the batch disposed, the connection is busy: another query on the same context fails on SqlClient without MARS, Npgsql, MySQL and YDB; on Firebird a commit closes the reader; on YDB an unread stream inside a transaction breaks it (U-27). Statements read without a transaction can see different states of the data, as remote already does.
