**Tier:** L  ·  **Status:** approved  ·  **Approved-at:** 2026-11-24 (user, after critic round 1)  ·  **Branch:** issue/4053-eager-load-transaction-option  ·  **PR:** [#6456](https://github.com/linq2db/linq2db/pull/6456) @ `4f3e5ec592`
**Schema:** `.claude/docs/work-plan.md`  ·  **Gates:** `.claude/docs/definition-of-done.md`

Tier L because the change adds public API outside `LinqToDB.Internal.*` (`LinqOptions` members, `DataOptionsExtensions`, `Configuration.Linq`). Milestone 6.7.0 (user, 2026-11-24). Shape (bool + nullable isolation level) and names chosen by the user, 2026-11-24.

## P1 Problem

On `origin/master` (`edb8febc69`) every eager load that runs on a `DataConnection` or `DataContext`, outside a `TransactionScope` and outside an open transaction, begins a transaction at `SqlProviderFlags.DefaultMultiQueryIsolationLevel` around its reads (`Source/LinqToDB/Internal/Linq/Query.cs:215-243`, decision in `GetTransactionOwner` `:313-339`). The level is a provider flag: `RepeatableRead` by default (`DataProviderBase.cs:60`, which SQL Server keeps), `Serializable` for SQLite (`SQLiteDataProvider.cs:54`). No `LinqOptions` / `DataOptions` member turns the transaction off or changes its level for a context.

[linq2db/linq2db#4053](https://github.com/linq2db/linq2db/issues/4053) reports deadlocks on SQL Server caused by this unseen `RepeatableRead` transaction (update locks taken by plain selects) and asks for an option to disable it; the maintainer answered there (2023-04-04) that it can be disabled "via `DataOptions`". The reporter's workaround is to assign `DataProvider.SqlProviderFlags.DefaultMultiQueryIsolationLevel = IsolationLevel.ReadCommitted` in a `DataConnection` constructor, which mutates the provider's shared flags and so changes every connection of that provider.

Observable — measured 2026-11-24 on master code with the scratch probe `Tests/Tests.Playground/Issue4053Probe.cs` (logs `.build/.agents/issue4053-probe-net10.log`, `…-net462.log`; 40/40 lines per TFM on SQLite.Classic, SQLite.MS, SQLite.Classic.MPU, SQLite.Classic.MPM): with `UseTracing`, `db.Parent.LoadWith(p => p.Children).ToList()` traces `BeginTransaction(Serializable), ExecuteReader, ExecuteReader, CommitTransaction`; `ToListAsync`, `await foreach` and the projected-collection `FirstOrDefault` trace the same with `BeginTransactionAsync(Serializable)` for the async ones; a `DataContext` traces the same. Nothing on the context can change it.

- SC-2 The default (`true`, no isolation override) is unchanged against master: the same entry points trace `BeginTransaction(<provider level>)`, the readers, `CommitTransaction`.  → TO-1, TO-2, TO-3, TO-4, TO-5, TO-6, TO-7 (on arms), TO-11

- SC-4 An isolation override with `UseEagerLoadingTransaction(false)` opens nothing.  → TO-10

## P3 Constraints & anti-goals (M/L)

Issue-scope reconciliation (#4053, line by line): its request, an option to disable the transaction, is SC-1; the isolation override (SC-3) is the user's addition and replaces the reporter's shared-flag workaround; the comments' EF Core comparison and FK question are the anti-goal below.

- Default behaviour equals master: with no option set, the same transaction at the same level, the same SQL, no baseline change.
- No change to `SqlProviderFlags`, `IDataProvider` or any provider: `DefaultMultiQueryIsolationLevel` stays the default the override falls back to.
- Binary compatibility with 6.6.0: the shipped 22-parameter positional constructor and `Deconstruct` stay callable through `[EditorBrowsable(Never)]` shims, like the two existing shim pairs (`LinqOptions.cs:304-440`).
- No change to the remote (`LinqService`) wire format.
- Anti-goal (issue narrowing, disclosed in the PR body): #4053's comparison with EF Core's single-query `LEFT JOIN` shape and the comment asking why `[Association]` creates no foreign key are out of scope; linq2db's split-query eager loading is unchanged.

User-visible deltas vs master:
- New public API: `LinqOptions.UseEagerLoadingTransaction` (default `true`), `LinqOptions.EagerLoadingIsolationLevel` (default `null`), `LinqOptions.WithEagerLoadingTransaction` / `WithEagerLoadingIsolationLevel`, `DataOptions.UseEagerLoadingTransaction` / `UseEagerLoadingIsolationLevel`, `Configuration.Linq.UseEagerLoadingTransaction` / `EagerLoadingIsolationLevel`, the 24-parameter `LinqOptions` constructor / `Deconstruct` and the 22-parameter shims.
- Only when a user opts out: the main query and its child queries can read different committed states, and the main rows of an enumerated eager load are handed to the caller as they are read instead of being read to the end first (`ExpressionQuery.cs:389-396`, `:169-176`, `:208-213`, `:245-252` take their `transaction == null` branch) — what master already does inside a `TransactionScope` or an open transaction.
- Shipped prose stating master's contract: `LinqOptions.cs:213-216` (`UseCombinedCommands` doc) says the eager load "already opens one whenever the query has harvesters", which is false once the option is off → E-2b. No other public `<summary>` / `<remarks>` and no readme mentions the transaction (P7 row 5).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — A bool plus a nullable isolation level

- **chosen:** `bool UseEagerLoadingTransaction = true` and `IsolationLevel? EagerLoadingIsolationLevel = null` (null = `SqlProviderFlags.DefaultMultiQueryIsolationLevel`). User's choice, 2026-11-24.
- **rejected:** bool only — leaves the reporter's shared-flag mutation as the only way to keep consistency at a lower level. Isolation level only — `IsolationLevel` has no free value for "off" (`Unspecified` already means "begin with the driver default", Access uses it, `AccessDataProvider.cs:66`).
- **why this:** separates "whether" from "at which level", and the override replaces the flag mutation with a per-context setting.
- **failure mode of the choice:** two knobs where one is ignored when the other is off; SC-4 / TO-10 pin that an override alone never opens a transaction.

### D-2 — Read the options in `Query`, at execution time, from the caller's context

- **chosen:** `GetTransactionOwner` returns null first when `dataContext.Options.LinqOptions.UseEagerLoadingTransaction` is false (before the harvester and owner checks); `StartLoadTransaction` / `StartLoadTransactionAsync` pass `EagerLoadingIsolationLevel ?? dc.DataProvider.SqlProviderFlags.DefaultMultiQueryIsolationLevel` to both the `DataContext` and the `DataConnection` branch.
- **rejected:** checks at the ten call sites in `ExpressionQuery` / `CompiledTable` — ten copies of one rule (U-1); a provider flag — per provider, not per context, and shared across connections (P1); a decision at query build time — the transaction is an execution concern, and a build-time flag would be frozen into the cached `Query`.
- **why this:** one rule at the one place the transaction is opened; every entry point inherits it.
- **failure mode of the choice:** the override must reach both branches (`Query.cs:222-225`, `:235-242`); applying it to only one leaves `DataContext` or `DataConnection` at the provider level. TO-8 (DataConnection) and TO-9 (DataContext) each go red on that mutation.

### D-3 — Both members join `LinqOptions.ConfigurationID`

- **chosen:** `.Add(UseEagerLoadingTransaction)` and `.Add((int?)EagerLoadingIsolationLevel)` (`IdentifierBuilder.Add(int?)` keeps null distinct, `IdentifierBuilder.cs:91-94`).
- **rejected:** leave them out because the transaction is decided at run time and the compiled `Query` does not depend on it — `LinqOptions.Equals` / `GetHashCode` are `ConfigurationID` (`LinqOptions.cs:504-515`), so two option sets differing only here would compare equal and could be swapped wherever options are cached by equality.
- **why this:** keeps `LinqOptions` equality exact, as the record's own comment requires (`LinqOptions.cs:267-269`).
- **failure mode of the choice:** a context that toggles the option compiles its own `Query` for the same LINQ (U-6) — one extra build per distinct value, no behaviour change. TO-15 pins distinct IDs.

### D-4 — Binary-compat shim for the 6.6 constructor and `Deconstruct`

- **chosen:** append the two parameters after `UseCombinedCommands`, add a 22-parameter `[EditorBrowsable(Never)]` constructor / `Deconstruct` pair mirroring the shipped 6.6 signature (`PublicAPI.Shipped.txt:6853`, `:6874`), and add two `out _` to each existing `Deconstruct` shim.
- **rejected:** no shim — an assembly compiled against 6.6 that calls the positional constructor or deconstructs a `LinqOptions` fails with `MissingMethodException`; a non-positional `init` property — breaks the record's single-shape convention and the copy-constructor / `ConfigurationID` checklist every other member follows.
- **why this:** the two earlier option additions (`LinqOptions.cs:304-440`) set the precedent.
- **failure mode of the choice:** a shim forwarding arguments in the wrong order compiles silently when types coincide (all bool); TO-17 calls the shim with a value pattern that a reordering changes.

### D-5 — `Configuration.Linq` setters for both

- **chosen:** `Configuration.Linq.UseEagerLoadingTransaction` and `Configuration.Linq.EagerLoadingIsolationLevel`, same shape and remarks as `UseCombinedCommands` / `UseDbBatch` (`Configuration.cs:486-526`).
- **rejected:** none — a user can write `Configuration.Linq.Options = … with { … }`, but the three most recent options all have the shortcut, and #4053's reporter configures SQL Server process-wide.
- **why this:** consistency with the sibling options.
- **failure mode of the choice:** two more public members to test and document; TO-16.

### D-6 — No buffering without the transaction

- **chosen:** with the option off the existing `transaction == null` branches run, so enumerated main rows stream (P3 delta).
- **rejected:** keep buffering the main rows without a transaction — the buffer exists only so the transaction can commit before the caller's code runs (`Query.cs:246-249`, `BufferedRows.cs:14`); without one it holds every row in memory for nothing and diverges from master's `TransactionScope` / open-transaction path.
- **why this:** the off path is master's existing no-transaction path, not a new one.
- **failure mode of the choice:** a caller that runs another command on the same connection while enumerating an opted-out eager load needs MARS or equivalent on providers that require it, exactly as for a plain query. Not documented as a case (user rule: option docs state the rule, not cases); P10.

### D-7 — Names and documentation

- **chosen:** `UseEagerLoadingTransaction` / `EagerLoadingIsolationLevel`; `WithEagerLoadingTransaction` / `WithEagerLoadingIsolationLevel` on `LinqOptions`; `UseEagerLoadingTransaction` / `UseEagerLoadingIsolationLevel` on `DataOptions`. XML docs state the rule — what the transaction is for, that `false` stops opening it so the main query and its child queries can read different states, that the level falls back to the provider default — with no case lists. The `UseCombinedCommands` sentence (E-2b) names the new option instead of claiming the transaction is always opened.
- **rejected:** `UseMultiQueryTransaction` (matches the provider flag's name) — the user picked the eager-loading name.
- **why this:** pattern of `UseDbBatch` / `UseCombinedCommands` (`DataOptionsExtensions.cs:363`, `:379`, `:720`, `:736`).
- **failure mode of the choice:** none beyond naming taste.
