## P1 Problem

Measured on this tree before D-1 (probe-run1, net10.0, direct + LinqService; DuckDB shares PostgreSQL's rewrite verbatim):
- `Sql.CharIndex("o", p.FirstName, 2)` returns `start - 1` (1) for names without an `o` on DuckDB (C# 0): `Position(sub in Substring(str, start, LENGTH(str) - start)) + (start - 1)` (`DuckDBSqlExpressionConvertVisitor.cs:122-143`, `PostgreSQLSqlExpressionConvertVisitor.cs:291-312`); Sybase `CharIndex(sub, Substring(str, start, Len(str))) + (start - 1)` (`SybaseSqlExpressionConvertVisitor.cs:201-221`) has the same not-found shape (read).
- `Sql.CharIndex("n", p.FirstName, 2)` misses a match on the last character on DuckDB ("John" 4 → 1, "Jürgen" 6 → 1): the `Substring` length `LENGTH(str) - start` is one short.
- Consumers inherit it (`Expressions.cs:510-524` pass `p1 + 1` and test `== 0`): `FirstName.IndexOf("x", 1)` → 0 (C# -1), `LastIndexOf("x", 1)` → 4 / 6 (C# -1), `LastName.IndexOf("r", 2, 5)` wrong, 3-arg `CharIndex` over `MiddleName` wrong on DuckDB.
- SQLite has no 3-arg `CharIndex` (renders the default `CharIndex(…)` → `no such function: CharIndex`; `IndexOf3`'s `no-issue` gate; `IndexOf2`, `CharIndex2` exclude `AllSQLite`).
- Already fixed in the tree (A-2 of #6450's plan, measured green ×16 there): SAP HANA 3-arg `Locate(str, sub, start)`, YDB `Unicode::Find` templates (0-based, NULL for not-found), `IndexOf(…, n, m)` mapping (`Expressions.cs:511,514`).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — 3-arg `CharIndex` emulations: 0 for a missing match, full tail

- **chosen:** a base helper `PositionFromStart(type, positionInTail, start)` = `CASE WHEN p = 0 THEN 0 ELSE p + (start - 1) END` (E-4); PostgreSQL / DuckDB `p = Position(sub in Substring(str, start))` (2-arg, no length — E-1, E-2), Sybase `p = CharIndex(sub, Substring(str, start, Len(str)))` (E-3), SQLite `p = INSTR(Substr(str, start), sub)` (E-5, new arm).
- **rejected:** `Coalesce(NullIf(p, 0) + (start - 1), 0)` — a NULL `str` becomes 0 (C# null); per-provider copies of the CASE — four identical shapes; a SQLite `[Function]` attribute — no native 3-arg form exists.
- **why this:** only the not-found arm and the tail change; NULL stays NULL (`p` NULL → ELSE → NULL); the 2-arg forms are untouched.
- **failure mode of the choice:** `p` renders twice (a computed `str` doubles once per nesting level); `start < 1` stays wrong (#6480) but its value moves on Sybase, from `-1` (old `0 + (0 - 1)`) to `0` (`PositionFromStart`'s THEN) — its gate joins the `! 1 <> 0` group (critic round 2); a start past the end gives 0 where C# clamps to the last character (P10).

### D-2 — YDB 3-arg templates declare `IfAnyParameterNullable`

- **chosen:** the two 3-arg YDB rows (`Sql.cs:526`, `:558`) return NULL for a NULL `start`, so they declare `IfAnyParameterNullable` (critic lead 11), as every other provider row does.
- **rejected:** keep `SameAsFirstOrSecondParameter` — the nullability then claims non-null for a NULL start.
- **why this:** the declaration matches the template.
- **failure mode of the choice:** none beyond a nullable result type where the start is nullable.

### D-4 — a NULL start gives NULL on SqlCe and Access

- **measured symptom:** `Sql.CharIndex("o", FirstName, MiddleName == null ? null : 1)` (C# NULL for a NULL start): SqlCe `CHARINDEX(sub, str, NULL)` answers a position (`2` / `0`); Access `InStr(NULL, …)` raises `Invalid use of Null` (after-run1). Pre-existing on master.
- **chosen:** a base helper (`NullWhenArgumentIsNull` since A-1, called with the start only here) = `CASE WHEN start IS NULL THEN NULL ELSE search END`, applied only when `start.CanBeNullable(NullabilityContext)` (E-4); used by the Access 3-arg arm (E-9) and a new SqlCe 3-arg arm (E-10) whose inner function is named `CHARINDEX` so the arm does not match its own output (`code-design.md`).
- **rejected:** an unconditional guard — every `IndexOf(s, n)` on Access / SqlCe would gain a CASE (its start `p1 + 1` is non-null); gating on #6480 — a fixable two-arm defect on this branch's topic (user decision 2026-11-26).
- **why this:** SQL for a non-nullable start is unchanged; the native search keeps its semantics otherwise.
- **failure mode of the choice:** a start the nullability context cannot prove non-null (a nullable parameter carrying a value) gains the CASE — correct, one extra branch.

### D-3 — A-2 carried as-is

- **chosen:** HANA `[Function("Locate", 1, 0, 2)]`, YDB `IF(… IS NULL, NULL, Coalesce(Unicode::Find(str, sub[, start - 1]) + 1, 0))` (A-3: needle `Coalesce(sub, ''u)`, result cast to `Int32`), `IndexOf(…, n, m)` → `CharIndex(p0, Left(obj, p1 + p2), p1 + 1)` (the form `LastIndexOf(…, n, m)` uses at `:519`, `:524`).
- **rejected:** re-designing them — measured green ×16 (#6450 plan A-2).
- **why this:** the measured state; TO-3, TO-5, TO-11, TO-12 add the missing obligations.
- **failure mode of the choice:** YDB renders `str` / `sub` twice (as D-1).
