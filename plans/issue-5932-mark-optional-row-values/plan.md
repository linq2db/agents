## P1 Problem

`LinqOptions.PreferClientCalculation` is meant to move only *where* a projection value is computed. Over a row a LEFT JOIN did not match it changes *what* is computed ([#5932](https://github.com/linq2db/linq2db/issues/5932), [#5923](https://github.com/linq2db/linq2db/issues/5923)). Repro (fixture `Tests/Linq/Linq/PreferClientCalculationTests.cs`, `MissedJoinEntity`, every row missed):

```
from e in table from j in table.LeftJoin(j => j.Id == e.Id + 1000)
select new { Plus = j.Value1 + 1, Compare = j.Value1 < 5 ? "a" : "b", Abs = Math.Abs(j.Value1 - 1), Year = j.Date.Year, Interp = $"[{j.Value1}]" }
```

measured on master behaviour (SQLite): option on `Plus 1, Compare a, Abs 1, Year 1, Interp "[0]"`; option off `Plus 0, Compare b, Abs 0, Year 0, Interp "[]"`. The client reads the missed row's column into `int` as `default(T)` *before* calculating; SQL calculates over NULL and the reader defaults the *result*. The option-on answer is what C# answers over a default row (AssertQuery's in-memory arm, `ApplyNullPropagationVisitor`).

Chosen semantics (the user's call): **in the projection, SQL calculates with every value the way the reader reads it into .NET** - a non-nullable scalar column that can be NULL in the query is `COALESCE(col, default(T))` wherever the projection calculates with it. The server then answers like the client, in both arms. The reader's own rule, which this mirrors: a value is null-checked when `nullability.CanBeNull(placeholder.Sql)` in the query's `NullabilityContext` (`Source/LinqToDB/Internal/Linq/Builder/ExpressionBuilder.QueryBuilder.cs:655`, context built at `:749`), and a NULL is replaced by `MappingSchema.GetDefaultValue(type)` (`Source/LinqToDB/Internal/Expressions/ConvertFromDataReaderExpression.cs:140-143, 178-184`).

## P2 Success criteria

- SC-2 A bare projected value is unchanged: `select new { j.Value1, j.Date, V = Sql.AsSql(j.Value1) }` renders without `COALESCE`, and `DISTINCT` over a bare projected column returns master's rows. → TO-2
- SC-3 Predicates, keys and query structure keep SQL NULL semantics and master's SQL: a missed row's column in `WHERE`, `JOIN ... ON` (including an association's join navigated from the projection), `GROUP BY`, `ORDER BY`, an entity comparison, the `WHERE` of a correlated subquery, and a translation used by both a predicate and the projection. → TO-3

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — What is read as the reader reads it: structural nullability in the consumer's frame

- **chosen:** a SQL leaf is defaulted when it is a `SqlFieldBase` or `SqlColumn` whose value the reader would null-check in the consumer's frame but whose declaration cannot be NULL: `leaf.CanBeNullable(NullabilityContext.GetContext(frame)) && !leaf.CanBeNullable(NullabilityContext.NonQuery)`; its CLR type (unwrapped) is a scalar value type that is not an enum; its column descriptor carries no value converter and no duration unit; and `MappingSchema.GetDefaultValue(type)` is not a NULL value. The replacement is `new SqlCoalesceExpression(leaf, PseudoFunctions.DEFAULT_VALUE(new SqlValue(QueryHelper.GetDbDataType(leaf, MappingSchema), MappingSchema.GetDefaultValue(type))))` — the value the reader substitutes (`ConvertFromDataReaderExpression.cs:142, 182`), typed as the column and lowered by the provider (D-7).
- **rejected:** a `MarkerExpression(OptionalRow)` carrier from `DefaultIfEmptyContext` — measured this session: needs a root-resolution special case for `j.X.Y`, a public `MarkerType` member, and broke null checks when kept on entities (187 failures); a speculative probe build — recorded dead end; defaulting every nullable operand (aggregates, subquery scalars too) — beyond the issue, and the user chose the structural rule.
- **why this:** it is the reader's own test (`QB:655`) restricted to values that are NULL only because of the query's shape; it lives on the SQL node, so it survives root rebasing (`j.Date.Year`), translators and nesting with no special case.
- **failure mode of the choice:** a frame that hides the outer join (U-6) answers "no" and keeps today's divergence for that shape; enums, converted columns and declared durations keep it too (P10).

### D-2 — Who decides: the consumer, on its operand's SQL, after nesting it into its own frame

- **chosen:** each consumer of D-3 passes its operand placeholder, already nested into its frame, through one helper that (a) returns it unchanged unless the projection scope holds (D-4), neither `InsideNullableCast` nor `ForSetProjection` does (the latter is where the option does not apply either, EBV:2296), the purpose is `Sql` or `Expression`, and the operand's CLR type *as written* (through a boxing `Convert(x, object)`, before any unwrap or collapse) is a non-nullable, non-enum scalar value type; (b) walks the operand SQL's *value positions* — a leaf (D-1), the operand of an `SqlCastExpression` to a non-nullable type, the results of an `SqlConditionExpression` / `SqlCaseExpression` (never their conditions) — and replaces each qualifying leaf; everything else stops the walk, an `SqlNullabilityExpression` included (identity functions need no case: they reach the consumer as the bare column, U-18); (c) returns a fresh placeholder only if something changed. Descriptor-driven checks run on the undecided SQL (U-15).
- **rejected:** a role flag carried from the consumer down to the member read, decided at `VisitMember` — scouted, not measured: flags inherit into every lazy structural build (U-3), so the role reaches `GROUP BY` keys, association joins and window specs, and each needs its own clear; a one-shot role instead needs forwarding at every pass-through node. Deciding inside `DefaultIfEmptyContext` or any context — its result is cached by the first writer (EBV:490, 629). An expression-level `COALESCE` — recorded dead end. A pass over the root query's select list at SQL-optimization time, with the reader's own `NullabilityContext` (QB:749) — it would need no scope, clears or cache partition, but it cannot see the written type: `(int?)x` and `x` are the same SQL once `CollapseNullableConvert` (EBV:4241) and placeholder retyping (EBV:2519) have run, so SC-4's lifted operators and nullable casts would be defaulted too.
- **why this:** the consumer is the one place that knows at once that it calculates, what its operand's written type is, and which frame it builds in; nothing but the scope has to survive into nested builds, and a decided operand never outlives the consumer that made it (U-9).
- **failure mode of the choice:** a consumer kind not listed keeps today's divergence for that shape (fail-safe); a pass-through node not in the walk (a cast to a nullable type, `COALESCE`, any function) stops it — also fail-safe.

### D-4 — The projection scope: set at the projection's roots, cleared where the build turns to structure

- **chosen:** `BuildFlags.ValueOfProjection` is set where a query's projection is built — `BuildQuery` (EB:276) and `FinalizeExpressionVisitor.TranslateExpression` (QB:129) — and inherited by everything the visitor builds for that value, including the builds it starts itself (`TryConvertToSql` EBV:2333, `HandleStringFormat` EBV:2708, `ConvertToExtensionSql`, `Translate` EBV:5514, `RemoveNullPropagation` EBV:2265), which already combine the current flags. It is cleared, for the duration, wherever the build stops computing the projected value and builds structure: around `context.MakeExpression` in `MakeWithCache` (EBV:474), in `ExpressionBuilder.TryBuildSequence` (EB:462), in set-wise translations (D-5), in object comparisons (`GenerateConstructorComparison`, `GeneratePathComparison`, `GenerateNullComparison`, EBV:3995-4233 — an entity comparison compares identities, not values), and already in `GetSubQuery` (EBV:5356).
- **rejected:** `BuildPurpose.Expression` as the scope (U-2: consumers run in `Sql`); a lexical scope that follows a `Select` body wherever it is inlined — it would default inside a `WHERE` over a projected member (U-4), changing a predicate's SQL (P3; the approved marker plan recorded this shape as `SELECT 1, WHERE NULL`); clearing inside each lazy build with `ResetPrevious` (measured: broke `Issue5576Tests`).
- **why this:** the projection is the only place the option moves a calculation, so the only place a divergence exists; the clears sit on the choke points every structural build passes through (U-3), not on a list of builds, so a lazy build added later is covered too.
- **failure mode of the choice:** a structural build reached by plain recursion rather than a choke point keeps the scope — `TryCreateAssociation`'s key builds (EBV:1790, 1873) are the ones known, and they build keys, which hold no consumer; set-operation branches rebuild under `ResetPrevious | ForSetProjection` (`MergeProjectionHelper.cs:48-49`) and keep today's answer, as the option does there (`PreferClientCalculation` excludes `ForSetProjection`, EBV:2296). A calculation inside a subquery's own projection (read through `AsSubQuery`, `Distinct`, `Take`) is built by the subquery's context with the scope cleared, so it keeps SQL semantics in both arms — the option does not move it either. The `TryBuildSequence` clear may prove to be defense-in-depth only: a sequence built from the projection builds its conditions in a frame of its own, which does not see the outer join (TO-3b, TO-3e); it stays because the failure it prevents is silent and the cost is a flag write.

### D-5 — Set-wise functions keep their inputs

- **chosen:** a member translation is set-wise when the translated call has an argument or instance typed as a lambda (`Expression<>`, a delegate, a quoted lambda) or a non-`string` `IEnumerable` / `IQueryable` — an inline array bound to a `params` parameter excepted; `TranslateMember` (EBV:5706) runs a set-wise translation with the scope cleared, so neither `Translate` nor any consumer inside decides, and its cache lookup and registration (EBV:5719, 5735) use the unpartitioned key. `ConvertExtension` (EBV:1220) does the same for an attribute that is an `[Sql.Extension]` — the chain machinery behind `Sql.Ext` aggregates and window functions, whose outermost link need not carry the flag (U-17) — or carries `IsAggregate || IsWindowFunction` (the flags it already reads at EBV:1232).
- **rejected:** clearing at `AggregationContext.TranslateExpression` only (`ExpressionBuilder.Aggregation.cs:61`) — misses window specs (U-5); the working tree's `UsingCurrentAggregationContext` hook — never reached (`AggregationInfo.TranslateValue` has no caller); deciding by the build context — a window's inputs are translated in the same context as a scalar function's (U-5); classifying an `[Sql.Extension]` chain by a pre-walk of its attributes — the chain itself only learns it is an aggregate or window function after converting its arguments (`Sql.ExtensionAttribute.cs:886`, flags over the whole chain at `:920-922`), and a builder decides during that conversion whether the call passes its argument through (`Sql.NoConvert`, `Sql/Sql.cs:226-229`), so a pre-walk would re-implement `BuildFunctionsChain` and still read a builder pass-through as a consumer.
- **why this:** NULL is how an aggregate or window function learns a row has no value; `Avg`, `Count(x)` and partitions answer differently once it is a zero. The shape is what distinguishes them: a function of one row takes values, a function of a set takes the set or a per-element selector.
- **failure mode of the choice:** a custom translator that lowers a scalar-signature call to an aggregate would be read as row-wise and have its argument defaulted — no built-in does (U-17); a scalar call taking a lambda or a sequence is read as set-wise and keeps today's divergence — among built-ins only string functions, which are never defaulted; a scalar function mapped with `[Sql.Extension]` keeps today's divergence (P10).

### D-6 — Translation caches are partitioned by the scope

- **chosen:** `ExprCacheKey` (EBV:5863-5904, a private struct of the visitor) gets a field saying whether `ValueOfProjection` held, compared and hashed with the others and copied by `Clone` (EBV:88-91, 113-116). It is set only where SQL translations are keyed — `GetSqlCacheKey` (EBV:594-597) and `HandleMember`'s own key (EBV:1655) — and left `false` everywhere else: the `MakeWithCache` key (EBV:463), the association key (EBV:1748) and the subquery key (EBV:2841) cache what is built with the scope cleared (D-4), so it does not depend on it, and splitting it would build structure twice. `GetAlreadyTranslated`'s error rule (EBV:647) is untouched: the flags stay `ProjectFlags.SQL`.
- **rejected:** a new `ProjectFlags` member — a build error: the repo-internal `ProjectFlagsAnalyzer` reports every member `GetProjectFlags` never produces (`Source/CodeGenerators/ProjectFlagsAnalyzer.cs:844-848`, `ProjectFlags.cs:17-18`; referenced as an analyzer in every configuration, `LinqToDB.csproj:26`), and producing it in `GetProjectFlags` would partition the `MakeWithCache` key as well (U-20); comparing cached SQL — placeholders compare equal whatever their SQL (U-8); not caching results that contain a default — needs a way to recognise "ours" in the SQL AST, an AST change the cross-cutting rule forbids for a local fix.
- **why this:** a row-wise translator's result built in the projection embeds decided arguments; served to a predicate it would default there, and a predicate's result served to the projection would lose them. The key already separates `Keys` / `MemberRoot` / `ForSetProjection` for the same reason, and a private field keeps the partition off every surface the analyzer models.
- **failure mode of the choice:** the column cache (EBV:5755) keys by path only, so a projected calculation that equals a sort or group key in the same query reuses the key's column. The key's column is made while the sequence is built, before the projection's `ToColumns`, so the key's SQL is never replaced (fail-safe); the projection keeps today's value for that shape (P10, TO-3h).

### D-7 — Dates the written type cannot hold are clamped, explicitly, per provider

- **chosen:** D-1 writes every default it injects as a pseudo-function, `PseudoFunctions.DEFAULT_VALUE(value)` — a non-nullable `SqlFunction` typed as the leaf's `DbDataType`, whose single argument is the `SqlValue` of `MappingSchema.GetDefaultValue(type)`. The base `SqlExpressionConvertVisitor.ConvertSqlFunction` (`Source/LinqToDB/Internal/SqlProvider/SqlExpressionConvertVisitor.cs:2009-2041`, where every pseudo-function is lowered) lowers it to its argument. The convert visitor of each provider whose date types start after 0001-01-01 lowers a `DateTime` / `DateOnly` / `DateTimeOffset` default by the column's **mapped `DataType`** — never by what the value converter would write for the CLR type, since SQL Server writes a `DateOnly` as `DATE` whatever the mapping (`SqlServerMappingSchema.cs:493-519`) and `COALESCE(datetime_col, DATEFROMPARTS(1, 1, 1))` is promoted to `datetime` and rejected — clamping a default below that type's range to its least value, and building the clamped value in the coordinate that provider's converter renders, so the literal does not move with the process's time zone (U-24):
  - SQL Server, in the one visitor keyed on the `_sqlServerVersion` it already holds (`SqlServerSqlExpressionConvertVisitor.cs:73`): `DataType.DateTime` 1753-01-01 and `DataType.SmallDateTime` 1900-01-01 on every version; below v2008, where `Date` / `DateTime2` / `DateTimeOffset` / `Undefined` are written as `DATETIME`, those too 1753-01-01. A `DateTimeOffset` default on a path the converter renders through `LocalDateTime` — mapped `Date` / `DateTime` / `DateTime2` / `SmallDateTime`, and every `DateTimeOffset` on 2005 (`SqlServerMappingSchema.cs:546-557`) — is lowered to a `DateTime` value, never a `DateTimeOffset`: 1753-01-01+00:00 renders as 1752-12-31T19:00 in UTC-5.
  - Access: 0100-01-01, every date type; a `DateTimeOffset` renders `.DateTime` (`AccessMappingSchema.cs:32`).
  - Sybase, by mapped type: `DateTime` / `Undefined` 1753-01-01 (the reader's own default, `SybaseMappingSchema.cs:36`), `SmallDateTime` 1900-01-01, `Date` unclamped; a `DateTimeOffset` renders `.DateTime` and is read as `datetime` (`SybaseDataProvider.cs:68`), so 1753-01-01. Because Sybase's date literal is an untyped string that takes the physical column's type (U-23), the lowered default is a mandatory cast to the mapped `DataType` with the column's `DbType` left out — `SqlCastExpression(…, isMandatory: true)`, which the optimizer keeps (`SqlExpressionOptimizerVisitor.cs:1352-1357`) and Sybase renders as `CAST(… AS DateTime)` (`BasicSqlBuilder.cs:4268-4275`) — so `COALESCE(smalldatetime_col, CAST('1753-01-01 …' AS DateTime))` resolves to `datetime` by ASE's datatype hierarchy, as SQL Server's typed literals do.
  - YDB: `Date` / `Datetime` / `Timestamp` 1970-01-01, the wide types unclamped; a `DateTimeOffset` renders `UtcDateTime` (`YdbMappingSchema.cs:502-508`), so it is built at offset zero.
  - ClickHouse: `Date` / `DateTime` 1970-01-01, `Date32` / `DateTime64` 1900-01-01; a `DateTimeOffset` renders `UtcDateTime` (`ClickHouseMappingSchema.cs:559, 564`), so it is built at offset zero.
  - SQL CE: `DateTime` / `DateOnly` 1753-01-01; it has no offset type (U-25).
  The override reads the default from its argument whether the child visit left it a `SqlValue` or turned it into a `SqlParameter` (children are visited before `ConvertSqlFunction`, `SqlExpressionConvertVisitor.cs:871, 876`; `VisitSqlValue` parameterises a value no converter can write, `:280-298`). The value converters stay as on HEAD, so no user literal and no write path changes (U-21).
- **rejected:** a clamp in the value converters (the carried design) — every date literal below the written type's range passes through them, `BulkCopyType.MultipleRows` rows, `InlineParameters` and `Sql.ToSql` included, where it would turn today's error into a silently stored least date (U-21; the user chose "Default only"); answering the calculation instead of the value (`CASE WHEN col IS NULL THEN <C# answer> ...`, memory `project_pr5926_prefer_client_calculation`: exact, but steps aside for a calculation mixing the date with another column); moving a date calculation to the client (recorded dead end); relying on the server's own saturation (ClickHouse) - not bulletproof; excluding dates from the rule (the option would diverge again for date calculations); a clamp independent of the written type (the carried Sybase converter: `COALESCE(smalldatetime_col, '1753-01-01')` is out of range, U-22); keying the lowering on what the value converter writes rather than on the mapped `DataType` (SQL Server's `DateOnly` → `DATE` over a `datetime` column, round 3); every Sybase date to 1900-01-01 (round 2) — valid for any physical type, but SQL then reads 1900 where the reader reads 1753 for the common `DateTime` shape, so a comparison the option moves to the client, `j.Date < new DateTime(1800, 1, 1)`, answers per arm, the SC-1 divergence the issue exists to remove; the typed cast removes the untyped-literal hazard without it; a clamped `DateTimeOffset` built without regard to the converter's coordinate (U-24); writing only date defaults as the pseudo-function — two paths where one serves, since a non-date default lowers to the same literal; the SQL Server 2005 rule as an override in `SqlServer2005SqlExpressionConvertVisitor` — every later version derives from it and would have to cancel it.
- **why this:** the clamp applies to the one value the fix introduces and to nothing a user wrote; the provider decides by the mapped type, which is what the reader reads by, and renders the value in its own coordinate; comparisons against dates at or after the clamp keep their answer; both option arms agree on date parts (U-11).
- **failure mode of the choice:** a date part of a missed row answers the clamped year (100 / 1753 / 1900 / 1970) instead of C#'s 1 on those providers, in both arms; a comparison the option moves to the client, against a bound below the clamp, answers per arm wherever the reader's default is below the clamp — 0001-01-01 on SQL Server 2005, Access, SQL CE, YDB and ClickHouse, and a Sybase `DateOnly` or `DateTimeOffset` mapped to a clamped type (Sybase's `DateTime` reader default already equals its clamp); ASE's promotion of the cast default inside `COALESCE` is reasoned from its datatype hierarchy, not probed (TO-7d measures it); a provider that is never given a lowering would render `$DefaultValue$(...)` literally — impossible here, because the base visitor lowers it for every provider and the overrides only refine dates. Recorded in P10.

- A column of a set-operation branch that reads a LEFT JOIN row, and a LEFT JOIN inside a CTE body, are not defaulted — the first is nullable even as declared (`NullabilityContext.cs:149-176`), the second is invisible to the enclosing query's nullability and to the reader alike (U-6).
