## P1 Problem

Operator precedence is one int chosen when an AST node is built (99 direct `new SqlBinaryExpression(`/`new SqlUnaryExpression(`/`CreateWithTypeInferred(` sites in 28 files, 225 factory-helper calls), drawn from the global table `Source/LinqToDB/SqlQuery/Precedence.cs:6-24` (`// TODO: precedence requires total refactoring, as it db-specific`, :3). `BasicSqlBuilder.Wrap` (`BasicSqlBuilder.cs:4709-4719`) then parenthesizes a child only when its level is 0, lower than the parent's, or equal to a `Subtraction`/`Multiplicative`/`LogicalNegation` parent — the same rule for every dialect and for both operand sides. Observable failures — valid SQL, wrong result:

- measured (#6243 comment 2026-11-15): SQLite.MS `r.A | r.B & r.C` renders `[r].[A] | [r].[B] & [r].[C]`; rows `(1,1,1) (1,2,0) (4,6,3) (5,3,6)` return `[1,0,2,6]`, .NET `[1,1,6,7]` (SQLite puts `& |` at one level, left to right).
- measured (#6243 comment 2026-11-16): SqlCe `p.ID | (p.ID ^ 1)` renders `[p].[PersonID] | [p].[PersonID] ^ 1`; 0 rows vs 2 (T-SQL evaluates `& ^ |` left to right at one level). Gated: `Tests/Linq/Linq/WhereTests.cs:224` `[ActiveIssue(6243, Configurations=[SqlCe, AllSqlServer, AllSybase])]`.
- measured (#6340, master `e7e282f31`): `Sql.AsSql(~(p.ID & 3))` renders `~[p].[ID] & 3` on SQLite.Classic/MS, SqlCe, DuckDB; returns `2,1,0,3`, expected `-2,-3,-4,-1`. `~(p.ID + 1)` wrong on SQLite and SqlCe. Cause: unary operand built at the unary node's own level (`BasicSqlBuilder.cs:4465`), node at `Bitwise` (`ExpressionBuildVisitor.cs:2784`).
- reported, reviewer-measured (#6146 review): Oracle `Id || ',' || Value1 - (Id - 1)` fails ORA-01722 — `||` and `-` share a level in Oracle; concat is `Concatenate=5` for every provider (`SqlConcatExpression.cs:24`).
- reasoned, unprobed: a parent at precedence 0 wraps no child (`Wrap` with `parentPrecedence == 0`), so ClickHouse's rebuilt decimal `/` at default 0 (`ClickHouseSqlExpressionConvertVisitor.cs:270`) renders `a / b * c` for `a / (b * c)` (#6376); Oracle's `~x → -1 - x` at 0 (`OracleSqlExpressionConvertVisitor.cs:276`) renders `-1 - a + b` for `~(a + b)`.
- reasoned, unprobed: right-nested equal-level operators lose grouping where `Wrap` has no arm — `Math.Pow(a, Math.Pow(b, c))` on Access renders `a ^ b ^ c` (patched by hand, `AccessSqlBuilderBase.cs:107-119`), T-SQL mixed `a + (b & c)`.
- reasoned, unprobed: unary output appends `-` with no space before an operand built through `Wrap` (`BasicSqlBuilder.cs:4362-4365`, `:4464-4465`); a negative literal is `Primary` (`SqlValue.cs:85`), so a negation over it renders `--5`, a line comment.
- Eleven point workarounds exist only because the decision sits at the wrong level (P7 → *Workarounds*), and two operators are told apart by their precedence number alone (Access XOR vs power, `AccessSqlExpressionConvertVisitor.cs:542`; MySQL `|`, `MySqlSqlExpressionConvertVisitor.cs:91`).
- Redundant brackets (#5527): the #5504 example `(Coalesce(col, '') + N'x') = @p` — concat at 5 under a comparison at 50.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — The SQL builder owns precedence, through a per-dialect table

- **chosen:** `BasicSqlBuilder` resolves every operator's level and associativity from `protected virtual SqlPrecedenceTable PrecedenceTable` (new, `Internal/SqlProvider/`), overridden per `*SqlBuilder`; version builders inherit.
- **rejected:** precedence set at node construction from `SqlProviderFlags` / `DataOptions` — keeps the decision in ~320 producer sites and in every rebuild that copies `element.Precedence` (P7), the drift P1 documents.
- **rejected:** a precedence hook on `IDataProvider` — cross-cutting interface change for something only the builder renders.
- **why this:** the builder is the only stage that knows the rendered token (`MOD`, `BAND`, `||`, `::`) and the dialect; scouts found no pre-builder decision besides the two discriminators D-5/E-12 remove (U-6).
- **the default table is conservative — a partial order, correct on any dialect.** The table stores, per key, a level, an associativity (Left or None) and an `Associative` flag; plus an *ordered-with* relation. Two keys whose relative order dialects dispute are **unordered** in the default table, and `NeedsParentheses` wraps a child whose key is unordered with its parent's, whichever side. Default orders — only `* / %` > `+ -` > comparison predicates > NOT > AND > OR (`+ -` share a level, `* / %` share a level, all Left and non-associative); master already renders these orders unbracketed on every provider. Unordered in the default: prefix `-` / `~` and negative literal with every binary operator (U-1/U-2 show dialects disagree; master builds `~` at `Bitwise`, below arithmetic, `ExpressionBuildVisitor.cs:2784`), every bitwise operator with every other operator (same-operator chains stay associative), concat with every arithmetic/bitwise operator, power with everything. Cast is `Primary` in the default (every builder but PostgreSQL and Informix renders `CAST(…)` / a function, `BasicSqlBuilder.cs:4290-4297`); the postfix-cast entry is declared only by the PostgreSQL and Informix tables. Dialect tables (E-7) declare total orders and relax these only after a measurement (step 0 probes, TO-1 baseline). Template classes (D-6) map onto the same entries. **Predicates and int-class parents:** prefix `-` and negative literal are ordered **above** every predicate key (master renders `-a = b` and `x = -5` bare: `Negate` at `Unary` 90, `ExpressionBuildVisitor.cs:2788`; negative `SqlValue` `Primary`); every other key outside the ordered chain (prefix `~`, bitwise, concat, power, postfix cast) is unordered with every predicate key and with every anonymous int-class parent other than `0` and `> Primary` (D-7) — master brackets those under a comparison (`~` built at `Bitwise` 40, `:2784`; bitwise 40; concat 5), so `~a = b`, `a & b = c`, `concat LIKE x` keep master's brackets on a dialect without a table. `SqlPredicate.Expr` is transparent (resolves as its `Expr1`); `True` / `False` predicates are `Primary`; comparison predicates are `Assoc = None` (a comparison under a comparison is wrapped); `NOT` over an equal-level `NOT` is wrapped, as master (`BasicSqlBuilder.cs:4718`). **Invariant (checked by TO-12 text arms, not by TO-11):** relative to master's `Wrap`, the default table removes a bracket only for an equal-level **left** child of a Left-associative operator — `(a + b) - c` (master: Additive 60 under Subtraction 70), `(a * b) * c`, `(a / b) * c`, `(a % b) * c` (master: equal-level `Multiplicative` arm, `:4717`) — all parse-equivalent; every other difference adds a bracket.
- **node getter values (D-4):** an operator node's `Precedence` returns the canonical constant of its class — `+ -` Additive (60), `* / %` and `//` Multiplicative (80), bitwise and `BAND BOR BXOR` Bitwise (40), `MOD` Multiplicative, concat (`||`, YDB binary `||`) Concatenate (5), unary Unary (90), unknown string Unknown (0). It is never a dialect level; only `ResolvePrecedence` produces those.
- **failure mode of the choice:** a provider that rewrites operator text in a `BuildBinaryExpression` override would bypass the table — scout: only Access overrides it (`AccessSqlBuilderBase.cs:107`), removed by E-11. The conservative default adds brackets on dialects that have no table yet — accepted churn, never a wrong result.

### D-2 — Table keys

- **chosen:** binary keys are the rendered `SqlBinaryExpression.Operation` string; unary keys are `SqlUnaryOperation`; plus concat (by `ConcatBuildStyle`), postfix cast, negative literal, function-rendered-as-infix (Access power), predicate kinds (ExprExpr comparison, LIKE/SearchString, BETWEEN, IN list/subquery, IS NULL, IS DISTINCT, IS TRUE, EXISTS, NOT, AND, OR, True/False as `Primary`, `SqlPredicate.Expr` transparent), and the canonical `Precedence` classes for templates (D-6). Unknown key → conservative entry: wrapped as a child, wraps every non-`Primary` operand.
- **rejected:** a new operator enum on `SqlBinaryExpression` — reshapes the AST beyond the user's decision and duplicates `Operation`, which 14 provider visitors and `QueryHelper.Evaluate.cs:395-406` already match on.
- **why this:** the census (P7) found 13 distinct binary strings; every one maps to exactly one entry per dialect.
- **failure mode of the choice:** a future provider emitting a new string silently gets the conservative entry — correct but bracket-heavy; never a wrong result.

### D-3 — One side-aware parenthesization rule

- **chosen:** `NeedsParentheses(child, parent, side)`, in order: (1) child level 0 → wrap; (2) child key unordered with parent key in this table → wrap; (3) **prefix reach** — for a **left** child at any level (higher *or* equal), descend its rightmost spine (right operands of binaries, operands of unaries, through transparent nodes) while each node would render without parentheses; if a prefix operator or negative literal is found whose level is **≤** the parent's level, wrap (`(a / -b) * c`, `(a * -b) + c`; `≤` is conservative, the step-0 probe U-1 may relax it to `<` per dialect); (4) lower → wrap; higher → no wrap; (5) equal + left → wrap iff parent is non-associative-to-the-left (`Assoc = None`); (6) equal + right → wrap unless child is the same operator (or a declared alias, e.g. YDB binary `||` = concat) and that operator is `Associative`. `Associative` only for AND, OR, concat, same-operator `& | ^` (and `BAND BOR BXOR`); `+` and `*` are not (SQL Server decimal scale, overflow order), so `a + (b + c)` keeps brackets. No supported dialect has a right-associative operator in scope, so the model has no Right associativity (P10). Unary operand: wraps when its level is below the unary level, and whenever its **rendered text starts with `-`** (covers negative literals, inlined negative parameters, `-1 * x` shortcut output, negative literal at the left of `*`/cast/power).
- **single-render invariant:** every node is rendered exactly once into the *current* `StringBuilder` (the one existing scratch — template arguments rendered by `WithStringBuilderBuildExpression`, `BasicSqlBuilder.cs:353-365` / `:4207` — swaps the property, so the rules below apply inside it unchanged). An operand whose wrap depends on its rendered form is handled as: record `len = StringBuilder.Length`; when the structural rule (steps 1, 2, 4-6) already says wrap, append `(` first (so the subquery check `StringBuilder[^1] == '('`, `BasicSqlBuilder.cs:3392`, keeps working); otherwise render, and the render **returns a summary** — its leading character and the lowest prefix level exposed on its rightmost spine (a negative literal or inlined negative parameter reports its sign from the text it just wrote) — and if step (3) or the leading-`-` rule then requires a wrap, `StringBuilder.Insert(len, '(')` and append `)` (precedent: `BasicSqlBuilder.cs:3150`, `YdbSqlBuilder.cs:535`). The leading character is read from `StringBuilder[len]` after rendering; only the exposed-prefix level needs a side channel, which is a **builder field** (the shipped renderers are `protected virtual void` — `BuildBinaryExpression` :4351, `BuildUnaryExpression` :4450, `BuildFunction` :4472, `BuildTypedExpression` :4290, `BuildSqlValue`/`BuildValue` :4342/:4324, `BuildParameter` :4189, and the 6-arg `BuildExpression` funnel :3190 overridden at `MySqlSqlBuilder.cs:336`, `OracleSqlBuilderBase.cs:228`). The non-virtual dispatch part sets the field for binary, unary, concat, transparent nodes and literals, and clears it ("nothing exposed") after every other element kind; an overridden operator renderer that never sets it leaves the conservative value "exposed at the lowest level" (wraps); the field is saved and restored across `WithStringBuilder*` and sub-builders. Summaries propagate up the left spine, so no ancestor re-scans or re-renders, and no memo by node reference exists (a `SqlValue` that falls back to `BuildParameter` — `BasicSqlBuilder.cs:4337`, `AccessSqlBuilderBase.cs:322-326`, `OracleSqlBuilderBase.cs:692` — mints its parameter exactly once per occurrence, as on master). Classification never calls `BuildParameter` separately; `OptimizationContext.AddParameter` (`OptimizationContext.cs:76,93`) runs once per rendered occurrence in render order.
- **rejected:** "wrap every non-`Primary` operand" — zero risk, but brackets everywhere, contradicting #5527.
- **rejected:** keep `Wrap` and add more equal-level arms — that is the status quo P1 documents.
- **why this:** covers every P1 shape and the critic's three-operator T-SQL case with one rule; associativity is data.
- **failure mode of the choice:** the prefix-reach scan walks only through binary right operands, unary operands and transparent nodes; a prefix hidden inside a template is invisible (templates are opaque — D-6 covers them by class).

### D-4 — Operator nodes lose their precedence; `ISqlExpression.Precedence` stays

- **chosen:** drop the ctor parameter from `SqlBinaryExpression` (`:11,20`) and `SqlUnaryExpression` (`:11,19`), from `SqlBinaryExpressionHelper.CreateWithTypeInferred` (`:332`), the 5-arg `factory.Binary` (`SqlExpressionFactoryExtensions.cs:211`), `SqlSelectClause.Expr<T>(…, int priority)` (`SqlSelectClause.cs:111,117`; Internal, no callers), the cloner (`QueryElementVisitor.cs:3122,3161`) and the serializer (`LinqServiceSerializer.cs:1054,1066,2277,2289`). The nodes' `Precedence` getter returns the canonical constant of their operator's class as listed in D-1 (*node getter values*), so pre-builder readers (`SqlPredicate.cs:164,178`; `QueryElementVisitor.cs:2951`; forwarding nodes `SqlNullabilityExpression.cs:71`, `SqlInlinedBase.cs:18`) keep a sane value. Mechanical sweep by script (`.build/.agents/`), not by hand.
- **rejected:** keep the parameter, ignore it — user chose "remove now" (2026-11-19).
- **why this:** removes the wrong-level input instead of shadowing it.
- **failure mode of the choice:** an external provider constructing these Internal types breaks at compile time — Internal namespace, accepted; noted for release notes.

### D-5 — Identity for operators that were told apart by precedence

- **chosen:** Access power stays `SqlFunction("Power")` through translation (`AccessMemberTranslator.cs:216-220` stops building a `^` binary) and the Access builder renders it infix `x ^ y` under its own table key; C# XOR `^` → `BXOR` unconditionally (`AccessSqlExpressionConvertVisitor.cs:542` loses the `{ Precedence: … }` pattern). MySQL `|` re-emission arm (`MySqlSqlExpressionConvertVisitor.cs:91-92`) is deleted; MySQL's table ranks `|` below `&`.
- **rejected:** a distinct operator token (`**`) for power — leaks into `QueryHelper.Evaluate.cs:395-406` and `ReduceIsNullExpressionVisitor.cs:183` null-propagation lists.
- **why this:** the function node already exists and LibRed renders it as `Power(x, y)` unchanged.
- **producers of `SqlFunction("Power")`** (all mean power, so name-keyed infix rendering is semantically safe): `ExpressionBuildVisitor.cs:3908` (`ExpressionType.Power`), `MathMemberTranslatorBase.cs:444` (`Math.Pow`), `AccessMemberTranslator.cs:220` (today a `^` binary, becomes the function), user `Sql.Function("Power")`. The Access builder matches name `Power` (ordinal-ignore-case) with exactly two parameters; anything else renders as a function call.
- **failure mode of the choice:** a `SqlFunction("Power")` rendered infix must also report the power level as a child — handled by the same table key in the precedence resolver (E-2).

### D-6 — Templates take part by declared class

- **chosen:** a template's declared int is an operator *class*: canonical constants (incl. `Unknown`) map to the dialect's level for that class; a non-constant maps to the nearest canonical constant, ties up (offset dropped — monotonic). The class is the template's **outer** level only. `BuildFormatValues` (`BasicSqlBuilder.cs:4195-4211`) wraps a placeholder argument whose level is **below** the template's class (as master: a `Primary` template keeps wrapping every lower-level argument, e.g. `{0}::text` fed `a + b`), and for a non-`Primary` template **also** one at an **equal** level (side unknown → conservative); an argument unordered with the template's class is wrapped too. A literal / inlined parameter argument is never wrapped for being negative (negative-literal entry applies under operator parents only; P10). A placeholder under a tighter operator inside the template text is the template's job: the in-repo audit (E-17) brackets or casts each one. The exact `{0}` pass-through template is transparent; `({0})` is not (U-11).
- **rejected:** parse template text for operators — the text is user-owned, provider-specific and can contain anything.
- **rejected:** "class at or below + offset" (draft) — not monotonic (`Comparison - 1` landed above `Comparison` on T-SQL), critic round 0.
- **why this:** keeps `Sql.ExpressionAttribute.Precedence` meaningful and dialect-correct with no public API change.
- **failure mode of the choice:** equal-level placeholder wrapping adds brackets to every non-`Primary` template — accepted churn (P3, U-12).

### D-7 — Bare-int parent entry points keep defined semantics

- **chosen:** an int parent passed to the shipped `BuildExpression(int, …)` / `BuildPredicate(int, int, …)` / `WithStringBuilderBuildExpression(int, …)` / `BuildSearchCondition(int, …)` is an anonymous, non-associative parent at that class's dialect level (D-6 mapping); `0` keeps "wrap nothing but 0-children"; any value above `Primary` (`int.MaxValue`, `OracleSqlBuilderBase.cs:256`) means "always wrap". New operator-aware overloads take `(parentOperator, side)`; core call sites move to them where the parent is an operator (P7 → *Int-parent sites*).
- **rejected:** remove the int overloads — breaks shipped protected API external providers subclass.
- **why this:** 54+ int-parent call sites (P7) keep their meaning; only operator parents gain side-awareness.
- **children too:** the decision works on `protected virtual SqlOperatorPrecedence ResolvePrecedence(ISqlExpression)` (new). It first unwraps transparent nodes (`SqlNullabilityExpression`, `SqlInlinedBase`, the exact `{0}` template) so the inner operator keeps its key for same-operator and unordered tests, then resolves operator, concat, cast, negative-literal and power nodes through the table by identity, and every other node through the shipped `GetPrecedence(ISqlExpression)` int, read as a **class** (D-6 mapping). So an external override of `GetPrecedence` keeps working for non-operator nodes, interpreted as a class; it can no longer re-rank an operator node (use `PrecedenceTable`). The two in-repo overrides (`FirebirdSqlBuilder.cs:29-30`, `SQLiteSqlBuilder.cs:39-40`) are deleted in PR1 and their concat levels become table entries in PR1 (D-9).
- **failure mode of the choice:** an external builder passing a dialect-specific int (e.g. `Precedence.Unary + 1`) gets the nearest class — documented on the overloads.
