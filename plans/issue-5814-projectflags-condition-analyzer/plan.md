# Work plan: issue-5814-projectflags-condition-analyzer — Internal analyzer for unsatisfiable / redundant ProjectFlags conditions

**Tier:** L  ·  **Status:** approved  ·  **Approved-at:** 2026-09-05  ·  **Branch:** issue/5814-projectflags-condition-analyzer
**Schema:** `.claude/docs/work-plan.md`  ·  **Gates:** `.claude/docs/definition-of-done.md`

Issue: [#5814](https://github.com/linq2db/linq2db/issues/5814), milestone 6.5.0. All `file:line` references below are against `origin/master` at `e144d065b`.

**Tier rationale:** three KB areas — `CODEGEN` (the analyzer), `EXPR-TRANS` (the conditions it fixes), `INFRA` (test project + CI). No `cross-cutting-core.md` path is touched (`Internal/Linq/Builder/**` is not in its `paths:` list) and no new public linq2db surface is added, but ≥2 areas puts it at L on its own.

## P1 Problem

`ProjectFlags` (`Source/LinqToDB/Internal/Linq/Builder/ProjectFlags.cs`) is one `[Flags]` enum carrying two different kinds of bit — a **mutually-exclusive build purpose** and **independent modifiers** — and nothing enforces the split. `ProjectFlagExtensions` (`ProjectFlagExtensions.cs:10-103`) exposes one flat `Is*()` predicate per bit, so any pair of predicates reads as equally plausible.

The observable failure: a condition that can never be true compiles, passes every test, and silently guards dead code.

- [#5727](https://github.com/linq2db/linq2db/pull/5727) added `if (flags.IsKeys() && flags.IsExpand())` guarding 43 lines in `EntityConstructorBase.BuildFullEntityExpressionInternal`. It survived four automated review passes and a green `test-all`, and was found only by instrumenting the call site: across `EagerLoadingTests` on SQLite, 1621 calls reached the method in six flag combinations — `SQL`, `Expression`, `SQL+Keys`, `SQL+MemberRoot`, `Expression+ForSetProjection`, `SQL+Keys+MemberRoot` — with `Expand` in none. The block never ran.
- Six conditions in the current tree are already unsatisfiable or redundant, enumerated in `P7`. Three are impossible flag pairs; three test a purpose that an unconditional early return earlier in the same method has already excluded, so they are dead code today.

The invariant is statically decidable. `ExpressionBuildVisitor.GetProjectFlags` (`ExpressionBuildVisitor.cs:495-548`) is the only producer of values reaching `IBuildContext.MakeExpression`, and it emits exactly one purpose bit plus a bounded modifier set — 13 purpose/`Keys` states × 4 modifier combinations = **52 reachable values**, small enough to enumerate instead of solving.

## P2 Success criteria

- SC-1 The #5727 shape (`flags.IsKeys() && flags.IsExpand()`) is a build error, reported **on `flags.IsExpand()`**; a satisfiable pair (`flags.IsSql() && flags.IsKeys()`) is not reported. → TO-1
- SC-2 An always-true flag clause (`flags.IsExpand() && !flags.IsKeys()`) is reported on the redundant clause itself; a meaningful one (`flags.IsSql() && !flags.IsKeys()`) is not. → TO-2
- SC-3 A flag test already excluded by an **unconditional** early return in the same method is reported; the same test is **not** reported when that early return sits under an unrelated condition, so the exclusion does not hold on every path. → TO-3
- SC-4 A flag-model change the analyzer's reader cannot parse produces `LINQ2DB0006` **and** silences `LINQ2DB0004`/`0005` for that compilation, instead of answering wrongly. → TO-4
- SC-5 The analyzer resolves symbols rather than matching the identifier `flags`: `var flags = Builder.DataContext.SqlProviderFlags; … flags.IsInsertOrUpdateSupported` is never touched. → TO-5
- SC-6 A Release build of the real `Source/LinqToDB` reports exactly the reconciled violation set from `P7` and nothing else — no diagnostic on any of the ~100 other `ProjectFlags` conditions in the assembly. → TO-6
- SC-7 The clause removals change no generated SQL and no baseline. → TO-7
- SC-8 The model-definition sites themselves (`GetProjectFlags`, `ProjectFlagExtensions`) are never flagged. → TO-8

## P3 Constraints & anti-goals (M/L)

**Must not change:**

- Generated SQL for any provider, and any file under `linq2db.baselines`. E-8..E-10 are always-true by the model, but the model is itself new code — that is a claim to verify (TO-7), not to assume.
- `ExprCacheKey.Flags` values (`ExpressionBuildVisitor.cs:5772-5787`). Those flags are opaque cache-key material participating in equality and hashing (`x.Flags == y.Flags` at `:5797`, `HashCode.Combine(…, obj.Flags)`), so altering a composed value there changes key identity. This explicitly covers the `ProjectFlags.SQL | ProjectFlags.Subquery` at `:2765` — **out of scope, do not "fix" it**.
- `Tests/Tests.Analyzers`'s Roslyn **4.8.0** host. That matches the shipped analyzer's consumer floor (`Source/LinqToDB.Analyzers/LinqToDB.Analyzers.csproj:21`, `VersionOverride="4.8.0"`) and is deliberate.
- Any `PackageVersion` in `Directory.Packages.props`. A different version for one consumer goes in a `VersionOverride`.
- `Build/Azure/pipelines/testing.yml` and `.github/workflows/tests.yml` — the provider matrices deliberately inherit `with_analyzer_tests: false` / omit analyzer tests. Do not wire DB-free tests into a provider leg.
- Public linq2db API. `Source/CodeGenerators` is `IsPackable=false` and referenced with `ReferenceOutputAssembly="false"`, so nothing here reaches the package surface — no `PublicAPI.Unshipped.txt` or `CompatibilitySuppressions.xml` work.

**Anti-goals:**

- Not splitting the purpose out of `ProjectFlags` into its own enum field. The issue considered and rejected it: it touches every `MakeExpression` implementation and the whole flag-threading path.
- No code fix and no `.editorconfig` options — internal `LINQ2DB0xxx` rules get neither (`.claude/docs/authoring-analyzers.md` → *Diagnostic IDs*). A fixer would additionally need its own project, since RS1038 forbids a `Workspaces` reference from an assembly containing a `DiagnosticAnalyzer`.
- Not touching the ~20 sites that hardcode a `ProjectFlags` literal (`P7`), beyond documenting two of them.

**Build constraints the analyzer source must satisfy.** `Source/CodeGenerators/Directory.Build.props` contains **no `<Import>`**, so neither `Source/Directory.Build.props` nor the repo-root props apply — Meziantou.Analyzer, the PublicApi analyzers and `Source/BannedSymbols.txt` are all absent, and there is no `NoWarn` list. ## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — The flag model is derived from `GetProjectFlags`, not duplicated in the analyzer

- **chosen:** at `RegisterCompilationStartAction`, read `ExpressionBuildVisitor.GetProjectFlags` and derive the classification — the unconditional `flags |= ProjectFlags.X` in each switch section is a **purpose**; a conditional add inside a section is a modifier permitted **with that purpose**; a conditional add after the switch is a **free** modifier. Every `ProjectFlags` member except `None` must land in one of those buckets, or the model is rejected.
- **rejected:** hardcode the three tables in the analyzer plus a rule that structurally cross-checks them against `GetProjectFlags`. Same walker code, but the table is duplicated and the cross-check becomes the only thing holding the two together.
- **rejected:** hardcode with no drift guard — the issue's literal proposal. Adding `Keys` to the `Expand` arm would silently make the analyzer wrong, which is the exact failure the issue names as its main risk.
- **rejected:** the issue's suggested mitigation, a unit test enumerating `GetProjectFlags` over every (`_buildPurpose` × `BuildFlags`) pair. **Infeasible**: `GetProjectFlags` is `private` on an `internal` type, `BuildPurpose`/`BuildFlags`/`ProjectFlags` are all internal, and the repo bans `InternalsVisibleTo` (`code-design.md` → *Never `InternalsVisibleTo`*). Reflection into a private method of an internal type on a `GetUninitializedObject` instance is the only route and is not worth having.
- **why this:** it makes the analyzer's model *linked* to the code it describes — the one property the issue asks for and the one a table cannot give. It also turns the reachable flag set into executable documentation; the issue notes that set is "documented nowhere and had to be recovered empirically".
- **failure mode of the choice:** a legitimate refactor of `GetProjectFlags` into a shape the reader does not parse breaks the build with `LINQ2DB0006` and forces someone to update the reader. That is the intended loud failure, but it is a real tax on a future refactor — and if the reader matches statement *order* rather than structure, the tax arrives for cosmetic edits too. Mitigation: match structurally (any unconditional add in the section, in any order), never positionally.

### D-2 — The model is read from **syntax**, not from an `IOperation` tree

- **chosen:** resolve `ExpressionBuildVisitor` and `ProjectFlagExtensions` via `Compilation.Assembly.GetTypeByMetadataName` (the **source** assembly, so a consumer compilation that merely references linq2db is unaffected and the test fixtures' stub types resolve unambiguously), then read each method's `DeclaringSyntaxReferences[0].GetSyntax()` and pattern-match the syntax: `case BuildPurpose.X:` labels, `flags |= ProjectFlags.Y;` compound assignments, and the one-line predicate bodies.
- **rejected:** `compilation.GetSemanticModel(tree).GetOperation(decl)` — **banned**, RS1030 is `error` here (U-6).
- **rejected:** compute the model inside an `OperationBlockAction` for `GetProjectFlags`, where semantics are legally available, and defer all reporting to `RegisterCompilationEndAction` to dodge the resulting ordering problem. It works, but turns every `0004`/`0005` into a compilation-end diagnostic — needing an RS1037 `CompilationEnd` tag and invisible in the IDE outside full-solution analysis, which is exactly where the author wants to see it.
- **why this:** ordering-free (the model exists before any condition is analyzed, which matters under `EnableConcurrentExecution`), RS1030-clean, and reporting stays per-operation so the rule is live while typing. Deriving each predicate's mask from its **body** also removes the `IsSql`→`SQL` name-mismatch hazard and picks up `IsSqlOrExpression`'s two-bit `(flags & (SQL | Expression)) != 0` with no special case — the scout confirmed that member is the only one of the 14 that is not a `HasFlag` call.
- **failure mode of the choice:** textual matching is more brittle than symbol resolution — a `using static`, an alias, or a renamed enum member would not resolve. Contained by D-1's fail-safe: an unparseable model reports `LINQ2DB0006` and disables the condition rules rather than answering wrongly. Note the *conditions* are still analyzed semantically (via `IInvocationOperation.TargetMethod` from the operation context, no semantic model needed), so SC-5's type-resolution requirement is unaffected by this choice.

### D-3 — Analysis is CFG dataflow over the reachable value set

- **chosen:** a forward may-analysis over `GetControlFlowGraph(...)`. State per basic block = which of the ~52 reachable values are still possible; entry block all-possible, every other block empty, join = elementwise OR, worklist to a fixed point. At a conditional block, filter `BranchValue` per `ControlFlowConditionKind`: a value survives on the true edge unless the condition evaluates `false` for it, on the false edge unless `true`. Evaluation returns `bool?`, so an opaque sub-expression leaves the value unconstrained. Report on the **outermost** fully-recognised sub-expression whose value is constant over the block's entry state — constant false ⇒ `LINQ2DB0004`, constant true ⇒ `LINQ2DB0005` — descending only *through* non-constant nodes and stopping at the first constant one. "Outermost", not "smallest": under `IsExpand()` the node `!flags.IsKeys()` is constant **true** and its operand `flags.IsKeys()` is constant **false**, so a smallest-node rule would report `LINQ2DB0004` on the operand where SC-2 wants `LINQ2DB0005` on the negation — the text a reader must delete. Nested graphs (`LocalFunctions`, `IFlowAnonymousFunctionOperation`) are analyzed with entry = all-possible.
- **rejected:** `&&`-chain-only analysis — flatten each maximal conjunction, check satisfiability and per-conjunct implication. Simpler, and catches all three `&&` violations, but misses the three early-return-shadowed dead tests in `P7` and any nested-`if` pair.
- **rejected:** enclosing-`if` fact propagation without a CFG (walk ancestors collecting then-branch conditions). Catches nested `if`s but not early returns, and needs its own guard against the tracked value being rebound — a guard the CFG provides for free.
- **why this:** the CFG lowers `&&`, `||`, ternaries, nested `if` and early returns into one conditional-block shape, so a single mechanism covers all of them, and the smallest-constant-sub-expression rule puts the diagnostic on the text to delete. The reachable set is small enough that exhaustive evaluation replaces a solver.
- **failure mode of the choice:** the widest scope has the widest false-positive surface — a defensive re-test a maintainer wants kept reads as redundant, and there is no way to know which those are before the census (SC-6/TO-6 is the gate). CFG construction is also the analyzer's dominant cost, so a bad gate on which bodies get one is a build-time regression; hence the `RegisterOperationBlockStartAction` → nested `RegisterOperationAction` → `RegisterOperationBlockEndAction` shape, which reuses the walk Roslyn already does instead of adding a `Descendants()` scan per method.

### D-4 — The provenance caveat is adjudicated, not engineered around

- **chosen:** analyze any `ProjectFlags`-typed local or parameter against the derived domain, and record the two out-of-domain literal values (U-3) as an accepted trade-off in `P10`. Neither receiving method contains a flag conjunction today, so no false positive exists; `#pragma warning disable LINQ2DB0004` at the site is the escape hatch if one appears.
- **rejected:** collect every literal `ProjectFlags` composition in the compilation and union it into the domain. Sound and self-maintaining, but nothing can be judged until collection finishes → compilation-end reporting, with D-2's RS1037 and IDE-visibility costs. It also *weakens* the rule: with `SQL|Expression` in the domain, `IsSql() && IsExpression()` stops being reported, and that is precisely the kind of impossible test the rule exists to catch.
- **rejected:** flag the out-of-domain compositions themselves and fix them, so the invariant becomes true of the whole assembly. `:2696`'s `| Expression` is inert (`ParseGenericConstructor` reads only `flags.IsSql()`), so dropping it is plausible — but `:2765`'s `SQL | Subquery` is `ExprCacheKey` material and changing it changes cache identity, which `P3` forbids. A rule needing a hardcoded "unless it flows into `ExprCacheKey`" exemption buys little and adds a fourth diagnostic.
- **why this:** the exposure is measured rather than assumed — 20 literal sites, 2 out-of-domain, 0 of them in a method containing a flag conjunction. Engineering around a false positive that does not exist costs the rule its headline finding.
- **failure mode of the choice:** someone later writes a genuine two-purpose test in a method reached only from `:2696` and gets a build error on correct code, with no way to tell why. The analyzer's `<remarks>` must name both sites and the reason, or the error is unactionable.

### D-5 — Unit tests go in a new `Tests/Tests.Analyzers.Internal` project

- **chosen:** a second DB-free test project on the Roslyn 5.6 line, referencing `Source/CodeGenerators` only. Snippets declare their own stub `ProjectFlags` / `ProjectFlagExtensions` / `ExpressionBuildVisitor.GetProjectFlags` in namespace `LinqToDB.Internal.Linq.Builder`, so it needs no linq2db reference — hence no reference-pack constraint, `net10.0`, and no `UseDotNet@2 runtime 8.x` provisioning (which `build-job.yml:36-46` only needs because `Tests.Analyzers` is net8.0).
- **rejected:** `VersionOverride="5.6.0"` on the existing `Tests/Tests.Analyzers`'s `Workspaces` reference. Two lines and no new project — but the shipped `L2DB1xxx` fixtures would then execute on Roslyn 5.6 instead of the 4.8 floor an SDK-8 consumer gets, undoing a documented deliberate alignment (`P3`).
- **rejected:** no unit tests, matching in-flight #5870 — whose internal `LINQ2DB0002`/`0003` analyzer has no fixtures. Defensible there because that rule is a thin wrapper over a detection core the *shipped* twin tests. This rule has no shipped twin, and its logic — syntactic model reader, atom recogniser, CFG dataflow — is where the bugs will be.
- **why this:** the only option that both covers the logic and leaves the 4.8 alignment intact, for one csproj plus three registration lines.
- **failure mode of the choice:** a second analyzer-test project is a second thing to keep in sync — a future Roslyn bump has to move two pins, and both Azure and GitHub Actions have to run two projects. If the analyzer is later moved or split, the project can be left orphaned.

### D-6 — Three diagnostic ids

- **chosen:** `LINQ2DB0004` (can never be true), `LINQ2DB0005` (always true), `LINQ2DB0006` (model unreadable). Category `Usage`, severity `Warning` — an error under `TreatWarningsAsErrors` in Release, matching `LINQ2DB0001`.
- **rejected:** one id with a `{0}` slot for all three. Cheaper in `AnalyzerReleases.Unshipped.md`, but `0004` (dead code — a defect) and `0005` (a redundant clause — cleanup) carry different weight, and folding the drift signal in makes it un-suppressible independently.
- **why this:** the three have different audiences — "your guarded code never runs", "delete this clause", "the analyzer is stale, fix its reader".
- **failure mode of the choice:** three ids to move Unshipped→Shipped at release, and a textual conflict with #5870's rows in the same file whichever branch merges second.

### D-7 — Domain-set representation is `bool[]`, not a `ulong` bitset

- **chosen:** a `bool[]` indexed by domain-value ordinal.
- **rejected:** a single `ulong` — elegant (join = `|`, "never true" = `(state & mask) == 0`) and it fits today's 52 values, but a third free modifier takes the domain to 104 and silently breaks it, or forces a `LINQ2DB0006` "model too large" bail that punishes an ordinary enum addition.
- **why this:** the CFGs are tiny (tens of blocks across tens of methods); clarity and an unbounded domain beat the micro-optimisation.
- **failure mode of the choice:** an allocation per block per method, on an every-keystroke path. Negligible at this scale, which makes `/profile-analyzers` a gate rather than a formality.

### D-8 — The always-true `Expand`-guard clauses are a scope decision, not a cleanup

The critic established (and the tree confirms) that these clauses encode **intent the producer cannot satisfy**, not stray noise, so deleting them silently would be mis-scoped. `TableBuilder.TableContext.cs:220` reads *"Expand is initiated by Eager Loading but there is need to expand in case when we need comparison"* — i.e. the `!flags.IsKeys()` at `:221` is the author asking for the `Expand`+`Keys` case, which `GetProjectFlags` never emits. `GroupByBuilder.cs:380-386` documents the same producer-side hazard in prose: *"under Expand a ForKeys build loses the Keys flag in GetProjectFlags, so the key would select every column instead of reducing to its PK (the Value1 over-fetch)"*. Three sites are affected (`TableBuilder.TableContext.cs:221`, `SelectContext.cs:89`, `GroupByBuilder.cs:494`); `SubQueryContext.cs:106` is a fourth always-true clause of a different kind (plain path-shadowing, no intent recorded).

- **chosen:** delete the clause **and** update the comment it falsifies, per `agent-rules.md` → *A comment a change has falsified is often the symptom* — recording in the commit that the guarded case is unreachable **by producer construction**, not merely unused. `SubQueryContext.cs:106` is deleted with no comment work.
- **rejected:** keep the clauses and `#pragma warning disable LINQ2DB0005` each, preserving the intent as an assertion for a future producer fix. Keeps a guard that provably cannot fire and turns the rule's first three findings into suppressions, which is the shape that trains people to suppress it.
- **rejected:** fix the producer so `GetProjectFlags` emits `Keys` under `Expand`. That is the change the comments actually ask for, and it is out of scope by a wide margin: it alters the reachable domain for **every** `MakeExpression` implementation, and `GroupByBuilder.cs:380-386` records that the current behaviour is being routed around deliberately rather than accidentally. If it is ever wanted it is its own issue.
- **why this:** the analyzer's job is to make the unreachable visible; leaving three suppressions behind defeats it, and widening into the producer converts a static-analysis PR into a query-builder behaviour change.
- **failure mode of the choice:** deleting the clause discards the only record that someone once wanted `Expand`+`Keys` to be distinguishable. Mitigated by the comment edits, and by filing the producer question separately if the maintainer wants it tracked.
