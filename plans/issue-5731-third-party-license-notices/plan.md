## P1 Problem

Three linq2db artifact families redistribute compiled binaries that linq2db does not own, and ship no license text, copyright notice, or attribution for any of them. Each declares `PackageLicenseExpression=MIT` and nothing else:

- **`linq2db.cli`** — `PackAsTool` (`Source/LinqToDB.CLI/LinqToDB.CLI.csproj:22`) with `ToolPackageRuntimeIdentifiers` over 7 RIDs (`:35`) × 3 TFMs publishes the whole dependency closure into per-RID sub-packages. Declared license `MIT` (`:42`); its 22 `PackageReference`s (`:74-96`) are the visible tip.
  **measured:** `dotnet publish -c Debug -f net10.0 -r win-x64 --no-self-contained` yields **161 files / 102.2 MB — 158 DLLs (62 of them satellite `.resources.dll` across 13 culture folders), from 90 NuGet packages** (`dotnet-linq2db.deps.json`, `libraries` where `type == package`). The closure is six times the reference list, and includes `Apache.Arrow`, `Google.Protobuf`, `Grpc.*`, six `Microsoft.IdentityModel.*`, `Portable.BouncyCastle`, four `SQLitePCLRaw.*`, `K4os.Compression.LZ4`, `NodaTime`, `Microsoft.Data.SqlClient.SNI.runtime`, `Ydb.Protos`.
- **14 T4 packages** — `linq2db.t4models` and 13 per-provider packages hand-list foreign DLLs under `tools/`: `NuGet/t4models/linq2db.t4models.csproj:92-134` plus the IBM `clidriver/**` tree injected at `:144-151`. **measured:** that clidriver tree is **223 files / 161.2 MB**, and its only license artifact is `license/odbc_notices.rtf`; the `IBM.Data.DB.Provider` nuspec has no `<license>`, only a `licenseUrl` pointing at an IBM click-through LAP form.
- **`linq2db.LINQPad.lpx`** (LINQPad **5** driver, a GitHub release asset) — `Source/LinqToDB.LINQPad/Nuget/Pack.cmd:32-34` runs `7z -r a … "%OUTDIR%*.*"`, archiving the *entire* `net472` output directory: every provider client, `linq2db4iSeries`, both architectures of `IBM.Data.DB2.dll` (`LinqToDB.LINQPad.csproj:138-141`), and the SQLite natives copied in at `:150-153`.

Falsifiable statement of the gap: unzip any of these artifacts today and there is no file carrying a third-party copyright line; the only license metadata is a nuspec `MIT` expression describing linq2db's own source.

**measured, and already an audit finding:** of the CLI's 90 packages, 82 declare an SPDX expression (65 `MIT`, 16 `Apache-2.0`, 1 `PostgreSQL`), 4 embed a license file and 4 carry only a legacy `licenseUrl`. Among the embedded files, `Microsoft.SqlServer.Types` 170.1000.7 ships **"MICROSOFT PRE-RELEASE SOFTWARE LICENSE TERMS / MICROSOFT SQL SERVER VNEXT COMMUNITY PREVIEW"** — and that package is bundled into `linq2db.cli`, `linq2db.SqlServer`, `linq2db.t4models` and the `.lpx`. `Oracle.ManagedDataAccess.Core` ships the *Oracle Free Distribution, Hosting, and Use Terms*, `FirebirdSql.Data.FirebirdClient` the *Initial Developer's Public License 1.0*, and `DuckDB.NET.Data.Full` **two** license files (its own MIT plus DuckDB's). Six packages declare no `<copyright>` at all.

Second, concrete symptom: `Redist/Readme.md:1` asserts the checked-in binaries there are *"not distributed by nuget, but required for testing"*. That is false for exactly two of its six components — `Redist/SqlCe/**` and `Redist/SapHana/v4.5/` reach end users through `NuGet/NuGet.csproj:31-49` → `NuGet/SqlCe/linq2db.SqlCe.csproj:36-37`, `NuGet/SapHana/linq2db.SapHana.csproj:37`, and `linq2db.t4models.csproj:98,114,127`.

## P2 Success criteria

- SC-1 Each of the **23 shipping artifacts** (`linq2db.cli` pointer + 7 RID sub-packages, 14 T4 nupkgs, `linq2db.LINQPad.lpx`) carries a `THIRD-PARTY-NOTICES.txt` — **16 distinct notices files**, since the 8 CLI packages share one — whose component list is a superset of the third-party binaries that artifact ships. Unmet if a binary in the artifact maps to no component in its notices. → TO-1
- SC-2 A newly bundled dependency — direct or transitive — fails CI **on the PR that introduces it**, naming the unmapped file. Unmet if adding a `PackageReference` that drags in a new assembly gets a green PR build. → TO-2
- SC-3 The checked-in notices are byte-identical to what the generator produces from `Build/licenses/components.json`, on a developer box and on `windows-2025` alike. Unmet if `-Action check` disagrees across machines, or if a hand-edit passes. → TO-3
- SC-4 Packages asserted to bundle nothing are asserted, not assumed: `linq2db`, `.Tools`, `.Scaffold`, `.Compat`, `.Extensions`, `.FSharp`, the six `.Remote.*`, the four `linq2db.EntityFrameworkCore` ids, `linq2db.Analyzers`, `linq2db.LINQPad`. Unmet if one of them acquires a bundled foreign DLL and CI stays green — **or** if the check passes vacuously on an artifact it failed to enumerate. The vacuity guard is per artifact *class*: implementation-bearing artifacts must yield a known first-party assembly, while the `linq2db.cli` pointer package must show its `DotnetToolSettings.xml` plus notices and no assemblies at all. → TO-4
- SC-5 The readmes of the three affected families state that `MIT` covers linq2db's own code while bundled components keep their own terms, and `Redist/Readme.md` no longer claims SqlCe / SAP HANA are undistributed. → TO-5
- SC-6 A dependency change that alters the bundled set or its versions is surfaced during release prep without a separate reminder: `/release-deps` refreshes the manifest from the post-apply restore graph, and `/release-verify` gates it against the packed output. Unmet if a `<PackageVersion>` bump reaches the end of release prep with a manifest that disagrees with the resolved graph, or if `/release-verify` completes with a manifest that disagrees with what was packed. → TO-6

## P3 Constraints & anti-goals

- **No binary is added to or removed from any artifact in this branch.** The audit classifies; changing what ships is a separate, user-approved decision (P10 / P11). Adding the notices *text file* to 23 artifacts is in scope and is not what this forbids. This is the most important anti-goal: a licensing PR that silently drops the SAP HANA client breaks T4 scaffolding for those users.
- **`PackageLicenseExpression=MIT` stays** (`Directory.Build.props:106`, `LinqToDB.CLI.csproj:42`). NuGet permits only one of `licenseUrl` / expression / file; switching to a license *file* would misdescribe linq2db's own code and change what nuget.org renders.
- **No build-time code generation.** Notices are checked in; the build only copies them.
- **No new tool dependency in CI** — one repo-local pwsh script, matching `Build/Azure/scripts/verify-nuget-sizes.ps1` and `verify-analyzer-delivery.ps1`.
- **No `Source/LinqToDB/**` change.** Zero engine code, zero public API, zero SQL, zero baselines.
- Notices are text and must not move any package across `verify-nuget-sizes.ps1`'s 180/200 MB lines.

## P4 Unknowns

- U-1 Does a `Pack="true"` `None` item also reach the per-RID tool payload? — **resolved-by critic probe of the SDK targets: no, and the correct lever is confirmed.** `Microsoft.NET.PackTool.targets:445-448` runs a full `Pack` per RID; `:200,223-225` glob `$(PublishDir)/**/*` into `tools/$(tfm)/$(rid)/` with `Publish` as the dependency (`:100`); `None` + `CopyToPublishDirectory` enters via `Microsoft.NET.Publish.targets:808-829`. So package-root packing and payload placement are two separate mechanisms (E-7 does both), the publish-dir probe is a faithful proxy for the payload, and the root `None` item lands in every RID package because each is a full `Pack`.
- U-2 Do any `NuGet/*/*.csproj` set `<PackageId>`? — **resolved-by scout: no**, and none sets `<AssemblyName>`, so project name == package id for all 15 projects there. Not true under `Source/`, where `LinqToDB.CLI`→`linq2db.cli`, `LinqToDB.Analyzers.CodeFixes`→`linq2db.Analyzers`, `LinqToDB.LINQPad.Pack`→`linq2db.LINQPad` and the four EF projects all diverge — E-7 therefore names its file literally instead of reusing E-6's keying.
- U-3 Is there a second pack path that would bypass a gate wired only into Azure DevOps? — **resolved-by critic: yes, live today.** `.github/workflows/build.yml` exists on the branch base (`on: pull_request` at `:21-24`), builds and packs `linq2db.slnx` to `.build/package/release` (`:78-82`), runs **both** sibling verifiers with `-NoAzdoLogs` (`:87-93`), and uploads `.build/lpx` (`:104-108`). AzDO `Build/Azure/pipelines/build.yml:6-10` is still `pr: '*'`, so **both** pipelines pack on every PR today, and the GHA one becomes the sole PR gate when AzDO's goes `pr: none`. Covered by E-9 **and** E-9b.
- U-4 Which components' vendor terms permit redistribution? — **resolved-by user answer (settled at planning time): out of this branch's scope.** The instruction was "audit, then bring findings back". `components.json` carries a `redistribution` field whose value may be `unresolved`; that is a deliberate shipping state changing no artifact, and the verdicts land as a decision list in a later turn (P11 if any of them changes a package). The design does not depend on the answer.
- U-5 Would a `linq2db*` prefix rule misclassify `linq2db4iSeries`? — **resolved-by scout: yes, on two axes.** Third-party (repo `LinqToDB4iSeries/Linq2DB4iSeries`; `.claude/knowledge-base/areas/PROV-DB2/INDEX.md:20`), package id starts `linq2db`, and its namespace starts `LinqToDB.` (`Source/LinqToDB.LINQPad/DatabaseProviders/DB2Provider.cs:9`). It reaches no nupkg as a binary — only as a nuspec dependency — but it **is** physically in the `.lpx`. E-5's first-party rule must be an exact assembly-name allow-list, never a prefix.
- U-6 Must the notices be readable at CLI runtime? — **resolved-by scope decision D-5:** no. The CLI registers 10 commands (`LinqToDBCliController.cs:28-37`), none of them `about`/`licenses`, and its only text-asset precedent is `EmbeddedResource` + `GetManifestResourceStream`.
- U-7 Is `-Action generate` byte-deterministic across a dev box and `windows-2025`? — **resolved-by design, made explicit in E-5**: ordinal sorting (`Sort-Object` is culture-sensitive by default, and both sibling scripts use it bare — `verify-nuget-sizes.ps1:76,84,95`, `verify-analyzer-delivery.ps1:203`), an explicit newline policy against `.gitattributes:1` `text=auto` (LF in-repo, CRLF on a Windows checkout), and no BOM. Any of the three left implicit makes `-Action check` red on one machine and green on another. Proven by TO-3, which must run on both.
- U-8 What is `version` in the manifest for, given that `verify` matches file *names*? — **resolved-by D-7**: it is checked where the artifact states it (the CLI payload's `deps.json` names package + version for all 90) and is informational elsewhere. SC-3/SC-6 and TO-6 are written to what the gate actually proves.

## P5 Decisions

### D-1 — Checked-in generated notices, not pack-time generation

- **chosen:** `Build/licenses/generated/THIRD-PARTY-NOTICES.<packageId>.txt` are tracked, produced by `-Action generate`, validated by `-Action check` (regenerate → compare → fail on drift).
- **rejected:** an MSBuild target generating into `$(IntermediateOutputPath)` at pack time — nothing generated in git, but the exact shipped text never appears in a diff and the review surface becomes a JSON manifest rather than the legal text that ships.
- **why this:** the repo already treats generated-but-reviewed files this way (`CompatibilitySuppressions.xml`, `PublicAPI.*.txt`), and the point of a notices artifact is that a human can read what went out.
- **failure mode of the choice:** 16 tracked files that must never be hand-edited, plus a drift check whose correctness depends entirely on U-7's determinism requirements. Mitigated by a `DO NOT EDIT` header naming the script, and by TO-3 running on both platforms.

### D-2 — Per-package scope, not one shared union file

- **chosen:** each artifact gets notices covering only what it ships; the manifest maps component → carrying artifacts.
- **rejected:** one union file in every affected package — trivial to build, but `linq2db.SQLite` would then ship Oracle's terms and IBM's, which actively misleads about what the user received.
- **why this:** the mapping already exists, hand-written, in the `<None Include="$(ToolsPath)/…">` blocks; the generator reads the same fact the packer does.
- **failure mode of the choice:** the mapping can drift from the packer's item list and under-report — which is exactly what D-3's artifact-driven `verify` catches.

### D-3 — Validate the produced artifact, never the csproj

- **chosen:** `-Action verify` opens the `.nupkg` / `.lpx` / publish dir and enumerates real entries.
- **rejected:** deriving the expected set from `project.assets.json` + csproj item lists — no build needed, but it re-implements NuGet resolution and goes wrong silently exactly when the closure changes, which is the case it exists for.
- **why this:** `verify-analyzer-delivery.ps1:12-14` already argues this stance in its own header, and the measured 90-package closure against 22 references is the quantitative case for it.
- **failure mode of the choice:** needs artifacts on disk, so no full local check without a pack/publish. Mitigated by `-PublishDir` (one RID publish ≈ the whole bundled set, per U-1) and by the T4 packs being cheap.

### D-4 — Gate both PR pack paths, in the GitHub Actions workflow and in AzDO

- **chosen:** E-9b adds the two steps to `.github/workflows/build.yml` after `:93`, mirroring the existing `-NoAzdoLogs` invocations; E-9 adds them to `Build/Azure/pipelines/templates/build-job.yml` after *"Pack Solution for Nuget"* (`:226-232`), under the same `with_nugets` condition.
- **rejected:** `nuget-job.yml` alone, where both sibling scripts are invoked for publishing — it is wired only into `default.yml` (master / release and release-targeting PRs), so a PR adding a dependency would pass, merge, and fail on master. Also rejected: GHA only — AzDO still packs on every PR *and* is the only path that publishes.
- **why this:** both pipelines pack on every PR today (`build.yml:6-10` is `pr: '*'`; the GHA workflow is `on: pull_request`), and the GHA one becomes the sole PR gate once AzDO's trigger is removed by the migration plan. Wiring one and not the other leaves a live hole either now or later.
- **failure mode of the choice:** two copies of the same two steps that can drift. Mitigated by both calling one script with identical arguments, and by the migration plan's phase 3 (`Build/CI/*.ps1` extraction) being the place they converge.

### D-5 — Notices are a file on disk, not a CLI feature

- **chosen:** ship the text; add no command, no help section, no runtime read.
- **rejected:** a `dotnet linq2db licenses` command or a `help` line — better discoverability, but new public behaviour on a compliance PR, needing its own tests.
- **why this:** keeps the blast radius at packaging + docs.
- **failure mode of the choice:** a user who installed globally must find the file under the tool payload directory. Mitigated by naming the path in `Source/LinqToDB.CLI/readme.md`.

### D-6 — Refresh in `/release-deps` after the apply; gate in `/release-verify` 4a

**User decision (this turn):** the notices refresh belongs to the release-prep phase *where nugets are updated* — task 1, `/release-deps`. That settles ownership; the placement *within* the skill is what has to answer the critic's timing objection.

- **chosen:** a **new step 5b in `/release-deps`, immediately after step 5's batch apply**. It runs `dotnet restore` on the three graph-owning projects — `Source/LinqToDB.CLI` (the 90-package closure, per TFM and per RID), `NuGet/NuGet.csproj` (net462, the T4 `tools/` set) and `Source/LinqToDB.LINQPad/LinqToDB.LINQPad.csproj` (net472, the `.lpx` set) — then `-Action harvest` reads their `project.assets.json`, diffs its proposal against `components.json`, and queues manifest edits + `-Action generate` into the same uncommitted working tree the release flow already carries forward to `/release-verify`. The **gate** stays in `/release-verify` step 4a (`SKILL.md:104-119`) — `-Action check` plus `-Action verify` against the packed output — because that is the only point where artifacts exist and where the sibling packaging guards already run.
- **rejected:** putting the refresh in `/release-deps` step 4, alongside the `4a`-`4f` predictive audits. Those run "from package metadata alone, **before** any file is edited" (`release-deps/SKILL.md:105-107`), so a harvest there would see the new version of a *direct* reference but not the ~75 transitive entries. Step 5b is after the apply, so a restore resolves the real post-bump graph — which is what makes this placement answer the objection rather than inherit it.
- **rejected:** doing both refresh and gate in `/release-verify` 4a (the pre-decision design). Mechanically sound, but it puts a dependency-driven manifest update in the build-verification task rather than in the dependency task, which is not where the user looks for it.
- **rejected:** a new numbered task in `/release`'s checklist — it reshapes `release-state.ps1`'s task template and the PR-body checklist, and task 1 already *is* "Dependencies update". No state-file change is needed.
- **why this:** a restore is enough to resolve the transitive closure, and it is far cheaper than a pack — so the refresh can sit where dependency work happens without waiting for the build gate. Reading a restore graph is legitimate for `harvest` and is **not** a D-3 violation: D-3 governs `verify` (what actually shipped), not `harvest` (what to propose).
- **failure mode of the choice:** the refresh and the gate now live in two different skills, so a release that runs `/release-deps` and skips `/release-verify` ships an un-gated manifest — but `/release-verify` is the mandatory build gate of every release prep. Second failure mode: an unconditional harvest adds a diff to adjudicate on every release even when nothing moved; mitigated by `harvest` printing nothing when its proposal already matches the manifest.

### D-7 — `version` is a per-TFM set, verified where the artifact states it

- **chosen:** `version` is a **map from TFM to resolved version**, not a scalar. For the CLI, `verify` reads each payload's own `dotnet-linq2db.deps.json` and checks it against the entry for *that* TFM, so a component with three resolutions passes on all three; the CLI notices file renders every version a TFM-split component has. For T4 packages and the `.lpx` there is no such manifest in the artifact, so those entries are single-valued (one TFM each — `net462` / `net472`) and are refreshed by the unconditional post-apply harvest in D-6 rather than gate-checked.
- **rejected:** a single scalar `version` per component — **measured refutation**: `.build/obj/LinqToDB.CLI/project.assets.json` resolves `Microsoft.Extensions.Hosting` to `8.0.0` / `9.0.0` / `10.0.0`, `Microsoft.Extensions.Caching.Memory` to `8.0.1` / `9.0.13` / `9.0.13`, and `Microsoft.Extensions.Logging.Console` to `8.0.1` / `9.0.18` / `10.0.10` across the net8.0 / net9.0 / net10.0 targets, uniformly across all 7 RIDs. This is deliberate — `Directory.Packages.props` conditions those `PackageVersion` entries on `$(TargetFramework)`. A scalar would false-fail on two of the three payloads inside every RID package, i.e. exactly the failure mode this decision rejects `FileVersion` for.
- **rejected:** gate-checking every artifact via assembly `FileVersion` — assembly version and package version diverge routinely (`Microsoft.SqlServer.Types` 170.1000.7, `Net.IBM.Data.Db2` 9.0.0.400), so it would produce false failures.
- **rejected:** dropping `version` entirely — a notices file that names no version is materially less useful, and the CLI case is checkable for free.
- **why this:** it makes SC-3/SC-6 promise exactly what the gate delivers, and it is the only shape that survives the repo's TFM-conditioned central package management.
- **failure mode of the choice:** the manifest gains a nested structure for ~5 components that the other ~85 don't need, so the generator must render a single-entry map identically to a scalar or every notices line churns. Pinned by TO-3's determinism control.

## P11 Amendments

- **A-1 — `.gitattributes` added as E-17.** U-7 requires `-Action generate` to be byte-deterministic across a developer box and `windows-2025`, and E-5 carries the ordinal-sort / newline / no-BOM requirements to that end. Those requirements are not sufficient on their own: `.gitattributes:1` is `* text=auto`, with no rule covering `.txt`, so git normalises the generated notices to LF in the repository and checks them out as **CRLF on Windows** and LF on Linux. A generator writing LF unconditionally would then be correct on the Linux legs and report drift on every Windows checkout — including `windows-2025`, where both CI pack paths run — while a generator writing the platform newline would produce a file that differs from its own repository content. Neither is fixable inside E-5. Pinning `Build/licenses/generated/**` and `Build/licenses/texts/**` to `eol=lf` makes the working tree match the repository on every platform, which is the precondition E-5's determinism requirements assume. The license *texts* are pinned as well as the generated files because the generator embeds their bytes verbatim, so a CRLF checkout of a text would propagate into the generated output.
  **This voids approval of the E-17 line only**; every other edit-point stands as approved. Surfaced to the user in the same turn it was found, before any file was written.
