## P1 Problem

An outer-joined sequence whose projection reads a value of an *enclosing* source (a sibling `from`, an outer range variable) returns that source's value on a row that has no match, instead of `NULL` / `default`. Measured on master `a261782a28`, SQLite.MS, shared `Tests/Linq` model:

```csharp
from p in db.Parent
from c in db.Child
where c.ParentID == p.ParentID
from v in db.GrandChild.Where(g => g.ChildID == c.ChildID).Select(g => p.Value1).DefaultIfEmpty()
select new { c.ChildID, V = v };
```

Children 61–66 and 77 have no grandchildren. Expected `V = null` for them; master returns `6` (61–66) and `1` (77). Master SQL reads the value from `p` directly, never through the LEFT JOIN:

```sql
SELECT [c_1].[ChildID], [p].[Value1]
FROM [Parent] [p] CROSS JOIN [Child] [c_1]
     LEFT JOIN [GrandChild] [v] ON [v].[ChildID] = [c_1].[ChildID]
WHERE [c_1].[ParentID] = [p].[ParentID]
```

Correct SQL guards the value with a marker that does come through the join (measured with the candidate fix):

```sql
SELECT [c_1].[ChildID], CASE WHEN [v_1].[not_null] IS NOT NULL THEN [p].[Value1] ELSE NULL END
FROM [Parent] [p] CROSS JOIN [Child] [c_1]
     LEFT JOIN (SELECT 1 as [not_null], [v].[ChildID] FROM [GrandChild] [v]) [v_1] ON [v_1].[ChildID] = [c_1].[ChildID]
WHERE [c_1].[ParentID] = [p].[ParentID]
```

**Mechanism — two sites, both in `Source/LinqToDB/Internal/Linq/Builder/DefaultIfEmptyBuilder.cs`:**

- **M1, the value.** `SelectManyBuilder.cs:97-110` wraps the collection in a new `DefaultIfEmptyContext` over `collectionSelectContext`, whose body `expanded` is the original collection's projection. The original collection was built with the outer `sequence` as its parent (`SelectManyBuilder.cs:47`), so `p.Value1` translates to a placeholder whose `SelectQuery` is the enclosing query. `DefaultIfEmptyContext.MakeExpression` (`:201-224`) builds it, `UpdateNesting(this, expr)` cannot move it (`ExpressionBuilder.QueryBuilder.cs:322-336` walks FROM/JOIN parents of `this.SelectQuery`; an enclosing query is not one, so the placeholder comes back unchanged), and `:211-224` returns it bare. The bare return relies on the outer join NULL-extending the value, which happens only to columns of the joined query.
- **M2, the marker.** `PrepareNoNullConditions` (`:19-58`) picks the "row exists" marker from every placeholder of the sequence's projection, outer ones included. A non-nullable outer value (`p.ParentID`) is chosen as the marker, so the marker is never NULL: `v == null` reads false on a missing row, and the one-row `DefaultIfEmpty()` branch (`:100-117`) aggregates the outer value (`DefaultIfEmpty().Max()` in a projection renders `MAX([p].[ParentID])`, which SQLite evaluates as an aggregate of the outer query and returns 1 row instead of 17).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Fix in the builder's `DefaultIfEmptyContext`, at the two sites of P1

- **chosen:** E-2 guards a placeholder that `DefaultIfEmptyContext.MakeExpression` cannot nest into its own query with the context's not-null conditions; E-1 keeps outer placeholders out of the marker candidates in `PrepareNoNullConditions`.
- **rejected:** (a) an optimizer guard in `JoinMoveSubQueryUp` (#6342's approach) — the value never passes through the join (P1 SQL), so there is nothing to attach to. (b) Routing the outer value as a column of the joined subquery (`CreatePlaceholder(this, placeholder.Sql, …)`) so the join NULL-extends it — the column would reference a sibling source inside an outer-joined derived table: on master `JoinMoveSubQueryUp` lifts such a column out without a NULL guard (the #6326 class; V32 is that failure reached by another route), and in a non-LATERAL LEFT JOIN the reference is out of scope (V17b's `no such column`), so the fix would depend on #6342 and on APPLY support. (c) Keeping `SqlDefaultIfEmptyExpression`'s guard in Sql purpose (`ExpressionBuildVisitor.cs:1994-1997`) and wrapping outer placeholders in it — the visitor cannot tell an own placeholder from an outer one, so it would guard every outer-joined column and move the corpus's baselines.
- **why this:** the context is the one place that knows both which query the sequence is and which marker proves the row exists; the guard is built from the existing `MakeNotNullCondition` idiom (`ProjectWithDefaultValue`, `:240-255`) and resolves through the same `not_null` special-property path that already works for V8.
- **failure mode of the choice:** when the sequence projects no own non-nullable column, the guard rests on the constant `not_null` marker, which Access and Oracle 11 do not NULL-extend (P1 grid V3/V6/V8): those providers still return the outer value on this model. A read that does not reach `MakeExpression` (V31's result selector) or a value that is already own (V32) is not covered. No input separates (b) from the chosen design on master alone; the choice stands on (b)'s dependency on #6342.

### D-2 — The guard's else-branch is `DefaultValueExpression(MappingSchema, type, isNull: true)`

- **chosen:** SQL `NULL`, client-side `default(T)` — the same as an own column NULL-extended by the join and read back, and the idiom `ExpressionBuildVisitor.cs:2015` uses for a forced default.
- **rejected:** `Expression.Default(type)` — renders `ELSE 0` for a non-nullable value, so `where v == 0` would match a missing row through an outer value but not through an own value of the same sequence (V35b).
- **why this:** one rule for every value of the element, own or outer (U-15).
- **failure mode of the choice:** a non-nullable outer value compares as SQL `NULL` in a predicate on a missing row, where LINQ to Objects sees `0` — exactly as an own non-nullable value does on master (V35a / V35b). No committed value test can separate D-2 from the rejected alternative without asserting the LINQ answer that own values also miss (P10 L-6).

### D-3 — Ownership test

- **chosen:** E-1 tests `EnumerateAccessibleSources(sequence.SelectQuery)` membership of `placeholder.SelectQuery` (pure, no columns created); E-2 tests `ReferenceEquals(placeholder.SelectQuery, SelectQuery)` after the `UpdateNesting` it already performs.
- **rejected:** calling `UpdateNesting(sequence, …)` in E-1 and comparing — it calls `MakeColumn` for every own placeholder of the projection, adding columns no consumer asked for.
- **why this:** both match `ParentInfo`'s FROM/JOIN tree (U-3); an own scalar-subquery column is classified own (U-14).
- **failure mode of the choice:** a placeholder whose query is own but sits outside the FROM/JOIN tree would count as outer. In E-2 that costs a redundant `CASE` (right value). In E-1 it removes the placeholder from the marker candidates; when it was the only non-nullable one, the marker becomes `not_null`, which Oracle 11 does not NULL-extend, so the value changes there; on Access (A-2) the misclassified sequence falls back to master's markers instead. No probed shape produced such a placeholder (V24 is the closest).

### D-4 — Access keeps master when the sequence has no non-nullable value of its own (A-2, replaces the A-1-era constant-marker fallback)

- **chosen:** with `IsAccessBuggyLeftJoinConstantNullability` and no own non-nullable placeholder, `PrepareNoNullConditions` picks the markers exactly as master did, over every placeholder including enclosing ones, and reports `guardsEnclosingValues = false`; E-2 leaves the enclosing value as it is. With an own non-nullable placeholder the fixed path applies.
- **rejected:** (a) the A-1-era design — own nullable placeholders as markers, or the constant marker when there are none — measured correct→wrong on matched rows holding a NULL in an own column (U-16, V40). Its gain was data-dependent: it fixed six Access variants on the shared data (V10, V13, V14, V21, V27, V30 — matched `GrandChild` rows hold no NULLs), and A-2 returns all six to master's wrong values (`p2/` → `f4/`). The option put to the user said so ("Access improves only for shapes with an own non-nullable column"). (b) returning `null` — `GetNotNullConditions` throws for `DefaultIfEmpty(x)` and the one-row branch (V8, V18).
- **why this:** the user's rule for a broken neighbour — it keeps master behaviour. Access has no reliable row-exists marker unless the sequence projects a non-nullable value, so the fix cannot be right there without one.
- **failure mode of the choice:** on Access these shapes keep master's wrong values for unmatched rows (and master's `v == null` answer); only sequences with an own non-nullable value are fixed. The separating input for the rejected (a) is TO-19.

### D-5 — Test scope `[IncludeDataSources(true, TestProvName.AllSQLite)]`

- **chosen:** the defect and the fix are in the provider-independent builder; the user's standing rule puts engine tests on SQLite. `true` keeps the `.LinqService` half, as the fixture's siblings do (`JoinOptimizeTests.cs:633-732`), so the new SQL also crosses the remote path. The other providers are measured by the probe grid (TO-15), not by committed tests: on this model Access and Oracle 11 would fail on the constant-marker engine limitation, which is not this fix.
- **rejected:** `[DataSources]` with Access / Oracle 11 gated — the gate would document the constant-marker defect, which deserves its own issue, not a gate on this branch.
- **failure mode of the choice:** no committed test sees Access, Oracle 11 or an APPLY provider, and no existing corpus test reaches E-2 (U-8), so the CI baselines cannot show the new SQL for any other provider either: their behaviour rests on the scratch grid (TO-15) alone.
