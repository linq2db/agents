## P1 Problem

On master, `Sql.Between` / `Sql.NotBetween` (`Source/LinqToDB/Sql/Sql.Between.cs:9-35`, 4 overloads) carry `[Sql.Extension("", "", PreferServerSide = true, IsPredicate = true, BuilderType = typeof(BetweenBuilder|NotBetweenBuilder))]`. The `ExtensionAttribute(string, string)` constructor also sets `ServerSideOnly = true` (`Source/LinqToDB/Sql/Sql.ExtensionAttribute.cs:454-460`). `ExpressionBuildVisitor.ConvertExtension` (`Source/LinqToDB/Internal/Linq/Builder/ExpressionBuildVisitor.cs:1279`) takes every `Sql.ExtensionAttribute` for a set function (`isSetFunction = attr is Sql.ExtensionAttribute || …`), and in a grouped projection roots the call at the `GroupByContext` (`:1300-1338`) and places it in the GROUP BY query (`:1341-1344`). Its operand (an aggregate, or a grouping key) is read as that query's own column from outside, so the predicate references a column of the subquery inside the subquery. It shows whenever a `where` over the grouping keeps the GROUP BY query as a subquery (a predicate `SelectQueryOptimizerVisitor` does not move to HAVING, such as `NotBetween`).

Failure mode 1 — invalid SQL (measured, master, SQLite.MS, probe 01):

```
from p in db.Person group p by new { p.FirstName } into g
where Sql.NotBetween(g.Sum(x => x.ID), 2, 3)
select new { g.Key.FirstName, InRange = Sql.Between(g.Max(x => x.ID), 1, 3) }

SELECT [g_2].[FirstName], [g_2].[InRange_1]
FROM (SELECT [g_1].[FirstName], SUM([g_1].[PersonID]) as [Sum_1], MAX([g_1].[PersonID]) as [InRange],
             [g_2].[InRange] BETWEEN 1 AND 3 as [InRange_1]
      FROM [Person] [g_1] GROUP BY [g_1].[FirstName]) [g_2]
WHERE [g_2].[Sum_1] NOT BETWEEN 2 AND 3
=> SqliteException: SQLite Error 1: 'no such column: g_2.InRange'
```

Same for `NotBetween(g.Max(…))` under a `Between` filter (probe 02, `no such column: g_2.OutOfRange`) and, on master, for `Sql.Between(g.Key.FirstName, "A", "K")` (probe 03, `no such column: g_2.FirstName`; the key case works on PR #6343's branch only). Target shape: the predicate at the outer level over the subquery's column — `[g_2].[InRange] BETWEEN 1 AND 3` — as `g.Max(x => x.ID) >= 1 && g.Max(x => x.ID) <= 3` already does.

Failure mode 2 — an operand without SQL form crashes (measured, master, probes 25/26): `Sql.Between(ClientOnly(p.ParentID), 3, 8)` throws `ArgumentNullException: Value cannot be null. (Parameter 'exp1')` in a projection and in a WHERE: `BetweenBuilder` passes the null operand from `builder.ConvertExpressionToSql(x)!` to `new SqlPredicate.Between(…)` (`Sql.Between.cs:41-42`).

## P3 Constraints & anti-goals (M/L)

- Public API outside `LinqToDB.Internal.*` keeps its signatures: the four methods swap `[Sql.Extension]` for `[ServerSideOnly]`; `BetweenBuilder` / `NotBetweenBuilder` are private. No new public or protected member (D-4), so no `PublicAPI.Unshipped.txt` entry; `PublicAPI.Shipped.txt:15472-15473,15557-15558` list the signatures only; `CompatibilitySuppressions.xml` untouched (no ApiCompat attribute rule configured — scout, P7).
- Generated SQL changes only for the shapes in the deltas below (A/B full-suite baselines, G-02).
- Anti-goal: the general fix for user-defined non-aggregate `[Sql.Extension]` functions over an aggregate (classifying an extension by its chain's `IsAggregate` / `IsWindowFunction`) — the PR body names it as remaining.
- Anti-goal: moving a `NotBetween` / `Between` filter to HAVING (`SelectQueryOptimizerVisitor` moves comparison predicates only).
- Anti-goal: anything from PR #6343's diff (`ConvertExtension` placement rules).
- Anti-goal: typing the bounds by the value operand's column descriptor (`UsingTypeFromExpression`), which `>=` / `<=` do — master does not (D-3).

User-visible deltas vs master (the PR body's *Behaviour change* is built from this list):

1. Fixed — `Between` / `NotBetween` over an aggregate or a grouping key in a grouped projection after a non-merged `where`: valid SQL (SC-1..3).
2. Fixed — an operand without SQL form: the projection is evaluated client-side (C# body) instead of throwing `ArgumentNullException`; a WHERE throws `LinqToDBException` instead of `ArgumentNullException` (SC-7, D-1, D-5).
3. Changed — D-2, a class: in a projection, any operand (value or bound) of a non-nullable scalar type read from an optional row is read as default(T), as the projection's own member is (`ReadsAsTheReaderReads` admits value types that are not nullable, not enums, and scalar, `ExpressionBuildVisitor.cs:2452-2461`). Measured instance: `Sql.Between(c.ChildID, 0, 100)` over a missed LEFT JOIN row returns `true` (`Coalesce([c_1].[ChildID], 0) BETWEEN 0 AND 100`) where master returned `false` (`CASE WHEN [c_1].[ChildID] BETWEEN 0 AND 100 THEN 1 ELSE 0 END` over NULL), matching `c.ChildID >= 0 && c.ChildID <= 100` (probe 27) and the projected `ChildID` value 0. The SQL shape changes with it (bare predicate instead of the `CASE`; the TO-6 baseline records it). `(int?)c.ChildID` keeps master's answer (probe 28). Deviation from the brief's "projected value must not change versus master" — accepted by the user (P10 L-5).

Shipped prose stating the old contract: none to edit. The four methods carry no XML doc. `Source/LinqToDB/Sql/Readme.md:7,16-17` lists them as built-in functions without naming the mapping; `docs/source/articles/how-to/teach-linq2db-convert-custom-net-code-to-sql.md:16-27` shows a user-written `[Sql.Expression]` Between, not a claim about the built-in one; `LinqOptions.cs:156-163` says members mapped `PreferServerSide` / `ServerSideOnly` stay in SQL, which `[ServerSideOnly]` keeps true for Between — except a call with an operand that has no SQL form, which is computed client-side (D-5; on master it threw).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Replace `[Sql.Extension]` with `[ServerSideOnly]`; the member translator is the only path

- **chosen:** delete the four `[Extension]` attributes and the private builders; mark the four methods `[ServerSideOnly]` (the property the `ExtensionAttribute` constructor gave them); register the four overloads in `SqlFunctionsMemberTranslatorBase`.
- **rejected:** keep the attributes as a fallback behind the translator (variant A). Same results as C on every probe except 25/26, where a declined call falls into `ConvertExtension` and throws `ArgumentNullException` exactly as master (`probe-A.txt`), and the buggy placement path stays reachable for every declined call. Separating input: an operand without SQL form → TO-7.
- **rejected:** remove the attributes with no marker (variant B). Between becomes client-evaluable over client values: probe 35 `!Sql.Between(null, 1, 3) ? "a" : "b"` folds at expose time to `a` where master answers `b`, and under `PreferClientCalculation = true` a conditional over Between moves client-side (probe 16). Separating inputs: TO-10 (probe 35's shape) and TO-8's conditional clause.
- **rejected:** fix the placement in `ConvertExtension` — PR #6343's territory and the general extension-classification fix (P3 anti-goals).
- **why this:** precedent — `Sql.Like` (`Source/LinqToDB/Sql/Sql.cs:464-491`) is translator-handled and marked `[ServerSideOnly]`; `Sql.NullIf`, `Sql.ToNullable`, `Sql.AsNullable` (`Sql.cs:71-102,175-188`) are translator-handled with no `[Expression]` attribute. A member translator translates operands in the current context, so an aggregate is read where the projection reads it (probes 01-03 on C).
- **failure mode of the choice:** `[ServerSideOnly]` is unconditional, unlike `Sql.Like`'s `#if !NETFRAMEWORK`: it keeps master's behaviour on every TFM, since the `[Extension]` attribute made Between server-side-only on every TFM. A call the translator declines is then evaluated client-side by its C# body in a projection (probe 25 on C) rather than failing; a provider that lost the registration would compute projected Betweens client-side silently — U-7 shows none does, and TO-8 goes red if the registration goes.

### D-2 — Operands read as the projection reads them (no exemption)

- **chosen:** translate operands with `ITranslationContext.Translate`, which in a projection reads a non-nullable operand of an optional row as default(T) (`ExpressionBuildVisitor.cs:5954-5969` → `ReadAsTheReaderReads` `:2432-2461`).
- **rejected:** exempt Between's operands (strip `BuildFlags.ValueOfProjection` for these calls as `ConvertExtension`'s `keepsSqlNull` does at `:1284-1286`, e.g. by listing them in `IsOperandOutsideDefaultDomain` `:2634`). It would keep master's value but re-encode, for these calls only, the "an extension is a set function" classification this change removes, and keep Between disagreeing with `x >= a && x <= b` and with the projected member itself (master probe 09: `{ChildID = 0, In = False}`). Separating input: Parent 5 (no children), bounds containing 0 → TO-6.
- **why this:** #5932's rule for a calculation of the projection (`BuildFlags.cs:25-27`); master's NULL-keeping for Between came from `isSetFunction` being true for every `ExtensionAttribute`, not from a decision about Between. An explicit `(int?)` cast still asks for the NULL (probe 28).
- **failure mode of the choice:** a user-visible value change (delta 3) for a projection over a missed optional row whenever default(T) lies in `[low, high]` (Between) or outside it (NotBetween). The brief asked for no value change against master; the user accepted the change (U-9, P10 L-5).

### D-3 — Operands are translated with the column descriptor reset, as master does

- **chosen:** `using var disposable = translationContext.UsingColumnDescriptor(null);` around operand translation: the descriptor of where the call stands (an assignment target, a compared column) types the call's boolean result, not its operands.
- **rejected:** no descriptor handling — measured leak in direct positions (U-4): constant bounds become parameters of the target column (`BETWEEN @YN AND @YN_1`). Separating input: TO-11 (literal bounds under a converter-mapped target); mutation `between-no-descriptor-reset` turns it red.
- **rejected:** reset only a descriptor carrying a converter or unit, as `StringMemberTranslatorBase.UsingUnicodeTypeFromOperand` does (`StringMemberTranslatorBase.cs:270-282`) — there the result is a string of the operand's kind and a plain descriptor is lent on purpose; a Between result is never a value of the target column, so no descriptor applies to the operands, which is master's `columnDescriptor: null` (`ExpressionBuildVisitor.cs:1414-1423`).
- **rejected:** type the bounds from the value operand (`UsingTypeFromExpression(methodCall.Arguments[0])`, as `TranslateLike` does at `StringMemberTranslatorBase.cs:282`) — a behaviour change master does not make (P3 anti-goal).
- **failure mode of the choice:** `Sql.Between(r.Cents, 1, 6)` over a converted column keeps comparing the stored value to unconverted bounds, as master (probe 30).

### D-4 — Home and surface: private handlers in `SqlFunctionsMemberTranslatorBase`

- **chosen:** two private handlers plus one static helper; no `protected virtual` hook.
- **rejected:** a `protected virtual` hook like `TranslateNullifMethod` (`SqlFunctionsMemberTranslatorBase.cs:59`) — new public surface with no consumer: `BETWEEN` renders in `BasicSqlBuilder.cs:2766-2774`, and the row form is lowered per provider in `SqlExpressionConvertVisitor.VisitBetweenPredicate` (`:1512-1519`).
- **rejected:** `StringMemberTranslatorBase` next to `TranslateLike` — Between is not string-specific.
- **failure mode of the choice:** a provider wanting a different Between must re-register the methods instead of overriding a hook; none needs one today.

### D-5 — Decline with `null` when an operand has no SQL form

- **chosen:** return `null` from the handler.
- **rejected:** `CreateErrorExpression` (as `TranslateLike` / `TranslateNullifMethod` do) — `TranslateMember` would take the error as a translation (`ExpressionBuildVisitor.cs:6187-6196`), so the projection arm of TO-7 would fail instead of evaluating the C# body; G-01 records the mutation that measures it.
- **why this:** a member translator declines rather than refuses; the WHERE arm still fails with `LinqToDBException` from the generic path (probe 26 on C).
- **failure mode of the choice:** a projection that cannot be translated is computed client-side silently; for these methods the C# body is their documented meaning, so the value is the C# answer.
