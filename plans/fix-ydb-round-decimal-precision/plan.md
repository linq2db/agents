## P1 Problem

`YdbMemberTranslator.RoundScaledAs` rounds a Decimal by scaling it by 10^p in a widened Decimal type, then `CAST(... AS Double)`, `Math::NearbyInt` / `Math::Round`, and back through `Text` to Decimal. A Double carries ~15-17 significant digits, so the rounding is silently wrong whenever the scaled value has more. Measured on local YDB (net10.0), `Decimal(22,9)` column, both midpoint modes, at PR head `153a68af7` vs master's `YdbMemberTranslator.cs`:

| value, precision | expected | PR head | master |
|---|---|---|---|
| `900719925474.09931`, 4 | `900719925474.0993` | `900719925474.0994` (silent) | `PreconditionFailed` (overflow) |
| `123456789012.34567`, 5 | `123456789012.34567` | `123456789012.34568` (silent) | `PreconditionFailed` (overflow) |
| `12345678901.234999999`, 2 | `12345678901.23` | `12345678901.24` (silent) | `12345678901.24` (silent) |
| `1234.56789`, 4 (control) | `1234.5679` | correct | correct |

Rows 1-2 are a regression introduced by the PR's widening (loud failure becomes a wrong value); row 3 is pre-existing on master (significant digits, not magnitude). The same Double step serves the no-precision path (`Math.Round(d)`), so `1234567890123.499999999` is expected to round to `...124` there too (unprobed, TO-5 settles it).

## P2 Success criteria

- SC-1 Constant-precision rounding of a Decimal whose scaled value exceeds 2^53 returns the exact result in both modes (rows 1-2 above). → TO-1
- SC-2 Constant-precision rounding of a Decimal with more than ~15 significant digits returns the exact result in both modes (row 3 above). → TO-2
- SC-3 Midpoint semantics are exact at high significance: to-even and away-from-zero disagree on exact ties and each returns its own answer, both signs. → TO-3
- SC-4 The runtime-precision path (`Sql.Round(d, r.P)` / `Sql.RoundToEven(d, r.P)`) is exact on the same inputs, positive and negative precision. → TO-4
- SC-5 The no-precision path (`Math.Round(d)`, `Sql.Round(d)`) is exact for a Decimal with more than ~15 significant digits. → TO-5
- SC-6 A Decimal column in the scaffolded shape `DbType = "Decimal(6, 2)", Precision = 6, Scale = 2` rounds exactly: the computed CASTs render their own precision/scale, not the `DbType` string (narrowed by A-1; `DbType`-only columns are out of scope, P10). → TO-6
- SC-7 No regression: every existing YDB rounding test stays green; rounding of `double` values on YDB emits byte-identical SQL. → TO-7, TO-8
- SC-8 The strategy comment above `TranslateRoundToEven` describes the new algorithm (D-1, D-2). → TO-9
- SC-9 (A-7) Rounding a Decimal to a precision below −(integer digits), constant or runtime, returns 0 (NULL for NULL) in the value's inferred type, and a computed value too large for that answer fails instead of returning 0. → TO-14
- SC-10 (A-8) Rounding a Decimal with neither declared Precision nor Scale (a computed value) is exact, both modes, for a real scale above the inferred 9 up to D-8's work scale: 22 with no precision (or constant 0), `22 − p` for a constant `0 < p < 9`, `22 − |p|` for a constant negative precision, 13 for a runtime `0 ≤ P ≤ 9`; a constant `p ≥ 9` and a runtime `P > 9` keep the head's results, and a real scale past the work scale is cut (P10). → TO-15

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Round a Decimal exactly with a scale-narrowing CAST

- **chosen:** in `RoundScaledAs`, for a Decimal value, replace the Double round-trip with `even = CAST(CAST(scaled AS Decimal(Pw,0)) AS scaleType)`, both casts mandatory. When `(scaleType.Scale ?? DEFAULT_DECIMAL_SCALE) == 0` the scaled value is already integral and is returned as is (the no-precision path passes the value's own type, whose Scale can be null).
- **rejected:** (a) cap the widened integer digits at 15 so rows 1-2 fail loudly again — leaves row 3 (master's class) wrong and turns now-correct values back into failures; (b) truncate with Decimal `%` and compare the residue — `%` on Decimal is a commented-out rewrite area in `YdbSqlExpressionConvertVisitor` (KB `PROV-YDB` INDEX) and needs sign handling the CAST gets for free; (c) `CAST(Decimal AS Int64)` — also half-to-even (probe: 2.5→2, 3.5→4) but caps at 18 digits and `YdbSqlExpressionConvertVisitor.cs:369-380` rewrites Decimal→integer through Double, reintroducing the defect.
- **why this:** one YQL primitive, measured exact (U-1), no Double anywhere, keeps the PR's widening intact for declared types (A-8's D-8 resizes it for values with no declared Precision/Scale).
- **failure mode of the choice:** correctness rests on YQL's narrowing-CAST rounding rule; a YDB build that truncated instead would make to-even silently wrong. TO-3's ties discriminate it (truncation turns `...123.5` into `...123`, which is even's answer only for even integers — the odd-integer tie rows go red).

### D-2 — Away-from-zero by tie detection, adjusting in the integer type

- **chosen:** `evenI = CAST(scaled AS Decimal(Pw,0))`, `even = CAST(evenI AS scaleType)`, `diff = even - scaled`. If `diff = -0.5 AND scaled > 0` the result is `CAST(evenI + 1 AS scaleType)`; if `diff = 0.5 AND scaled < 0` it is `CAST(evenI - 1 AS scaleType)`; otherwise `even`. The ±1 is done in `Decimal(Pw,0)`, which has spare integer digits, so every overflow still surfaces through a CAST exactly as today.
- **rejected:** `scaled ± 0.5` in `scaleType` then round — needs a truncation primitive YQL lacks (CAST rounds), and YQL Decimal `+` overflow behaviour at the type maximum is unprobed.
- **why this:** away-from-zero differs from to-even only on an exact tie that to-even resolved toward zero; detecting that in exact Decimal arithmetic needs only U-6's operations.
- **failure mode of the choice:** a longer SQL expression (nested condition → `CASE`). The separating input is an exact tie on an even integer part (`...122.5` → even `...122`, away `...123`); TO-3 carries it, and the mutation "drop the tie branches" turns its away rows red.

### D-3 — Both rounding casts are mandatory

- **chosen:** `factory.Cast(..., isMandatory: true)` for `scaled → Decimal(Pw,0)` and `Decimal(Pw,0) → scaleType`.
- **rejected:** default non-mandatory casts — the optimizer folds the pair back to `scaled` (U-2) and the rounding vanishes silently.
- **why this:** `QueryHelper.cs:1953-1961` documents mandatory as the way to keep a semantically required cast.
- **failure mode of the choice:** a mandatory cast to an identical type would survive as a redundant CAST; excluded by the `scale == 0` short-circuit, which is the only case where `Decimal(Pw,0)` equals `scaleType`. Mutation "isMandatory: false" must turn TO-1/TO-2 red.

### D-4 — Strip `DbType` from the computed intermediates (narrowed by A-1)

- **chosen:** the integer type and `ScaledDecimalType`'s result are built without `DbType` (a new `DbDataType(SystemType, DataType, null, Length, P, S)`), so the CASTs render the computed `Decimal(P,S)`. The final narrowing cast back to the value's own type keeps its `DbType`. Precision/Scale are taken from the mapping only; a `DbType` string is never parsed (A-1).
- **rejected:** (a) keep `DbType` — the integer CAST and the widening CAST render the source type, so a scaffolded column (`DbType` + `Precision` + `Scale`) is not rounded at all; (b) parse P/S from a `Decimal(p,s)` `DbType` (rounds 1-3; implemented and measured green, reverted) — type inference from `DbType` is a known gap the user defers to the v7 mapping redesign; (c) decline when `DbType` is set and P/S are incomplete — rejected by the user for the same reason.
- **why this:** the computed types are internal intermediates; only the value's own type is user-facing, and the scaffolder always emits `Precision`/`Scale` beside `DbType`.
- **failure mode of the choice:** a `DbType`-only column with a declared scale above 9 is widened from the `(22,9)` defaults and silently rounded by the widening cast (P10, accepted). The separating input for the kept behaviour is TO-6a (red at head with `Decimal(6,2) != Decimal(7,2)`).

### D-5 — `double` values keep the Double path

- **chosen:** the change is gated on `isDecimal`; the `roundToInt` lambdas remain for doubles.
- **rejected:** one path for both — a double has no exact Decimal form to round, and changing its SQL is outside P3.
- **why this:** keeps SC-7's symmetry guard meaningful.
- **failure mode of the choice:** two code paths in one method; TO-8 guards the unchanged one.

### D-6 — Truncate a Decimal to an integer exactly (A-6)

- **chosen:** in `YdbSqlExpressionConvertVisitor.ConvertConversion`, a cast from a Decimal of scale `S` (`?? DEFAULT_DECIMAL_SCALE`) to an integer type: `S == 0` → the base cast, unchanged (exact, and the re-visit guard of U-18); `S == P` or `UseParametrizedDecimal == false` → the existing Double route (`S == P` is conservative: U-16 refuses only `(35,35)→(35,0)` among the shapes D-6 would emit, but `|x| < 1` truncates to 0 exactly through Double anyway); otherwise, with `Decimal(35,S)` / `Decimal(35,0)` built without `DbType` as `new DbDataType(SystemType, DataType, null, Length, 35, S|0)` (as `RoundDecimal` does, `YdbMemberTranslator.cs:853`, D-4 — a `DbType` would render verbatim, U-3), `w = CAST(x AS Decimal(35,1))`, `r = CAST(w AS Decimal(35,0))`, `back = CAST(r AS Decimal(35,1))`, all mandatory, then `CAST(CASE WHEN x > 0 AND back > x THEN r - 1 WHEN x < 0 AND back < x THEN r + 1 ELSE r END AS <int>)` — truncation toward zero from the half-to-even CAST (U-1). The comparisons read the value itself, not `w` (A-7). `w` may round, but `|w − x| ≤ 0.05` and `|r − w| ≤ 0.5` put `r` on one of the value's two neighbouring integers, and comparing that integer with the value picks the truncation (U-21, U-22). Scale 1 rather than the inferred S (A-7 round 2): an inferred S above 16 (`SUM` typed `Decimal(31,18)`, U-24) would leave `w` fewer integer digits than an Int64 needs; `Decimal(35,1)` keeps 34, and `(P,P) → (35,1)` is accepted (U-16: `(35,35) → (35,1)`).
- **rejected:** (a) skip the hop only when the source is known integral (a Round result) — the Round result is cast back to the value's own scale, so the cast cannot see it, and `(long)d` is wrong the same way (U-17); (b) `CAST(Decimal AS Int64)` directly — half-to-even, not truncation (D-1 rejected (c)); (c) pin to the source's own `Decimal(P,S)` — a computed value's YQL type can be wider (A-3), and narrowing it to the inferred precision overflows where the Double route answered; (d) compare against the pinned `w` (the A-6 design) — the pin's rounding then decides the result (U-21, measured `2.999999999998` → `3`); (e) no pin at all (3fb89d062) — a computed value whose YQL type is `Decimal(P,P)` reaches `CAST(… AS Decimal(35,0))`, which YQL refuses (U-26, measured on `(long)(F * F)`).
- **why this:** the same YQL primitives as D-1/D-2, measured exact; the arithmetic (`r ± 1`) is all `Decimal(35,0)`, comparisons tolerate mixed types (U-22), and `Decimal(P,P) → Decimal(35,S ≥ 1)` is accepted (U-26); the excluded shapes keep today's behaviour, so nothing that works now starts failing. Only a value needing more than 34 integer digits overflows `w`, far past any integer target.
- **failure mode of the choice:** every Decimal→integer cast on YDB renders a `CASE` over casts instead of one Double hop (SQL size, baselines move — P7). Separating inputs: TO-13 (odd integer parts past 2^53, both signs; `(long)(H + H)` over `Decimal(20,12)`; `(long)(F * F)` over `Decimal(4,4)`); mutation "drop the ±1 branches" turns its `(long)` rows `9007199254740993.75`, `-9007199254740993.75` and `12345678901234567.50` red; mutation "compare against `w`" turns its `H + H` rows 1-2 red; mutation "no pin" turns its `F * F` column red.

### D-7 — A precision below −(integer digits) rounds to 0 (A-7)

- **chosen:** in `RoundScaled`, for a Decimal value with `intDigits = max(P − S, 0)` (defaults `(22,9)`; a `Precision`-only mapping such as `(5,9)` has none rather than −4): a constant precision `p < −intDigits` returns `RoundedToZero`; a runtime precision is wrapped as `CASE WHEN p < −intDigits THEN RoundedToZero ELSE <the A-6 sign branch, unchanged> END` (only the taken branch is evaluated, U-25). `RoundedToZero = CAST(Ensure(value − value, (value < B AND value > −B) OR value IS NULL, 'ROUND value is out of range for Decimal(P,S)') AS <value's inferred type>)`, the cast mandatory like every other Round exit's narrowing (`value − value` carries the value's real YQL type, which `IF` and arithmetic would reject beside the inferred one, U-22), with `B = 10^min(intDigits, 28)` as a `Decimal(35,0)` literal. `ScaledDecimalType`'s comment is corrected to "running out of integer digits fails the values that no longer fit rather than misrounding them".
- **rejected:** (a) leave it — values from 10^(35−S−|p|) up fail although the answer is 0 (U-23); (b) clamp p to −intDigits — `Round(9.9·10^12, −13)` is 10^13, not 0; (c) fold without the guard — a computed value can exceed its inferred integer digits (U-24), so `Round(D * D, −14)` would answer 0 for 10^28; (d) bound by `0.5·10^−p` (exactly the "rounds to 0" condition) — a C# `decimal` literal cannot hold it past 10^28, and a runtime precision would need it computed at run time.
- **why this:** every value of the inferred type is below 10^intDigits ≤ 0.1·10^−p, so 0 is exact for it; B ≤ 10^intDigits ≤ the true half-bound, so the guard never lets a non-zero answer through — it can only fail loudly where 0 was right (a value of a type with more than 28 integer digits, or a computed value between B and the half-bound).
- **failure mode of the choice:** a computed value above B fails the query instead of rounding (U-24, measured with `Round(D * D, −14)`). Separating inputs: TO-14 (`Round28` rows from 1.5 to 9999999999999.999999999, both signs, NULL; `Round23` rows at −14/−20 on the runtime path; the `D * D` guard row; `Round(D * D, −14) + D22s9`, red without the cast; `Round29`'s runtime row over a computed value).

### D-8 — A Decimal with no declared scale is sized as if its scale were as wide as its integer digits allow (A-8)

- **chosen:** in `RoundScaled`, a Decimal value whose `valueType.Precision` and `valueType.Scale` are both null ("inferred": computed values, and columns mapped with neither `Precision` nor `Scale`, U-29) gets its own work types, with `i = 13` and `S = 9` the integer digits and scale of the `(22,9)` defaults; every type is built without `DbType` like `ScaledDecimalType`'s. A `Precision`-only mapping (`[Column(Precision = 30)]`) is not inferred: its real type is `(P, 9)` end to end (DDL, writes, reads), so it keeps today's sizing (critic round A-8 2: keyed on `Scale` alone, `i = 21` gave it a scale-6 work type at `p = 8`):
  - no precision, and a constant `p = 0` (which `hasPrecision` already routes to the no-precision path, `YdbMemberTranslator.cs:754`; the key is `hasPrecision`, not `precision == null`): `scaleType = Decimal(35, 35 − i)`, so A-3's mandatory pin no longer cuts the scale;
  - constant `0 < p < S`: `scaleType = Decimal(35, 35 − i − p)` (scale ≥ 14 > p for `i = 13`) instead of `ScaledDecimalType`'s `(i + p + S, S)`;
  - constant `−i ≤ p < 0`: `scaleType = Decimal(35, 35 − i)` (`S − p ≤ 22`, so `10^p` fits); D-7 still answers `p < −i`;
  - runtime: `positiveType = Decimal(35, 35 − i − S)` (`(35,13)`) instead of `(i + 2S, S)`; the clamp of the positive branch to `S` is kept; `negativeType` is already `Decimal(35, 35 − i)`;
  - constant `p ≥ S`: the head's no-op shortcut is kept (user decision, A-8 option A).
  Every result is still narrowed to `valueType`, so A-7's shapes are unchanged. Declared types keep today's sizing exactly.
- **rejected:** (a) pin to the inferred `(22,9)` (A-3, head) — measured wrong (U-28); (b) for constant `p ≥ S`, round in `Decimal(35, 35 − i − p)` — its scale falls below `p` from `p = 12` (cuts a value the no-op answered right), reaches `Decimal(35,0)` at `p = 22` (rounds to an integer) and a negative scale past it (critic round A-8); (c) for constant `p ≥ S`, pin to `(35,22)` then CAST directly to `Decimal(35, p)` with the tie correction — exact for real scale ≤ 22, but the result cannot be narrowed to `valueType`, so `Round(<computed>, p) + <operand>` that works at head fails loudly, and it redesigns D-1 for that path (user chose option A over it); (d) fail a runtime `P > S` with `Ensure` — loses the head's correct answer for every computed value whose real scale is ≤ 9, the common case (critic round A-8); (e) treat only computed values as inferred (`GetDbDataTypeWithoutSchema(value).DataType == Undefined`) — an undeclared column also has null scale, and its real type is whatever the table has.
- **why this:** the inferred `(22,9)` is a guess at the value's precision, not a fact; where the answer fits the inferred type (no precision, `p < S`, `p < 0`, runtime `P ≤ S`), the widest scale the inferred integer digits leave in 35 is the most real scale one work type can carry, at no cost in integer digits; where it does not (`p ≥ S`), the head's behaviour is kept rather than trading a silent cut for a loud failure in arithmetic.
- **failure mode of the choice:** a real scale above the work type's (`35 − i − p`, `35 − i`, or 13 on the runtime positive branch) is still cut before rounding; a constant `p ≥ 9` over a real scale above `p` returns the value unrounded, and a runtime `P > 9` over a real scale above 9 rounds to 9 places (both as at head, P10); a computed value past the inferred 13 integer digits still overflows loudly, as today (U-24). Separating inputs: TO-15.

- A rounding carry past the declared precision at the type's maximum (`Math.Round(9999.99m, 1)` on `Decimal(6,2)`) still overflows: through `Unwrap` it fails the query for a non-null value, and for a nullable value the CAST yields NULL. Pre-existing, write side, outside P3; filed as a follow-up issue rather than fixed here.

Its intermediates are sized from the `(22,9)` defaults, so with a declared scale above 9 the widening cast rounded the value silently (critic round 1: `Decimal(30,15)` `1.234999999999995` at p=2 → `1.24`), where PR head failed with a different-decimals error.
