## P1 Problem

[#6182](https://github.com/linq2db/linq2db/issues/6182). A projection member defined by a window function, read through a `GroupJoin` (`join … into`), is re-translated at the level of whoever reads it instead of at the level that defined it. Mechanism (measured with probes in `HandleRoot` and `TranslateRowNumber`, SQLite.MS): `GroupJoinBuilder.BuildMethodCall` (`GroupJoinBuilder.cs:22-44`) builds its result `SelectContext` directly over the raw outer context, so the result body's `q` is `Ref(<outer SelectContext>)`. A consumer that wraps the GroupJoin in a `SubQueryContext` (`SelectManyBuilder.cs:37`, `ExpressionBuilder.SqlBuilder.cs:63`) resolves the root of `x.q` with `ProjectFlags.Root`, which `SubQueryContext.MakeExpression` passes through unchanged (`SubQueryContext.cs:99-104`), so `FoundRoot` is the raw outer `SelectContext`; `MakeWithCache` (`ExpressionBuildVisitor.cs:1559`) then hands back `Rank`'s defining expression `Sql.Window.RowNumber(...)`, and `Visit` translates it in the consumer's context — `WindowFunctionsMemberTranslator` places it on `translationContext.CurrentSelectQuery`. Every working shape (explicit `SelectMany`, `Join`, `Select`) had a `SubQueryContext` as the root instead. Two observable failure modes:

- **FM-1, throws:** a `where` on the window value after the join builds `ROW_NUMBER() OVER (PARTITION BY t12.ParentID ORDER BY t12.ChildID DESC) <= 1` in the outer WHERE, and `BuildWhere` refuses it (`ExpressionBuilder.SqlBuilder.cs:82-86`): `LinqToDBException: … 'q.Rank <= 1' could not be converted to SQL. Additional details: 'Window functions cannot be used in search condition.'` Reproduced for `GroupJoin` + `SelectMany(DefaultIfEmpty)` (the issue's shape, with and without an inner left join in `query`) and for `GroupJoin` alone (`where q.Rank <= 1 select new { …, pj.Count() }`).
- **FM-2, silent wrong values:** projecting the window value after a row-multiplying left join computes `ROW_NUMBER()` over the joined rows. Parent ranked by `ParentID`, left-joined to Child: 18 rows, ranks `1..18` instead of each parent's own rank `1..7` — 16/18 rows wrong on SQLite.MS and SQLite.Classic.

Controls that already work on master: the same `query` with an inner `join … on` (no `into`), an explicit `from p in db.Parent.Where(…).DefaultIfEmpty()`, and `select new { q } into x where x.q.Rank <= 1`.

## P2 Success criteria

- SC-1 The issue's shape — window value in `query` (with an inner left join), outer `join … into` + `DefaultIfEmpty()`, `where q.Rank <= N` — translates and returns, per row, exactly the rows whose window value satisfies the predicate over `query` alone. → TO-1
- SC-2 Projecting the window value after a row-multiplying `join … into` + `DefaultIfEmpty()` returns, on every row, the value computed over `query` alone. → TO-2
- SC-3 `where` on the window value directly after a `join … into` with no `SelectMany` translates and returns the correct rows and group counts. → TO-3
- SC-4 Across the test suite, GroupJoin queries whose outer projection has no window or aggregate value generate byte-identical SQL to master; an aggregate outer may change table aliases only. Outside the suite (`A-3`), with or without an aggregate, shapes that mark or read the GroupJoin result's query now generate the `Select` form's SQL. → TO-5, TO-5b
- SC-7 `AsSubQuery().SubQueryHint(…)` on a GroupJoin result puts the hint inside the subquery, where the `Select` form puts it (`A-3`). → TO-7

- SC-6 `ConcatenateOrderBy` still prepends an `OrderBy` placed before a `GroupJoin` to a later `OrderBy`. → TO-4b

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Put the subquery boundary in `GroupJoinBuilder`

- **chosen:** `GroupJoinBuilder.BuildMethodCall` wraps the built outer sequence in a `SubQueryContext` before preparing the outer key, the `GroupJoinInnerContext` and the result body — the shape every sibling join builder already has (`JoinBuilder.cs:46`, `AllJoinsLinqBuilder.cs:77`, `SelectManyBuilder.cs:37`, `SelectBuilder.cs:42`). `q` then resolves to the wrapper, whose `MakeExpression` builds `Rank` inside the outer and lifts it as a column (`SubQueryContext.cs:99-122`).
- **rejected A:** in `ExpressionBuildVisitor.VisitMember`, translate a member expansion that contains a set function inside the context that defined it, then lift it — the job `SubQueryContext` already does for the other builders. It runs on every member access, needs a translation to discover the set function, and fixes all callers to compensate for one builder that skips the boundary.
- **rejected B:** stop `ProjectFlags.Root` resolution at a `SubQueryContext` whose inner root is a `SelectContext` on another query. Root resolution through subqueries is relied on by table, association and CTE lookups (`P7`); whole-product blast radius for a one-builder defect.
- **rejected C:** wrap only when the outer projection contains a window/aggregate value. Needs the projection translated before the builder decides, and leaves two GroupJoin shapes to maintain; the unconditional wrapper costs nothing in SQL when the optimizer removes it (`U-1`). `A-3`: true for the test suite only — shapes that mark or read the sequence's query (`AsSubQuery`, `SubQueryHint`, `DistinctBy`, `Update`) or a limited outer with an aggregate now get the `Select` form's SQL.
- **why this:** the defect is the outlier builder, not the consumers; the fix restores the invariant the others share.
- **failure mode of the choice:** every GroupJoin gains a subquery level. If the optimizer cannot collapse it for some outer shape, SQL changes for queries with no window value — caught by `TO-5` / `G-02` for the test suite; untested shapes measured and listed in `A-3`.

### D-2 — `IsSelectWrapper = true` on the wrapper

- **chosen:** mark the wrapper `IsSelectWrapper`, as `SelectBuilder` does. The GroupJoin result selector is a projection over the outer, and the walks that look through projections — `GetOrderSequence` (`Select((x, i) => …)`), `ConcatenateOrderBy`, the legacy aggregation-root walk — step through select wrappers only.
- **rejected:** a plain `SubQueryContext` (the `JoinBuilder` shape). `GetOrderSequence` would stop at it (`SequenceHelper.cs:834-843`), find an empty `ORDER BY` on the wrapper's query, and `Select((x, i) => …)` after `OrderBy(…).GroupJoin(…)` would fail with `Error_OrderByRequiredForIndexing` where master shares the outer's query and finds the `ORDER BY` at once.
- **why this:** keeps the reach of every projection walk equal to master's, except the legacy aggregation-root walk (`P7` row 1), which now matches `Select` over `GroupBy`.
- **failure mode of the choice:** the legacy walk in `ConvertExtension` now reaches a `GroupByContext` behind a GroupJoin and sets `findAggregationRoot = true` for a non-aggregate `Sql.Extension` call in the result selector — a behaviour change master did not have. Discriminating inputs for D-2 vs a plain wrapper, measured with the mutation "IsSelectWrapper = false" (playground, SQLite.Classic + SQLite.MS): `OrderByDescending(ParentID).GroupJoin(…).Select((x, i) => …)` fails with `For retrieving index of row, specify OrderBy part.` (green on master and with the chosen wrapper) → `TO-4`; `OrderBy(ParentID).GroupJoin(…).OrderByDescending(ChildID)` under `UseConcatenateOrderBy(true)` loses the first key and returns rows `7/77, 6/66, …` instead of `1/11, …` (green on master and with the chosen wrapper) → `TO-4b`.

### D-3 — No alias and no `BuildExtractExpression` on the wrapper

- **chosen:** do not call `SetAlias` or `BuildExtractExpression` (both of which `SelectBuilder.cs:39-43` does; `JoinBuilder.cs:121` and `AllJoinsLinqBuilder.cs:94` call `SetAlias` but not `BuildExtractExpression`). GroupJoin set no alias before, and `SubQueryContext.SetAlias` also renames the inner sequence (`SubQueryContext.cs:46`). The decision rests on the measured A/B (`U-1`): without either call, no baseline moves outside the two alias-only aggregate-outer files.
- **failure mode of the choice:** where the wrapper survives in SQL (window shapes only, `U-1`) it carries a generated alias (`t1`) rather than the range variable's name. Alias propagation into an aggregate outer still changes (`U-1`, measured: `g_1`→`p1`, `elements_1`→`q`). Mechanism reasoned, unprobed: `SelectContext.SetAlias` names the single FROM table of its own `SelectQuery` (`SelectContext.cs:219-227`), and the GroupJoin `SelectContext`'s query is now the wrapper's, one level above the outer's. Cosmetic; accepted (`P3`).
