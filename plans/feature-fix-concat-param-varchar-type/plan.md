## P1 Problem

Split out of #5673 review finding MAJ004. On SQL Server, a closure parameter concatenated with a column mapped `DataType.VarChar` is sent as non-Unicode, so non-Latin text comes back as `?`. Measured on master `12bc7fe140`, SqlServer.2019.MS (CI-equivalent `Latin1_General` collation), new tests in `Tests/Linq/Linq/StringConcatTests.cs` (`.build/.agents/concat-red-master.log`, `.build/.agents/concat-red2-pg.log`):

- projection `Sql.AsSql(p.Sku + suffix)` with `suffix = "Жук"` → `A-100???` (`DECLARE @suffix VarChar(20) -- AnsiString`, `[p].[Sku] + Coalesce(@suffix, '')`); `suffix + p.Sku + suffix` → `???A-100???`; `string.Concat(p.Sku, suffix)` → `A-100???`. SQLite returns the right text.
- predicate `p.Title(NVarChar) == p.Sku + suffix` and `p.Sku + suffix == p.Title` → no rows (expected row 1).
- IN list `titles.Contains(p.Sku + suffix)` → no rows (expected row 2): the list values are already `N'…'`, the concat is varchar.

The same shapes over an NVarChar column, and `string.Join` / `string.Concat(array)` / `$"{p.Sku}{suffix}"` over the VarChar column, already send `NVarChar` (probe trace `.build/.agents/concat-unicode-probe.SQLite.MS.txt` for SQLite; SQL Server master trace in `concat-red-master.log` — the SQL Server probe file was later overwritten by mutation runs).

Two mechanisms, both probed:

1. **Translator:** string `+` is offered to the member translators first (`ExpressionBuildVisitor.VisitBinary :3440` → `TranslateMember`); `StringMemberTranslatorBase.TranslateBinaryStringConcat` forwards to `TranslateConcat`, which runs `translationContext.UsingTypeFromExpression(arguments)` (`StringMemberTranslatorBase.cs:234` on master, from #5504 `de4d000024`): the first operand with a column descriptor becomes current for every fragment. `HandleBinaryMath` (named in the hand-off brief) is unreachable for a column-bearing string `+` — `VisitBinary :3487-3498` (confirmed by the round-1 critic).
2. **Typing walk:** a comparison types both sides from the left operand's suggestion (`ConvertCompareExpression :4640` → `SuggestColumnDescriptor(left, right) :3372-3382`), and for a concat that suggestion is `QueryHelper.GetColumnDescriptor`'s `SqlConcatExpression` arm (`QueryHelper.cs:645-655` on master), which returns the first operand's descriptor with no `forTyping` guard — so `p.Sku + suffix == p.Title` re-types `suffix` from `Sku` even without mechanism 1 (mutation M3).

A string literal beside the column also gets VarChar at build time but renders `N'…'` on master because `SqlExpressionOptimizerVisitor.VisitSqlConcatExpression :1290` re-mints folded string constants as plain string; #5673 owns that re-mint.

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — a concat fragment takes a sibling column's type only when that type is Unicode

- **chosen:** `TranslateConcat` replaces `UsingTypeFromExpression(arguments)` with a local helper that pre-translates each operand, looks up `QueryHelper.GetColumnDescriptorForTyping`, and makes current the first descriptor whose completed `DataType` is `NChar`/`NVarChar`/`NText`; any other (non-Unicode string, non-string, none) leaves the enclosing descriptor in place. User's choice ("B'"), 2026-10-27.
- **rejected (B, drop the scope entirely):** on Oracle the default string type is `VarChar(255)`, so `select x.Name(NVarChar2) + p` would move from `NVarchar2` to `Varchar2`, losing non-Latin text in a database whose charset is not Unicode (the setup `NVARCHAR2` exists for). Separating input: `p.Title + suffix` — B sends `NVarChar(4000)` on SQL Server, B' sends `NVarChar(40)` (mutation M1, TO-4).
- **rejected (A, `UsingColumnDescriptor(null)`):** a concat with a column compared with an indexed VarChar column becomes an nvarchar comparison (`CONVERT_IMPLICIT` on the column, no seek under SQL collations). Separating input: the join of TO-5 — A sends `NVarChar(4000)` (mutation M2).
- **rejected:** fix it in the optimizer re-mint — reaches literals only, and belongs to #5673.
- **why this:** it removes exactly the non-Unicode inheritance (the hand-off brief's wording), keeps master on every Unicode-sibling cell, and keeps comparison/assignment typing — and so index use — as on master.
- **failure mode of the choice:** under a comparison or assignment with a VarChar column, a non-Latin parameter fragment is still sent as VarChar (P10 L-1). A projection into a mapped entity member declared VarChar still types the fragment from that member (P10 L-2). A Unicode sibling still lends its `ValueConverter` (master behaviour).

### D-2 — the typing walk takes a concat's type only from a Unicode operand column

- **chosen:** in `QueryHelper.GetColumnDescriptor`'s `SqlConcatExpression` arm, under `forTyping`, skip operand descriptors whose completed `DataType` is not `NChar`/`NVarChar`/`NText`; return the first Unicode one, else `null` so the other side of the comparison types it. User's choice ("(a)"), 2026-10-27.
- **rejected (narrow SC-2 to "column on the left"):** leaves `p.Sku + suffix == p.Title` returning no rows (measured red on master and under M3).
- **rejected (refuse any descriptor for a concat under `forTyping`):** `p.Name + "x" == key` would type `key` with the default type — `VarChar(255)` on Oracle, losing `NVarchar2` (same Oracle argument as D-1's B). Separating input on SQL Server (round 2 objection 3): `p.Sku + p.Title == key` declares `NVarChar(40)` under the chosen form, `NVarChar(4000)` under this one — TO-2d, mutation M5.
- **why this:** the same rule as D-1 on the other side of a comparison; a concat containing any Unicode fragment is Unicode, which a non-Unicode first column does not describe.
- **failure mode of the choice:** `p.Sku + "x" == key` (no Unicode column in the concat) now sends `key` as the default string type (`NVarChar(4000)` on SQL Server, was `VarChar(20)`) — a type change in the comparison of a computed value, with no index on that side to lose.
