# Work plan: feature-query-batches — Reduce value-position predicates after the wrap decision

**Tier:** L  ·  **Status:** approved  ·  **Approved-at:** 2026-10-29 (user, after critic round 2; A-2 re-approved after critic round 4; A-3 asked for by the user; A-4 re-approved as implemented after critic round 6)  ·  **Branch:** feature/query-batches
**Schema:** `.claude/docs/work-plan.md`  ·  **Gates:** `.claude/docs/definition-of-done.md`

Scope note: PR #5673 predates this plan. This plan covers only the reduce-ordering fix, authored 2026-10-29 at head `bbd9de082`. Everything else on the branch is outside it.

## P1 Problem

PR #5673 merges the optimizer and the convert visitor into one children-first pass (commit e0f681262). The CompareNulls null-guard reduce (`ReduceExprExprPredicate` / `ReduceIsTruePredicate` / `ReduceInListPredicate`, called at `SqlExpressionConvertVisitor.cs:482`, `:499`, `:733`) now runs on a predicate *before* its parent decides whether to fold it into a value with `WrapBooleanExpression` (`SqlExpressionConvertVisitor.cs:2607`). On master the wrap happened in the convert pass and the reduce ran later, at render (`BasicSqlBuilder.cs:932/3203/3217` on origin/master, `reducePredicates: true`). Two baseline regressions on baselines PR linq2db/linq2db.baselines#2234 follow from the new order.

1. `PredicateTests.Test_ComplexPredicateComparisonWithUnknown` regresses on every provider without predicate comparison: 68 files across Firebird.2.5, Informix.DB2, Oracle.11–23 Managed, SapHana.Native/Odbc, SqlCe, SqlServer.2005–2025 (+ .MS, CS, Contained) and Sybase.Managed. In the NESTED nullable cases (`TruePredicate() == (Equal(r.Value1, r.Value4) ==/!= Equal(subquery, …))`) the inner predicate operand is reduced with `IsInsidePredicate = true` (set by `SqlExpressionOptimizerVisitor.cs:1771-1774`, kept through `Visit` because a `SqlSearchCondition` is an `ISqlPredicate`, `:116-125`). `SqlPredicate.cs:499-516` therefore appends `AND NOT (A IS NULL AND B IS NOT NULL) AND NOT (A IS NOT NULL AND B IS NULL)`. Only afterwards does `ConvertExprExprPredicate` (`SqlExpressionConvertVisitor.cs:691-711`) wrap it into `IIF(X, 1, 0)` / `CASE`. In a CASE WHEN condition UNKNOWN already selects the ELSE arm, so the guards are redundant, and each one repeats a correlated `COUNT(*)` subquery twice. Master emits `IIF(A = B OR A IS NULL AND B IS NULL, 1, 0)`. The PR emits the same plus the two guards. measured: a local SqlCe run at bbd9de082 captured `(SqlCe,False).sql` byte-identical to #2234's, and +74/−18 lines against master.
2. `ParameterTests.Issue_BooleanNullPreserved`, all 6 Firebird.2.5 variants: the SET value for `!value` changes from `WHEN "t1"."Value" = '1' THEN '0'` to `WHEN "t1"."Value" <> '0' THEN '0'`, and no other provider changes. measured: `git diff --name-only -G"WHEN .* <> '0' THEN"` over #2234 returns exactly these 6 files. Mechanism (from peer session linq2db-claude-4f's reading, reasoned, unprobed): the `IsTrue` is reduced to `ExprExpr(x, =, '0')` before `WrapBooleanExpression` builds `CASE WHEN p … WHEN NOT p …` (`SqlExpressionConvertVisitor.cs:2648-2655`). `NOT p` then goes through `ExprExpr.Invert` (`SqlPredicate.cs:368`) instead of `IsTrue.Invert`. The `x != false → x = true` flip at `SqlPredicate.cs:416-427` matches only `SqlValue { Value: bool }`, and FB 2.5's boolean constants are char `'1'`/`'0'`.

## P3 Constraints & anti-goals (M/L)

- Keep the PR's single optimize+convert traversal. Reintroducing a whole-statement late reduce pass is an anti-goal; the PR measured 13 cross-provider regressions when that pass was relocated (comment at `SqlExpressionConvertVisitor.cs:478-481`).
- No public API change outside `LinqToDB.Internal.*`. The new `protected` property on `SqlExpressionOptimizerVisitor` gets its `get`/`set` pair in `PublicAPI.Unshipped.txt`, as the sibling `IsInsidePredicate` has at `:137-138`. Without the pair, the Release build reports RS0016.
- `SqlPredicate.cs` (`Reduce`, `Invert`, the `!=` flip) stays untouched. The fix is in when the reduce runs, not in what it does.
- No provider-specific edits. Providers only reach the change through the base `SqlExpressionConvertVisitor`.
- Baselines may change only toward master: in the wrapped-predicate shapes, and in the non-wrapped shapes listed in SC-3 / P10 (U-6, U-7).

## P5 Decisions (M/L; rejected alternatives mandatory at L)

### D-1 — Defer the reduce in opt-in value slots and finish it at the slot's wrap decision

- **chosen:** Add a `protected bool DeferPredicateReduce` beside `IsInsidePredicate` on `SqlExpressionOptimizerVisitor`. `Visit` saves, resets (for elements that are not predicates) and restores it exactly like `IsInsidePredicate`. The three convert-side reduce calls (`SqlExpressionConvertVisitor.cs:482/499/733`) are skipped while the flag is set. Value slots set it around the visit of their value child:
  - ExprExpr operands: `SqlExpressionConvertVisitor.VisitExprExprPredicate` sets it around `base.VisitExprExprPredicate`. After `ConvertExprExprPredicate`, every operand that is still a predicate (not wrapped) is visited again with the flag off and `IsInsidePredicate = true`, which is today's reduce context.
  - The `WrapBooleanExpression` slots whose base visit has no condition slot: select column, output column, function argument, ORDER BY item, window order item, SET value, GROUP BY item, PARTITION BY item, coalesce operands. When `WrapBooleanExpression` wraps, its existing `Visit(expr)` of the new CASE/IIF reduces the predicate as a condition. `WrapBooleanExpression` itself is **not** changed. Each of these slots then calls a new helper, `FinishDeferredPredicate(expr)`: if the returned expression is still a predicate (U-8), it is visited with the flag off and the slot's own `IsInsidePredicate`, so it is reduced in place in today's context. The comparison-operand calls at `:702/:705` never call the helper. Their non-wrapped operands are finished by the comparison visit instead, with `IsInsidePredicate = true`.
- **rejected:** (0) Finish the non-wrapped case inside `WrapBooleanExpression` (round-1 draft). That exit is shared with the operand calls at `SqlExpressionConvertVisitor.cs:702/705`, which run after the optimizer has restored `IsInsidePredicate` to the parent's value (`SqlExpressionOptimizerVisitor.cs:1771-1774`, comment at `SqlExpressionConvertVisitor.cs:466-467`). A WHERE-level operand would be reduced with `false`. `ExprExpr.Reduce` then consumes `UnknownAsValue` (`SqlPredicate.cs:392`, `:441`), so the `IS NOT NULL` guards are lost for good and `UNKNOWN = FALSE` drops rows C# keeps. The critic refuted the draft on this point. (a) Narrow: visit wrapped ExprExpr operands with `IsInsidePredicate = false`. It fixes P1.1 only; the FB 2.5 `NOT p` built from a reduced `p` stays. (b) A whole-statement late reduce pass (master's shape): P3 anti-goal, 13 measured regressions. (c) Recognise the guarded shape at wrap time and strip the guards: pattern-matching on `Reduce`'s output couples the convert visitor to `SqlPredicate.cs` internals, and it does not address P1.2. (d) A generic deferral in `Visit` for every predicate under a non-predicate parent, with an exception list for condition slots: one mis-classified condition slot (WHERE / ON / HAVING / CASE / FILTER / MERGE) would defer whole conditions, which is the late pass again with a silent hole. (e) Fix the char-vs-bool `!=` flip in `SqlPredicate.cs`: it fixes P1.2 only, and the user chose the ordering fix.
- **why this:** The wrap decision exists only at the value slot, so the slot is the only place that knows whether the predicate becomes a CASE condition. Opting in per slot keeps every condition slot on today's order by construction, except NOT (D-3, A-2). Each finish runs in the context the slot had today (SC-3), except U-6 / U-7, which move toward master.
- **failure mode of the choice:** (i) A value slot missing from the opt-in list keeps the PR's order, so a wrapped predicate there keeps redundant guards. That is no worse than today, but it is not fixed. (ii) A slot that opts in but forgets to finish leaves an unreduced predicate. An unfinished `IsTrue` is loud: `BasicSqlBuilder.BuildPredicate` has no `IsTrue` case and throws (`BasicSqlBuilder.cs:2851-2852`). An unfinished `ExprExpr` / `InList` is silent: under `CompareNulls.LikeClr` it returns wrong results for NULL comparisons. TO-7 has one mutation-proven test per slot for the silent case. (iii) U-2 / U-6 / U-7 can move PR baselines toward master. TO-5 checks that every move lands on master's version.

### D-2 — CASE/IIF result slots and Informix's forced re-wraps stay on today's order

- **chosen:** Leave `ConvertSqlCondition` / `ConvertSqlCaseExpression` / `ConvertCaseItem` (`SqlExpressionConvertVisitor.cs:2569/2570/2584/2597`) and the Informix overrides unchanged.
- **rejected:** Deferring around `base.VisitCaseItem` / `base.VisitSqlConditionExpression`: per U-4 that also defers the condition slot. A slot-precise version is possible without touching the shared visitor: the convert already overrides `VisitCaseItem` (`SqlExpressionConvertVisitor.cs:176-183`), and the base body is one line (`QueryElementVisitor.cs:3739-3742`). It is still not taken, because it would re-implement the base visits of two node types for a shape no baseline shows.
- **why this:** No baseline in #2234 shows a wrapped CASE/IIF *result* predicate regressing. The FB 2.5-style residual changes only how values outside `{'0','1',NULL}` read (critic round 1).
- **failure mode of the choice:** A predicate used as a CASE/IIF result on a provider without a boolean type keeps reduce-before-wrap. P10 records this.

### D-3 — The NOT operand is a deferral slot (A-2)

- **chosen:** E-11. Inversion is NOT's "wrap decision": the optimizer tries `Invert` on the operand (`SqlExpressionOptimizerVisitor.cs:1048-1051`, `:1062-1065`), and an unreduced `IsTrue` inverts to `IsTrue(!isNot)`, which reduces to `= TrueValue`. A reduced `ExprExpr(x = FalseValue)` inverts to `x <> FalseValue`. Master inverted before reducing, because its reduce ran at render.
- **rejected:** (a) Fix the `!=` flip in `SqlPredicate.cs:416-427` so it recognises a mapped boolean char: it touches `SqlPredicate.cs` (P3), and `Reduce` has no mapping schema to build the opposite constant. (b) FB 2.5 typed boolean constants (the user's option B): it changes every FB 2.5 boolean constant. (c) Accept `<> '0'` (the user's option C): the user chose to fix it.
- **why this:** the same principle as D-1 (decide, then reduce), applied to the one condition-side node that rewrites its operand's shape.
- **failure mode of the choice:** a NOT whose operand cannot invert before or after reducing is visited one extra time. A NOT nested in a deferred value predicate is finished later by its slot (`DeferPredicateReduce` gate). If the finish loop failed to converge it would recurse; measured to converge on TO-1/TO-3.
