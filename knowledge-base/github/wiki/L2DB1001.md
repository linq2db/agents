# L2DB1001: Use the `Sql.Window` API instead of the legacy `Sql.Ext` window functions

|            |                            |
|------------|----------------------------|
| Category   | LinqToDB                   |
| Severity   | Info (configurable)        |
| Package    | [`linq2db.Analyzers`](https://www.nuget.org/packages/linq2db.Analyzers) — comes in with [`linq2db`](https://www.nuget.org/packages/linq2db), no extra reference needed; reference it directly only to run the rule against an older linq2db |

## Cause

Code uses the legacy analytic / window-function API exposed through `Sql.Ext` (the `AnalyticFunctions` class), e.g. `Sql.Ext.RowNumber().Over().PartitionBy(...).OrderBy(...).ToValue()`.

## Rule description

The `Sql.Ext` analytic / window-function API is superseded by the newer, lambda-based **`Sql.Window`** API and is slated for removal in a future major release. Both currently produce the same SQL, so migration is behaviour-preserving.

A code fix is offered for mechanically-convertible chains; it rewrites the call to `Sql.Window` while **preserving your comments and formatting**.

## Example

```csharp
// Legacy Sql.Ext API (flagged)
var q = db.Orders.Select(o => new
{
    o.Id,
    RowNum = Sql.Ext.RowNumber().Over().PartitionBy(o.CustomerId).OrderBy(o.Date).ToValue(),
    RunningTotal = Sql.Ext.Sum(o.Amount).Over().PartitionBy(o.CustomerId).OrderBy(o.Date)
        .Rows.Between.UnboundedPreceding.And.CurrentRow.ToValue(),
});

// After the code fix — Sql.Window API
var q = db.Orders.Select(o => new
{
    o.Id,
    RowNum = Sql.Window.RowNumber(f => f.PartitionBy(o.CustomerId).OrderBy(o.Date)),
    RunningTotal = Sql.Window.Sum(o.Amount, f => f.PartitionBy(o.CustomerId).OrderBy(o.Date)
        .RowsBetween.Unbounded.And.CurrentRow),
});
```

The fix covers ranking, aggregates (including the `DISTINCT` modifier), statistical functions, `Lead`/`Lag`, value functions (`FirstValue`/`LastValue`/`NthValue`, `IGNORE NULLS`, `FROM FIRST/LAST`), Oracle `KEEP`, `Median`, `RatioToReport`, and windowed `PercentileCont`/`PercentileDisc`, along with `PartitionBy` / `OrderBy` / `ThenBy` (`Desc` and `NULLS` variants) and `ROWS`/`RANGE` frames.

## When no fix is offered

Some legacy shapes are reported (the API is still legacy) but have no direct `Sql.Window` equivalent, so no automatic fix is offered — migrate them by hand:

- `ListAgg` and the legacy `Filter` clause;
- a `DISTINCT` aggregate combined with `KEEP` (`Sql.Window`'s `KEEP` builder has no `.Distinct()` state, so the two cannot be combined);
- cases where the `Sql.Window` overload's return type differs from the legacy `ToValue<TR>()` slot (e.g. it returns `double?` and the surrounding code uses an explicitly-typed `double` slot, or `NTile` returns `long` where the legacy call produced `int`). This is opt-out-able — see [Code-fix options](#code-fix-options) below.

## When the rule does not fire

The rule targets genuine **window** usages — chains containing `.Over()`. It does not flag legacy `Sql.Ext` calls that are not window functions and have no `Sql.Window` counterpart:

- a plain aggregate with no `.Over()`;
- the ordered-set *group* form (`PercentileCont`/`PercentileDisc` with `WITHIN GROUP` but no `.Over()`).

## How to suppress or change severity

Set the severity in an `.editorconfig`:

```ini
# raise to a build warning
dotnet_diagnostic.L2DB1001.severity = warning

# or silence it
dotnet_diagnostic.L2DB1001.severity = none
```

Every rule linq2db ships is in the `LinqToDB` analyzer category, so one line covers the whole set:

```ini
dotnet_analyzer_diagnostic.category-LinqToDB.severity = warning
```

To turn the analyzers off entirely for a project — including when they arrive as a dependency of `linq2db` rather than as a direct reference — set the MSBuild property:

```xml
<PropertyGroup>
	<EnableLinqToDBAnalyzers>false</EnableLinqToDBAnalyzers>
</PropertyGroup>
```

## Code-fix options

By default the fix withholds itself when the `Sql.Window` overload's return type differs from the legacy `ToValue<TR>()` slot, so it never turns compiling code into a type error unasked. If you would rather apply the migration everywhere and reconcile the types yourself, opt in via `.editorconfig`:

```ini
# default: false
linq2db.L2DB1001.apply_fix_on_return_type_mismatch = true
```

With this enabled, the fix is applied even where the return type diverges. **Most such sites still compile** — when the result flows into a `var` local or an anonymous-object member, the inferred type simply follows the new type (`double?`, `long`, …). A minority produce a genuine compile error you then fix by hand, typically:

- **CS0266** — the new nullable / wider type isn't implicitly assignable to an explicitly-typed target (e.g. `double?` into a `double` field); widen the declared type or add a cast.
- **CS1929** — a downstream call expected the old element type; adjust the consumer.

Leave the option off (the default) to keep the fix strictly type-preserving.
