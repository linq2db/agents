# L2DB1002: A duration comparison the declared unit can never match

|            |                            |
|------------|----------------------------|
| Category   | LinqToDB                   |
| Severity   | Info (configurable)        |
| Package    | [`linq2db.Analyzers`](https://www.nuget.org/packages/linq2db.Analyzers) — comes in with [`linq2db`](https://www.nuget.org/packages/linq2db), no extra reference needed; reference it directly only to run the rule against an older linq2db |

## Cause

A query compares a member declared `[Duration(DurationUnit.X)]` with `==` or `!=` against a constant `TimeSpan` that is not a whole number of `X` units.

## Rule description

`[Duration(DurationUnit.Second)]` says the column stores a whole number of seconds. Asking whether it equals one and a half of them asks for a value the column cannot hold, so the query returns nothing — always, for every row, on every provider.

The translation is correct, and it does not change. Equality against a declared duration is asked as the two comparisons it is made of — *at least* this duration and *at most* this duration — each rounding its bound the way its own operator needs. The two bounds meet exactly when the value is representable and cross over when it is not, and a crossed-over range is precisely what equality means for a value the column cannot represent.

What is missing is any signal. The generated SQL is an ordinary-looking range over two parameters:

```sql
InSeconds >= @p1 AND InSeconds <= @p2   -- @p1 = 2, @p2 = 1
```

Nothing in the log, the exception surface or the query plan says the predicate is unsatisfiable by construction. And the translator cannot say it either: the rounding runs per execution, while the parameter value is produced, so `== TimeSpan.FromSeconds(1.5)` shares a cached query shape with `== someVariable`. Refusing there would mean a data-dependent runtime error on an already-cached query.

Where the compared duration is a **constant**, the mistake is decidable without running anything — which is what this rule does.

## Example

```csharp
[Column, Duration(DurationUnit.Second)] public TimeSpan InSeconds { get; set; }

// L2DB1002: 'InSeconds' stores whole seconds and cannot represent 00:00:01.5000000,
//           so this comparison can never match
var q = db.Runs.Where(r => r.InSeconds == TimeSpan.FromSeconds(1.5));

// fine — 2 seconds is a value the column can hold
var ok = db.Runs.Where(r => r.InSeconds == TimeSpan.FromSeconds(2));
```

The intended fix is usually one of two things: compare a duration the column can represent, or declare the column in a finer unit (`DurationUnit.Millisecond`, or `DurationUnit.Tick`, which represents every `TimeSpan` exactly).

## Which constants are recognised

The compared duration does not have to be written at the comparison. The rule resolves:

- `new TimeSpan(...)`, `TimeSpan.FromTicks`, and the `TimeSpan.From*` factories;
- `TimeSpan.Parse` / `ParseExact` over a constant string;
- `TimeSpan.Zero`, `MinValue`, `MaxValue`;
- addition and subtraction between any of the above;
- a local that is assigned once from one of the above and never reassigned;
- a `foreach` variable over a constant array;
- the range variable of a LINQ element selector (`Where`, `Select`, `Any`, …) over a constant array.

"Constant array" means array-creation syntax — `new[] { … }` or `new TimeSpan[] { … }`. A collection expression (`TimeSpan[] bounds = [ … ]`) is not recognised: the analyzer is built against the Roslyn bundled with the lowest supported .NET SDK, which does not expose that shape. Write the array form where you want the rule to see the values.

`TimeSpan.ParseExact` is recognised only in its overloads without a `TimeSpanStyles` argument, since that argument can change the value's sign.

When a loop or a sequence supplies several constants and only some of them are unrepresentable, the message says so — the comparison is degenerate on those iterations, not on all of them.

Anything the rule cannot resolve is left alone. It never guesses.

## When the rule does not fire

- **Ordering operators.** `> 1.5s` is exactly `> 1s` for a column of whole seconds — the bound moves to a representable value in the direction the operator asks, which is already the right question. Only `==` and `!=` are reported.
- **`DurationUnit.Tick`** represents every `TimeSpan` exactly, and **`DurationUnit.Nanosecond`** is finer than a tick, so nothing is unrepresentable in either.
- **A non-constant operand** — a parameter, a field, a value read at runtime. The rule reports only what it can decide statically.
- **Outside a query.** The comparison must sit inside a lambda that becomes an expression tree. An in-memory comparison against an object that never came from the database is a legitimate thing to write.
- **A `double`-factory value that your target framework's own rounding makes representable.** `TimeSpan.From*(double)` does not agree across runtimes: .NET Framework rounds the product to a whole millisecond, while .NET 5 and later truncate the tick product. The rule carries only the readings your target can produce — it takes the presence of `TimeSpan.FromMicroseconds` (.NET 7) or `System.Half` (.NET 5), neither of which exists on .NET Framework, as proof the rounding cannot apply — and reports only when none of the readings it carries is representable. So `TimeSpan.FromMilliseconds(0.5)` against a `[Duration(DurationUnit.Millisecond)]` column is silent on .NET Framework, where it really is one whole millisecond, and on `netstandard2.0`, which can run there; it is reported on .NET 5 and later, where it is 5000 ticks. The column's unit decides this too: the same constant against a `[Duration(DurationUnit.Second)]` column is reported on every target, since half a millisecond is a whole second under no reading.
- **Configuration-scoped declarations.** If every `[Duration]` on the member names a `Configuration`, a configuration matching none of them leaves the column with no duration semantics at all. Likewise, when a member carries several `[Duration]` attributes and any one of them *can* represent the value, nothing is reported — that configuration genuinely matches.

## Known limitation: the rule reads the unit off the member

The rule reads `[Duration(DurationUnit.X)]` where it is written — on the member. It does not follow any of the other routes that can declare the same unit, so none of these is diagnosed:

```csharp
// not diagnosed — the unit is not on the member
builder.Property(e => e.Elapsed).HasDuration(DurationUnit.Second);
builder.Property(e => e.Elapsed).HasAttribute(new DurationAttribute(DurationUnit.Second));
```

The same applies to a unit registered on a mapping schema and to any custom `IMetadataReader`. All of them behave identically at runtime; the rule simply does not look there.

Note this is a limit on what the rule **reads**, not on what a compiler can know — the second line above states its unit in source, and only the mapping-schema and `IMetadataReader` routes are genuinely undecidable. Either way the consequence is the same and it is the safe one: a column configured by one of these routes is **silent**, never wrongly reported. The rule treats a member with no `[Duration]` on it as "nothing to say about", not as "not a duration column".

An attribute *derived* from `DurationAttribute` is diagnosed when it passes the unit through — `[MyDuration(DurationUnit.Second)]` — and not when it hard-codes the unit in its own constructor's base call, since the unit is then nowhere in the attribute application.

## The rule assumes a linq2db queryable

It reports inside any lambda that becomes an expression tree, and it cannot tell one provider's tree from another's. If you query a `[Duration]`-mapped type through a different LINQ provider, or build a tree with `.Compile()` and run it in memory, the comparison is ordinary `TimeSpan` equality and does match — the diagnostic would be wrong there. Set `dotnet_diagnostic.L2DB1002.severity = none` for such a project.

## Why there is no code fix

The intended value cannot be inferred. `TimeSpan.FromSeconds(1.5)` against a whole-second column might have meant 1 second, 2 seconds, or that the column should have been declared in milliseconds — and each is a different change in behaviour. The rule reports and leaves the choice to you.

## How to suppress or change severity

Set the severity in an `.editorconfig`:

```ini
# raise to a build warning
dotnet_diagnostic.L2DB1002.severity = warning

# or silence it
dotnet_diagnostic.L2DB1002.severity = none
```

Every rule linq2db ships is in the `LinqToDB` analyzer category, so one line covers the whole set:

```ini
dotnet_analyzer_diagnostic.category-LinqToDB.severity = warning
```

To turn the analyzers off entirely for a project — including when they arrive as a dependency of `linq2db` rather than as a direct reference — set the MSBuild property:

```xml
<PropertyGroup>
	<EnableLinqToDBAnalyzers>false</EnableLinqToDBAnalyzers>
</PropertyGroup>
```
