# L2DB1004: A server-side-only stub should throw `ServerSideOnlyException`

|            |                            |
|------------|----------------------------|
| Category   | LinqToDB                   |
| Severity   | Info (configurable)        |
| Package    | [`linq2db.Analyzers`](https://www.nuget.org/packages/linq2db.Analyzers) — comes in with [`linq2db`](https://www.nuget.org/packages/linq2db), no extra reference needed; reference it directly only to run the rule against an older linq2db |

## Cause

A member is declared server-side only and its body is a single `throw`, but the exception is something other than `ServerSideOnlyException`.

## Rule description

A server-side-only member's stub exists to report a mistake: someone called, outside a query, an API that only works inside one. `ServerSideOnlyException` says exactly that and names the member —

> 'MyFunc' is server-side API.

`NotImplementedException` says "the method or operation is not implemented", which is both wrong and unhelpful; `InvalidOperationException` with no message says less still. The member *is* implemented — just not for the client.

The rule accepts any of the four ways to declare a member server-side only: `[ServerSideOnly]`; an `Sql.Expression`-derived attribute whose `ServerSideOnly` is true (every `Sql.Extension` constructor sets it, so a bare `[Sql.Extension("…")]` counts); an `Sql.TableFunction`-derived attribute; or `[ExpressionMethod]`.

## Example

```csharp
// Flagged
[ServerSideOnly]
public static int MyFunc(int x) => throw new NotImplementedException();

// After the code fix
[ServerSideOnly]
public static int MyFunc(int x) => throw new ServerSideOnlyException(nameof(MyFunc));
```

Both body shapes are recognised — `=> throw …` and `{ throw …; }`.

## When the rule does not fire

- A marked member with a **real body** is valid and never reported. Inside a query it emits mapped SQL; outside one the body runs.
- A stub that already throws `ServerSideOnlyException`.
- Constructors, operators and indexers, and a `set => throw` beside a real getter.
- Generated code — a `*.generated.cs` file, or any file with an `<auto-generated>` header, including a data model scaffolded by `linq2db.cli`. You maintain those through the tool that emits them, so the rule stays out of the way.

## Options

If your codebase has its own exception for this, add it. The list is **additive** to the `ServerSideOnlyException` default and matches type names **exactly**, not by subclass — so listing a base type does not admit everything derived from it:

```ini
linq2db.L2DB1004.allowed_exception_types = MyCompany.ServerSideException, MyCompany.SqlOnlyException
```

An entry that cannot be resolved is ignored rather than treated as an error, so a typo or a type from an unreferenced assembly will not break your build.

## How to suppress or change severity

```ini
dotnet_diagnostic.L2DB1004.severity = warning
dotnet_diagnostic.L2DB1004.severity = none
```

Every rule linq2db ships is in the `LinqToDB` analyzer category, so one line covers the whole set:

```ini
dotnet_analyzer_diagnostic.category-LinqToDB.severity = warning
```

To turn the analyzers off entirely for a project — including when they arrive as a dependency of `linq2db` rather than as a direct reference:

```xml
<PropertyGroup>
	<EnableLinqToDBAnalyzers>false</EnableLinqToDBAnalyzers>
</PropertyGroup>
```
