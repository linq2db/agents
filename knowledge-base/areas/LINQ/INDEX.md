# LINQ -- query caching, executor lifecycle, and the `IQueryable` adapter

The execution and caching half of the LINQ pipeline. Owns the shared LINQ query cache (`QueryCache.Default`, global and bucketed -- see `## Subsystems` below), the compiled executor delegates (`GetElement`, `GetElementAsync`, `GetResultEnumerable`, plus the eager-aware `GetEagerElement[Async]` / `GetResultFromReader`), the `IQueryable<T>` / `IQueryProvider` adapter exposed to user code, the eager-loading execution engine (`Harvester`, combined multi-result-set enumeration, `BufferedRows<T>` -- see `## Subsystems` section 7), and the ADO.NET execution loop that runs `IQueryRunner` against a `DbDataReader` and drives the materialization mapper. Translation of the LINQ expression tree into `SqlStatement` lives in the EXPR-TRANS area (`Source/LinqToDB/Internal/Linq/Builder/**`) and is invoked from here exactly once per cache miss, via `ExpressionBuilder.Build<T>` in `Query<T>.CreateQuery` (`Source/LinqToDB/Internal/Linq/Query{T}.cs:256`).

## Key types

- **`Query`** (`Source/LinqToDB/Internal/Linq/Query.cs:21`) -- public abstract base. Holds a single `QueryInfo QueryInfo` (`Query.cs:39`, set in `Init` / by the CRUD builders -- the former `QueryInfo[]` shard array is gone: multi-statement expansion is now modelled by `SqlCommandScenario` at render time in `DataConnection.QueryRunner.GetCommand`, and `GetQueries()` just wraps the one `QueryInfo`), the cached `MappingSchema` / `SqlOptimizer` / `SqlProviderFlags` / `DataOptions` snapshot taken at build time, the `QueryCacheCompareInfo` used for cache-key comparison, the `ParameterAccessors` list that binds runtime values into `SqlParameter`s, and the `Harvester[]` for eager-loading prefetches (`SetHarvesters`, `IsAnyHarvesters`, `HarvestersArray`, `InitHarvesters[Async]`, `Query.cs:160-213`) that replaced the old `Preamble[]`. `GetElement` / `GetElementAsync` (`Query.cs:23-24`) are the executor delegates set by `QueryRunner.Set*Query` once per build and now take a `SqlCommandExecutionContext?` (the harvester results plus compiled-query parameters) instead of a raw `object?[]? preambles`. `GetEagerElement` / `GetEagerElementAsync` (`Query.cs:32-33`) are set only by `FirstSingleBuilder`: First/Single element selection routed through the combined eager engine so those queries batch their eager children like `ToList()` does. `ConfigurationID` / `ContextType` / `InlineParameters` / `IsEntityServiceProvided` are no longer stored on `Query` itself -- they are pinned by the `QueryCache` bucket key (`ContextType` + `ConfigurationID` + `QueryFlags`, the latter encoding `InlineParameters` and `HasEntityServiceInterceptor`), so `Query.Compare` (`Query.cs:68`) only re-checks the expression tree plus optional dynamic-accessor / value-comparison probes. `Query` also owns the implicit "load transaction" helpers `StartLoadTransaction(IDataContext)` / `StartLoadTransactionAsync(...)` (`Query.cs:215`, `228`, with private `GetTransactionOwner`, `Query.cs:313`), shared by `ExpressionQuery<T>` and `CompiledTable<T>`. They return `null` unless `IsAnyHarvesters()` is true, the context is a `DataConnection` / `DataContext`, and there is no `TransactionScope` or existing transaction. The returned `Query.LoadTransaction` (nested class, `Query.cs:250`) now covers the **reads only**: an enumeration buffers the main rows and commits via `Complete()` / `CompleteAsync()` before returning the first row, so caller code never runs inside a transaction it did not open (disposing uncommitted rolls back).
- **`Query<T>`** (`Source/LinqToDB/Internal/Linq/Query{T}.cs:20`) -- sealed generic. `GetQuery` (`Query{T}.cs:146`) is the cache-lookup entry point: it runs `BinaryExpressionAggregatorVisitor`, `IExpressionPreprocessor`, the `IQueryExpressionInterceptor`, then probes the shared `QueryCache.Default` (see `## Subsystems` below -- the per-type copy-on-write cache this bullet used to describe was replaced by one global bucketed cache). On miss it runs `ExposeAndPrepareExpression` (which fixed-points the exposer + interceptor up to 10 iterations) and probes a second time with the `QueryFlags.ExpandedQuery` bit set before falling through to `CreateQuery`. The interceptor runs before the lookup (so on every execution) because the cache key is built from the rewritten tree. `ClearCache()` / `CacheMissCount` delegate to `QueryCache.Default.ClearForType(typeof(T))` / `GetMissCount(typeof(T))` (`Query{T}.cs:98`, `103`). It carries `GetResultEnumerable` plus the new `GetResultFromReader` (set only for combinable SELECT queries by `SetRunQuery`: materializes rows from an externally opened reader) and the `GetEagerEnumerable[Async]` helpers (`Query{T}.cs:59`, `73`) that centralize the "combined multi-result-set executor if eligible, else sequential `InitHarvesters` + `GetResultEnumerable`" decision for every `ExpressionQuery<T>` enumeration path.
- **`ExpressionQuery<T>`** (`Source/LinqToDB/Internal/Linq/ExpressionQuery.cs:20`) -- abstract `IExpressionQuery<T>` / `IAsyncEnumerable<T>` adapter. This is the type the public `IQueryable<T>` surface materializes to: it implements `IQueryProvider.CreateQuery` / `Execute` / `IQueryProviderAsync.ExecuteAsync` / `ExecuteAsyncEnumerable` and the synchronous / async `IEnumerable<T>` / `IAsyncEnumerable<T>` traversals. Concrete subclasses are `Table<T>`, `CteTable<T>`, `ExpressionQueryImpl<T>`. It carries an optional internal `CompiledExpressions` (`IQueryExpressions`) handed over by `CompiledTable<T>`. `GetOwnExpressions` reuses it instead of wrapping `Expression` in a fresh `RuntimeExpressionsContainer`, because accessors built against the compiled container may be rooted at dynamic entries a rebuilt container lacks (e.g. a query filter closing over a value). The `Preambles` field is now typed `SqlCommandExecutionContext?` and is set only on the sequential (non-combined) path. Sync enumeration (`GetEagerEnumerator`, `ExpressionQuery.cs:373`) buffers the main rows with `BufferedRows<T>.Read` when a load transaction is active, commits, then hands back the buffered enumerator, and the async paths do the same with `BufferedAsyncEnumerable<T>`. `Execute` / `ExecuteAsync` prefer `query.GetEagerElement[Async]` when set. `GetForEachAsync` and `GetForEachUntilAsync` share one `GetForEachCoreAsync(Func<T,bool>)`.
- **`IQueryRunner`** (`Source/LinqToDB/Internal/Linq/IQueryRunner.cs:12`) -- the per-execution ADO.NET handle owned by `IDataContext`. Provides sync + async `ExecuteNonQuery` / `ExecuteScalar` / `ExecuteReader` and exposes `DataContext`, `Expressions`, `Parameters`, `Preambles`, `ExecutionContext` (new: the `SqlCommandExecutionContext` wrapping harvester results and compiled-query parameters, threaded into the materialization mapper -- `Preambles` now just surfaces its `Results` array), `MapperExpression`, `RowsCount`. `QueryNumber` is `[Obsolete]` and always 0 (batches are modeled by `SqlCommandScenario`). Concrete implementation lives in DATA (`DataConnection.QueryRunner`, owned by `IDataContext.GetQueryRunner`).
- **`QueryRunnerBase`** (`Source/LinqToDB/Internal/Linq/QueryRunnerBase.cs:12`) -- abstract default plumbing for `IQueryRunner`: its constructor takes `(query, queryNumber, dataContext, parametersContext, expressions, parameters, harvesters)` and re-wraps the two transport arrays into one lazily allocated `SqlCommandExecutionContext` (null when both are null, so regular queries stay context-free on the hot path). `SetCommand` calls `QueryRunner.SetParameters(Query, Expressions, ParametersContext, parameterValues, ExecutionContext)` to bind a `SqlParameterValues`, then defers the actual command shaping to `SetQuery(IReadOnlyParameterValues, bool forGetSqlText)`. `Dispose` closes `IDataContext` when `CloseAfterUse` is set.
- **`QueryRunner`** (`Source/LinqToDB/Internal/Linq/QueryRunner.cs:34`) -- static partial. The hub between a built `Query` and the runtime executor: assembles `Mapper<T>` (a per-data-reader-type `Func<IQueryRunner, DbDataReader, T>` cache with slow-mode fallback on `FormatException` / `InvalidCastException` / `*NullValueException`), wires `query.GetResultEnumerable` / `query.GetResultFromReader` / `query.GetElement` via `SetRunQuery` (two overloads) / `SetScalarQuery` / `SetNonQueryQuery`, and provides per-operation entry points (`Insert<T>`, `Update<T>`, `Delete<T>`, `InsertOrReplace<T>`, `InsertWithIdentity<T>`, `CreateTable<T>`, `DropTable<T>` -- see partial files). `SetNonQueryQuery2`, `SetQueryQuery2` and `SetIfExistsUpdateElseInsert` no longer exist in `Source/LinqToDB/Internal/Linq` -- the multi-statement fallbacks moved to render-time scenarios. It also hosts the eager-loading executors `ExternalReaderResultEnumerable<T>`, `EagerResultEnumerable<T>` and `TryGetCombinedEagerEnumerable<T>` (see Subsystems section 7). `QueryRunner.Cache<T>.QueryCache` (the `MemoryCache` used by `CompiledTable<T>`) is size-bounded (`SizeLimit = 1000`, per closed `T`, `QueryRunner.cs:52`) while `Cache<T,TR>.QueryCache` (`QueryRunner.cs:67`) is not.
- **`QueryInfo`** (`Source/LinqToDB/Internal/Linq/QueryInfo.cs:12`) -- the single `SqlStatement` holder for a `Query` (one `QueryInfo` per `Query`, not an array of shards any more). Implements `IQueryContext`. Besides `Statement` / `Context` / `IsContinuousRun` / `DataOptions` it carries two render caches built from the same `PreparedCommand` templates: `Prepared` (`PreparedQuery`, the rendered commands of the main query) and `EagerCommandCache` (`PreparedScenario`, the combined eager-loading scenario with its step facts and group list). They are separate slots because a `LoadWith` query uses both on the same `QueryInfo` -- the eager executor for data, `GetCommand` for `ToString` / `GetSqlText`. The `QueryInfo` instance also serves as the monitor object that serializes in-place statement mutation by `GetCommand` and the eager render.
- **`QueryCacheCompareInfo`** (`Source/LinqToDB/Internal/Linq/QueryCacheCompareInfo.cs:8`) -- the key structure for cache equality. Holds the canonical `MainExpression`, optional `DynamicAccessors` (satellite expressions that need re-fetching from the live `IDataContext` to compare), and optional `ComparisionFunctions` (compiled value-equality probes). `IsFastComparable` is `true` when neither list is needed -- `ExpressionQuery<T>` only memoizes a `Query<T>` reference into its `Info` field when this flag holds (`ExpressionQuery.cs:106`).
- **`QueryCache`** (`Source/LinqToDB/Internal/Linq/QueryCache.cs:42`) -- public sealed, process-wide singleton (`QueryCache.Default`, `QueryCache.cs:45`) that replaced the old per-`Query<T>` copy-on-write array cache. Buckets entries by a `CacheKey` (`ResultType`, `ContextType`, `ConfigurationID`, `QueryFlags`, and an 8-level `ChainHash` of the LINQ method/member chain -- `QueryCache.cs:102-144`, `525-553`). Inside a bucket, `TryFind` still verifies candidates with `Query.Compare`. Each entry tracks its own idle-timeout deadline with hit-rate-tiered extension (`EffectiveTimeoutTicks`, `QueryCache.cs:988-1005`). A single-flighted background sweep (`ThreadPool.UnsafeQueueUserWorkItem`, `QueryCache.cs:591-628`) expires stale entries and trims the global count toward `DefaultMaxEntries` (10,000) when over capacity. The `TimeSpan` to Stopwatch-tick conversion (`ToStopwatchTicks`) is integer-only (whole seconds times `Stopwatch.Frequency` plus a ceil-divided fractional part, saturating at `long.MaxValue`) because hosts that unmask FPU exceptions (C++Builder, Delphi) crash the x86 JIT on a `double` compared against `long.MaxValue` (#6042). The static constructor of `QueryCache.Default` registers the only `Query.CacheCleaners` entry needed for the LINQ query cache (`QueryCache.cs:50-55`) -- `Query<T>` no longer registers a per-closed-generic-type cleaner.
- **`ExpressionCacheManager`** (`Source/LinqToDB/Internal/Linq/ExpressionCacheManager.cs:22`) -- the build-time companion to `QueryCacheCompareInfo`. Tracks accessor mappings (`AccessorsMapping`), parameter cache entries (`_parameterEntries`), duplicate-parameter checks, by-value comparisons, and `_bySqlValueCompare` registrations. `BuildQueryCacheCompareInfo` finalizes them into the `Query.CompareInfo` + `Query.ParameterAccessors` actually stored on the cached `Query`. The client-value getter lambda it compiles now has the four-parameter shape `(IQueryExpressions, IDataContext?, object?[]?, SqlCommandExecutionContext?) -> object?` (parameters `QueryExpressionContainerParam`, `DataContextParam`, `ParametersParam`, `ExecutionContextParam`, `ExpressionCacheManager.cs:527`).
- **`IQueryExpressions`** / **`RuntimeExpressionsContainer`** (`Source/LinqToDB/Internal/Linq/IQueryExpressions.cs:5`, `RuntimeExpressionsContainer.cs:9`) -- wrapper that decouples `MainExpression` (the user tree) from satellite expressions referenced by id. Used everywhere a `ParameterAccessor` or `DynamicExpressionInfo` needs to retrieve the current value of subtree N from the live request.
- **`ParameterAccessor`** / **`ParameterCacheEntry`** (`ParameterAccessor.cs:14`, `ParameterCacheEntry.cs:5`) -- runtime side and build-time side of a `SqlParameter` value pipeline. `ParameterAccessor.ClientValueAccessor(IQueryExpressions, IDataContext?, object?[]?, SqlCommandExecutionContext?) -> object?` extracts the user-visible value from the expression tree (the execution context is the new fourth argument -- how a keyed eager-load detail query reads its master keys from a result slot). `ClientToProviderConverter` / `ItemAccessor` / `DbDataTypeAccessor` map it to the provider-shaped value + type.
- **`Harvester`** (`Source/LinqToDB/Internal/Linq/Harvester.cs:14`) -- internal abstract class that replaced `Preamble` (file deleted): a deferred prefetch executed before the main query. Eager loading materializes one harvester per `LoadWith` group, and `Query.InitHarvesters[Async]` runs them in array order and writes each result into a `SqlCommandExecutionContext` slot so later harvesters (and the mapper) can read earlier results. Members: abstract `Execute` / `ExecuteAsync` / `GetUsedParametersAndValues`, virtual `IsInlined` (default `false`, `Harvester.cs:26`, marks a harvester that resolves from the main result set -- CteUnion single-query mode -- so `Query.IsAnyHarvesters()` ignores it for the implicit-transaction decision), and the non-virtual `Harvest` / `HarvestAsync` (`Harvester.cs:34`, `40`) that pick between self-execution (reader null) and materializing from a shared combined reader. The companion interface **`IStepMaterializer`** (`Harvester.cs:52`, same file) is implemented only by combinable harvesters (Default strategy, `Harvester<TKey,T>`) and exposes `CanCombine`, `GetCombinableQueryInfo`, `AddCombinableParameterValues`, `MaterializeFromReader[Async]`.
- **`BufferedRows<T>`** (`Source/LinqToDB/Internal/Linq/BufferedRows.cs:17`) -- new internal sealed `IEnumerator<T>` / `IAsyncEnumerator<T>` over the main rows of an eager load, read to the end before the read-consistency transaction commits. `Read(IEnumerable<T>)` / `ReadAsync(IAsyncEnumerable<T>, ct)` fill an `ArrayPool<T>`-rented array (plain `new T[]` where `SUPPORTS_SPAN` is off, initial capacity 16, doubling in `Grow`). The array is returned (cleared if the element type holds references) on the first `Dispose` only, guarded by `Interlocked.Exchange`, because returning twice would hand one array to two renters. `WithCancellation` stores the token that `MoveNextAsync` checks. Its async sibling is `Internal/Async/BufferedAsyncEnumerable<T>`.
- **`Table<T>`** (`Source/LinqToDB/Internal/Linq/Table{T}.cs:13`) -- concrete `ITable<T>` implementation. Builds its own initial expression tree from `Methods.LinqToDB.GetTable.MakeGenericMethod(T)` against an `SqlQueryRootExpression`, then layers `TableName` / `SchemaName` / `ServerName` / `DatabaseName` / `TableID` / `TableOptions` / `UseTableDescriptor` calls on top via the `Apply*` helpers as user code mutates the table.
- **`CompiledTable<T>`** (`Source/LinqToDB/Internal/Linq/CompiledTable{T}.cs:15`) -- backs `CompiledQuery`. Constructed from `(Expression, int[] dependentArgumentIndexes)` (the `LambdaExpression` and the `ReplaceAsyncWithSync` async-to-sync rewriting are gone). Caches a `Query<T>` in the global `QueryRunner.Cache<T>.QueryCache` (`MemoryCache<IStructuralEquatable, Query<T>>`, size-limited to 1000) keyed by `(operation "CT", configurationID, table = this, queryFlags, dependent = DependentArgumentValues)` -- the fold site is identified by reference (`this`), not structurally. The `dependent` component holds the runtime values of `[SqlQueryDependent]` arguments that expose materialises (compared type-strictly, with `FormattableString` raw-SQL arguments compared by format and arguments). Slot discovery is self-correcting: `BuildQuery` reports `materializedSlots` from `ExpressionBuilder.ExposeExpression(..., out materializedSlots)`. If a slot is not in the known `_dependentArgumentIndexes` the freshly built query is returned but not published, the index set is widened under `_learnLock` (`Union`), and `GetInfo` loops (see Subsystems section 6). `Create` / `Execute` / `ExecuteAsync` take no preamble/harvester argument: `Execute*` start the load transaction themselves and call `query.InitHarvesters[Async](db, expressions, parameters)`, which always returns a `SqlCommandExecutionContext` for a compiled query (it carries the argument array even when there are no harvesters). That context is passed to `GetElement[Async]` (`CompiledTable{T}.cs:179-215`). `ExecuteAsync` takes a `CancellationToken`, and `Create` returns a `Table<T>` over `query.CompiledExpressions.MainExpression` with `CompiledExpressions` pre-set.
- **`DependentArgumentValues`** (`Source/LinqToDB/Internal/Linq/DependentArgumentValues.cs:15`) -- new sealed `IEquatable` holder for the `object?[]` of dependent-argument values used inside the `CompiledTable<T>` cache-key tuple (a raw array would compare by reference under the tuple default comparer). Equality is element-wise and recursive over non-string `IEnumerable` values, hash is combined likewise, `None` is the shared empty instance. Values of different runtime types never compare equal (a raw-SQL argument is read back as its build-time type, collections included), and `FormattableString` values are compared by format plus arguments via `FormattableStringHelper.AreEqual` / `ComputeHashCode` (`LinqToDB.Internal.Common`), recursing with the same value comparer, so two raw-SQL calls with equal format and equal arguments share a compiled-query cache entry.
- **`IQueryableWrapper<TSource>`** (`Source/LinqToDB/Internal/Linq/IQueryableWrapper.cs:6`) -- new internal covariant interface for `IQueryable<T>` wrappers (queries returned by `LoadWith` or provider hint methods) exposing `WrappedQuery`, so consumers can see the linq2db query behind the wrapper. Consumed by `LinqInternalExtensions.UnwrapQueryable` / `AsLinqToDBQuery`.
- **`IExpressionCacheKey`** (`Source/LinqToDB/Internal/Linq/IExpressionCacheKey.cs:13`) -- opt-in marker for constants that should *participate* in the cache key (used by `ExpressionCacheHelpers.ShouldRemoveConstantFromCache` to decide whether to replace the constant with a `ConstantPlaceholderExpression`, which would erase its value from the comparison).

## Subsystems

### 1. Query cache (global, bucketed, hit-rate-tiered expiration)

**Rewritten in an earlier delta (was: per-`Query<T>` copy-on-write array, max 100 entries -- see AUDIT-NOTE).** `Query<T>` no longer owns a per-type cache. All typed queries share one process-wide `QueryCache.Default` singleton (`QueryCache.cs:45`), a `ConcurrentDictionary<CacheKey, Bucket>` (`QueryCache.cs:66`). `CacheKey` is `(ResultType, ContextType, ConfigurationID, QueryFlags, ChainHash)` (`QueryCache.cs:102-144`); `ChainHash` walks up to 8 levels of the LINQ method/member chain from the root expression, hashing `MethodCallExpression.Method` / `MemberExpression.Member` / node-type+type for anything else (`ComputeChainHash`, `QueryCache.cs:525-553`). `ConfigurationID`, `ContextType`, `InlineParameters`, and `IsEntityServiceProvided` used to be separate fields compared inside `Query.Compare`; they are now folded entirely into the bucket key (the latter two via `QueryFlags.InlineParameters` / `HasEntityServiceInterceptor`, set by `QueryFlagsHelper.GetQueryFlags`), so `Query.Compare` (`Query.cs:68`) only re-checks `CompareInfo.MainExpression.EqualsTo(...)` plus the optional dynamic-accessor / value-comparison probes -- same tail behavior as before. (Later delta: `EqualsTo` no longer takes the `IDataContext`, and the value-comparison probe uses `ExpressionEqualityComparer.CompareValues(value1, value2)` instead of an inline null-aware `Equals`.)

Each bucket is a copy-on-write `Entry[]` capped at `BucketCap = 16` (`QueryCache.cs:57`); a full bucket evicts by earliest expiration deadline, then oldest access time, then lowest hit rate (`FindBucketVictimIndex` / `CompareForEviction`, `QueryCache.cs:1034-1069`). Each `Entry` carries its own `BaseTimeoutTicks` (captured from `LinqOptions.CacheSlidingExpirationOrDefault` at add time) and an `ExpiresAtTicks` deadline that only ever extends, never shortens; the extension multiplies the base timeout by a hit-rate tier -- under 5/hr keeps 1x, under 50/hr gets 4x, under 500/hr gets 12x, 500/hr or more gets 24x (`EffectiveTimeoutTicks`, `QueryCache.cs:988-1005`). Timeout-to-tick conversion deliberately avoids floating point (`ToStopwatchTicks`: integer seconds and remainder, saturating add) so it is safe in hosts with unmasked FPU exceptions. Hot-path hits sample the heavyweight deadline-extension write (1-in-16 within a 100ms window, `HitSampleMask`, `QueryCache.cs:847-878`) to avoid hammering shared cache lines. A single-flighted global sweep (`ThreadPool.UnsafeQueueUserWorkItem`, debounced by `_sweepRunning`, `QueryCache.cs:591-628`) runs every `DefaultSweepIntervalMs` (5 min) or when the approximate global `_entryCount` exceeds `DefaultMaxEntries` (10,000, overridable via `MaxEntriesOverride`); it updates hit-rate EMAs, reaps expired entries per bucket, then trims any remaining overage globally, sorted ascending by expiry, then last-access, then hit-rate (`TrimGlobalToCapacity`, `QueryCache.cs:703-758`).

Two-phase lookup is unchanged in shape: `Query<T>.GetQuery` first probes `QueryCache.Default.TryFind` with the user raw expression and `QueryFlags.None`; on miss it runs `ExposeAndPrepareExpression` (fixed-points `ExpressionBuilder.ExposeExpression` + `IQueryExpressionInterceptor.ProcessExpression` up to 10 iterations) and probes a second time with `QueryFlags.ExpandedQuery` set (`Query{T}.cs:191`, `222`). Cache miss falls through to `CreateQuery` (`Query{T}.cs:256`), which invokes EXPR-TRANS via `new ExpressionBuilder(...).Build<T>(...)` and, on `ErrorExpression` non-null, retries once with `validateSubqueries: true` before throwing. Cache miss is recorded per-result-type in `QueryCache._misses` (`ConcurrentDictionary<Type, CounterBox>`) via `IncrementMissCount`, surfaced through `Query<T>.CacheMissCount => QueryCache.Default.GetMissCount(typeof(T))` (`Query{T}.cs:103`, `QueryCache.cs:228-235`).

`Query.CacheCleaners` is still a `ConcurrentQueue<Action>` (`Query.cs:143`), but the static constructor of `QueryCache.Default` registers the single cleaner needed for the LINQ query cache (`cache.ClearAll`, `QueryCache.cs:50-55`) instead of each closed generic `Query<T>` registering its own -- the per-CRUD-op caches (`QueryRunner.Cache<T>`, `QueryRunner.Cache<T,TR>`, `Update<T>.Cache`) still register individually, unaffected by this change. `Query.ClearCaches()` still walks the queue unchanged (`Query.cs:148-154`).

### 2. Cache-key normalization

Constants are not raw-compared. `ExpressionCacheHelpers.ShouldRemoveConstantFromCache` (`ExpressionCacheHelpers.cs:10`) replaces non-scalar constants with `ConstantPlaceholderExpression` before they enter `CompareInfo.MainExpression`, *unless* the value is `null`, an `EntityDescriptor`, a `FormattableString`, a `RawSqlString`, or implements `IExpressionCacheKey`. Implementers of `IExpressionCacheKey` must be immutable and provide value-based equality -- they get hashed/compared by their own `GetHashCode` / `Equals`, so distinct logical values produce distinct cache lines without explosion of cache size for incidental reference-different but value-equal keys.

`ExpressionCacheManager.RegisterParameterEntry` (`ExpressionCacheManager.cs:172`) deduplicates parameter entries: structural equality on `ClientValueGetter` / `ClientToProviderConverter` / `ItemAccessor` / `DbDataTypeAccessor` + `DbDataType` collapses two trees into one `ParameterId`; if structural equality fails but the parameters share a name and `EvaluatedValue`, a `RegisterDuplicateCheck` runtime probe is registered so cache hits still distinguish "same shape, different runtime value" later. Updated in a later delta: the signature gained `bool allowNameLookup` (the by-parameter-path-name lookup compares structurally different occurrences, so it is only valid for scalar values). A structurally equal pair is now shared only after `TryProveEqual` evaluates both occurrences and the values agree (skipped when no evaluator is supplied, or when both are the same expression instance). Previously an impure getter or method call returning different values per call produced a single shared parameter whose duplicate check could never be satisfied, so the cached query was rejected on every execution. If evaluating the user code throws (other than cancellation or OOM) the pair is treated as not proven equal, each occurrence keeps its own parameter, and the original exception resurfaces later from the accessor that needs the value (instead of being misread by the caller as "not a parameter").

`ExpressionCacheManager.SuggestParameterDisplayName` now names a parameter after the member the value is read from, additionally walking the value spine through array-index reads, indexer reads (special-name `get_*` taking at least one argument, so `[IndexerName]`-renamed indexers and `string.Chars` qualify), `IndexExpression`, and the parameterless `Nullable<T>.GetValueOrDefault()`. Index and call arguments are never walked because they are substituted out of the cache key; value-computing calls (e.g. `today.AddDays(-7)`) still return `null`.

Delta f90c5bcfb: the compiled client-value getter now has the 4-parameter shape `(IQueryExpressions, IDataContext?, object?[]?, SqlCommandExecutionContext?)` (`ExpressionCacheManager.cs:527`, `ParameterAccessor.cs:18`), so an accessor can read a result slot (eager-load master keys) from the live execution context. `QueryRunner.SetParameters` (`QueryRunner.cs:300-351`) has a folded overload that sources the compiled-query parameters from the context.

### 3. Executor delegate wiring

A built `Query<T>` carries up to three executor delegates: `GetElement` (sync scalar/aggregate), `GetElementAsync` (async scalar/aggregate), `GetResultEnumerable` (sync + async iteration), plus `GetResultFromReader` (rows from an externally opened reader, set only for SELECT queries) and, for First/Single only, `GetEagerElement[Async]`. All element/enumerable delegates now receive a `SqlCommandExecutionContext?` (harvester results + compiled-query parameters) instead of a raw preamble array. They are assigned by `QueryRunner.Set*Query` once at the end of `ExpressionBuilder.Build<T>`. Choice of setter encodes the result shape:

| Setter | Result | When |
|---|---|---|
| `SetRunQuery<T>(query, mapper)` | `IResultEnumerable<T>` (+ `GetResultFromReader`) for `Cast` / `Concat` / `Union` / `OfType` / `ScalarSelect` / `Select` / `SequenceContext` / `Table` | Default for `IQueryable<T>` materialization |
| `SetRunQuery<T>(query, scalarMapper)` (overload returning `object`) | First-row `GetElement`/`Async` for `Aggregation` / `All` / `Any` / `Contains` / `Count` | First-row materialization |
| `SetScalarQuery` | `runner.ExecuteScalar()` -> `GetElement` | DB-side scalar (e.g. a COUNT aggregate, and now `InsertWithIdentity`) |
| `SetNonQueryQuery` | `runner.ExecuteNonQuery()` -> `GetElement` returning `int` | Insert/Update/Delete/InsertOrReplace affected-row counts |

`SetNonQueryQuery2`, `SetQueryQuery2` and `SetIfExistsUpdateElseInsert` (the old 2-/3-query fallbacks for `InsertOrReplace`, `InsertWithIdentity` and the Upsert-with-When-predicate fallback) are gone from `QueryRunner`. Multi-statement behavior is now a `SqlCommandScenario` built at render/execution time (e.g. `DmlServiceBase.BuildInsertOrUpdateScenario`, see `QueryRunner.InsertOrReplace.cs:142-145`) and walked by `DataConnection.QueryRunner`, so the `Query` always has exactly one `QueryInfo`.

`SetRunQuery<T>` runs `FinalizeQuery(query)` first, which calls `query.SqlOptimizer.Finalize` on the single `query.QueryInfo.Statement` (`QueryRunner.cs:275-286`). If the provider does not support skip with the current take value (`SqlProviderFlags.GetIsSkipSupportedFlag`), `GetExecuteQuery` folds `Skip` into a larger `Take` and wraps the result in a `LimitResultEnumerable<T>` that drops the first N rows client-side (`QueryRunner.cs:434-472`). The same emulated skip is now also applied to the `GetResultFromReader` path (`QueryRunner.cs:1182-1195`), so a combined command reader gets identical semantics.

### 4. Materialization mapper (`Mapper<T>`)

`QueryRunner.Mapper<T>` (`QueryRunner.cs:72`) caches a compiled `Func<IQueryRunner, DbDataReader, T>` per concrete data-reader type -- the runtime reader type matters because different providers expose different `Get*` overloads, and `MapperExpressionTransformer` (`QueryRunner.cs:161`) rewrites the original expression `ConvertFromDataReaderExpression` nodes against the actual reader instance (`QueryRunner.cs:215-221`). The transformer also rewrites `SqlQueryRootExpression` references to read the live `IDataContext` off the `IQueryRunner` (`QueryRunner.cs:200-213`). `WrapMapper` (`QueryRunner.cs:1207`) binds the mapper lambda locals (`IDataContext`, `Expressions`, compiled-query `parameters`, `SqlCommandExecutionContext`) from `IQueryRunner` properties only when the body references them; the compiled-query args are read as `qr.ExecutionContext.Parameters`.

On `FormatException` / `InvalidCastException` / `LinqToDBConvertException` / `*NullValueException` (Oracle, MySql), `ReMapOnException` (`QueryRunner.cs:113`) switches the column to slow-mode (`slowMode: true` in `TransformMapperExpression`, `QueryRunner.cs:255`), which keeps the `ConvertFromDataReaderExpression.ColumnReader` in the tree instead of inlining the typed `Get*` call. The `IsFaulted` flag on `ReaderMapperInfo` prevents infinite retry on a column that genuinely cannot be read.

When `Configuration.OptimizeForSequentialAccess` is true, `SequentialAccessHelper.OptimizeMappingExpressionForSequentialAccess` rewrites the mapper to read each column exactly once -- required for `CommandBehavior.SequentialAccess` semantics where re-reading a column throws (`SequentialAccessHelper.cs:57`, invoked at `QueryRunner.cs:264-265`).

The mapper is invoked in three places: `BasicResultEnumerable<T>.GetEnumerator` / `GetAsyncEnumerable` for set-returning queries (`QueryRunner.cs:499-626`), `ExternalReaderResultEnumerable<T>` for rows read from a reader owned by someone else (combined eager loading, `QueryRunner.cs:634-739`, it opens a runner only to give the mapper its context -- the command is never executed), and `ExecuteElement<T>` / `ExecuteElementAsync<T>` for first-row aggregates (`QueryRunner.cs:1284-1363`). The set-returning and first-row paths apply `IUnwrapDataObjectInterceptor.UnwrapDataReader` before the first read so providers like MiniProfiler can hand back the underlying reader for mapper compilation.

### 5. `IQueryable<T>` adapter and execution entry

`ExpressionQuery<T>` is the type the public API surfaces as `IQueryable<T>`. The execution paths it implements (`IEnumerable<T>.GetEnumerator`, `IEnumerable.GetEnumerator`, `IQueryProvider.Execute(T)`, `IQueryProviderAsync.ExecuteAsync<TResult>`, `ExecuteAsyncEnumerable`, `GetForEachAsync` / `GetForEachUntilAsync` / `GetAsyncEnumerator`) all share the same skeleton: obtain the expressions container (`GetOwnExpressions`: the compiled container when `CompiledExpressions` is set, otherwise a fresh `RuntimeExpressionsContainer` over `Expression`), call `GetQuery` (which memoizes the `Query<T>` reference via `Info` only when `CompareInfo.IsFastComparable` is true and `dependsOnParameters` is false -- `ExpressionQuery.cs:106`), call `StartLoadTransaction[Async]` (a thin delegation to `Query.StartLoadTransaction[Async]`, `ExpressionQuery.cs:145-153`) to start an implicit transaction *only* when `query.IsAnyHarvesters()` and the data context is not already in a `TransactionScope` or transaction, then run harvesters and call the executor. Enumeration goes through `query.GetEagerEnumerable[Async]` (combined or sequential, see section 7); element execution (`Execute`, `ExecuteAsync`) uses `GetEagerElement[Async]` when set, else `InitHarvesters[Async]` + `GetElement[Async]`. When a load transaction exists the main rows are buffered (`BufferedRows<T>.Read` for sync, `BufferedAsyncEnumerable<T>.CreateAsync` for async) and the transaction is committed *before* the first row is returned.

The "fast comparable" memoization avoids the cache lookup entirely on subsequent calls to the same `IQueryable<T>` instance. This is only safe when the query has no dynamic accessors / value-equality probes (because those need to be re-evaluated against the live context every call) and when the exposer did not mutate the tree (`dependsOnParameters` is true when the second-phase `ExpandedQuery` lookup was the one that hit / created the entry -- `Query{T}.cs:207-215`).

### 6. Compiled tables and dependent arguments

`CompiledTable<T>` (behind `CompiledQuery`) shares one global per-`T` `MemoryCache` across all compiled queries, so its key must separate fold sites and argument values. The key is the tuple of operation tag CT, `ConfigurationID`, `this`, `QueryFlags` and `DependentArgumentValues`. Expose can materialise an argument read from the parameter array when the target is `[SqlQueryDependent]` (hints, table names); the resulting `Query<T>` is only valid for those values, so their positions (`_dependentArgumentIndexes`, seeded from a pre-expose scan by the constructor caller) are part of the key. Because expansion is recursive, a dependent position can appear only after several rewrites; `GetInfo` therefore (1) tries the cache, (2) builds the query outside the cache via `BuildQuery` (publishing before validation would let another thread hit an entry built for different argument values), (3) compares `materializedSlots` against the known indexes with `IsCovered`, and (4) either publishes a sized entry (`Size = 1`, sliding expiration from `LinqOptions.CacheSlidingExpirationOrDefault`) or, on an unseen slot, returns the uncached query, widens `_dependentArgumentIndexes` under `_learnLock` and retries. The per-`T` cache is capped (`SizeLimit = 1000`, `QueryRunner.cs:48-52`) since entry count now follows distinct argument values. `Create` returns a `Table<T>` over the exposed tree (`query.CompiledExpressions.MainExpression`) with `Info`, `Parameters` and `CompiledExpressions` pre-set so `ExpressionQuery<T>` does not re-expose against a mismatched tree. Async-to-sync method rewriting (`ReplaceAsyncWithSync`) was removed from this class. Execution passes the compiled argument array into `InitHarvesters[Async]`, which returns a `SqlCommandExecutionContext` even for a query with no harvesters (`Query.cs:185-213`), and that context feeds both the parameter accessors and the mapper.

### 7. Eager-load execution: harvesters, combined commands, buffered rows

**Added in delta f90c5bcfb** (replaces the old `Preamble` / `InitPreambles` model). Entry point is `Query<T>.GetEagerEnumerable[Async]` (`Query{T}.cs:59`, `73`), called by every `ExpressionQuery<T>` enumeration path. It first asks `QueryRunner.TryGetCombinedEagerEnumerable<T>` (`QueryRunner.cs:1108`) for a combined enumerable, and otherwise falls back to the sequential path: `InitHarvesters` runs each `Harvester.Execute` in index order and `GetResultEnumerable` streams the main query.

The combined path returns `null` (sequential fallback) unless all of these hold: `query.GetResultFromReader` is set, the query has harvesters, `LinqOptions.UseCombinedCommands` is on (master switch, off by default in 6.x because combining changes the emitted SQL and the ADO.NET path), the context is a `DataConnection` / `DataContext` whose provider has `IsMultiStatementBatchSupported` and `IsMultipleResultSetsSupported`, no `QueryHints` / `NextQueryHints` are pending (the sequential `GetCommand` applies and clears them), `DataConnection.ProcessQuery` is not overridden (`IsProcessQueryOverridden`), at least one harvester is combinable (`IStepMaterializer.CanCombine` with a non-null `GetCombinableQueryInfo`), and `IsCombinableOrderSafe` holds (`QueryRunner.cs:1108-1153`, `824-857`).

`EagerResultEnumerable<T>` (`QueryRunner.cs:750`) models all harvesters plus the main query as one `SqlCommandScenario` whose step index equals the harvester build index (main query last). Combinable harvesters become `Reader` steps, non-combinable ones (KeyedQuery, CteUnion, detached, buffer, no-op) become `SelfExecuting` steps with no statement. ORDERING INVARIANT (`BuildGroups`, `QueryRunner.cs:945`): non-combinable steps run first as singleton groups in ascending index order, then the combined groups, so a non-combinable harvester may only read slots of lower-indexed siblings. `IsCombinableOrderSafe` refuses the combined path for any layout where a non-combinable harvester sits above a combinable one, because that would silently yield an empty collection. `BuildPlan` (`QueryRunner.cs:966`) renders through `CombinedReaderBatch` and caches the statement-free step facts, the group list and the command templates on `QueryInfo.EagerCommandCache` (`PreparedScenario`), so a warm execution only allocates this run parameter values and DbParameters. A `PreparedScenario` built for the other backend (DbBatch vs concatenated commands) is discarded (`WasBatch` check). The walk itself is `DataConnection.QueryRunner.RunGroups[Async]`, whose callbacks write each harvest into the `SqlCommandExecutionContext`; the main result set (last step of the last group) streams lazily from the open reader, which the enumerable owns.

Locking and connection state: `BuildPlan` holds `lock (_query.QueryInfo)` plus the monitors of every combinable child `QueryInfo` (`CombinableMonitors`, main first then children in index order) -- the same monitor `GetCommand` takes before its in-place Modify-mode visitors, which also makes the cache read/render/publish atomic. A `DataContext` run takes `AcquireLock()` for the whole enumeration. `CloseAfterUse` is suppressed on the shared connection while the combined reader is walked (nested runners disposing would close the context and the reader mid-walk, seen with the EF Core bridge) and restored before the final dispose.

Read-consistency transaction: `StartLoadTransaction` only starts when `IsAnyHarvesters()` is true, and the transaction now covers reads only. `BufferedRows<T>.Read` / `BufferedAsyncEnumerable<T>.CreateAsync` drain the main enumerable, `LoadTransaction.Complete[Async]` commits, then the buffered rows are handed to the caller, so user code never runs inside the implicit transaction. On the combined path `Preambles` stays untouched (`ExpressionQuery.Preambles` is set only when `combined` is false) because the combined enumerable owns its harvesters, and `GetForEachUntilAsync` relies on that.

## Known issues / debt

- **Global cache is now a single shared resource across all result types.** (Superseded item -- see AUDIT-NOTE.) The single-threaded per-type reorder debt this bullet used to describe no longer applies -- the old per-`Query<T>` copy-on-write array cache (bounded 100 entries, `Monitor.TryEnter` reorder) was replaced by one process-wide `QueryCache.Default` bucketed by `(ResultType, ContextType, ConfigurationID, QueryFlags, ChainHash)`. New watch point: the approximate `_entryCount` used for the `DefaultMaxEntries` (10,000) global trim is maintained via `Interlocked` adds/subtracts rather than a live count, so it can transiently drift under concurrent `TryAdd`/sweep races -- `ReconcileEntryCount` (`QueryCache.cs:291-306`) is the only path that recomputes it exactly, and it only runs from `ClearAll`. The drift only affects when the global sweep triggers, not correctness -- per-bucket eviction (`BucketCap = 16`) still bounds any single bucket exactly.
- **Static state, narrowed.** The per-type static `_queryCache` on `Query<T>` this bullet used to describe is gone (see `## Subsystems` section 1) -- the main LINQ query cache is now a single eagerly-created `QueryCache.Default` static field (`QueryCache.cs:45`), registered once. Per-pair-type static `QueryRunner.Cache<T>` / `Cache<T,TR>` plus `Update<T>.Cache` still exist for the CRUD-op caches (Insert/Update/Delete/InsertOrReplace/etc.) and still register their own cleaner in a `static` constructor each -- `Query.CacheCleaners` still only fires for types that have been touched. Worth knowing when chasing memory growth from those op-specific caches; the main query cache memory is now bounded globally (`DefaultMaxEntries`) regardless of how many result types are in play. `QueryRunner.Cache<T>.QueryCache` (used by `CompiledTable<T>`) is bounded per closed `T` (`SizeLimit = 1000`), not globally.
- **`TODO: debug cases when our tests go into slow-mode (e.g. sqlite.ms)`** -- repeated comment in `Mapper<T>.Map` (`QueryRunner.cs:101`) and both copies of `BasicResultEnumerable<T>` (`QueryRunner.cs:537`, `603`). Indicates the slow-mode fallback is hit in tests and the maintainers do not have a clean reproduction story.
- **`IBuildContext` reachable from `CloningContext`.** `CloningContext` (`CloningContext.cs:15`) lives in this area but transitively touches `IBuildContext` from EXPR-TRANS -- the area boundary is fuzzy here. `CloningContext` is invoked from translator paths in `Builder/`, but its public API (`Clone*` / `Correct*`) is also reusable elsewhere.
- **`PersistentTable<T>.DataContext` returns `null!`.** (`PersistentTable{T}.cs:38`) Any code path that pulls a `DataContext` off a queryable wrapped in `PersistentTable` will NRE -- the type exists for narrow scenarios where the underlying queryable is not a linq2db one and SQL generation is not expected.
- **`CompiledTable<T>` dependent-slot learning costs one extra build per newly discovered slot** (the uncached build is discarded and retried); the index set only grows, never shrinks, so a fold site that once materialised a wide slot set keys on all of it thereafter.
- **Combined eager loading is opt-in and layout-restricted.** It requires `LinqOptions.UseCombinedCommands` (off by default in 6.x) plus provider multi-statement / multi-result-set support, and silently falls back to the sequential harvester path for pending query hints, an overridden `DataConnection.ProcessQuery`, or any layout where a non-combinable harvester precedes a combinable one (`QueryRunner.cs:1108-1153`). The ordering invariant is enforced by a predicate, not by construction: a future harvester strategy that violates it loses combining, not rows. Memory cost: the buffering in `ExpressionQuery.cs` via `BufferedRows<T>` hold every main row in memory when an implicit load transaction is active (the price of committing before the first row is yielded).
- **Obsolete `IQueryRunner.QueryNumber`** is always 0 and slated for removal in version 7 (`IQueryRunner.cs:67-68`); `GetElement`-family callers still pass the literal 0 to `GetQueryRunner`.

## Pointers

- Cache miss diagnosis: instrument `Query<T>.CacheMissCount` and `Query.CacheCleaners`. A miss with a tree that *should* match an existing entry usually means `ExpressionCacheHelpers.ShouldRemoveConstantFromCache` is returning `false` for a non-scalar value that does not implement `IExpressionCacheKey` (the new `QueryCache` buckets on `ChainHash` first, but a hash collision or divergence there only costs a bucket-list scan, never a false negative, since `Query.Compare` still does the real equality check). A cached query rejected on every execution can also come from duplicate-parameter sharing of impure expressions -- see Subsystems section 2.
- Mapper crash with `FormatException` / `InvalidCastException`: check `Configuration.OptimizeForSequentialAccess` first -- sequential-access mode rewrites the mapper aggressively and the failure may be in the rewrite, not the materialization.
- Implicit-transaction surprises (deadlocks under eager loading): `StartLoadTransaction` (`Query.StartLoadTransaction`, shared with `CompiledTable<T>`) only kicks in when `query.IsAnyHarvesters()` is true. Eager-loading queries open one transaction across all harvesters + the main query, but it now covers reads only: the main rows are buffered (`BufferedRows<T>`) and the transaction committed before the first row is returned. `IsAnyHarvesters()` returns `false` when every harvester is `IsInlined` (e.g. CteUnion single-query mode) even if the array is non-empty.
- `CompiledQuery` correctness: `CompiledTable<T>` is keyed by fold-site identity plus the values of `[SqlQueryDependent]` arguments (`DependentArgumentValues`); the older `ReplaceAsyncWithSync` rewrite and original-expression key no longer exist. If a compiled query returns SQL built for another call hint or table name, check `_dependentArgumentIndexes` coverage in `GetInfo` (Subsystems section 6).
- Upsert with a When predicate on a provider without MERGE/ON CONFLICT: the older `SetIfExistsUpdateElseInsert` / `SetNonQueryQuery2` orchestration in `QueryRunner.InsertOrReplace.cs` is gone. Trace through `DmlServiceBase.BuildInsertOrUpdateScenario` (outside this area) and the `SqlCommandScenario` walk in `DataConnection.QueryRunner` instead. The old three-query path was documented as non-atomic across sessions, so callers needing atomicity should still wrap the `Upsert` call in their own transaction (not re-verified for the scenario path).
- Eager load that returns an empty collection with no exception: check `IsCombinableOrderSafe` / the ordering invariant (Subsystems section 7) and whether a harvester reads a result slot that has not been populated yet. Toggle `LinqOptions.UseCombinedCommands` to compare the combined and sequential paths.
