# Authoring scripts under `.claude/scripts/`

When and *whether* to reach for a script lives in [agent-rules.md](agent-rules.md) → *PowerShell Core scripts for complex operations*. This doc covers how to write one once you've decided to.

## Why scripts beat raw Bash chains

- **Contract, not a recipe.** The script exposes a single stdin-JSON / stdout-JSON interface. The caller doesn't need to shuttle intermediate values through temp files, environment variables, or shell-variable plumbing — all multi-step state lives inside the script.
- **One permission rule per operation.** The permission system evaluates each unique Bash command string independently, so a sequence of N related commands fires N allowlist prompts even when each piece is individually permitted. A single script invocation matches one rule for all internal calls it makes.
- **No compound-command friction.** The Bash chain rule in `agent-rules.md` forbids `&&`, `;`, and shell control flow. Work that genuinely needs branching, loops, or error-gated sequencing fits naturally inside a script and stays off the Bash surface.
- **Structured error handling.** The script can fail early with a non-zero exit and a diagnostic line on stderr, or emit a partial-success JSON with per-item `ok` flags. The caller reads one result object instead of reconstructing status from several partial Bash outputs.
- **Cross-platform.** `pwsh` behaves identically on Windows (including Git Bash), macOS, and Linux, sidestepping the MSYS path-mangling gotchas that bite raw `gh` / `git` calls.

## Contract

- Single entrypoint, named after the operation in kebab-case (e.g. `pr-context.ps1`, `post-pr-review.ps1`).
- Emit exactly one JSON result to stdout — nothing else. Diagnostics and errors go to stderr.
- **Fail with a machine-readable remediation.** When a failure has a concrete fix the caller can apply, pass `Exit-WithError -NextAction '<instruction>'` — it emits a stable `next_action:` stderr line the calling agent can act on and re-invoke, instead of only reporting the failure. Keep the hint a specific, actionable instruction (`pass -ManifestFile <path>`, `write non-empty JSON to <file>`), not a vague "check your input". The shared manifest/stdin readers already do this; adopt it in a new script wherever the error is caller-fixable.
- **Input shape — pick the form that minimises permission prompts.** Stdin pipes / heredocs from Bash create novel command strings that miss `Bash(pwsh -NoProfile -File <path> *)` allowlist matches and trigger prompts. Prefer one of these single-command forms:
  - **Scalar / few-field inputs:** declare a `param()` block with named CLI parameters (e.g. `-Pr 5503`, `-NoFetch`). Caller invokes `pwsh -NoProfile -File <path> -Pr 5503` — single token sequence, allowlist matches.
  - **Structured / nested inputs (arrays of files, hunks, comments):** accept a `-ManifestFile <path>` parameter and read the JSON via the shared `Read-ManifestFromFileOrStdin` helper. Caller writes the manifest to `.build/.agents/<script>-<id>.json`, then invokes `pwsh -NoProfile -File <path> -ManifestFile <json>`.
  - **Stdin JSON** (legacy): keep accepting it for shell heredoc callers and pre-existing flows. New scripts should not require it.
  - **A `pwsh -File` parameter is always a *string* — a `[string[]]` param does not collect a comma-separated argument.** `-File` invocation does no PowerShell argument parsing, so `-Names a,b,c` arrives as the single string `"a,b,c"` bound to element `[0]`, and the script then acts on one nonsense value while reporting success for the rest. Declare `[string]` and split explicitly (`$List.Split(',', [StringSplitOptions]::RemoveEmptyEntries) | ForEach-Object { $_.Trim() }`), or take a list through `-ManifestFile`. The failure is quiet: a deletion loop given `-Names a,b,c` printed `MISSING a,b,c….md` once and reported *"dropped 1 files"* where 9 were intended.
- Common helpers live in `_shared.ps1`, dot-sourced at the top of each script (`. "$PSScriptRoot/_shared.ps1"`). Use `Read-ManifestFromFileOrStdin -ManifestFile $ManifestFile` for the structured-input pattern — it falls back to stdin when the parameter is empty.
  - **That stdin fallback is not reachable from the PowerShell tool — always pass `-ManifestFile`.** `$json | & .claude/scripts/<name>.ps1` looks like the obvious call once you have the manifest in a variable, and the "falls back to stdin" wording above reads as an invitation, but a PowerShell *pipeline* into `& <script>.ps1` does not put anything on the script's stdin; the script exits with `no manifest JSON on stdin` and its `next_action:` hint. Write the JSON out first — `[System.IO.File]::WriteAllText($path, $payload, (New-Object System.Text.UTF8Encoding $false))` — then invoke with `-ManifestFile $path`. Stdin remains reachable from a Bash heredoc, which is the caller that fallback exists for.
- Invoke as `pwsh -NoProfile -File .claude/scripts/<name>.ps1 -<Param> <value>` from Bash. `-NoProfile` skips user profile load (faster startup, no side effects).
- Do not write scratch files unless the manifest asks for one. When a caller needs to stream a large body into the script, accept either an inline field (`"body"`) or a file path (`"bodyFile"`) and resolve it server-side.
- Fan-out parallelism inside a script uses `Start-ThreadJob` or `ForEach-Object -Parallel` — both require PowerShell 7+ and run independent subprocess invocations without adding any Bash-call cost to the caller.
- **Resolve DB connection strings from config — never hardcode them.** A committed script that needs a provider connection string looks it up **by name** from `DataProviders.json` / `UserDataProviders.json` (walk `MyConnectionStrings` → `LocalConnectionStrings` → `CommonConnectionStrings`, exactly as `release-test-cli-scaffold.ps1`'s `CN()` helper does), rather than inlining a server / port / password. File-DB providers (SQLite / DuckDB / Access) may compose their `Data Source=` path in-script — that's a repo-relative file path, not a secret. (Corrected on #1553: `Tests/FSharp.Scaffold/generate.ps1` hardcoded the PostgreSQL / SQL Server strings.)

## Gotchas

Discovered while building the current set of scripts — worth knowing before you add a new one:

- **`$using:` does not nest.** A `Start-ThreadJob` spawned inside `ForEach-Object -Parallel` cannot access `$using:foo` from the outer parallel scope. Flatten to one parallel level, or copy the value into a local variable first.
- **`exit` inside a parallel block only kills that runspace.** Surface fatal errors from inside `Start-ThreadJob` / `ForEach-Object -Parallel` by returning an object with an `error` field and letting the parent check it — do not call the shared `Exit-WithError` helper from inside the scriptblock.
- **`ConvertFrom-Json` parses numbers as `[int64]`, not `[int32]`.** A plain `-is [int]` check fails for every JSON-sourced integer. Use the `Test-IsInteger` helper in `_shared.ps1` (or coerce via `[long]` / `-as [int]`) when validating numeric manifest fields.
- **`ConvertFrom-Json` parses ISO-8601 strings as `[datetime]`, not `[string]`.** A field like `"2026-05-08T11:01:12Z"` round-trips through the manifest as a `[datetime]`; `[string]$v` then renders it in the **current culture** (e.g. `05/08/2026 11:01:12`), not ISO -- silently breaking anything that re-emits the value as a timestamp (a GitHub `since=` filter, a cursor write-back, a downstream JSON field, a comparison against an ISO string). Normalize before use or output: `if ($v -is [datetime]) { $v.ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ssZ') }`. (Bit `kb-fetch-github.ps1`: the `since` filter went out malformed so the fetch returned `0` items, and `next_cursor` was written back in local culture, corrupting the saved cursor.)
- **GitHub REST node IDs commonly exceed `Int32.MaxValue`.** Comment IDs, review IDs, and reply IDs returned from `/repos/{o}/{r}/pulls/{n}/comments` and friends now routinely exceed 2.1B. `Test-IsInteger` accepts the value (since it allows Int64), but a subsequent `[int]$item.commentId` cast throws `Cannot convert value … to type System.Int32` at runtime. Cast to `[long]` (not `[int]`) for any GitHub REST id field — including the response side (`[long]$replyResult.data.id`, not `[int]$replyResult.data.id`). Surfaced 2026-05-10 in `post-pr-thread-replies.ps1`.
- **Empty arrays get unwrapped in single-expression `if/else` assignments.** `$x = if ($cond) { @(...) } else { @() }` stores `$null` in `$x` when the else branch is taken, and `ConvertTo-Json` then serialises the field as `null`. Use statement form: `$x = @(); if ($cond) { $x = @(...) }`.
- **Use forward slashes for dot-source paths.** `. "$PSScriptRoot/_shared.ps1"` works on every platform; backslashes are literal characters in filenames on Linux/macOS and cause the lookup to fail there.
- **Plan-style scripts (compute → write plan file → consumer reads plan file): keep stdout summary-only.** When the script's contract is "compute a plan, write it to disk, downstream actions read from disk", duplicating the full plan content to stdout is wasted bytes — it pushes large stdout into permission-prompt / truncation territory, and the agent reads the disk plan anyway. Emit counts + paths + per-item change flags on stdout; full arrays / before-after content stay on disk. Surfaced 2026-05-14 on PR #5521: `release-publicapi-reconcile.ps1 -Action plan` was writing 10+ MB JSON (72 PublicAPI files × full shipped/unshipped before/after arrays) until trimmed to summary-only.
- **Declare on/off parameters as `[switch]`, never `[bool]` — a `[bool]` param is unsettable from every caller we have.** `pwsh -File` passes every argument as a **string**, and a `[bool]` parameter rejects strings outright: both `-AzdoLogs $false` and `-AzdoLogs 0` die with *"Cannot process argument transformation on parameter 'AzdoLogs'. Cannot convert value "System.String" to type "System.Boolean""*. That kills the Bash `pwsh -NoProfile -File …` form, the PowerShell tool's `-File` form, and an Azure Pipelines `arguments:` string alike — a `[bool]` is only reachable from `-Command`/dot-sourcing, which we never use. When the flag should default **on**, invert the default into the name (`-NoAzdoLogs`) rather than defaulting a `[bool]` to `$true`. (Surfaced 2026-07-29 authoring `Build/Azure/scripts/verify-analyzer-packaging.ps1`; its sibling `verify-nuget-sizes.ps1` still carries a `[bool] $AzdoLogs` that no pipeline caller can actually set.)
- **Don't name a helper function after a PowerShell keyword.** `function Do {…}` is a parse error (`Missing statement body in do loop`) because `do` is reserved (`do { } while`). Same trap for `If`/`For`/`While`/`Switch`/`Trap`. Use `Run`/`Invoke-X`/a verb-noun name.
- **Indexing a single-element pipeline result hits a *scalar*, not a 1-element array.** A pipeline that yields one item returns that item unwrapped; `$x[0]` then indexes *into* it — for a string, `'Feature'[0]` returns the char `'F'`, silently corrupting comparisons (a label-`Implied` helper returned `'F'`/`'B'`/`'T'` and every equality check failed → 226 false "mismatch" flags). Wrap pipeline results you intend to index/`.Count` in `@(...)`: `$parts = @(… | Select-Object -Unique)`. (Same family as the empty-array-unwrap gotcha above.)

  **`return` unrolls too, so a helper that returns a collection needs a leading comma.** `return $copy` hands back a bare element when `$copy` has one item, and the caller's `.Count` then throws *"The property 'Count' cannot be found on this object"* under `Set-StrictMode` — or, without StrictMode, silently reads a string's characters. `return , $copy` (and `return , @()` for the empty case) pins it. This bites a sort/filter helper hardest, because it works on every multi-item input and fails only on the one-item one: a manifest where most components resolve to exactly one version made *every* call hit the scalar path. (Surfaced 2026-09-03 in `Build/Azure/scripts/third-party-notices.ps1`.)
- **Rewriting a source file line-by-line: read with `[System.IO.File]::ReadAllLines`, not a ``-split`` on a `` "`r?`n" `` regex.** The `-split` form mis-split a real source file this session (the subsequent index assignment threw *index out of range*); `ReadAllLines` splits reliably on any of CRLF / LF / CR. And **preserve the file's line endings + trailing newline** or git reports a whole-file diff: detect the EOL before splitting (`$nl = if ($raw.Contains([char]13 + [char]10)) { … CRLF } else { LF }`), join with it, and re-append a trailing newline when the original had one. Prefer the `Edit` tool for a few known lines; reach for a script only for *computed* edits across many lines (e.g. column-alignment via `PadRight`). (PR #5703 review fixes.)
- **An `[ordered]` hashtable rejects *new* keys via property syntax.** `[ordered]@{}` produces an `OrderedDictionary`, not a `PSCustomObject`: assigning to an existing key with dot notation works, but adding one throws *"The property 'matches' cannot be found on this object. Verify that the property exists and can be set."* Use the indexer for anything conditional — `$result['matches'] = @(...)` — or declare every key up front. Bites exactly where it is least convenient: building a result object whose optional fields depend on parameters, so the script works until the first caller passes the optional flag. (Hit twice in one session on a scratch AzDO log-fetcher; the plain `@{}` form has no such restriction, which is why the habit doesn't transfer.)
- **String comparison is case-*insensitive* by default — in `-eq`/`-ne`, `-contains`, `-in`, `Group-Object`, and `@{}` hashtable keys alike.** For any analysis where a case-only difference *is* the signal — diffing identifiers, building a rename map, deduping symbol names, comparing SQL parameter names — the default silently reports "no change". Use `[string]::Equals($a, $b, [System.StringComparison]::Ordinal)` for the comparison and `[System.Collections.Generic.Dictionary[string,object]]::new([System.StringComparer]::Ordinal)` (or `-CaseSensitive` on `Group-Object` / `Sort-Object -Unique`) for the accumulator. (Surfaced reviewing PR #5733: a baselines rename scan keyed on `-ne` dropped the case-only `@Usage` -> `@usage` rename entirely — 684 occurrences across 58 providers — and reported 13 renames where there were 14. The miss was caught only because a subagent had counted independently.)

  **`-like` and `-match` are case-insensitive too, and there the damage is a false *positive* rather than a missed diff.** A prefix pattern written for one id quietly swallows another that differs only in case: `'linq2db.ClickHouse' -like 'linq2db.cli*'` is **`$true`** — `Cli` matches `cli`, and the rest is absorbed by the wildcard. Use `-clike` / `-cmatch` whenever the pattern encodes an identifier, and prefer an exact test plus a *delimited* prefix (`$id -eq 'linq2db.cli' -or $id -like 'linq2db.cli.*'`) over a bare `id*`, so a longer sibling id cannot match at all. (Surfaced 2026-09-03 mapping packed artifacts to their notices: `linq2db.ClickHouse`'s twelve components were folded into `linq2db.cli`'s notices file and ClickHouse's own came out with none. The shipped script was unaffected only because its prefix carried the trailing dot.)
- **`` `t `` / `` `n `` inside a double-quoted string is a tab/newline escape, not a literal backtick.** Building output with `"…`type:`…"` injects a TAB before `ype:` (the backtick + `t`), so a label like `` `type:` `` renders as `<TAB>ype:`. Use single-quoted strings for literal text containing backtick-adjacent letters, or escape the backtick (`` `` ``). Em-dashes / other non-ASCII in *captured* output are a separate hazard (console code-page mangling — see [`windows-dev-gotchas.md`](windows-dev-gotchas.md)); writing the script to a file with the `Write` tool (UTF-8) avoids the inline-mangling path.
