# Review rubric module: packaging

Rules of the [`code-reviewer`](../../agents/code-reviewer.md) rubric that fire only on a path-identifiable change kind. Read when the briefing's `rubricModules` lists this module, or omits the field. Rule numbers are the core rubric's; "rule N" resolves through the core's **Focus scoping** index. In a multi-pass review, apply only the rules of your pass's focus:

| Rule | Focus |
|---|---|
| 15 | `api-and-test` |
| 17 | `api-and-test` |

15. **Bundled-dependency license notices.** Three artifact families physically redistribute third-party binaries under a `PackageLicenseExpression` that covers only linq2db's own code: `linq2db.CLI` (`PackAsTool` publishes the whole dependency closure into the package rather than declaring it), the 14 T4 packages under `NuGet/` (each copies named provider assemblies into `tools/`, including SQL CE and the SAP HANA client out of `Redist/` and IBM's `clidriver` tree), and the LINQPad **5** `.lpx` (`Pack.cmd` archives the entire `net472` output directory). The LINQPad *nupkg* is not one of them — it declares its clients as dependencies since #5786.

    Since #5731 this is mechanised, so the review question has moved. `Build/licenses/components.json` inventories every redistributed component and `Build/Azure/scripts/third-party-notices.ps1` enforces it on **every PR** in both `build-job.yml` and `.github/workflows/build.yml`: a bundled binary that no notices file accounts for fails the build, and a hand-edited or un-regenerated notices file fails it too. So do **not** file "this new dependency's license may not match" as a finding — CI answers that, and the pre-existing-gap caveat this rule used to carry is obsolete.

    What still needs a human is the **content of a manifest entry**, which CI cannot check. When a PR touches `Build/licenses/components.json`, review: the `license` and `copyright` against the package's own nuspec or embedded license file (resolve from nuget.org rather than guessing — `https://api.nuget.org/v3/registration5-gz-semver2/<lowercase-id>/index.json` → the newest `catalogEntry.licenseExpression`); `versions` being a per-TFM map wherever `Directory.Packages.props` conditions that package on `$(TargetFramework)`; `artifacts` listing every artifact that actually ships the file; and `redistribution` — an entry flipped from `unresolved` to `permitted` is an assertion about vendor terms and needs the evidence stated, which is `MAJ` if it is merely asserted. A generated file under `Build/licenses/generated/` edited by hand is a defect regardless of its content. `Build/licenses/README.md` documents the schema.

    Do **not** apply any of this to ordinary library projects — their dependencies travel as NuGet references and carry their own licenses. (Rule origin: PR #5678, where `ModelContextProtocol` — Apache-2.0 — was added to the `MIT`-declared `linq2db.cli` package; generalised and mechanised by #5731.)
17. **Dependencies moved from a shipped package to runtime provisioning.** When a PR removes `PackageReference`s from a *packed* project so the dependency is supplied at runtime instead — a host provisioning them per connection / per session, a plugin loader, an on-demand download — enumerate every code path that loads an assembly the product does not itself ship, and establish **which process each runs in**. The removal is invisible to a source-only read: the code compiles unchanged, CI is green, and the failure appears only where something tries to load a now-absent assembly. Look for `Assembly.LoadFrom` / `LoadFile` / `Load`, host helpers such as `DataContextDriver.LoadAssemblySafely`, and any type enumeration over a *third-party or user-supplied* assembly (`GetExportedTypes`, `GetTypes`) — the last is the sharpest, because enumerating types forces resolution of their base types and interfaces. Flag `MAJ` when a path that used to resolve no longer can. Also check the reverse direction: prose or a readme added by the PR that describes the new model as unconditional, when a fallback path still provisions everything. (Surfaced on PR #5786: the LINQPad driver's 22 client packages left the nuspec, and the connection dialog — which runs in LINQPad's own process, seeing only the driver's *static* dependencies — could then no longer load a user's static-context assembly that referenced one of them. Three review passes read the nuspec change; none asked what loads external assemblies. It surfaced in manual testing.)
