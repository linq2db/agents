# Review rubric module: tests

Rules of the [`code-reviewer`](../../agents/code-reviewer.md) rubric that fire only on a path-identifiable change kind. Read when the briefing's `rubricModules` lists this module, or omits the field. Rule numbers are the core rubric's; "rule N" resolves through the core's **Focus scoping** index. In a multi-pass review, apply only the rules of your pass's focus:

| Rule | Focus |
|---|---|
| 6 | `api-and-test` |
| 10 | `code-correctness` |
| 22 | `api-and-test` |

6. **Test coverage.** Is there a test? Does it cover the edge cases the fix is about? Is it in the right file? **New public surface needs a test:** every new public member surfaced in `api_changes[]` needs at least one test exercising it — a new public API with no test is a **MAJ** (the "a fix that clearly needs a test" rule, extended to new surface). **`DisableBaseline` reason strings are a regression signal.** When the PR adds a new `using (new DisableBaseline("…"))` (or `using var x = new DisableBaseline("…")`) to an existing test, read the reason string. If it describes a translation symptom — "current time in literals/parameters", "client-side fallback", "non-deterministic SQL" — it usually means the PR introduced a translation regression: previously deterministic server-side SQL now embeds a runtime parameter / literal, breaking baseline capture. Trace the affected `Sql.<Member>` / `<Type>.<Member>` through the registration table in the relevant translator base (e.g. `DateFunctionsTranslatorBase`) and check whether each per-provider override still returns server-side SQL. Reasons that just describe non-determinism in the test data (e.g. `"Server-side date generation test"`) are independent and don't apply.

    **For a *translation* feature, a predicate-shaped test guards itself and a projection-shaped one does not.** When the PR teaches the builder to translate some member or call, its tests split into two groups with very different power. A test that uses the shape in a `Where` is safe by construction: a declined translation throws `could not be converted to SQL`, so the test cannot pass on a regression. A test that uses it in a `Select` is not, because a decline falls back to client-side evaluation over the materialized row and returns **exactly the same values** — so a value-only assertion stays green with the feature entirely removed. Flag a projection-shaped test whose only assertion is on the returned values, and ask for an assertion on the emitted SQL. Two things to get right before filing it, both cheap:

    - **Check that an assertion is even possible.** Some shapes emit identical SQL either way, and then the test is not weak — there is nothing to assert and the finding is wrong. An accessor that translates to *the column itself* is the usual case: selecting `opt.Value` and selecting the option column then unwrapping it in memory both emit `SELECT [col]`. Compare the baseline for the shape against the same query with the feature suppressed; if they match, drop the finding rather than proposing a non-discriminating assertion.
    - **Name a discriminator that survives every provider.** The assertion has to be a token the translated form contains and the fallback does not — `IS NOT NULL` for a null test, a function name for a function. Beware "the SQL must not mention sibling column X": a client-side fallback selects only the columns it needs, so X is often absent from both forms.

    (Surfaced on #5704, measured by mutation: with `FSharpMemberTranslator` fully disabled, 16 of 17 option tests went red and `OptionQuery_IsSomeProjection` stayed green — its SQL had silently lost the `IS NOT NULL` from the SELECT list. The same pass wrongly accused two `.Value` projection tests, which emit byte-identical SQL either way.)

    **Apply [`test-review-checklist.md`](../test-review-checklist.md) to every new / modified test in the diff.** That doc enumerates the recurring test-quality traps (substring SQL assertion too weak, `LastQuery` captured at the wrong point, `IsAnyOf(ProviderName.X)` against versioned context names, `[DataSources]` missing on regression tests, time-based assertions that depend on DB-server-vs-runner timezone, identifier-length limits like Firebird 3's 31-char cap, `query.ToSqlQuery()` vs the SQL of an aggregate call, etc.). Each item has its own severity guidance; findings go in the regular `findings[]` stream.

    **A provider-gated test must gate the *call*, not just the assertion — and the gate must express the capability the API actually requires.** Two failure modes, both of which pass review by looking gated:
    1. **The gate guards only an assertion.** `var skipCnt = !context.SupportsRowcount(); … var cnt = db.NewApi(x); if (!skipCnt) cnt.ShouldBe(1);` suppresses the *comparison* while the call one line above still executes. That is harmless while the API merely returns an unreliable value, and becomes a hard failure the moment the PR makes it **throw** for that provider class. Whenever a PR introduces or extends a throw-for-unsupported-provider path, grep the fixture for gates of this shape and check each one guards the invocation.
    2. **The gate expresses the wrong capability.** A helper such as `SupportsRowcount()` encodes one flag, but the API's real precondition may be a disjunction (`IsUpdateOutputRowsSupported || IsAffectedRowsCountSupported`). A gate narrower than the precondition over-skips providers where the contract *is* enforceable (losing coverage silently); one broader than it lets the call run where the API throws. Derive the gate from the flags the implementation actually reads, and prefer reading them off `db.SqlProviderFlags` over a name-based test helper.
    Flag `MAJ` when the mismatch makes a test fail on a provider leg, `MIN` when it only over-skips. (Surfaced on #5643: five tests gated on `SupportsRowcount()` — exactly `IsAffectedRowsCountSupported` — while the API required that flag **or** update-output support, so the unguarded calls threw on ClickHouse: 10 failures across direct and LinqService. The same helper simultaneously over-skipped YDB in the concurrency-failure test, where the OUTPUT path makes the contract fully enforceable. A prior human review had noted the gate as merely "imprecise".)

    **New provider-fanned test mirroring a gated pattern must carry the same gate.** When the PR adds a provider-parameterized test (`[DataSources]` / `[EFDataSources]` over all providers) that exercises a feature/model an *existing* test already gates — via `[ActiveIssue(<providers>)]` (same helper + model — e.g. `IdentityTable` + `CreateTempTable`) **or** via a provider-capability gate from the `[ThrowsForProvider]` family (`[ThrowsRequiresCorrelatedSubquery]` and kin) — check whether the new test needs the same gate. A copied pattern that drops the gate reintroduces the known per-provider failure at CI, not review. Flag `MAJ` with the gated sibling cited, `suggestion` adds the matching gate. (Surfaced on PR #5378: `TempTableSurvivesAcrossCommands` copied `Issue4333Test`'s identity-temp-table pattern but omitted its `[ActiveIssue(TestProvName.AllPostgreSQL)]` — PostgreSQL identity-column temp tables are a known limitation, #4333 — so it failed only on PostgreSQL CI.)

    **The gate's *variant* must match too, not only its presence.** A gate that is too wide fails CI just as surely as a missing one, with the opposite message: *"Expected a LinqToDBException to be thrown, but found: ''"* on every provider that actually runs the query. The common case is `[ThrowsRequiresCorrelatedSubquery]` (default `simple: false`, expecting YDB **and** ClickHouse to throw) on a simple correlated shape that ClickHouse executes, where the same-shape siblings carry `simple: true`. Compare the arguments, not just the attribute name. Flag `MAJ` with the sibling cited. (Surfaced on #6027: `Issue6024_CorrelatedAnyOwnIsNotNull` used the default while every other `Any` test in `AllAnyTests.cs` used `simple: true`, and all six ClickHouse contexts went red.)

    **Key off the *operation*, not off a copied sibling in the same file.** The rule above is naturally read as "the PR duplicated a neighbouring test and dropped its attribute", which is why it misses the commoner shape: a test written from scratch, in its own `Issue<N>Tests.cs`, using an operation whose gated siblings live in a *different* file the diff never touches. Nothing in the diff points at them. So when a new `[DataSources]` test uses a construct with known per-provider limits — a set operation, an affected-rows assertion, a window frame — grep the suite for other tests using that same construct and compare their attributes, rather than only scanning the enclosing file. (Surfaced on #5833: `ExceptBranchProjectingDerivedType` was a fresh test in `Issue5683Tests.cs`, and the `[ThrowsRequiresCorrelatedSubquery(simple: true)]` it needed sits on `SetOperatorTests.TestExcept` — a file the PR does not modify. It reached CI ungated and reddened the YDB leg. See [`testing.md`](../testing.md) → *`Except` / `Intersect` in a `[DataSources]` test need the YDB correlated-subquery gate*.)

    **An assertion the run never reaches asserts nothing — and a green run cannot tell you it fired.** The rules above all ask whether a test *covers* the right thing; this one asks whether its assertions execute at all. The dangerous shape is an assertion placed on a conditional path: inside a `catch`, behind an `if`, under a `context.IsAnyOf(...)` branch, or after an early `return`. Such a test passes in two very different worlds — the assertion ran and held, or the path was never taken — and the pass/fail count cannot distinguish them, so it reads as coverage in CI, in the baselines, and in the PR body. The `catch` case is the one that survives review, because the surrounding prose usually explains *why* a throw is expected and that explanation is what gets checked instead of the behaviour. **Treat the explanation as a claim: confirm the guarded path is actually taken at HEAD.** Where the claim is that some other still-open issue makes the call fail, that is precisely the claim to test — a bug filed against a different shape or a different model need not reach this one. Flag `MAJ` when the assertion cannot fire at all (the test is vacuous as written), `MIN` when it fires only on some providers in its gate. (Surfaced on the second review of #5840: `UpdateWithOutputDefaultProjectionOverInheritanceRoot` asserted `Is.Not.InstanceOf<ArgumentException>()` inside a `catch`, on the documented premise that the query still fails on #5838. It does not — measured across SQLite ×2, SqlServer.2019 ×2, PostgreSQL.16 and DuckDB plus LinqService variants, it raises nothing at all, so the `catch` never ran and the test asserted nothing on any provider. Two source-reading review passes and a green CI leg had all accepted it.)

    **A test whose *input* cannot separate the arms proves nothing either — and unlike the case above, its assertion really does run.** The rule above catches an assertion the run never reaches; this one catches the mirror, where the assertion executes, holds, and is nonetheless blind. The shape: a fixture named after a specific case, on an input for which the correct implementation and the suspected defect agree. It passes in both worlds, so the pass/fail count cannot distinguish them and the *name* is the only thing asserting coverage. Reviewing a diff that adds or renames a fixture, don't stop at "is there a test for X" — ask **which input decides X**, then check the fixture uses it. The tell is a fixture whose input is byte-identical to a sibling's, or whose name mentions a condition the input never varies. Where the decision is a predicate with two clauses, the discriminating input is the one where the clauses disagree, and it is usually derivable from the predicate's own definition. Flag `MIN` and name the input; propose the mutation check (break the product, confirm only the intended fixture reddens) rather than asserting the gap from reading. (Surfaced on #5788 round 3, three times in one PR: `ReportsAttributedStubWithServerSideOnlyExplicitlyFalse` used `Sql.Function`, which does not derive from `Sql.ExtensionAttribute` and therefore already yields `false` when unset — so it stayed green under an inverted read of the very predicate it is named for, proved by mutation; a second fixture was byte-identical to one 320 lines above it; and a documented `GeneratedCodeAnalysisFlags` behaviour had no fixture on either host.)

    **A shared test-config change must account for every consuming assembly, not just Tests.Linq.** When the PR edits a shared test resource — `DataProviders.json` / `.template` connection strings, `TestConfiguration`, a `TestBase` setup — verify that *all* test assemblies reading it stay correct. The **EF.Core** test project (`Tests/EntityFrameworkCore`) is a *separate* assembly that re-derives its own connection string in `TestBase.GetConnectionString` (runs the base CS through `SqliteConnectionStringBuilder`, overriding only `DataSource`) and has none of Tests.Linq's assembly setup (e.g. the in-memory keep-alive anchor in `TestsInitialization`). A base-CS change that leans on Tests.Linq-only setup silently breaks EF.Core at CI, not review. Flag `MAJ` with the unhandled assembly cited. (Surfaced on PR #5698: switching `SQLite.MS` to `Mode=Memory;Cache=Shared` left `Mode`/`Cache` in the EF-derived CS, so the shared-cache in-memory DB — kept alive only in Tests.Linq — evaporated between EF ops → `no such table`.)
    **A new test that exercises an already-gated feature owes the same gate — check the canonical fixture.** The rules above ask whether the assertions are meaningful; this one asks whether the test can *run* everywhere it says it does. When a PR adds a test that uses a feature some providers cannot support, the exclusions are usually already written down somewhere — in the fixture that owns that feature — and the new test, written against a fresh `[DataSources]`, simply doesn't carry them. Nothing in the diff points at the omission: the new file looks self-consistent, and the gap only appears as a red provider leg after CI has run the whole matrix. Reviewing a diff that adds a test using a named strategy / option / API, grep `Tests/` for the fixture that already covers it and diff the `[DataSources]` attributes; when they disagree, ask why. Flag `MIN` (`MAJ` when the omission would redden a leg), and prefer the combination-scoped `Assert.Ignore` guard over a whole-test exclusion when only one `[Values]` arm is affected — [`testing.md`](../testing.md) → *Excluding a provider from one combination*. (Surfaced on #5938: two new eager-load tests parameterized over `EagerLoadingStrategy.KeyedQuery` used a bare `[DataSources]`, while all ~30 tests in `EagerLoadingStrategyKeyedQueryTests.cs` carry `[DataSources(TestProvName.AllAccess, TestProvName.AllSybase)]` — KeyedQuery emits a FROM-less `UNION ALL` key set Access rejects. 16 red Access cases, found by CI rather than by review.)

10. **Playground project leaks.** Two playground edits are PR-acceptable: structural updates to `Tests/Tests.Playground/Tests.Playground.csproj` (SDK / package / property changes that keep the project building) and updates to `Tests/Tests.Playground/TestTemplate.cs` (keeping the template current). Flag the rest with severity `BLK`, regardless of who authored the PR:
    - **New source files added under `Tests/Tests.Playground/`** (any `.cs` other than `TestTemplate.cs`) — tests belong in `Tests/Linq/`, playground access is via `<Compile Include>` link, so a new file in this directory is by definition local scratchpad.
    - **New `<Compile Include>` test-fixture references in `Tests.Playground.csproj`** — those are `test-writer`'s `playgroundLink` entries, fast-iteration scratch that should not be committed.

    The fix is "revert this hunk": for a new line in the csproj, emit a `suggestion` that removes the entry; for a new `.cs` file, demote to file-level and describe the revert in `fix`. Do not exempt fork-author commits or "they probably meant to push it" rationales.
22. **A test gate narrowed or split on *asserted* provider behaviour needs a run behind it.** When a PR replaces a blanket gate with a narrower one — an `[ActiveIssue]` `Configuration` list, a `ThrowsForProvider` expectation, or a new method carved out of a `[Values]` / `[ValueSource]` arm — the justification arrives as prose stating what each provider does. Ask whether the PR could *observe* that. The providers with no GitHub-CI leg are exactly the ones an author working from a local run cannot reach (Oracle and SQL Server 2005–2016 on netfx are Azure-only; the Jet and ACE Access drivers differ from each other), so a claim about them is a hypothesis in a comment's voice. The tell is prose asserting behaviour — *"passes everywhere"*, *"only X gets it wrong"*, *"both drivers word it the same"* — with no run covering the named set; some gates admit it themselves, carrying `unvalidated:` or "not reachable from this workstation" in their own `Details`. Flag `MAJ` when the narrowing un-gates a provider the PR never ran, `MIN` when it only rewords `Details`. Ask for the CI round, not for better reasoning — [`ci-tests.md`](../ci-tests.md) → *The GitHub half* covers finding the legs that settle it, and note that a gate's own `Details` is not evidence about the gate. (Surfaced on PR #5882, which carved four methods out of gated tests on stated premises — *"RowByRow inserts a row at a time and never builds the empty column list, so it passes everywhere"*, *"the true arm … which only ClickHouse gets wrong"*, *"both ACE drivers reject it with the same sentence"*, and a null-arm declaration inherited from the non-null arm. A full two-system CI round refuted all four: RowByRow emits `DEFAULT VALUES` and fails on seven providers, Oracle fails the true arm a step earlier than ClickHouse, the Jet drivers word it two other ways, and SQL Server 2005 and 2008 each raise something different again.)

    **The gate's own declared error is the same kind of assertion, and it is the half that gets read as data rather than as a claim.** The rule above fires on a gate being *narrowed*; a gate being *added* carries `ErrorType` / `ErrorTypeName` / `ErrorMessage` naming an exception and a message for a provider the author may not be able to run, and those fields look like transcription even when nothing was transcribed. Check that the declared type and text are traceable to something — a CI log, a `.trx`, an `ErrorHelper` constant — rather than to the author's recollection of the failure. Two tells: a message worded like a different provider's dialect (a SQL Server overflow sentence on an Access gate), and a type that cannot be reached by the wrapper the context uses ([`testing.md`](../testing.md) → *`[ThrowsForProvider]` covers the `.LinqService` context* — the direct case must **start with** the declared type, so a pin naming the inner exception of a wrapped failure never matches). `MIN` on its own, `MAJ` when the gate is the only thing standing between the suite and an unverified provider claim. (Surfaced on PR #5708: `[ThrowsForProvider(typeof(InvalidOperationException), ProviderName.AccessJetOleDb, ErrorMessage = "Conversion failed because the Int16 data value overflowed")]` was written from memory on a workstation that cannot run the 32-bit Jet drivers. The run throws `LinqToDBConvertException` — *"The numerical value is too large to fit into a 96 bit decimal"* — so the pin failed on exactly the one leg it existed for, and was the PR's only red leg.)
