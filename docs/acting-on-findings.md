# Handling a review finding — yours or someone else's

What to do once a finding exists: proving it, weighing a suggestion you are about to accept, and choosing its
disposition. Loaded on demand; [`agent-rules.md`](agent-rules.md) → *Before coding a fix or feature* keeps the
triggers.

Neighbouring docs: severity vocabulary and output shape are in [`review-conventions.md`](review-conventions.md),
review orchestration in [`review-orchestration.md`](review-orchestration.md), and the probe that proves a finding
in [`evidence-discipline.md`](evidence-discipline.md).

**Red test first for a review-finding fix.** When fixing a reproducible review finding (yours or a reviewer's), write the failing (red) regression test *before* the fix — it confirms the finding is real and that the fix targets it. If no repro can trigger it, don't fix on speculation: post a "could not reproduce" FYI with repro details + a test pinning the current (correct) behaviour, rather than a speculative core change.

**Verifying a finding means checking its mechanism *and* its stated consequence — they fail independently.** A finding has two halves: the structural claim ("this handler swallows X") and the fallout claim ("so Y happens"). Confirming the first says nothing about the second, and the first is the easy one — it's visible in the diff, so it's what a verification pass naturally checks, after which the whole finding reads as confirmed. Trace what the failure path actually produces before repeating the consequence back. The correction is usually not "the finding is wrong" but "the finding is right for a different reason", which changes its severity and the reply you owe its author. Applies symmetrically to an objection *you* raise against someone else's finding: an argument from absent precedent ("nothing in the repo does it this way") is a claim about the corpus, not about whether the approach works — measure it before it costs the author a rewrite. (Surfaced on #5701: a reviewer's `FlattenInvariantException`-swallowing finding was structurally exact, but its "execution continues with the un-flattened `INNER JOIN LATERAL` shape" fallout was wrong — a decline there leaves the node *un-reduced*, so `UnwrapLambda` throws and the failure is loud, not silent row loss. In the same review a `ThrowsForProvider`-over-provider-exclusion suggestion was objected to on absent precedent; one probe against a live YDB container showed it works on both the direct and `LinqService` legs, and the objection was dropped.)

**A suggestion you are about to *accept* is a claim too — especially a "tightening" the reviewer says they did not probe.** The rules above gate findings you *dispute*; the acceptance direction has no gate, and it is the one that ships. A restructuring suggestion — add a condition, narrow a guard, make the code match its own doc comment — reads as a free consistency win, so it gets recommended on the strength of its argument rather than on a run. But the argument is about *intent*, while which states actually reach the code is a fact about the program: a condition that "obviously cannot matter" is precisely the shape of a condition nobody has measured. When the reviewer has already said they didn't probe it (*"I did not probe whether …, so this is a tightening rather than a demonstrated defect"*), read that sentence as the instruction to run it. Apply, run the affected tests, *then* recommend — the run costs one build and the withdrawal costs the author's trust in every other disposition in the same walk. (Surfaced on #5818: SUG003 proposed confining `DeclinedForSetProjection` to `BuildPurpose.Expression`, was recommended for acceptance on the reasoning that the existing tests would decide, and the tests decided against it — all three binary-`+` set-operation tests came back with the original bug, because `StringMemberTranslatorBase.TranslateBinaryStringConcat` re-enters the visitor through `TranslationContext.Translate` under `BuildPurpose.Sql` while `CombineBuildFlags` keeps the flag. The recommendation was withdrawn one turn later.)

  **A suggestion declined *on a premise* is not settled once your own work invalidates that premise — re-raise it, naming the change.** Options presented in a walk carry an implicit justification, and the user's "no" attaches to the justification, not to the suggestion forever. The recurring shape is a wider fix declined because it would disturb a file the task otherwise leaves alone — a perfectly good reason, and one a later item in the same walk can quietly destroy by modifying that file anyway. When it does, the original "no" is now protecting nothing, and shipping the narrow fix leaves an inconsistency the PR *itself* created: one call site changed, its identical twin two functions away untouched, in a file the diff already rewrites. Re-raise once, in one sentence, stating what changed rather than re-arguing the merits — the user is deciding against different facts, not being asked twice. Do **not** treat this as licence to relitigate a decline whose premise still holds; the trigger is a *specific* invalidated premise you can name. (Surfaced on #5704: MIN001's banned `Activator.CreateInstance` was offered as *fix* vs *fix + sweep the identical sibling*, and the sweep was declined while `FSharpOptionSupport.fs` was untouched. Three items later a `'T option`-over-single-case-union fix rewrote that file's converter builder. Re-raised with that fact, the answer was *"yes, sweep"*.)

  **This binds hardest where it feels weakest: an *example* a reviewer supplies for a doc fix.** The rule above is framed around a restructuring suggestion, so it does not fire on the case that looks like pure prose — a reviewer says a comment is inaccurate and offers two concrete shapes to prove it, and you write those shapes into the comment. Nothing about that reads as a behavioural claim, which is exactly the problem: an example asserting "input X reaches this code and produces Y" is a claim about the program, and shipping it into a doc comment publishes it under your name in the place future readers will trust most. Run each example before it goes in the file. (Surfaced on #5740: a pass argued a doc comment overstated a walk's restrictions and cited `values.Length` and `-x` as unary shapes crossing it. Both went into the rewritten summary unrun. Measured, `ArrayLength` over a captured array never reaches the method at all — the translator claims the expression and rejects it — and `t.Int1 == -x` parameterises the operand and emits the negation in SQL, so naming the parameter after `x` is correct. The doc fix shipped two wrong examples and needed a correcting amend of its own commit.)

  **The mirror is a rationale you write for your *own* design choice, and it evades every rule above because it does not read as a claim at all.** Choosing design A over B and writing down why produces a sentence of the shape *"X rather than Y, which would Z"* — a comparative behavioural assertion about two implementations, one of which you never built. It goes into the commit message and the PR body, where it becomes the durable explanation a future reader trusts most, and nothing about writing prose feels like it needs a run. Run the arm you rejected, or state the reason without the counterfactual. (Surfaced on #5893: a `_disposed` latch was chosen over nulling `_enumerator` because nulling *"would let `MoveNextAsync` silently re-run the query"*, and that sentence shipped in both the commit message and the PR body. Neither arm had been run — the latch guarded only `DisposeAsync`, so a post-dispose `MoveNextAsync` re-ran the query anyway, and measured, it also left the implicit load transaction open past two further `DisposeAsync` calls. A review probe found it, one line of guard closed it, and the rationale had to be corrected in public.)

  **A "now identical to its twin" correctness argument is a duplication finding.** When the case for a fix being right is that the code now matches a sibling verbatim, read your own sentence back: the verbatim match you are citing as evidence is the property that let the two drift in the first place, so restoring it restores the exposure. This is the cheapest of these rules to apply — no plan, no probe, just noticing what your justification rests on — and among the highest-yield, because the twin is already open in front of you. Decide unify-vs-patch explicitly instead. (Surfaced on #5893: *"The method body is now identical to `GetForEachAsync` apart from the predicate break"* went into the PR body as proof the fix was complete. That identity is exactly why `GetForEachUntilAsync` had missed the load transaction, the preamble initialisation and the enumerator disposal its twin acquired years earlier; a review pass read the same sentence as a hazard, and the two were given one shared body for −15 lines.)

**An incidentally observed failure is not coverage — the assertion is what tests a mechanism, not the red you happened to see.** Proving a fix by running new tests against the unfixed code shows you a lot of reds, and some are *not* the failure the test asserts: a test aimed at X can fail through mechanism Y on the way. Watching Y happen feels like having tested Y, and that is the moment a severe failure mode gets crossed off a list nobody ever wrote down. Credit a mechanism as covered only when some assertion would fail if it regressed and nothing else did. (Surfaced on #5893: exception masking was named in the PR body *and* in a public discussion reply as *"the more damaging case"*, and the body's own red-on-master table credited `CurrentBeforeMoveNextTest` with covering *"the masking mechanism itself"* — on the strength of an NRE it had watched replace its own assertion failure. That test never invokes the initializer, so the masking path was never entered, and none of the six new tests constructed it. A seventh closed the gap, and it needs a `LoadWith` query: `Query.StartLoadTransactionAsync` returns null without beginning a transaction when there are no preambles, so on a plain query the initializer has nothing that can fail.)

**An adjacent shape you noticed while fixing a proven regression gets a test written, not offered.** The rules above are framed around a *review finding*; the gap they leave is the regression you found yourself. Having proved one defect and named a neighbouring shape nothing covers — "no current test exercises this; worth pinning if you want" — write the test instead of closing with the offer. Two reasons, and the second is the real one. The cheap reason is that you already have the worktree built, the provider configured and the repro in hand, so the marginal cost is one build. The load-bearing reason is that **the test is what tells you how bad the defect actually is**: a shape you can only reason about gets written up at the severity your reasoning supports, and severity assessed that way is systematically too low. Verify the neighbours before you report, then report what they showed. (Surfaced on #5750: a fix was proposed with the note that neither a `Union` nor a `WHERE` shape was covered and either was "worth a regression test if you want it pinned". The maintainer's answer was *"ah, add those regression tests before ci"* — and writing them moved the finding from *extra columns in the SELECT* to **wrong results** (a `Union` returning ten rows where three were selected) plus a **hard translation failure** (`The LINQ expression … could not be converted to SQL`) on a query that worked on master.)

**Check a deliberate-looking element's provenance before flagging or changing it — it may exist because of an earlier review, possibly your own.** When a finding targets something that reads as a considered decision — a named error message, an explicit gate, a comment defending a choice — spend one `git log -S "<token>"` over the PR's own commits plus a scan of the review threads on that file before proposing anything. It changes the output in two ways. The element may have been added *in response to a prior finding*, in which case the right artifact is a **`Correction:` retraction of that finding** rather than a fresh defect filed against the author, who implemented what they were asked for. Or its rationale may already be recorded at the site, in which case the finding is at most that the rationale is *wrong* — a much stronger and more specific claim than "undocumented". Cheap: one `git log -S` and one grep of the thread bodies already loaded with the PR context. (Surfaced on #5750, at the user's prompting — *"check why message was added"*. A translation-stage refusal carrying a named message traced to my own earlier `MIN003`, which the author had implemented verbatim and closed with my own premise quoted back at me. Measurement then showed that premise — that a translation-time refusal leaves a projection free to fall back to .NET — was false. Without the provenance check it would have been filed as a defect in their work instead of a retraction of mine.)

**Once a review finding is reproduced, "fix it here" is the default recommendation — reserve track-it-separately for what is structurally unfixable in the PR.** Having proved a defect red, don't offer a tracking issue, a comment-only touch-up, or a doc note as the *recommended* disposition when the fix lands inside the code the PR already changes. The test to apply is whether the fix is **reachable from this PR's own surface**: a defect in the same file / package the PR edits is in reach and should be proposed as a fix plus a regression test; a defect whose correct fix needs a capability the PR doesn't have — a new provider feature, a different target shape the API cannot express, a cross-cutting core seam — is the genuine tracking case, and saying so explicitly is what makes the tracking issue land without pushback. Distinguishing the two is the whole judgement; defaulting to "track it" for both is what the rule forbids. (Surfaced on #5701: a proven three-chained-`groupJoin` row-loss bug was written up with a recommendation to *"fix the comment + file a sibling issue"* — the maintainer's answer was **"add tests and fix here"**, and the fix was nine lines in the file the PR already changed. In the same walk, a correlated-inner-sequence gap that genuinely could not be expressed as a flat `GroupJoin` was accepted as a tracking issue without objection.) Pairs with [`review-orchestration.md`](review-orchestration.md) → *Default the recommendation to a pushed fix, not a posted comment*.

**A correct refutation does not vouch for the explanation shipped with it.** The rules above gate a
claim you might *accept*; this one gates the moment you have just been proven wrong. A reviewer who
demolishes your mechanism usually offers a substitute in the same breath, and the demolition — which
you can verify instantly, often from evidence already in front of you — lends the substitute an
authority it has not earned. They are two separate claims from the same author, and the second one
is exactly as unverified as yours was. Test it the same way you should have tested yours; the cost
is one probe and the alternative is trading a wrong mechanism for a wrong mechanism you now believe.
(Surfaced on the Octonica investigation: a Fable review correctly killed a claim that
`ClickHouseDataReader.Close(disposing: true)` swallowed the real exception — the repro's own output
disproved it — and proposed the drain-loop swallow via a partial read instead. Building that case
showed the exception surfaces there too. The actual masking was plainer and in neither account: the
exception from `TempTable.Dispose()` replaces the original during `using`-scope unwinding.)
