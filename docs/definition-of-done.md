# Definition of done

A consolidated completion checklist for a code change on linq2db. The completion gates already live, canonically, in the rules this doc points at — they were scattered, so this file gathers them in one place to walk before declaring a change "done" or proposing to commit / push. **Nothing here is a new rule; each item links its owner.** Not every item applies to every change — skip the ones that don't, but skip them knowingly.

Referenced from [`AGENTS.md`](../AGENTS.md) → *Definition of done*.

**This is the *exit* checklist; its entry counterpart is the work plan.** A change's design — problem, success criteria, authorized edit-points, impact map, test obligations — is recorded before the first edit in `.claude/plans/<key>/plan.md` ([`work-plan.md`](work-plan.md)). The two interlock: a plan's `P9` block records **results against the items below**, under the gate ids `G-01`…`G-08` that [`work-plan.md`](work-plan.md) → *P9 Verification gates* maps to them. The gates themselves are defined here and nowhere else; the plan only records what they returned, and `work-plan.ps1 -Action gates` derives which of them a given change's edit-points make applicable.

## The checklist

- [ ] **Tests run and pass via `/test`.** Don't `dotnet build` / `dotnet test` by hand around the skill — it injects the `CreateDatabase` filter and runs the baselines diff. New behavior has a red→green test; a fix that clearly needs a test has one. On any branch that edited `Tests/`, run `test-diff-sweep.ps1 -IncludeWorkingTree` before push; on a planned branch `G-01` also records its counts on the **implemented** tree — the amendment-time sweep cannot see tests written after it. A hit on branch test code that the plan does not cover is still a branch finding, never waived as "outside this plan", and the sweep re-runs before every push that touches `Tests/`. Naming a hit a review item is an option only for commits by another author that an amendment adopts (`/work-plan` → *Mode: amend* step 4); a hit in the branch author's own commits is fixed. (#6186: four one-line chains on a branch with no plan. #5673: the plan's `G-01` set the branch's hits aside as outside its scope, and later pushes added more. #5708 A-19: the author named its own 84 chains and 5 unreasoned narrowed sets review items, and round 4 raised them.) ([`agent-rules.md`](agent-rules.md) → *Running tests*; [`testing.md`](testing.md).)
- [ ] **A new `[DataSources]` test runs beyond SQLite before push, including one taken from a reviewer's snippet.** The snippet ran only where the reviewer ran it. Run it on Access and SqlCe locally and on every provider with a container in `docker ps -a`, asked for as one named batch, and name each family left out with its reason. It re-runs with the sweep on every follow-up commit to an open PR. This binds a branch with no plan; on a planned branch it is the `G-01` rule in [`work-plan.md`](work-plan.md) → *P9 Verification gates*. (#6438: `BetweenOfValueAndOneConvertedBound`, taken from a review snippet run on SQLite and PostgreSQL, was pushed after a SQLite-only run and failed all 20 Access and Firebird configurations.)
- [ ] **A branch that ports code from, or is an alternative to, another open PR carries that PR's review answers.** Walk its review threads: each test and out-of-diff doc added in response comes over with the ported code, or is named as not applying. This binds a branch with no plan. (#6444: four review findings had been answered on #6314 before most of the branch's commits.) ([`work-plan/SKILL.md`](../skills/work-plan/SKILL.md) → *Is this branch an alternative to another open PR*.)
- [ ] **On a planned branch, the plan is reconciled before every push — CI-triage commits included.** `work-plan.ps1 -Action reconcile -Key <key> -Head HEAD` exits non-zero when a changed file has no `E-n`, and when validate reports a `P9`/`P11` error (an amendment without its `conventions:` line, critic round or sweep counts — #6037: A-7's three such errors stood while its merge was pushed); write the `A-n`, with its `conventions:` line for a test edit, before the commit rather than at the next review, which is the only other place reconcile runs. (#5843 `7d8fa9752` and #6208 `0af703ad3`: CI-fix commits pushed with no amendment, so the test conventions reached the code only at review.) ([`work-plan/SKILL.md`](../skills/work-plan/SKILL.md) → *Mode: check*.)
- [ ] **Baselines reviewed, not just regenerated.** A moved baseline is reviewed for intent; a baseline that drifts on every run (embedded `DateTime.Now` / `Guid` / clock) is a test bug to fix at the source, not noise to wave through. ([`bug-investigation.md`](bug-investigation.md) → *Non-deterministic baselines*.)
- [ ] **New public surface is accounted for.** Any added / changed public (non-`Internal.*`) member: `PublicAPI.Unshipped.txt` updated, XML doc present, and at least one test exercising it. ([`code-design.md`](code-design.md) → *Public API is a contract*; `AGENTS.md` → *Code conventions*.) For any public member, `Internal.*` included, the doc is checked for **content**, not presence: it states the contract points the plan's `D-n` / `A-n` give the member — a keep-all arm, a throw, a delegate's call shape. (#6008: SUG002 in round 2 and SUG003 in round 3, both on `FormattableStringHelper`, each a doc that existed and omitted or contradicted the contract.)
- [ ] **API baselines are NOT a per-PR task.** `Source/**/CompatibilitySuppressions.xml` is regenerated once during release prep (`/release-verify` → `/api-baselines`), not on each feature PR — regenerating them on a branch adds churn the release flow redoes anyway. A feature PR's obligation stops at `PublicAPI.Unshipped.txt` (the item above) — **unless the PR removes or changes a member present in the baseline package**: then "Build and pack" fails with ApiCompat `CP0002`/`CP0001`, and the PR runs `/api-baselines` itself (#5971). When they *are* regenerated, it is through the `/api-baselines` skill and never by hand. A project that sets `EnablePackageValidation=false` because it has no shipped version yet is switched on by the first bump after it ships (`/release-postpublish` step 4, baseline = its first release), so the comment names that step — not "next release" with no owner (#5640), and not "next major" (#6351). ([`agent-rules.md`](agent-rules.md) → *Agent guardrails (anchor set)* → never hand-edit API baseline files.)
- [ ] **Third-party notices ARE a per-PR task** — unlike the item above, and that contrast is the whole reason this one gets missed. `Build/licenses/components.json` keys on *files inside a packed artifact*, not on new packages, so a TFM-conditional `PackageReference` added to an already-packable project (`LinqToDB.CLI`, the T4 packages, the LINQPad `.lpx`) puts new DLLs under `tools/<tfm>/<rid>/` **by construction** and reddens the branch's own `Build and pack` plus the Azure `build`. The test is *"does a packable artifact gain a file"*, never *"does the branch add a package"*. Run `Build/Azure/scripts/third-party-notices.ps1 -Action harvest`, add the proposed entries and any new `texts/` body, `-Action generate`, then `-Action check` — and commit `components.json`, the new text and the regenerated `generated/` files together. Before pushing, `-Action verify -PublishDir <dir>` against one cross-published non-Windows RID; CI checks all seven. ([#5956](https://github.com/linq2db/linq2db/pull/5956): the work plan's impact map excluded `components.json` on the grounds that the branch produces no new package — 35 unmapped DLLs across every CLI RID.)
- [ ] **A package or NuGet-audit change restores everything CI restores.** Restore `linq2db.slnx` **and** `Examples/Examples.slnx` with `-p:Configuration=Release` — `-c Testing` restores net10.0 only, and the Examples solution is outside `linq2db.slnx`. A pin that changes a version the CLI bundles is a notices change too (item above), even when no file is added. ([`code-design.md`](code-design.md) → *Shipped packages don't pin vulnerable transitive dependencies*; #6043: two CI rounds, one per gap.)
- [ ] **A shipped project that gains or loses a .NET Framework target is added to or removed from the FPU JIT sweep.** Both the `Tests.FpuJit.csproj` `ProjectReference` and `ExpectedAssemblies` in `Program.cs`; a missed addition leaves the gate green. ([`testing.md`](testing.md) → *The x86 FPU JIT sweep*.)
- [ ] **Builds on the portable TFMs**, not just the latest TFM. The `Testing` config builds only `$(LatestTargetFramework)`; a BCL API newer than netstandard2.0 needs a `Directory.Build.props` polyfill or a CI-red `build` leg. ([`agent-rules.md`](agent-rules.md) → *TFM API availability*.)
- [ ] **Release build of every edited project, `Tests/Linq/Tests.csproj` included.** Analyzers and XML-doc checks run in Release only, repo-wide; a `Source` Release build cannot see a test file's errors. On a planned branch the result is a `P9` row under `G-05`. (#5772: `LinqToDB` was clean in Release while the PR's own tests failed MA0154 and CA1846; #6145.) ([`AGENTS.md`](../AGENTS.md) → *Build gotchas that fast-iteration hides*.)
- [ ] **A new or moved TFM gate withholds a feature, not recognition of unchanged source**, and a dropped TFM comes with its ns2.0 break inventory. An ns2.0 fix is proven red with `worktree-test.ps1 -LinqToDBAsset netstandard2.0`, because CI never runs those code paths. ([`code-design.md`](code-design.md) → *A TFM gate may withhold a feature, never recognition of unchanged source*.)
- [ ] **An added .NET major TFM comes with a ban-list overload check** — `banned-api-overloads.ps1` against the new and previous ref packs, new same-hazard overloads banned beside their twins, result in the PR body. ([`code-design.md`](code-design.md) → *Adding a .NET major TFM: re-check the ban lists*.)
- [ ] **No unrelated reformatting / renames.** Only lines the task touches are changed; intentional column alignment is preserved. ([`agent-guardrails.md`](agent-guardrails.md); [`code-design.md`](code-design.md) → *Column-aligned formatting is intentional*.)
- [ ] **No playground scratch staged.** No new `.cs` under `Tests/Tests.Playground/` (beyond `TestTemplate.cs`) and no new `<Compile Include>` test-fixture links committed. ([`agent-rules.md`](agent-rules.md) → *Git commit rules*.)
- [ ] **Cross-cutting core changes were surfaced, not made silently**, and rest on a red→green test or CI — not static reasoning. ([`agent-rules.md`](agent-rules.md) → *Before coding a fix or feature*; [`agent-guardrails.md`](agent-guardrails.md) → *Cross-model verification for high-blast-radius core changes*.)
- [ ] **The diff got an adversarial read before the PR opens** (Tier M/L; a Tier S mechanical change skips it). **A branch with no plan has no tier, so this item binds it whenever the change is not mechanical**: more than one source file, or any edit under `Internal/Linq/Builder` or `Internal/SqlProvider`. (A 13-commit, 18-file predicate fix with no plan had all ten review findings produced afterwards by this same pass.) Run the `code-reviewer` pass over the branch's diff and walk what it returns, exactly as a review of someone else's PR would. When the branch has a plan, run `work-plan.ps1 -Action validate -Done` first: it fails on any gate still `(pending)` and on a `G-01` that names no test for some `TO-n`, and a read against blank gates only re-derives what they should already record. **Not** a posted self-review — no GitHub write, no draft; the point is the rubric applied cold by something that did not write the code. This is the exit counterpart to the plan's `plan-critic`: the *design* is attacked before implementation by a different model, and without this the *diff* is attacked only once the PR is public, which spends a maintainer's review round on findings one subagent call would have produced. Every other item on this list is a mechanical check, so nothing else here asks an adversarial question about the code. (Measured on [#5893](https://github.com/linq2db/linq2db/pull/5893): a single pass over the 3-file diff surfaced all five changes the post-PR review later landed — three as findings, two as out-of-scope observations.) **On a branch not pushed yet** (or whose `origin/pr/<n>` still holds a superseded design), `diff-reader.ps1` / `verify-lines.ps1` have no ref to read: brief the pass with `git -C <worktree> diff <base>` plus the untracked files to read directly, tell it to read files from the worktree, and to verify line anchors by reading them there. (#6008: two findings and two out-of-scope observations, all acted on, from a pre-push pass briefed that way.) **Either way, brief `rubricModules`** with the `modules` field of `pwsh -NoProfile -File .claude/scripts/review-rubric-modules.ps1 -Base <base> -RepoRoot <worktree>` (committed, uncommitted and untracked paths), even when it is `[]`. ([`review-pr/SKILL.md`](../skills/review-pr/SKILL.md) → step 6; [`code-reviewer.md`](../agents/code-reviewer.md).) **An amendment pushed to an already-open PR owes the same read.** A Tier M/L `A-n` that adds or re-words edit-points gets a `code-reviewer` pass over the amendment's own diff before its push, recorded in `P9` as its own `G-09` line. (#5707 round 3: a 7k-line amendment went to an open PR without one, and three of the four review findings were prose or test code that one pass would have caught.)
- [ ] **Re-run on the merged tree when master has moved under the branch's tests.** If `git log origin/<branch>..origin/master -- <every file the branch changes>` is non-empty, merge master and re-run the branch's tests before declaring the branch ready. Key it on the source files too, and on any file declaring a member the tests read: master can move the internals a test observes without touching the test. (#6033: #5673 moved the command cache from `QueryInfo.Context` to `Prepared`, touched only `Source/`, and the merged branch's tests failed 520 times while still compiling.) After such a merge, re-walk the next item against the PR body as well. A clean auto-merge can still carry a gate or a split test that the fix now makes red. After the merge, re-walk this checklist for items that arrived with it: a long-lived branch predates them and nothing re-checks it. ([`review-pr/SKILL.md`](../skills/review-pr/SKILL.md) → step 2c, *A green check on a stale base* and *Grep for gates on the issues the PR closes*; #5892; #5640, whose new net462 package missed the FPU JIT item above because the sweep landed on master after the branch's base.)
- [ ] **A merge resolution that keeps the branch's implementation over master's owes a behaviour diff.** When master implemented the same behaviour after the branch point, and the conflict resolution keeps the branch's version, run both at boundary inputs: a sub-unit remainder, a negative amount, `NULL`. List each difference in the PR body as a change to shipped behaviour. A green re-run does not show the two are equivalent when the branch's own tests pin the branch's version. (#5931 MIN006: resolving the conflict with #5987 kept a truncating SQLite `DateTime` shift in place of 6.5.1's rounding one, and the body said the PR "keeps one SQLite lowering".)
- [ ] **The PR body matches the code after every push.** Its *Behaviour change* section matches the plan's "User-visible deltas vs master" list, and its *Tests* section names the current test set — a follow-up commit that adds a test or a delta updates both, not only the appended follow-up section. When an `A-n` records a base change (a stacked parent merged, a rebase onto master), the body's opening context (*stacked on* / *depends on*) and the plan header are refreshed in the same push (#6008 round 3). The same holds for every other factual claim in the body: a "no public API added" line is checked against the branch's `PublicAPI.Unshipped.txt` diff, and a behaviour claim that a doc comment was corrected for is corrected in the body too. (#5673: the body said no non-Internal API was added beside eight new public members, and kept a transaction claim the XML doc had dropped after review.) ([`work-plan.md`](work-plan.md) → *P3*; [`pr-and-push.md`](pr-and-push.md); #6008.)
- [ ] **Subagent output verified** with `git status` **and `git -C .claude status`** after each invocation — the only modified files are the ones the task justifies (the superproject's status is blind to the corpus). ([`agent-rules.md`](agent-rules.md) → *Agent guardrails (anchor set)*.)
- [ ] **Parked for review, not published.** "Done" means staged and ready for the user to review / commit; commit / push / PR / comment each need an explicit go-ahead this turn. ([`agent-rules.md`](agent-rules.md) → *Git commit rules*.)

## When it's not code

For a corpus change, a release task, or a GitHub-authoring action, the gates differ. This checklist is scoped to changes under `Source/` / `Tests/`; use the owning skill's completion criteria for the rest — the release sub-skill's own checklist, or the wording / verify-after-PATCH rules in [`github-authoring.md`](github-authoring.md).

A **corpus change** (anything under `.claude/`) is done when: the edit is committed **inside the submodule** and pushed to the agents repo's `master` (an uncommitted corpus edit is invisible to the superproject's `git status` and can be wiped by the user's parallel curation); no linq2db branch carries it and the `.claude` gitlink is unbumped; and cross-references still resolve — a moved or renamed doc/skill leaves dangling links elsewhere in the corpus, which `/audit-agents` checks.
