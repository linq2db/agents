# Definition of done

A consolidated completion checklist for a code change on linq2db. The completion gates already live, canonically, in the rules this doc points at — they were scattered, so this file gathers them in one place to walk before declaring a change "done" or proposing to commit / push. **Nothing here is a new rule; each item links its owner.** Not every item applies to every change — skip the ones that don't, but skip them knowingly.

Referenced from [`AGENTS.md`](../AGENTS.md) → *Definition of done*.

**This is the *exit* checklist; its entry counterpart is the work plan.** A change's design — problem, success criteria, authorized edit-points, impact map, test obligations — is recorded before the first edit in `.claude/plans/<key>/plan.md` ([`work-plan.md`](work-plan.md)). The two interlock: a plan's `P9` block records **results against the items below**, under the gate ids `G-01`…`G-08` that [`work-plan.md`](work-plan.md) → *P9 Verification gates* maps to them. The gates themselves are defined here and nowhere else; the plan only records what they returned, and `work-plan.ps1 -Action gates` derives which of them a given change's edit-points make applicable.

## The checklist

- [ ] **Tests run and pass via `/test`.** Don't `dotnet build` / `dotnet test` by hand around the skill — it injects the `CreateDatabase` filter and runs the baselines diff. New behavior has a red→green test; a fix that clearly needs a test has one. On a planned branch that edited `Tests/`, `G-01` also records `test-diff-sweep.ps1 -IncludeWorkingTree`'s counts on the **implemented** tree — the amendment-time sweep cannot see tests written after it. ([`agent-rules.md`](agent-rules.md) → *Running tests*; [`testing.md`](testing.md).)
- [ ] **Baselines reviewed, not just regenerated.** A moved baseline is reviewed for intent; a baseline that drifts on every run (embedded `DateTime.Now` / `Guid` / clock) is a test bug to fix at the source, not noise to wave through. ([`bug-investigation.md`](bug-investigation.md) → *Non-deterministic baselines*.)
- [ ] **New public surface is accounted for.** Any added / changed public (non-`Internal.*`) member: `PublicAPI.Unshipped.txt` updated, XML doc present, and at least one test exercising it. ([`code-design.md`](code-design.md) → *Public API is a contract*; `AGENTS.md` → *Code conventions*.) For any public member, `Internal.*` included, the doc is checked for **content**, not presence: it states the contract points the plan's `D-n` / `A-n` give the member — a keep-all arm, a throw, a delegate's call shape. (#6008: SUG002 in round 2 and SUG003 in round 3, both on `FormattableStringHelper`, each a doc that existed and omitted or contradicted the contract.)
- [ ] **API baselines are NOT a per-PR task.** `Source/**/CompatibilitySuppressions.xml` is regenerated once during release prep (`/release-verify` → `/api-baselines`), not on each feature PR — regenerating them on a branch adds churn the release flow redoes anyway. A feature PR's obligation stops at `PublicAPI.Unshipped.txt` (the item above) — **unless the PR removes or changes a member present in the baseline package**: then "Build and pack" fails with ApiCompat `CP0002`/`CP0001`, and the PR runs `/api-baselines` itself (#5971). When they *are* regenerated, it is through the `/api-baselines` skill and never by hand. A project that sets `EnablePackageValidation=false` states the real lifetime of the switch — off until the next major resets `BaselineVersion` — not a "next release" that no release step performs (#5640). ([`agent-rules.md`](agent-rules.md) → *Agent guardrails (anchor set)* → never hand-edit API baseline files.)
- [ ] **Third-party notices ARE a per-PR task** — unlike the item above, and that contrast is the whole reason this one gets missed. `Build/licenses/components.json` keys on *files inside a packed artifact*, not on new packages, so a TFM-conditional `PackageReference` added to an already-packable project (`LinqToDB.CLI`, the T4 packages, the LINQPad `.lpx`) puts new DLLs under `tools/<tfm>/<rid>/` **by construction** and reddens the branch's own `Build and pack` plus the Azure `build`. The test is *"does a packable artifact gain a file"*, never *"does the branch add a package"*. Run `Build/Azure/scripts/third-party-notices.ps1 -Action harvest`, add the proposed entries and any new `texts/` body, `-Action generate`, then `-Action check` — and commit `components.json`, the new text and the regenerated `generated/` files together. Before pushing, `-Action verify -PublishDir <dir>` against one cross-published non-Windows RID; CI checks all seven. ([#5956](https://github.com/linq2db/linq2db/pull/5956): the work plan's impact map excluded `components.json` on the grounds that the branch produces no new package — 35 unmapped DLLs across every CLI RID.)
- [ ] **A package or NuGet-audit change restores everything CI restores.** Restore `linq2db.slnx` **and** `Examples/Examples.slnx` with `-p:Configuration=Release` — `-c Testing` restores net10.0 only, and the Examples solution is outside `linq2db.slnx`. A pin that changes a version the CLI bundles is a notices change too (item above), even when no file is added. ([`code-design.md`](code-design.md) → *Shipped packages don't pin vulnerable transitive dependencies*; #6043: two CI rounds, one per gap.)
- [ ] **A shipped project that gains or loses a .NET Framework target is added to or removed from the FPU JIT sweep.** Both the `Tests.FpuJit.csproj` `ProjectReference` and `ExpectedAssemblies` in `Program.cs`; a missed addition leaves the gate green. ([`testing.md`](testing.md) → *The x86 FPU JIT sweep*.)
- [ ] **Builds on the portable TFMs**, not just `net10.0`. The `Testing` config is net10.0-only; a BCL API newer than netstandard2.0 needs a `Directory.Build.props` polyfill or a CI-red `build` leg. ([`agent-rules.md`](agent-rules.md) → *TFM API availability*.)
- [ ] **A new or moved TFM gate withholds a feature, not recognition of unchanged source**, and a dropped TFM comes with its ns2.0 break inventory. An ns2.0 fix is proven red with `worktree-test.ps1 -LinqToDBAsset netstandard2.0`, because CI never runs those code paths. ([`code-design.md`](code-design.md) → *A TFM gate may withhold a feature, never recognition of unchanged source*.)
- [ ] **An added .NET major TFM comes with a ban-list overload check** — `banned-api-overloads.ps1` against the new and previous ref packs, new same-hazard overloads banned beside their twins, result in the PR body. ([`code-design.md`](code-design.md) → *Adding a .NET major TFM: re-check the ban lists*.)
- [ ] **No unrelated reformatting / renames.** Only lines the task touches are changed; intentional column alignment is preserved. ([`agent-guardrails.md`](agent-guardrails.md); [`code-design.md`](code-design.md) → *Column-aligned formatting is intentional*.)
- [ ] **No playground scratch staged.** No new `.cs` under `Tests/Tests.Playground/` (beyond `TestTemplate.cs`) and no new `<Compile Include>` test-fixture links committed. ([`agent-rules.md`](agent-rules.md) → *Git commit rules*.)
- [ ] **Cross-cutting core changes were surfaced, not made silently**, and rest on a red→green test or CI — not static reasoning. ([`agent-rules.md`](agent-rules.md) → *Before coding a fix or feature*; [`agent-guardrails.md`](agent-guardrails.md) → *Cross-model verification for high-blast-radius core changes*.)
- [ ] **The diff got an adversarial read before the PR opens** (Tier M/L; a Tier S mechanical change skips it). Run the `code-reviewer` pass over the branch's diff and walk what it returns, exactly as a review of someone else's PR would. When the branch has a plan, run `work-plan.ps1 -Action validate -Done` first: it fails on any gate still `(pending)` and on a `G-01` that names no test for some `TO-n`, and a read against blank gates only re-derives what they should already record. **Not** a posted self-review — no GitHub write, no draft; the point is the rubric applied cold by something that did not write the code. This is the exit counterpart to the plan's `plan-critic`: the *design* is attacked before implementation by a different model, and without this the *diff* is attacked only once the PR is public, which spends a maintainer's review round on findings one subagent call would have produced. Every other item on this list is a mechanical check, so nothing else here asks an adversarial question about the code. (Measured on [#5893](https://github.com/linq2db/linq2db/pull/5893): a single pass over the 3-file diff surfaced all five changes the post-PR review later landed — three as findings, two as out-of-scope observations.) **On a branch not pushed yet** (or whose `origin/pr/<n>` still holds a superseded design), `diff-reader.ps1` / `verify-lines.ps1` have no ref to read: brief the pass with `git -C <worktree> diff <base>` plus the untracked files to read directly, tell it to read files from the worktree, and to verify line anchors by reading them there. (#6008: two findings and two out-of-scope observations, all acted on, from a pre-push pass briefed that way.) **Either way, brief `rubricModules`** with the `modules` field of `pwsh -NoProfile -File .claude/scripts/review-rubric-modules.ps1 -Base <base> -RepoRoot <worktree>` (committed, uncommitted and untracked paths), even when it is `[]`. ([`review-pr/SKILL.md`](../skills/review-pr/SKILL.md) → step 6; [`code-reviewer.md`](../agents/code-reviewer.md).)
- [ ] **Re-run on the merged tree when master has moved under the branch's tests.** If `git log origin/<branch>..origin/master -- <the branch's changed test files>` is non-empty, merge master and re-run those tests before declaring the branch ready. A clean auto-merge can still carry a gate or a split test that the fix now makes red. After the merge, re-walk this checklist for items that arrived with it: a long-lived branch predates them and nothing re-checks it. ([`review-pr/SKILL.md`](../skills/review-pr/SKILL.md) → step 2c, *A green check on a stale base* and *Grep for gates on the issues the PR closes*; #5892; #5640, whose new net462 package missed the FPU JIT item above because the sweep landed on master after the branch's base.)
- [ ] **The PR body matches the code after every push.** Its *Behaviour change* section matches the plan's "User-visible deltas vs master" list, and its *Tests* section names the current test set — a follow-up commit that adds a test or a delta updates both, not only the appended follow-up section. When an `A-n` records a base change (a stacked parent merged, a rebase onto master), the body's opening context (*stacked on* / *depends on*) and the plan header are refreshed in the same push (#6008 round 3). ([`work-plan.md`](work-plan.md) → *P3*; [`pr-and-push.md`](pr-and-push.md); #6008.)
- [ ] **Subagent output verified** with `git status` **and `git -C .claude status`** after each invocation — the only modified files are the ones the task justifies (the superproject's status is blind to the corpus). ([`agent-rules.md`](agent-rules.md) → *Agent guardrails (anchor set)*.)
- [ ] **Parked for review, not published.** "Done" means staged and ready for the user to review / commit; commit / push / PR / comment each need an explicit go-ahead this turn. ([`agent-rules.md`](agent-rules.md) → *Git commit rules*.)

## When it's not code

For a corpus change, a release task, or a GitHub-authoring action, the gates differ. This checklist is scoped to changes under `Source/` / `Tests/`; use the owning skill's completion criteria for the rest — the release sub-skill's own checklist, or the wording / verify-after-PATCH rules in [`github-authoring.md`](github-authoring.md).

A **corpus change** (anything under `.claude/`) is done when: the edit is committed **inside the submodule** and pushed to the agents repo's `master` (an uncommitted corpus edit is invisible to the superproject's `git status` and can be wiped by the user's parallel curation); no linq2db branch carries it and the `.claude` gitlink is unbumped; and cross-references still resolve — a moved or renamed doc/skill leaves dangling links elsewhere in the corpus, which `/audit-agents` checks.
