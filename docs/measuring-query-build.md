## Measuring query-build performance

How to measure and profile linq2db's LINQ→SQL build path (not test-suite runtime, not analyzer build
cost — for the latter see [`../skills/profile-analyzers/SKILL.md`](../skills/profile-analyzers/SKILL.md)).

Read this before writing a benchmark or reaching for a profiler: every trap below cost a build-and-run
cycle to discover on 2026-08-12.

For *interpreting* what you measure — why a work count is not a time measurement, and why a corpus
aggregate can hide the pathological case — see [`bug-investigation.md`](bug-investigation.md) →
*Perf work*.

### BenchmarkDotNet's normal toolchain does not run in this repo

`dotnet <linq2db.Benchmarks.dll> --filter <pattern>` fails during BDN's build step:

```
BenchmarkDotNet.Autogenerated.csproj : error NU1101: Unable to find package
linq2db.Benchmarks-Job-XXXXXX-1. No packages exist with this id in source(s): nuget.org
// BenchmarkDotNet has failed to build the auto-generated boilerplate code.
```

BDN generates a child project under `.build/bin/...` and restores it; the repo's build props and
central package management apply to that generated directory and break the restore. Consequences:

- **`--inProcess` does not replace the configured jobs, it adds one.** `Config.cs` registers four
  explicit jobs (net462 / net8 / net9 / net10), so `--inProcess` yields *five* — the in-process one
  measures fine while the other four fail to build, and the process exits non-zero (`0xE0434352`)
  with no summary table even though real iterations ran. You cannot drop those four from the CLI;
  only editing the shared `Config.cs` would, which isn't worth it for a one-off measurement.
- **Use the manual-runner pattern instead.** `Program.cs` already carries this escape hatch for the
  same class of problem: a `manual-cache` argument dispatching to
  `CacheActivityBenchmark.RunManually(warmups, iterations)`, which does its own warmup + `Stopwatch`
  loop and prints a markdown table. It gives a fixed, predictable budget — which matters because one
  operation of an association-heavy shape can cost seconds, making BDN's auto-iteration impractical.
  Copy that shape rather than inventing one.
- The project file is **`linq2db.Benchmarks.csproj`**, not `Tests.Benchmarks.csproj`.

### A connection-less benchmark

`QueryGenerationBenchmark` is the model to copy: it builds SQL through provider instances with no
database. `NorthwindDB(IDataProvider)` wraps `new DataOptions().UseConnection(provider, new
MockDbConnection(...))`, and `.ToSqlQuery().Sql` produces SQL without opening anything. Add
`.UseDisableQueryCache(true)` when the thing under measurement is the *build* — otherwise the second
iteration onward is served from the query cache and you measure nothing.

### `Console` is banned in the benchmarks project

RS0030 rejects `Console.*` there (*"use BaselinesManager.LogQuery"*). A benchmark that prints results
needs the same suppression the precedent uses, on the method:

```csharp
[System.Diagnostics.CodeAnalysis.SuppressMessage("ApiDesign", "RS0030", Justification = "Benchmark output requires Console")]
```

### Temporary instrumentation in `Source/LinqToDB` trips Release-only analyzers

Counters added to the library for a measurement build compile fine in `Debug` / `Testing` and then
fail the moment anything builds `Release` (banned interpolated `StringBuilder.AppendLine` without an
`IFormatProvider`, `MA0111` pushing `string.Create` over `FormattableString`, `IDE0330`/`MA0158`
demanding `System.Threading.Lock` over `lock (object)`). Counts are configuration-independent, so
**build instrumentation in `Debug`** and don't contort throwaway code to satisfy analyzers. Conversely
`-c Testing` is net10.0-only and hides API gaps on `net462`/`netstandard2.0` (`Environment.ProcessId`
is the classic — use `Process.GetCurrentProcess().Id`); see [`../AGENTS.md`](../AGENTS.md) → *Build
gotchas that fast-iteration hides*.

### Profiling with `dotnet-trace`

`dotnet-trace` is installed as a global tool. Collect a CPU-sampling trace by launching the process:

```
dotnet-trace collect --format speedscope --output <out>.nettrace -- dotnet <app>.dll <args>
```

Reading the result has two non-obvious properties:

- **The profiles are `evented`, not `sampled`.** The exporter is TraceEvent's, which emits
  `{"type":"O"|"C","frame":i,"at":t}` event streams rather than sample/weight arrays. Code that
  aggregates speedscope's `samples`/`weights` finds nothing and reports zero total.
- **Self time is useless; use inclusive time.** Leaves collapse into TraceEvent's pseudo-frames, so a
  self-time ranking reads ~81% `CPU_TIME` / ~19% `UNMANAGED_CODE_TIME` and nothing else. Inclusive
  time per frame is what localises the cost. Remember the total is summed across threads, so
  normalise per thread — a saturated finalizer thread and the worker thread can each show ~50%.
- **The JSON is large** (~100 MB for ~18 s of a deep-recursion workload, because the stacks are deep).
  `ConvertFrom-Json` is not viable. Use
  [`../scripts/speedscope-top.csx`](../scripts/speedscope-top.csx) via `dotnet script`, which streams
  it with `System.Text.Json` and prints top-N self and inclusive frames:

```
dotnet script .claude/scripts/speedscope-top.csx -- <trace>.speedscope.json 25 [nameFilter]
```

A worked example: this is how a ~4.5 s build of a 13-level `LoadWith` chain was localised to
`BuildConstant` → `EvaluateExpression` (81% of the worker thread) plus
`DynamicResolver+DestroyScout.Finalize` (85% of the finalizer thread) — i.e. lambda compilation — which
a counter pass then pinned to 38 460 `Expression.Lambda(..).Compile()` calls for `default(T)`.

### Counters beat profiles for "how many"

A profile tells you *where*; a counter tells you *how many* and *how cacheable*. The decisive artifact
above was a throwaway static class incrementing per-call counts plus a histogram keyed by
`expr.NodeType` and `expr.ToString()`, dumped from an `AppDomain.CurrentDomain.ProcessExit` handler to
`.build/.agents/<name>.<pid>.txt`. "38 460 compiles across **2** distinct shapes" is the sentence that
picked the fix; no profile says that. Note the dump lands relative to the *process's* working
directory unless you hardcode a path — see [`worktree.md`](worktree.md) → *Running tests from a
worktree*.
