## Working in this repo — Claude Code operational overlay

This is the **Claude-Code-specific operational overlay**, auto-imported by `CLAUDE.md` (which also imports [`AGENTS.md`](../AGENTS.md), so both are always-loaded for Claude). It carries only Claude Code harness mechanics — shell/tool rules, permission patterns, worktrees, corpus/submodule mechanics, subagent verification, skill workflows — and **does not restate agent-agnostic rules already canonical in `AGENTS.md`**: where a topic is owned there, this file keeps a one-line pointer rather than a second always-loaded copy. Agent-agnostic *detail* lives in the focused docs under `.claude/docs/` (loaded on demand by any agent — Claude / Codex / Copilot). Nothing here may contradict `AGENTS.md`.

### Creating a new branch

- **Name.** If the user didn't specify a branch name, derive one from the task:
  - For an issue-backed task: `issue/<id>-<kebab-slug>` (e.g. `issue/1234-fix-cte-column-aliases`).
  - For a feature: `feature/<id-or-slug>-<kebab-slug>` (e.g. `feature/5501-duckdb-provider`).
  - **Kebab-slug rules.** 2–5 words, lowercase, hyphen-separated, derived from the task goal. Prefer verb-led for issues (`fix-…`, `support-…`, `reject-…`). Strip filler words (`the`, `a`, `in`, `on`, provider names already obvious from the issue). Keep it under ~40 characters. If the task doesn't give enough context to infer a slug, ask the user rather than guessing.
  - Applies to every skill that creates branches — `/fix-issue`, `/review-pr` checkouts of new branches, `/create-issue` when it suggests a follow-up branch, ad-hoc branching from the main agent.
- **Base.** Always branch from `origin/master`. Run `git fetch origin master` first so the base isn't stale. Branch from something else only if the user explicitly says so.
- **Dirty working tree.** If there are staged or unstaged changes before branching, stop and ask the user whether to stash or discard them. Never silently discard or carry them across.
- **Blocked `git checkout` / `gh pr checkout`.** If the switch fails because uncommitted changes would be overwritten, stop and ask the user how to proceed (stash, commit, discard) — name the blocking files in the question. Do **not** silently `git worktree add` as a workaround.
- **Worktrees are the default for branch-based task work.** Create a worktree rather than `git switch` / `git checkout`-ing the primary clone — switching the main checkout disturbs its branch and whatever work sits there, and the user keeps a worktree per open PR. For a new branch: `git worktree add <worktrees-root>/<slug> <base>` and work there, leaving the main checkout untouched. **`<worktrees-root>` is an environment convention, not a corpus constant** — a dedicated worktrees directory, or a location beside the primary clone, depending on the user's setup; take it from auto-memory or ask, and never assume the worktree is an ancestor *or* a descendant of the primary clone (see [`worktree.md`](worktree.md) → *`<worktrees-root>` — where worktrees go*). (`/review-pr` is read-only — it reads `origin/pr/<n>` via `diff-reader.ps1`, so it needs no checkout at all.) Worktree-specific mechanics (**bootstrapping `.claude/`** — a fresh worktree has none, `UserDataProviders.json` placement, gitignored files in the main repo): see [`worktree.md`](worktree.md).
- **A distinct shared-engine fix discovered mid-task gets its own branch/PR — don't bundle it onto another open PR.** When work on one PR surfaces a separable fix in shared engine code (SQL builder, optimizer, expose pipeline), put that fix on its **own** new branch off `origin/master` with a standalone draft PR — even when it's thematically "related" to an existing open PR. Keep it on the originating branch too if needed to stay green, but the standalone PR is where it's reviewed and CI'd. (Corrected after an expose-pipeline fix was pushed onto the correlated-detection PR instead of its own.) **Scope: only a *separable* fix — one with a standalone observable effect, reviewable/shippable on its own.** A tightly-*coupled* enabling fix (no observable effect without the originating change — e.g. a code branch that change first makes reachable) stays on the originating PR; don't split it, and don't offer to split it, without an explicit user request. (Corrected on #5659: a `RecordReaderBuilder` fix that only mattered once raw-SQL materialization was routed through it was kept on the PR — "no splitting without explicit request".)
- **Don't switch to a recovery branch mid-rebase.** When a rebase / in-flight task surfaces an *unrelated* master breakage (usually a CI failure from a merge race), finish the in-flight branch first: resolve the conflict → force-push the rebased branch → `git switch -c <recovery-branch> origin/master` → open the recovery PR (it can run CI in parallel once the in-flight is pushed). Switching mid-rebase strands the in-flight branch rebased-but-unpushed and costs context.
- **Prefer `git merge` over `git rebase` for multi-commit feature branches that already contain "Merge master" commits.** On a long-lived branch (50+ commits, prior `Merge branch 'master'` commits), `git rebase origin/master` replays every commit and forces a conflict resolution at each step (dropping the merge commits); `git merge origin/master` resolves once in a single commit, matching the branch's pattern. The final squash-merge into master collapses the history either way. Use rebase only on short-lived branches (< 10 commits, no merge commits) or when the user wants linear history.
- **Recurring merge-conflict recipes** (read mid-merge): `LinqOptions` positional-record's five update sites, params inserted *ahead* of optionals breaking positional callers, end-appended serialized enums keeping master's members first — [`pr-and-push.md`](pr-and-push.md) → *Merging master into a feature PR — recurring conflict recipes*.

### The corpus is a submodule — corpus edits go to the agents repo

`.claude/` is a git submodule ([linq2db/agents](https://github.com/linq2db/agents), branch `master`), so the corpus is identical on every linq2db branch and never needs carrying across a branch switch. What follows from that:

- **Commit corpus edits inside the submodule and push them to its `master`** — `git -C .claude add <pathspec>`, `git -C .claude commit`, `git -C .claude push` — each still gated by the *Git commit rules* below. They never land on a linq2db branch, and the superproject's `.claude` gitlink is left alone: it is a bootstrap pointer, not a version pin (`.githooks/pre-commit` refuses a staged bump, and `submodule.ignore = all` stops `git add .` from staging one). The single corpus change that *also* needs a linq2db commit is extending the root `CLAUDE.md` trampoline's import list.
- **The superproject's `git status` is blind to the corpus.** `ignore = all` hides uncommitted corpus edits *and* the submodule being ahead of the gitlink, so "clean tree" in linq2db says nothing about `.claude/`. Run `git -C .claude status` before asserting a clean tree, and after any subagent invocation that could have written there (see *Agent guardrails* below — the `git status` verification rule needs both).
- **The user curates the corpus in parallel.** An *uncommitted* `.claude/` edit you apply (e.g. from `/session-reflect` or `/audit-agents`) can be silently wiped by their concurrent commit / working-tree reset — a `/session-reflect` `testing.md` edit was lost this way. After applying a curation edit, don't assume it persists: either commit it in the same turn (when the user asked you to) or re-verify it survived; when the user is actively curating, prefer *proposing* the edit for them to fold in over leaving it uncommitted.
- **A fresh worktree gets its corpus from `post-checkout`, not from git.** `git worktree add` cannot populate a submodule itself, and an empty `.claude/` reads as a *clean* tree — so the failure mode is an agent running with zero project rules and nothing saying so. Since [#5820](https://github.com/linq2db/linq2db/pull/5820) the hook bootstraps it at checkout time, but the hook that runs is the **primary clone's** copy: a primary clone on a pre-#5820 branch still yields an empty `.claude/`, silently. Confirm the corpus is there before working, and note the bootstrapped submodule lands on a **detached HEAD** (so a corpus push from the worktree needs `git -C <worktree>/.claude switch master` first): [`worktree.md`](worktree.md) → *Bootstrapping `.claude/` in a worktree*.

### Bash command rules

Each Bash tool call must be a single command — the user may have a PreToolUse hook that rejects compound calls, and the permission system evaluates them as one opaque string anyway:

- No `&&` / `||` / `;` chaining; no shell control flow (`for`, `while`, `until`, `case`, `if`, `function`); no nested chains inside `$(...)` (plain `$(cmd)` is fine).
- Pipes (`|`) and heredocs are allowed but every pipe / `>` redirect creates a novel command string that misses allowlist matching — prefer the command's own flag (`git log -n N`, `gh api --jq`, `Grep head_limit`) or persist raw output to the tool-result store and `Read` the path.

Split chained work into separate tool calls — parallel when independent, sequential when dependent.

#### Dedicated tools over raw CLI

`grep`, `rg`, `find`, `cat`, `head`, `tail`, `sed`, `awk` aren't allowlisted and prompt every time. Use the dedicated Claude Code tool:

| Want to… | Use | Not |
|---|---|---|
| Search file contents | `Grep` (`pattern`, `-n`, `-i`, `-A`/`-B`/`-C`, `head_limit`, `multiline`, `glob`, `type`; note `offset`/`head_limit` paginate *result* lines, not file lines) | `grep`, `rg`, `ack`, `ag` |
| Read a file (full or sliced) | `Read` (`offset` / `limit`) | `cat`, `head`, `tail`, `less` |
| Find files by name / glob | `Glob` | `find`, `ls -R`, `fd` |
| Edit a file | `Edit` / `Write` | `sed -i`, `awk -i`, redirect-into-file |
| Check-and-read a possibly-absent file | `Read` (returns a clean "does not exist" error you can branch on) | `test -f X && cat X` (compound → hook-rejected; recurred on the `docker-session-started.txt` check) |
| Search **with surrounding lines** | `Grep` (`-A` / `-B` / `-C` + `output_mode: "content"`) | `git grep -n "x" -A 20` — `git grep` reads a bare `-A` in that position as a **revision** and dies with `fatal: unable to resolve revision: -A`, so the miss looks like a different class of error than "unknown option" (hit twice in one session out of habit). Reserve `git grep` for plain which-files-contain-X sweeps and for searching a **non-checked-out ref** (`git grep <pattern> <ref> -- <path>`), which `Grep` cannot do. |

Reserve Bash for `git`, `gh`, `dotnet`, `pwsh`, helper scripts under `.claude/scripts/`.

**The table applies to a background task's output file too — that path is the single most-violated case.** A `run_in_background` completion notification hands you an absolute path, and reaching for `grep -n "error\|failed" <path>` / `tail -30 <path>` / `sed -n '117,200p' <path>` feels like shell work because the path came from the harness rather than from a tool. It isn't: `Grep` with a pattern plus `head_limit` extracts a build/test failure summary from a 600-line log in one call, and `Read` with `offset`/`limit` replaces every `sed`/`tail` slice. Same rule, same reasons — it just doesn't *look* like a repo search. (Counted 12 raw-CLI calls on task-output files in a single #5643 session, alongside correct `Grep`/`Read` use everywhere else in the same session.)

**Finding the newest test heartbeat is `test-status.ps1`, not `ls -t`.** `.claude/scripts/test-status.ps1` reads the latest `.build/.agents/test-progress.<tfm>.<pid>.json` and relays the one-line status. Listing the directory to find the newest file then `Read`ing it is two calls for what the script does in one, and the directory accumulates heartbeats from prior sessions and concurrent runs, so "newest by mtime" is a guess about whose run you are looking at. `/test-progress` wraps the same script. (Done four times in one session before the script was recalled.)

#### Permission-friendly patterns

Patterns that triggered prompts in real sessions — full table in [`windows-gotchas.md`](windows-gotchas.md) → *Permission-friendly Bash patterns*. The four highest-impact:

- **`>` redirect** (`gh api … > path`) misses `Bash(gh api *)` — prefer `gh api … --jq '…'` or let raw output persist + `Read`.
- **Inline `pwsh -NoProfile -Command "…"`** is never allowlisted safely — use `Grep` / `Read` instead.
- **`gh … --body @-` / `-f body=@<file>`** sets the body to the literal string `@-` or `@<file>` — use `--body-file <path>` (or `--input <json>` for PATCH).
- **Scratch scripts** must live under `.build/.agents/*.ps1` — only that path is allowlisted for ad-hoc invocations.

When data is already on disk (e.g. `diff-reader.ps1`'s `writeDir` cache at `.build/.agents/pr<n>/`), `Read` or `Grep` it directly rather than re-fetching via `git show …` pipelines — the `Read` tool preserves tabs and trailing whitespace literally for whitespace-byte inspection.

### Windows Git Bash gotchas

MSYS path-mangling and stdout-decoding bite well-formed `gh` / `git` / `docker` calls. Full reference: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) (tool-neutral git/gh/docker/dotnet/PowerShell); the Claude-tool-specific `Glob` + permission-allowlist gotchas are in [`windows-gotchas.md`](windows-gotchas.md). One-line triggers — when you hit one of these, read the relevant doc:

- `gh api` rejects a leading-slash endpoint (use `gh api user`, never `gh api /user`).
- `git show <ref>:<path>` fails with `ambiguous argument` when `<ref>` contains `/` — use `git ls-tree` + `git cat-file -p` instead.
- **`git ls-tree … -- '<glob>'` does not glob, and an empty result is not absence.** The pathspec matches literal paths / directory prefixes, so `-- '*Foo*'` or `-- '**/Foo*'` exits **0 with no output** even when matching files exist — indistinguishable from "nothing there". Enumerate with `git diff --name-only <base>...<ref>` or `git ls-files`, then filter with `Grep`. This bites hardest right after the rule above sends you to `ls-tree`: on #5764 **both** review subagents hit it in one session, and one concluded "no baseline files exist for either new test" — abandoning an empirical probe — while 100 such files were on the branch.
- **`gh … --body` is banned.** Always `--body-file <path>` or `--body-file -`. For `/azp run …` triggers use `.claude/scripts/azp-run.ps1`. (`gh … --body @-` is *not* stdin either — it sets the body to the literal string `@-`.)
- `git fetch <headRefName>` of a fork PR may produce no usable ref — fetch via `refs/pull/<n>/head:refs/remotes/origin/pr/<n>`.
- Transient `fatal error — add_item (… errno 1)` on fork bursts (and sometimes single sequential calls): retry once; if it recurs, switch to the PowerShell tool rather than retry-looping.
- `docker exec <container> /<path>` mangles the path: prefix with `MSYS_NO_PATHCONV=1` and wrap in `bash -c '…'`.
- Captured `gh` / `git` stdout decodes via the console code page, not UTF-8 — non-ASCII (emoji, em-dash) gets mangled. Don't capture body-ish output into a pwsh variable; use `Invoke-Gh` helpers, file roundtrip, or ASCII-only anchors.
- `Glob` returns "No files found" for a path documented in CLAUDE.md / a SKILL / `agent-rules.md` — `Read` the documented path directly before concluding it's missing or reimplementing the helper.
- A tracked file stays `M` after `git restore` / `git stash`, with a diff whose two sides look identical — a lone CRLF in the *committed blob* under `core.autocrlf=true`, which no working-tree state can reproduce. Don't chase it: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *A file that stays dirty after `git restore`* (and read its merge-blocked case before reaching for `git update-index --assume-unchanged`, which does **not** get a merge past it).
- `linq2db.wiki` clones and commits normally since 2026-07-31 — the one colon-named page was renamed (`f338e68`), the long-lived clone is a full checkout again, and `wiki-commit.ps1` is no longer mandatory (still correct, and still the safe default for a scripted edit). Wiki page titles can contain a colon, so if a checkout ever fails with "invalid path … : …" again, **rename the page** rather than reintroducing the sparse-checkout dance; the fallback recipes and the `update-index -c core.protectNTFS=false` trap live in [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *Cloning the `linq2db.wiki` repo*.

### Batching and user interaction

Reduce round-trips and preserve the user's attention span.

- **Batch independent tool calls.** When multiple reads, searches, or shell commands don't depend on each other's output, issue them in a single assistant turn (multiple tool calls in one message). Sequential calls are only for true dependencies. This applies to Read, Grep, Glob, Bash, and any other non-mutating tool.
- **Ask-ask-do-all, not ask-do-ask-do.** When a task requires multiple user decisions, don't interleave question → action → question → action. Front-load every question you can anticipate into a single turn (numbered list so the user can reply by number), wait for all answers, then execute all resulting actions in one batch. Only fall back to interleaving when a later question genuinely depends on the outcome of an earlier action.
- **Do not batch code-change reviews.** Each unrelated code change should be proposed in its own review turn, even if that means more round-trips. Mixing several unrelated diffs into one confirmation forces the user to context-switch between concerns and makes "approve partially" awkward. Group diffs only when they belong to the same logical change.
- **Interactive review of findings/comments: one at a time, with context.** When walking review comments, review findings, or any list of substantive decisions the user must adjudicate item-by-item, present **one item per turn** — the finding, its context, your recommendation — and resolve it before moving to the next. Do **not** collect several into a single `AskUserQuestion` or a numbered multi-question prompt: the user needs room to weigh and discuss each decision, and batching forces parallel context-switching. This is the decision-review counterpart to *Do not batch code-change reviews* above; it **overrides** *Ask-ask-do-all* below, which applies only to anticipatable setup/parameter choices, not to substantive judgment calls. (Corrected twice in one session after findings were batched into `AskUserQuestion`.)
- **On a surprising failure, stop and wait.** If a command, test run, or agent invocation fails in a way the plan didn't anticipate (connection refused, unexpected parser error, container not running, permission denied, etc.), don't improvise alternative paths to keep the session flowing — report what happened in one or two sentences and wait for user direction. Workarounds invented mid-failure often mask a real signal (wrong premise, wrong tool, wrong target); the user's redirect is usually faster than the bot's recovery.
- **Cap same-failure retry loops with a hard count, not just judgment.** When iterating on the *same* failing fix or a red CI leg, bound the retries numerically — roughly 3 local fix-and-retest attempts, fewer (1–2) for a full CI round-trip — then stop, summarize what was tried, and reconsider or ask rather than firing another near-identical attempt. A qualitative "am I flailing?" check misses slow token bleed across many almost-identical retries. This is the self-retry counterpart to *On a surprising failure* above (which stops on the *first* unexpected failure) and the *two-correction rule* below (which counts *user* corrections); this one counts *your own* retries against one failure. The cap is a backstop, not a quota — stop earlier the moment attempts stop changing the outcome.
  - **At the cap, ask for a budget rather than deciding alone.** Stopping and continuing are not the only options, and both are worse than the third: say what the next attempt would test, what it would cost, and what you'd conclude either way — then let the user grant or decline it. A probe that keeps *refuting hypotheses* is progress, not flailing, so a silent stop can abandon a live thread one build short of the answer; a silent continue spends the user's machine on your hunch. Announcing the cap also makes the spend legible. (On #5737 the fourth probe into an alias change was offered this way — *"one more build to test it?"* — and answered *"yes, one more"*; it refuted the last hypothesis and settled the finding as cosmetic.)
- **After launching a background task, await its completion notification — don't poll the output file.** A `run_in_background` Bash task (a long build, a full test run) streams to its task-output file and fires an automatic `<task-notification>` when it exits. Re-`Read`ing that file before the notification arrives just returns *"Wasted call — file unchanged"* — pure round-trip waste with no new information. `Read` it once, when the notification lands (or when the user asks for progress). Poll only a genuine external heartbeat (e.g. `/test`'s `test-progress` JSON), never the captured stdout file of a task that will notify you anyway. **This covers any file the task writes — including your own `>` redirect target — and any tool you inspect it with.** The harness's *"Wasted call — file unchanged"* guard only fires for `Read`, so `Grep` / `grep -c` polling of a redirect log draws no pushback and silently burns a round-trip per call: the absence of a warning is not permission. And if a turn's only content would be "still waiting", don't emit it — the notification arrives on its own. (Corrected on #1553 after ~15 wasted polls across background builds, and again on #5720 where ~15 more went to `Grep`-polling redirect logs.)
- **An unanswered question outranks a background notification — lead with the question, not the result.** When a `run_in_background` task completes while an interactive-walk item (or any question you posed) is still unanswered, the completion notification hands you a turn *the user never asked for*. Filling that turn with the task result silently buries the question: the user sees a wall of test output and no prompt, and the walk stalls until they ask what you were waiting on. Report the result in a line or two, then **restate the open item's question as the turn's last word**. Two corollaries: a notification is never an answer (the system-reminder says so, but the pull to read the turn as "progress" is strong), and if several notifications land in a row, name which item is still open rather than re-pasting the whole question each time. This is the interaction-side counterpart to the don't-poll rule above — same trigger, but the cost is the user's attention rather than a round-trip. (Surfaced on #5809: three consecutive test-run notifications followed one walk question, every turn led with the run result, and the user had to ask *"what is item 3"* to recover it.)
- **Don't edit a source file while a background build / test run is in flight.** The compiler may read the file mid-edit and fail on a half-applied state, producing an error that describes your *intermediate* text rather than your change — so it reads as "the change is wrong" instead of "the build raced the editor". Queue the edit until the completion notification lands; if you've already started, expect to re-run rather than trusting the result. This is the write-side counterpart to the don't-poll rule above: same trigger (a `run_in_background` task you launched), opposite operation. (Hit on #5701: moving a `type private FreeVarMarker` declaration above a doc comment — two `Edit` calls, insert then delete — while the net462 leg compiled produced `error FS0037: Duplicate definition of type … 'FreeVarMarker'`, a type that existed twice only in the window between the two edits. Cost a full rebuild cycle.)
- **Fetch an external binary document once, then mine it from disk.** When the authoritative answer lives in a `.docx` / `.pdf` / archive rather than a web page (LINQPad's `DataContextDrivers8.docx` is the recurring case — its macOS/XPF driver contract appears on no web page), download it **once** to `.build/.agents/`, extract the text, and `Grep` that file for each subsequent question. Re-downloading per question costs a multi-hundred-KB fetch plus a re-extract for every lookup. (On #5786 the same docx was fetched three times to read three sections.) Same logic as the `diff-reader.ps1` `writeDir` cache rule above: when the bytes are already on disk, read them.
- **Project the fields you need out of a script's JSON — never `ConvertTo-Json` a whole sub-object.** These payloads are large by design (`baselines-pr-scan.ps1` output has measured 1.7 MB) and the cost is invisible until it lands in context: dumping `$s.casts` at depth 3 spilled ~100 `perFileLosses` entries to obtain three aggregate numbers, where `$s.casts.perFileLosses | Group-Object <provider> | …` would have answered in three lines. Reach for `Group-Object` / `Measure-Object` / `Where-Object` + `Select-Object -First N` and print a formatted table; serialize a whole object only when you genuinely need every field. Same instinct as `Grep`'s default `head_limit`.
- **Batch edits on a single config file.** When reshaping multiple sections of one file (several providers across TFMs in `UserDataProviders.json`, several `<PackageReference>` versions in `Directory.Build.props`, etc.), read it once, plan the full edit set, then apply as a single `Edit` — or a back-to-back sequence with no intermediate re-reads when one `Edit` can't span the headings. Incremental nibbles (edit, read back, edit, read back) burn permission surface and miss cross-section invariants.
- **Two-correction rule — stop repeating, reframe.** If the user corrects the same thing twice and the second attempt still misses, don't fire a third near-identical attempt or restate the correction louder. Stop and change the frame: state in one line what you believe the goal is, then split the task, ask for a concrete expected-output example, or surface a standing instruction that may be pulling against the correction. A third identical try usually signals a goal-level mismatch, not an execution slip — see [`bug-investigation.md`](bug-investigation.md) → *Repeated resistance to a correction signals goal misalignment*.

**Write exactly the list you got approval for — widening it inside shared infrastructure needs its own ask.**
When the user approves a concrete set (processes to kill, files to delete, packages to bump) and you then
write it into a shared file — a CI template every job runs, `Directory.Packages.props`, a hook — put *that*
set in, not a superset you think is obviously implied. Additions you reasoned your way to were not part of
the analysis the user reviewed, so they land unreviewed in shared infrastructure. Propose them separately;
they're usually one sentence to describe and cheap to approve. (Surfaced on #5614: a reviewed list of 13
idle processes to kill was written into `test-workflow-windows.yml` together with four unreviewed
`Stop-Service -Force` calls on system services — `TrustedInstaller`, `wuauserv`, `WSearch`, `UsoSvc`. The
auto-mode classifier blocked the edit; re-proposed on its own, the same addition was approved immediately,
and it turned out to carry a real defect — `Stop-Service` has no `-NoWait`, so it blocks until the service
stops and hung five jobs inside the step.)

### Capability self-assessment

Before reporting a task as infeasible ("can't bisect", "can't build", "runtime test outside my reach"), do a one-pass environment check:

- `docker ps -a --filter name=<container>` for provider containers — use the **container name** from `test-databases.md` (e.g. `pgsql19`, `sql2022`, `firebird50`), **not** the engine/provider name. `--filter name=postgres` returns nothing even when `pgsql19` exists; when unsure of the exact name, run `docker ps -a` unfiltered.
- `Glob` under `.claude/scripts/` for helper scripts wrapping multi-step sequences
- `UserDataProviders.json` (root) and a sibling `linq2db` clone's `UserDataProviders.json` (alongside this clone, e.g. `../linq2db/UserDataProviders.json`) for connection strings
- Existing skills (`/test`, `/test-providers`) for workflow coverage
- `/kb-ask` or `areas/<AREA>/` for prior context on the subsystem (known issues, decisions, patterns) before declaring something unknown or infeasible — see *Consult the knowledge base* above
- Measuring or profiling **query-build performance** → [`measuring-query-build.md`](measuring-query-build.md) (BenchmarkDotNet's child-process toolchain fails in this repo — use the manual-runner pattern; `dotnet-trace` is installed, and [`../scripts/speedscope-top.csx`](../scripts/speedscope-top.csx) reads its output). Interpretation rules — a work count is not a time measurement — in [`bug-investigation.md`](bug-investigation.md) → *Perf work*.
- Investigating a **red CI run**'s per-test failures → `.claude/scripts/azp-build-failures.ps1 -BuildId <n>` (see [`ci-tests.md`](ci-tests.md) → *Reading failed CI test runs*). It does the timeline + parallel `/logs/<id>` fetch + per-failure parse in one call — don't hand-roll the Azure `timeline` + log curl-and-grep flow.

When the capability exists but the runtime cost is real, surface the cost and let the user decide.

**Diagnose "stuck" as effort vs. capability before escalating.** When your own output falls short, separate the two orthogonal knobs. Skipped verification, abandoned steps, shallow searches, not reading the whole file/log → an *effort* shortfall: do the missing work (and if the user is tuning the harness, higher effort is the lever). Genuine inability to reason about the domain or a subtle bug → a *capability* shortfall: a larger model is the lever. Reach for more effort first — it's the cheaper fix — and a bigger model only for a real capability gap. Higher effort also costs materially more tokens (~7× low→high on the same task), so it's a real trade-off, not a free default.

### Inferring rules from user input

When the user gives a rule that names a specific package / file / case, treat it as scoped to that case unless they explicitly generalize ("for all X…", "every Y in this family…"). Don't extrapolate to similar-looking cases without asking — "you gave rule X for P; case Q looks similar — same rule, or different?" An extra question is cheap; silent over-generalization costs a redo of every affected case plus a doc revert.

### Comments justify decisions, not mechanics

**Write a comment only for what the code cannot say: a non-obvious decision, a rejected alternative, a constraint that isn't visible locally.** A change that follows an established pattern in the same file gets **no** comment — the pattern is the explanation. Do not narrate what the line does, and do not turn a commit message's rationale into an inline comment; the commit message already holds it.

The tell that a comment is unwanted: it explains *why this line exists* when the neighbouring code already answers that. On #5614 a one-line `_visited = null;` added to a `Cleanup()` method — which the sibling class already did, i.e. an established cleanup pattern — was given a three-line comment about pooling and retention. Maintainer: *"it is a bit of a PITA that you often generate useless comments … we have established visitor cleanup pattern and never comment trivial code like that."* The rationale belonged in the commit message and the PR body, both of which already carried it.

This is the inline-comment counterpart to the density rule in the system prompt (match the surrounding code's comment density): in this codebase that density is **low**, so the default for a small, pattern-following change is zero comments. Where a comment *is* warranted — a genuinely surprising constraint, a measured trade-off, a workaround for external behaviour — keep it, and state the reason rather than the mechanics.

### Before coding a fix or feature

See [`AGENTS.md`](../AGENTS.md) → *Working discipline* for the orientation passes (consult the KB for the area + enumerate existing tests before writing code or invoking `test-writer`), *keep digging to the root* (once the user picks "fix" over "gate", don't resurface "just gate it?" or offer to hand off to "the author" while they're driving — build a baseline worktree, instrument, attempt-then-test), *un-gate verification* (verify **every** gated provider — incl. locally-runnable netfx/file-DB ones like SqlCe/Access — don't assume a hard-to-reach one stays broken), and *least-invasive resolution* (exhaust built-in API / `Sql.Extension` / mapping-schema registration before touching cross-cutting core; never interpolate a user value into a SQL string — parameterize).

**Do a blind-spot pass before coding in an unfamiliar subsystem.** Before writing a fix/feature in code you don't know well, explicitly surface what you might be missing — ask what unknown-unknowns the change could hit (edge cases, provider quirks, cross-cutting invariants) or enumerate the assumptions the plan rests on — rather than coding straight from the first read. Cheap insurance against being confidently wrong on unfamiliar ground; complements the KB-consult + enumerate-existing-tests orientation passes above.

**Offer the root-cause alternative even when the user prescribes a mechanical fix.** When the user hands you a specific prescribed approach — especially a mechanical / CI-side / workaround-shaped one — still surface the simpler root-cause alternative (with its trade-offs) as an explicit option before implementing, rather than just executing the prescription. Present their approach first (respecting intent), then the root-cause option, and let them pick. (On #5715 the user prescribed a CI-side baselines-staging fix but, offered a test-harness root-cause gate as the alternative, chose it — *"let's try 2 — I like it"*.)

**Red test first for a review-finding fix.** When fixing a reproducible review finding (yours or a reviewer's), write the failing (red) regression test *before* the fix — it confirms the finding is real and that the fix targets it. If no repro can trigger it, don't fix on speculation: post a "could not reproduce" FYI with repro details + a test pinning the current (correct) behaviour, rather than a speculative core change.

**An adjacent shape you noticed while fixing a proven regression gets a test written, not offered.** The rules above are framed around a *review finding*; the gap they leave is the regression you found yourself. Having proved one defect and named a neighbouring shape nothing covers — "no current test exercises this; worth pinning if you want" — write the test instead of closing with the offer. Two reasons, and the second is the real one. The cheap reason is that you already have the worktree built, the provider configured and the repro in hand, so the marginal cost is one build. The load-bearing reason is that **the test is what tells you how bad the defect actually is**: a shape you can only reason about gets written up at the severity your reasoning supports, and severity assessed that way is systematically too low. Verify the neighbours before you report, then report what they showed. (Surfaced on #5750: a fix was proposed with the note that neither a `Union` nor a `WHERE` shape was covered and either was "worth a regression test if you want it pinned". The maintainer's answer was *"ah, add those regression tests before ci"* — and writing them moved the finding from *extra columns in the SELECT* to **wrong results** (a `Union` returning ten rows where three were selected) plus a **hard translation failure** (`The LINQ expression … could not be converted to SQL`) on a query that worked on master.)

**Check a deliberate-looking element's provenance before flagging or changing it — it may exist because of an earlier review, possibly your own.** When a finding targets something that reads as a considered decision — a named error message, an explicit gate, a comment defending a choice — spend one `git log -S "<token>"` over the PR's own commits plus a scan of the review threads on that file before proposing anything. It changes the output in two ways. The element may have been added *in response to a prior finding*, in which case the right artifact is a **`Correction:` retraction of that finding** rather than a fresh defect filed against the author, who implemented what they were asked for. Or its rationale may already be recorded at the site, in which case the finding is at most that the rationale is *wrong* — a much stronger and more specific claim than "undocumented". Cheap: one `git log -S` and one grep of the thread bodies already loaded with the PR context. (Surfaced on #5750, at the user's prompting — *"check why message was added"*. A translation-stage refusal carrying a named message traced to my own earlier `MIN003`, which the author had implemented verbatim and closed with my own premise quoted back at me. Measurement then showed that premise — that a translation-time refusal leaves a projection free to fall back to .NET — was false. Without the provenance check it would have been filed as a defect in their work instead of a retraction of mine.)

**Once a review finding is reproduced, "fix it here" is the default recommendation — reserve track-it-separately for what is structurally unfixable in the PR.** Having proved a defect red, don't offer a tracking issue, a comment-only touch-up, or a doc note as the *recommended* disposition when the fix lands inside the code the PR already changes. The test to apply is whether the fix is **reachable from this PR's own surface**: a defect in the same file / package the PR edits is in reach and should be proposed as a fix plus a regression test; a defect whose correct fix needs a capability the PR doesn't have — a new provider feature, a different target shape the API cannot express, a cross-cutting core seam — is the genuine tracking case, and saying so explicitly is what makes the tracking issue land without pushback. Distinguishing the two is the whole judgement; defaulting to "track it" for both is what the rule forbids. (Surfaced on #5701: a proven three-chained-`groupJoin` row-loss bug was written up with a recommendation to *"fix the comment + file a sibling issue"* — the maintainer's answer was **"add tests and fix here"**, and the fix was nine lines in the file the PR already changed. In the same walk, a correlated-inner-sequence gap that genuinely could not be expressed as a flat `GroupJoin` was accepted as a tracking issue without objection.) Pairs with [`review-orchestration.md`](review-orchestration.md) → *Default the recommendation to a pushed fix, not a posted comment*.

**Reachability precedes reproduction.** A "this code path fails for input type/shape X" finding — even one a reviewer marks *confirmed* — is only a defect if X is **reachable**: verify X is constructible and actually reaches the path (compile + run), because language/framework constraints can make it unconstructible or route it elsewhere. A code path that *could* mishandle a type it can never receive is a robustness gap for unreachable input, not a live bug — don't add untested defensive branches for it. (On #5701 a reviewer "partially confirmed" that `FSharpRewriteVisitor.CreateSentinel`/`GetUninitializedObject` silently falls back for captured `Nullable<T>` / interface / abstract free vars; empirically unreachable — `Nullable<T>.Value` on a captured local won't compile in an F# quotation (`FS3155`), and an interface-typed *local* is an ordinary closure, never a `SubstHelper` free var (those are the outer query range variables, always entity reference types). `Issue1813Test8` pins the interface-local case green; no `CreateSentinel` change made.)

  **The same test applies to a *host* — check the product ships to the configuration before writing up a platform gap.** The rule above is framed around input types, which is why it doesn't fire on its most embarrassing case: a finding of the form "on platform / OS / architecture / runtime P this would break". P has to be reachable too, and that is one lookup against the vendor's own download or support matrix — cheaper than the analysis it invalidates, and it must come *first*, because a platform-shaped finding reads as urgent and gets written up in detail before anyone asks whether P exists. (On #5786 a finding was drafted that IBM's macOS DB2 client ships arm64-only natives, so DB2/Informix would be offered and then fail to load on an Intel Mac. The maintainer's reply was *"which arch for macos linqpad support?"* — LINQPad 9 for macOS is published for Apple Silicon only, so the driver never runs on an Intel Mac and the arm64-only client is an exact match. The finding was dropped, not demoted.)

**But absence from a corpus sweep is not proof of unreachability — and severity turns on the difference.** The rule above stops you fixing a path that genuinely cannot receive X. It does **not** license concluding "unreachable" because a sweep of the existing corpus (regenerated baselines, the test suite, a `git grep`) finds no instance: that only shows the corpus doesn't *exercise* the shape, which is exactly what you'd expect of an untested gap. When the mechanism is confirmed against source and the only open question is reachability, spend one probe **constructing** the shape before down-scoping — a playground query plus a `git worktree` at `origin/master` for attribution is usually enough. (On #5723 a marker-under-cast finding was scoped MIN because none of the 649 regenerated baselines showed the trigger shape; one probe built it from ordinary LINQ — `Sql.Convert<string, int>(Sql.AsSql(name).Length)` — and showed Firebird dropping a *declared* `VARCHAR` cast that `master` emitted. It was a MAJ, fixed in `bdbb45d93`.)

**Better than constructing one shape: instrument the suspect code and let the existing corpus enumerate its real inputs.** When the question is *"which types / shapes can actually reach this function?"*, a construction probe only tests the shape **you** thought of — so it confirms or refutes one hypothesis and says nothing about the rest of the input domain. Instead, temporarily log the function's actual argument at its entry (append to a file under `.build/.agents/`), run the existing test suite over the feature, then read the distinct values back. One run yields the whole reachable input set, including the members you would never have guessed, and the instrumentation comes out with the fix. (On #5701 a reviewer said a `Nullable<T>` free variable could reach `CreateSentinel`; a prior session had replied "unreachable — always entity reference types". Logging every `t.FullName` across the `Issue1813` set returned entity types, `Tuple<,>`, **`Nullable<int>`** *and* **`String`** — refuting the "always entity" claim, showing the reviewer's `Nullable<int>` was reachable but harmless, and surfacing `String` as the type that actually threw. A construction probe aimed at `Nullable<T>` would have concluded "no defect".)

  **To prove a block is dead, delete it *and* instrument its call site in the same build.** A third variant of the same one-build discipline, for the question *"does this code ever run, and is removing it safe?"* — which is two questions, and each half alone under-answers it. Logging the inputs shows the guard's combination never arrives but says nothing about whether something downstream depended on the block's side effects; deleting it and getting a green suite shows removal is safe but not *why*, so the result reads as "the tests don't cover it" rather than "the code is unreachable". Doing both in one build yields the mechanism and the safety proof together, which is what makes a delete-N-lines recommendation land instead of inviting "are you sure the tests cover that?". Log to an absolute path — a relative one follows the invoking process's cwd (see [`worktree.md`](worktree.md) → *Run artifacts follow the invoking process's working directory*). (Used on #5727 to retire 43 lines: the log recorded 1621 calls in six flag combinations with `Expand` absent from every one, while the same build ran 162/162 green with the block gone.)

  **Every probe write needs a lock — provider lanes run in parallel.** The three rules above all say "append to a file under `.build/.agents/`", which was safe when the suite was serial. Since [#5614](https://github.com/linq2db/linq2db/pull/5614) the same test method runs concurrently across provider lanes, so an unsynchronized `File.AppendAllText` throws `IOException: the process cannot access the file … because it is being used by another process` — and because the probe sits inside the code under test, that exception **fails the test it is instrumenting**. The failure reads as a product regression in whichever lane lost the race, which is the expensive part: you go looking for a bug in the change rather than in the probe. Wrap the write in a `lock` on any stable object, or give each lane its own file (`…-<context>.txt`). (Surfaced on #5737: an unlocked probe reddened `ReusesDuplicateTphConstructors("SQLite.Classic")` while `SQLite.MS` wrote fine; earlier probes in the same session happened to take a lock and were unaffected, so the difference looked like a provider-specific defect.)

  **To attribute a behaviour change to a commit, run the old implementation *beside* the new one in one build — don't revert to compare.** The rule above instruments one implementation to learn its inputs; this variant instruments two to learn which one changed the answer. Paste the pre-change version of the function in next to the current one under a throwaway name, log both results for the same input, and run once. A revert-and-rebuild cycle costs two builds, tells you only *that* the outcome flipped, and leaves the working tree in a state you have to remember to undo; the side-by-side costs one build and prints the two values, which is what identifies the mechanism. Use it when a suspect commit is already narrowed to a handful and you need to confirm which — not as a substitute for narrowing (see [`baselines-repo-layout.md`](baselines-repo-layout.md) → *Commit granularity*). (On #5750 a canonicalization fix was suspected of breaking a converter comparison. Logging the current and the pre-fix canonical forms together returned `ct1 = Convert(p, Nullable\`1).ToString()` / `ct2 = p.ToString()` against `Lt1 = Lt2 = p.ToString()` — the old form matched, the new one didn't, and no exception was thrown on either. That last part mattered: the leading hypothesis had been that the old code would *throw* on this input, and only running it proved otherwise.)

**Repro blocked by a separate, known engine bug → gate the test, defer the fix.** A third case beyond *reproducible* and *can't-reproduce*: the finding's mechanism is verified against core code, but you can't drive an end-to-end red repro because an *unrelated, independently-tracked* engine bug blocks the only path to it. Then commit the regression test `[ActiveIssue]`-gated on the **blocker's** issue and defer the actual fix until the blocker merges — so the fix is verified over the real path once un-gated (per *Verify a fix by the same path that surfaced the bug* below), rather than applying a speculative fix that can't yet be exercised. (On #5704 a single-case-DU null-read defect, verified against `ConvertFromDataReaderExpression`'s `HandlesNulls` path, was unreachable from F# because the captured-lambda predicate translation it needed is blocked by #1813 / open PR #5701; the gated `DuQuery_NullReadKey` carries the intent and the `handlesNulls=false` fix waits for #5701.)

**Adding a runtime guard? Its false-positive set is what grep cannot see — run the corpus before pushing.** The rules above are about finding which inputs reach code that already exists. The mirror case is a *new* assert you add to shared test infrastructure or a shared engine path: you sweep for the shapes that violate it, annotate those, and push. But a guard's cost is not the violations you found — it is every **legitimate** caller whose shape your sweep did not model, and those are invisible to a grep aimed at the shape you already have in mind. Run the affected suite once before pushing; the false positives announce themselves in a way no amount of reading will. (Surfaced on #5614: a guard requiring every remote-context creator to be classified remote was swept for by `[DataSources]`-shaped parameters, and the three matching tests were annotated. Four cases in `DataContextTests` took no context parameter at all — a shape the sweep had no way to express — and, being `[NonParallelizable]`, already satisfied the invariant by a route the classifier never sees. The guard turned 11 CI legs red on a run that cost ~40 minutes to discover what one local run would have shown.)

**Verify a fix by the same path that surfaced the bug.** When a defect was found empirically — a dogfood run, a repro, a CI leg — confirm the fix over that *same* end-to-end path, not only a fresh unit test. A green unit test proves the narrow case; it doesn't prove the fix holds on the real corpus/flow that exposed the bug. (Surfaced when a code-fix defect found by dogfooding was "verified" with a unit test alone — *"was it dogfooded?"* — the end-to-end re-run was the actual proof.)

**A fix in cross-cutting core gets a core-layer regression test, not only the consumer-level one.** When a bug surfaces through one consumer (e.g. `linq2db.EntityFrameworkCore`) but the defect lives in shared engine code (SQL AST, `ProviderDetectorBase`, an `IDataProvider` seam), add a provider/consumer-agnostic test at the core layer *in addition to* the consumer repro — the core test pins the general contract the fix restores, and proves the bug was never consumer-specific. (#5296: the EF `Issue5296Test` proved the `EnsureCreated` symptom, but the leak was in `ProviderDetectorBase`'s `AutoDetect` path; `ProviderDetectionDoesNotLeakConnection` in `DataConnectionTests` pins it directly — red across net462/8/9/10 pre-fix.) To prove the core test is genuinely red once the fix is already committed, see [`bug-investigation.md`](bug-investigation.md) → *Proving a red test after the fix is committed*.

**A statically decidable invariant wants an analyzer, not a reflection guard test.** When the gap is "nothing enforces that declaration X accompanies implementation shape Y", prefer a Roslyn analyzer over a reflection test that walks a fixed type list: the analyzer fires on new code as it is written and, if it goes in the shipped `linq2db.Analyzers` package, covers user-defined members too, whereas a reflection test only ever covers the types it names. The repo already hosts both flavours — repo-internal rules (`LINQ2DB0001` in `Source/CodeGenerators`, wired via `OutputItemType="Analyzer"`, shipped in no package) and user-facing ones (`L2DB1001` in `Source/LinqToDB.Analyzers`) — and `Source/LinqToDB/LinqToDB.csproj` deliberately omits `OutputItemType="Analyzer"` on the user-facing reference, so the two hosts are separate by design and an internal invariant needs an internal rule. Note `Tests/BannedSymbols.txt` bans every `MemberInfo.GetCustomAttribute*` overload, so a reflection test would have to route through `AttributesExtensions.GetAttribute<TAttribute>(bool inherit)` anyway. (Established on #5783: a reviewer suggested a reflection test pinning `[ServerSideOnly]` across `WindowFunctionBuilder`'s 104 hand-annotated methods; the maintainer's call was *"we already created analyzer task which will handle it better and for all"* — filed as #5788, covering both directions of the implementation-vs-contract mismatch and `Sql.GroupBy`'s unmarked `Rollup`/`Cube`/`GroupingSets` with it.)

**Proposing a new cross-cutting core capability? Include a beneficiary survey.** When a task leads to proposing a new core seam (interface, hook, extension point), don't justify it by the driving case alone — sweep for existing code exhibiting the same gap (grep for the workaround pattern, e.g. `MappingSchema.Default` fallbacks) and existing/potential issues it addresses (KB github indexes + `gh search issues`), and fold that adoption analysis into the design artifact. A core change justified only by one consumer is a workaround wearing a design's coat. (Established on #5675, the schema-aware metadata-reader task.)

Before calling a code change "done" — and before proposing to commit / push — walk the consolidated completion checklist in [`definition-of-done.md`](definition-of-done.md). It gathers the completion gates that otherwise live scattered across these rules (tests green via `/test`, baselines reviewed, `PublicAPI.Unshipped.txt` updated for new public surface, `CompatibilitySuppressions.xml` refreshed via `/api-baselines`, no playground scratch staged, XML docs on new public members) into one place so none is silently skipped. The individual rules stay canonical; the checklist only points at them.

### Investigating & fixing bugs

- **Start from the KB and recorded dead-ends.** Before reproducing, check the area's `areas/<AREA>/issues.md` / `tech-debt.md` / `detected-issues/` *and* auto-memory `project_*` entries (indexed in `MEMORY.md`) — the symptom may be a known issue, a prior fix, or a `Don't re-attempt:` dead-end a past session already paid for. Capture *new* dead-ends via `/session-reflect`. Orientation only; re-verify against current source (see *Consult the knowledge base* above).
- **Situational triggers** — fix-or-disable batches, "regression after switching package X→Y", reproducing a regression (HEAD-contains check), tracing a token via `git log -S "<token>" --all -- "*<File>"`, `[ActiveIssue]` enable, provider-limitation flags (find the flag before gating, regress wide), non-deterministic failures (assert all valid outcomes), don't-weaken-the-test — full detail and the war-stories behind each: [`bug-investigation.md`](bug-investigation.md). Read it when one fires.
- **Attribute a failure to the right layer before working around it.** When a task fails through an external tool (a formatter, driver, build step, SDK), prove the defect isn't in *our* code before accepting "the tool is limited" and routing around it — isolate it in the tool's underlying SDK or a minimal harness. (Surfaced when a `dotnet format` under-application looked like a tool limitation but was our `WellKnownFixAllProviders.BatchFixer` choice; the real fix was ours — a custom `FixAllProvider`.)
- **Explain the mechanism before proposing the fix — and certainly before offering a choice between fixes.** A remedy chosen from a symptom encodes whatever the symptom suggested, and a fix menu built that way asks the user to pick between options that may all be answering the wrong question. Write the causal chain out first — what ran, in what order, in which process, and why that made the operation fail — then let the scope of the fix fall out of it. This is cheap and it collapses work: the same explanation that justifies a fix usually also deletes half the candidates. (Surfaced on #5786: offered a four-option menu for two "problems", the maintainer replied *"explain failure first"*, and writing the chain out dissolved one of the problems entirely — a misread stack trace, see [`bug-investigation.md`](bug-investigation.md) → *A frame's type name names the branch* — while narrowing the other from six call sites to two.)

### Issue-proposed fix details are written from memory — verify them

See [`AGENTS.md`](../AGENTS.md) → *Issue-proposed fix details* — a concrete identifier / constant / version in an issue is a hypothesis; verify against the actual artifact before implementing, or the fix can silently no-op.

**A comment a change has falsified is often the symptom, not the finding — check whether the change is mis-scoped first.** When a diff makes a neighbouring comment untrue, the tempting write-up is "stale comment, update the wording". Ask instead whether the *comment* was right and the *code* is wrong: a comment describes intent, so a change that contradicts one has, by construction, altered intent — sometimes further than intended. The highest-yield case is a `PackageReference`, `VersionOverride` or property override placed in an **unconditional** `ItemGroup` of a multi-TFM project, where it silently applies to every TFM including ones that must not have it; the falsified comment is then the only visible trace. Verify the resulting per-TFM state from the restore graph (`project.assets.json`) or the built artifact before proposing either fix. (Surfaced on #5786: a stale `System.Reflection.Metadata` resolver comment in `DriverHelper` was written up as a doc nit; the maintainer's answer was *"that's oversight. netfx too should use 5.6.0, only net8 should use downgraded version"* — an unconditional `VersionOverride` had silently downgraded the LINQPad 5 build's Roslyn. Scoping it to the intended TFM fixed the defect and made the comment true again, so the doc nit dissolved.)

  **The mirror applies to your own changes: after altering behaviour, grep the prose for statements about it.** The rule above is easy to read as being about *someone else's* comment in a diff under review, and that reading is how it gets violated — a behaviour change you make yourself falsifies a readme or doc paragraph, and nothing in the diff points at it because the prose lives in another file. So when a change alters *when* something happens, *where* it is reported, or *which* platform it applies to, search the readme, the docs and the neighbouring comments for the old claim before calling the change done; it is one `Grep` per behaviour word. (Surfaced on #5786 within one session of adding the rule above: restoring Windows message boxes left the driver readme asserting that errors outside the connection dialog are *never* shown in one — true before the change, macOS-only after it, and caught two commits later rather than in the commit that broke it.)

**A cited external precedent is a claim too — check the shipped artifact, not the source repo.** When a review / issue / doc says "project X does it this way", read what X actually *publishes* (the nupkg's nuspec, the released binary, the deployed config), not only its source tree. A repo's source can under-describe its own behaviour: shared props / imported targets / generated metadata supply what the visible file omits, so a source-only read yields a precedent that is real but incomplete — and copying it half-way ships a half-fix. (On #5720 a review cited EF Core's `EFCore.csproj` analyzer reference; `EFCore.Relational.csproj` looked like a plain `ProjectReference` that broke the chain, but the published `Microsoft.EntityFrameworkCore.Relational.nuspec` carries `exclude="Build"` — a shared props file supplies the metadata. Reading only the csprojs would have left every satellite package's hop excluding analyzers.)

**A flag you are about to rely on is a claim too — read `--help` before building a plan around it.** When a proposed approach's *safety* rests on a CLI option (`--dry-run`, `--check`, `--no-act`, `--what-if`), confirm the option exists on that exact subcommand and version before offering the plan, not while executing it. Tools are inconsistent about which subcommands get a dry-run, and the failure mode is silent: the flag is unrecognised or treated as a positional argument, and the "safe probe" performs the real, irreversible action. (On 6.4.0 a plan to reproduce a release-tag failure via `gh release create … --dry-run` was proposed and approved; `gh release create` has no such flag, so running it would have published a real GitHub release. Caught only by reading `gh release create --help` first.) The same caution applies to an option you *remember* existing on a neighbouring subcommand — `--dry-run` on one is no evidence for another.

**A `WebFetch` answer is a claim too — pull the raw artifact for anything load-bearing.** `WebFetch` renders the page and answers your prompt through a *small fast model*, so what comes back is a summary with summary-grade reliability: fine for orientation, not for a fact that a fix, a plan, or a review finding will rest on. When the claim is load-bearing **and** the source is a file in a public repo, fetch the bytes and inspect them yourself — `gh api repos/<owner>/<repo>/contents/<path> -H "Accept: application/vnd.github.raw"` into a file (via the PowerShell tool, which avoids the `>`-redirect prompt), then `Grep` / `Read` it. Reading the implementation also beats reading the vendor's docs, which can contradict their own code. (On PR #5756 a `WebFetch` correctly quoted YDB's `use_in_memory_pdisks_flag`, but in the same session asserted that `YDB_PDISK_SIZE` "does not appear in the provided code" when it does, and relayed a docs table that contradicted the implementation it linked to. The raw-file check settled all three.)

**To prove a *negative* about external code, enumerate with a repo-wide code search — one file is not the tree.** Reading the single file where a symbol is used establishes what *that file* does; it cannot establish that nothing else does it, which is the claim any "this state can only come from X" conclusion actually rests on. `gh search code --repo <org>/<repo> "<SYMBOL>"` returns every file, so "exactly one writer" becomes checkable rather than assumed — and the answer is often that the definition and the single writer are the only two hits, which is exactly the evidence you need. (On the #5757 review the conclusion turned on PostgreSQL's `DATCONNLIMIT_INVALID_DB` having one writer: reading `dbcommands.c` alone showed one assignment inside `dropdb()`, but only the repo-wide search ruled out `createdb()` / `movedb()` / recovery paths in other files and turned *"an invalid database can only follow an interrupted DROP DATABASE"* from plausible into sound. Note `WebFetch` on the vendor's own docs had already answered the same question with "the documentation does not specify" — twice.)

A dump also tends to strand the findings in the transcript rather than landing them on the PR — the tell is the user asking *"where is review results?"*. (Surfaced on #5737, twice in one session: findings were first scattered across progress turns, then re-delivered as a single table, and the correction was *"well, why you don't offer standard interactive walk then"*.)

### Running tests

When the user asks to run tests, **invoke `Skill(test)`**. Don't call `Agent(test-runner)` directly, and don't run `dotnet build` before the skill — `dotnet test` rebuilds inside the skill, and bypassing it silently skips `CreateDatabase` filter injection and the baselines diff. Project selection (Playground vs Linq), multi-TFM gating, and `playgroundLink` are the skill's responsibility — see [`.claude/skills/test/SKILL.md`](../skills/test/SKILL.md) → step 3.1.

**Every hand-run `dotnet test` / test-exe invocation carries `--test-progress`.** `/test` and `test-runner` pass it for you; the runs that lose it are the ad-hoc ones — a worktree repro, a bisect step, a quick filtered check. Without it there is no heartbeat at `.build/.agents/test-progress.<tfm>.<pid>.json`, so a long run is unobservable, nobody can answer "how far along is it", and — worse — the *absence* of a heartbeat is the corpus's own evidence that a run never started (see *Agent guardrails* → liveness), so a flagless run is indistinguishable from a dead one. It is a plain CLI option with a default path, costs nothing, and a bare `--test-progress` is the whole addition. The only checkouts where it doesn't exist are pre-#5621 ones ([`testing.md`](testing.md) → *Scoping a run to specific providers*).

For a **worktree** target (e.g. validating fixes during `/review-pr` interactive mode), `/test` still owns the run: pass `run <filter> worktree <abs-worktree-path>` so it forwards `repoRoot` to `test-runner` and builds/tests the worktree rather than the primary clone. Don't hand-run `dotnet test` against a worktree — you'll miss the custom `--provider` arg / `--settings .runsettings` / the `CreateData.CreateDatabase` prefix and burn calls on .NET 10 MTP CLI quirks (`dotnet test` needs `--project`; without `--provider`, `[IncludeDataSources]` tests resolve zero providers → "0 tests"). The full recipe is in [`worktree.md`](worktree.md) → *Running tests from a worktree* — read it before testing in a worktree.

### Build & push gotchas

Pre-push build rules are operative in [`AGENTS.md`](../AGENTS.md) → *Build gotchas that fast-iteration hides* (always-loaded), with full detail in the linked docs:

- **TFM API availability** — `-c Testing` builds net10.0 only and misses `net462`/`netstandard2.0` API gaps; **analyzers are Release-only** (`Testing`/`Debug` skip Roslyn / Meziantou / banned-API). - **Iterative-build file locks / disk space** (build-server lock, `.build/bin/` accumulation): [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *Iterative-build gotchas*.
- **MSBuild override precedence** (env vars don't beat conditional `<PropertyGroup>`; only `-p:` does): [`msbuild-override.md`](msbuild-override.md).
- **Before deleting a type or member — or removing/renaming a build or packaging concept (a NuGet package, a project's packable role, a target model) — sweep for references in XML doc-comments and inline comments, not just call sites.** A dangling `<see cref="…"/>` / `<paramref …/>` pointing at a removed type is a **build error** under `TreatWarningsAsErrors` (CS1574 / analyzer), not silent doc rot; a stale inline comment naming the removed symbol is just misleading. Grep the whole worktree for the symbol (code, XML docs, comments) plus `.csproj` (in case of an explicit `<Compile Include>`) before removing it. When the removed thing is a build/packaging concept rather than a symbol, extend the sweep to sibling project/build files (`Directory.Build.props`, sibling `.csproj`, `Directory.Packages.props`) whose comments may still describe the old model. **For a removed/renamed NuGet package id, also establish whether it was ever published** — `git log --oneline --diff-filter=A -- <the project's .csproj>` for the commit that introduced it, then `git tag --contains <sha>`: no release tag means the id only ever existed inside the current dev cycle and can be dropped silently, while a tagged (published) id makes the removal consumer-facing, needing a deprecation/unlist decision and a release-notes line. (Surfaced on #5711 removing the unused `CacheEvictionPolicy` enum — the user explicitly asked to "check it is not referenced in any xml/comments"; and on #5720, where making `LinqToDB.Analyzers.CodeFixes` non-packable left four sibling build files still describing the removed standalone `linq2db.Analyzers` package — an id `git tag --contains` showed had never shipped, which is what made folding it into `linq2db` a non-breaking change.)

### PowerShell Core scripts for complex operations

When the agent would otherwise make ≥ 3 related `gh` / `git` calls whose outputs feed each other (load → transform → post), wrap the sequence in a single **PowerShell Core script under `.claude/scripts/`** instead. One allowlist match instead of N, multi-step state stays inside the script, no compound-Bash friction, identical behavior on Windows / macOS / Linux. Skip for one-shot calls — the overhead isn't worth it.

The same rule of three applies one level up: a *procedure* you've hand-run 3+ times across sessions — not just a single call-chain — is a candidate to codify rather than re-derive each time (a script for a mechanical sequence, a skill for a multi-step workflow). Surface the candidate to the user, or route it through `/session-reflect`; don't silently keep repeating it.

A **review finding that names a gap in a repo *procedure* the skills own** — a release / release-prep step, a maintenance workflow — rather than a defect in the PR's code, is addressed by adding the missing step **verbatim to the owning skill** (a corpus commit in `.claude/`, pushed to the agents repo), not by a PR code change and not by a loose "post-merge follow-up" note that gets forgotten. Treat it as a curation task even when it surfaced while reviewing a feature PR. (Established on #5703: an "ensure the release procedure handles the `AnalyzerReleases` Unshipped→Shipped transition" review comment became a verbatim step in `/release-publicapi`.)

Authoring contract, parallelism rules, and pwsh-script gotchas live in [`script-authoring.md`](script-authoring.md). Read it before adding or extending a script under `.claude/scripts/`.

**Prefer the PowerShell tool over `Bash(pwsh -NoProfile -File …)`** when invoking these scripts. Routing the call through Claude Code's PowerShell tool skips the Git-Bash / MSYS layer entirely — no path-mangling on slash-prefixed args, no `\??\C:\…` cygheap races, no quoting differences, no double allowlist hop. Use the Bash wrapper only when you need shell features the PowerShell tool can't express (multi-stage stdin heredoc piped between non-pwsh commands, etc.).

This applies equally to **inline `pwsh -NoProfile -Command "…"` containing `$variables`** — not just `-File`. Bash expands `$c` / `$j` / etc. as its *own* (undefined) variables before pwsh ever sees them, so `pwsh -Command "$c = Get-Content … | ConvertFrom-Json; …"` reaches pwsh as `= Get-Content …` and dies with `The term '=' is not recognized` (hit twice in one session parsing JSON with `ConvertFrom-Json`). Any pwsh needing `$vars` — JSON parsing, multi-statement transforms — must go through the PowerShell tool, never `Bash(pwsh -Command …)`.

### Temp files

Any skill, subagent, or ad-hoc command that writes a scratch file (JSON for `gh api --input`, generated diffs, intermediate output) must place it under **`.build/.agents/`** (gitignored) — never `%TEMP%` / `/tmp` / an absolute OS temp path. `mkdir -p .build/.agents` before the first write; name files by skill + id (`.build/.agents/review-pr-1234.json`). Cleanup is optional (gitignored dir; the last payload is useful for debugging).

**`.build/.agents/` is shared across concurrent sessions — never blanket-delete it.** The user runs parallel Claude Code sessions against the same clone, so the directory can hold another session's *live* diff cache, context JSON, and review manifests. When you do clean up (including on a "finalize session" request), remove only the files this session created — match on your own task / PR id prefix (`pr<n>*`) and enumerate before deleting; never `rm -rf .build/.agents` or `.build/.agents/*`. The task/PR-id naming convention above is what makes this possible, which is a second reason to follow it. (Surfaced 2026-07-29: a cleanup pass at the end of a #5720 session found `pr5678-*` files written minutes earlier by a concurrent session — a blanket delete would have destroyed its in-flight review cache mid-run.)

### Git commit rules

**Never publish without an explicit user request in the current turn.** This rule covers `git commit`, `git push`, `git tag`, `gh pr create`, posting GitHub comments, and requesting reviews — each new action needs its own go-ahead, even if the user just approved one a turn ago. "Explicit" means the user told you to do it this turn (e.g. "commit", "push", "create the PR"). Finishing edits, passing tests, or a clean working tree are not requests. When in doubt, stop and ask.

- **"Done" for an agent means "ready for your review", not "published".** When you finish a unit of work — edits applied, tests green, a draft written — park it in an explicit awaiting-acceptance state and say so ("changes are staged, ready for you to review / commit"); don't treat completion as license to commit, push, or post. Each publish action above needs its own go-ahead this turn.
- **Never commit playground scratch.** Under `Tests/Tests.Playground/`, only `Tests.Playground.csproj` structural updates and `TestTemplate.cs` are PR-acceptable — **no** new source files (tests belong in `Tests/Linq/`, linked via `<Compile Include>`) and **no** new `<Compile Include>` fixture refs (those are `test-writer`'s session scratch). Audit and `git restore --staged` them before any commit/push; if the user asks to commit one, stop and confirm. (Detail: [`AGENTS.md`](../AGENTS.md) → *Never commit playground scratch*.)
- **Large-scale deletions are a red flag** (>100 files removed, or removed:added > 5:1) — usually incomplete build output (failed pre-build, wrong staging dir, regenerated-empty generated file like `CompatibilitySuppressions.xml` / `PublicAPI.*.txt`), not a real shrink. Check `git diff --stat <ref>..HEAD` before publishing. See [`AGENTS.md`](../AGENTS.md) → *Large-scale deletions*.
- **Amending a commit on a non-checked-out branch with a dirty current tree.** Don't `stash`/`switch`/`--amend`/`switch -`/`pop` — the pop can conflict on overlapping files. Use the `commit-tree` + `update-ref` recipe in [`pr-and-push.md`](pr-and-push.md) → *Amending a commit on a non-checked-out branch with a dirty current tree*.
- **`git commit --amend` takes the *whole* index — amend with `--only -- <pathspec>` whenever anything else is staged.** In the one-change-per-commit workflow (staging with an explicit pathspec, or letting `git checkout <ref> -- <paths>` stage a batch), the files for the *later* commits sit staged while you amend the current one. A bare `git commit --amend -F-` silently rewrites that commit to include all of them; recovery is `git reset --soft HEAD~1` then re-commit with the pathspec, which is cheap but only if you notice — the tell is the amend's file count. `git commit --amend --only -F- -- <path>` amends with just that path. (Hit on #5795 splitting 16 commits out of #5614: a message-only amend absorbed five unrelated staged files.)
- **Multi-line commit messages: `Write` the message to a file and `git commit -F <file>`.** `@'…'@` is PowerShell here-string syntax — the **Bash** tool does *not* parse it, so `git commit -m @'…'@` passes the literal `@` characters through as leading/trailing message lines (had to amend). Use `-F <path>` (or the PowerShell tool with a proper `@'…'@` here-string), never `-m` with a here-string in Bash. Repeated `-m "para"` flags (one plain double-quoted string per paragraph, blank-line-joined by git) are the simplest Bash-safe multi-paragraph form — no scratch file (a `-F` target under `.build/.agents/` may hit a Write "read it first" refusal when it already exists from a prior session), no here-string. Prefer this unless the body needs literal formatting a shell arg can't carry — **or the message text contains a `;`, `&&` or `||`**, which the compound-command PreToolUse hook rejects: it matches the whole command string and cannot tell prose from shell syntax, so a paragraph like `… CAST(@name AS Decimal(18, 10)); the declared cast is dropped` fails with `';' chaining` even though nothing is being chained. Any body carrying one of those characters must go through `-F <file>`. (Hit on #5723 writing a commit message that quoted rendered SQL.)

### Push to remote rules

Detail-heavy mechanics live in [`pr-and-push.md`](pr-and-push.md). One-line triggers — when one fires, read the doc:

- **When several related PRs are active in one session (a main PR + its offloads, each in its own worktree), pin an unnamed push / `/azp run` / commit instruction to the PR the user's *primary goal* concerns — not the most-recently-touched worktree.** Confirm the target PR when the instruction is ambiguous. (Corrected after "sync with master, push and run ci" fired a full `test-all` on offload #5710 when the user meant the parallelization PR #5614 — *"what are you doing. on tests parallelization pr"*.)
- **After every successful push, check for a PR on the branch.** If one exists, diff the new commits against its body. **On a PR the user authored**, propose a body edit (as a diff, never a full rewrite) — and when the user already has prose there, append a `## Follow-up commit` subsection rather than rewriting their text. **Do the append with `.claude/scripts/pr-body-edit.ps1`** (anchor-based, round-trips through UTF-8 file I/O) — never hand-roll fetch-body → mutate → `gh pr edit`/`gh api`, which collapses the *existing* body's newlines onto one line (headings fuse to their paragraphs; see [`github-authoring.md`](github-authoring.md) → *Verify after every manual PATCH/PUT*). After the edit, verify the **whole** stored body renders (fetch it back and check heading/blank-line structure over the head, not just the appended tail — a tail-only check passes while the head is silently collapsed; this is how #5686's body got mangled). **On a PR authored by someone else, do not edit the body at all** (per [`github-authoring.md`](github-authoring.md) → *Never edit content authored by other users* — appending to their body is still editing it); convey the follow-up via the review you post or a new comment instead. If no PR exists, propose creating one (see **Pull request rules**).
- **After every successful push, re-request Copilot review** — auto-trigger is unreliable: `gh pr edit <N> --repo linq2db/linq2db --add-reviewer copilot-pull-request-reviewer`. Don't pass the slug `Copilot` here (errors); don't fall back to the REST `requested_reviewers` endpoint (silently no-ops when Copilot already reviewed an earlier commit on the same PR).
- **When follow-up commits rename / move / delete a test — or wrap a previously-capturing test in `DisableBaseline` so it stops emitting — read the orphaned baselines correctly, but don't treat them as an action item.** `linq2db.baselines` files are keyed by the fully-qualified test name and never auto-prune, so the branch carries files for the *old* name / the now-suppressed test as orphans. At review time this shows up as captured `.sql` files for a test the current head `DisableBaseline`s — stale orphans, not the PR's new baselines; read them as such rather than as additions (`baselines-reviewer` misclassifies them as `new_correct`, so cross-check against the head's `DisableBaseline` usage yourself). **Over-baselining is not a problem in itself and needs no cleanup** — the release flow resets `linq2db.baselines` to the documented anchor commit so CI regenerates clean baselines on the release PR (see [`.claude/skills/release-publish/SKILL.md`](../skills/release-publish/SKILL.md)), so orphans never become permanent expectations. Do **not** propose closing the baselines PR or deleting its branch to "clean up" orphans, and never make it a review finding. (Corrected 2026-07-30 on #5732, where 14 orphans from a superseded pre-revert CI run were nearly written up as a blocker on the baselines PR — *"we regenerate baselines during release, no over-baselining is not a problem"*.)

### Docker containers: start/stop/create only

See [`AGENTS.md`](../AGENTS.md) → *Docker containers*: scope is `docker start` / `stop` / `create` / `ps` only (no compose / `inspect` / config reads); start the container a test needs if it exists-but-stopped (don't run on "whatever's up"); `UserDataProviders.json` connection strings are authoritative; ask only when the container doesn't exist. If a test won't connect after start, report and wait — don't chase credentials by inspecting the container.

**Scope-change prompt for session-started containers (Claude-specific).** A `docker start <name>` run during the session is *intended* to be captured by the `track-docker-start` PostToolUse hook into `.build/.agents/docker-session-started.txt`, with the `cleanup-docker-session` SessionEnd hook stopping each of them when the session exits. **Treat that as opt-in, not guaranteed: verify the state file rather than relying on it.** Both hook scripts live in `.claude/hooks/`, but nothing under `.claude/` registers them — there is no `.claude/settings.json`, and `.claude/settings.local.json` carries no `hooks` key — so unless they are wired up in the *user-level* settings they never fire. (Surfaced 2026-07-30: three `docker start` calls produced no state file, the SessionEnd cleanup had nothing to act on, and the containers were reported to the user as tracked.) If it lists containers the session started, stop and ask the user whether to stop them before the scope change; name the containers in the question. Do not stop them silently — scope change doesn't always mean the user is done with the providers. Containers that were already running when the session started are not tracked and are out of scope.

### Agent guardrails (anchor set)

The most-violated guardrails stay inline. Lower-traffic guardrails (Surface trade-offs, Build configurations `==` vs `!=`, Document arbitrary values, Default to script over hook, Provider / Codebase claim verification, Distinct lenses for parallel reviewers, Cross-model verification for cross-cutting core, Persona framing, Editing whitespace / control characters) live in [`agent-guardrails.md`](agent-guardrails.md). Codebase design invariants these protect — public-API contract, cross-cutting internals, SQL AST namespace placement, column-aligned formatting — live in [`code-design.md`](code-design.md).

- **Don't reformat, rename, or clean up unrelated code.** The repo's column-aligned formatting is intentional (see `code-design.md` → **Column-aligned formatting is intentional**). *Unrelated* is the key word: the rule forbids touching lines the current task doesn't already modify — it does **not** suppress review findings on lines the PR itself adds or modifies. On PR-introduced lines, flag any of: **trailing whitespace on a line**, **3+ consecutive blank lines**, **mixed tabs/spaces that visibly misalign**, or **indentation not matching the enclosing scope**. These are new noise the codebase didn't have before, and the fix is a one-line ```suggestion. Don't flag the same patterns on lines the PR doesn't touch — that *is* reformatting unrelated code.

  **But an inconsistency the PR *creates* on an untouched line is in scope.** The added/modified test above is about *noise the PR introduced on its own lines*; it is not the full boundary. When the PR changes line A and that makes untouched line B inconsistent with it, B is reviewable — the PR caused the divergence even though it never edited B. Such a finding usually can't take an inline anchor (GitHub rejects a line comment outside a diff hunk), so route it to a **file-level** comment naming the line in the text. Read the rule as "don't go looking for pre-existing problems", not "never mention an unmodified line". (Surfaced on #5750: the PR fixed `%` precedence in `SqlExpressionFactoryExtensions.Mod`, leaving `SqlServerSqlExpressionConvertVisitor`'s own float-`%` rebuild on the old default — two paths that previously agreed now differ. It was nearly skipped as "unrelated code"; the user's call was *"bump to min and post"*.)
- **Don't reshape cross-cutting internals for a local fix.** When a task scoped to one provider or test seems to need a change in the SQL AST, `IDataProvider`, or translator interfaces, raise the question explicitly before making the change — the blast radius is the whole product (see `code-design.md` → **Cross-cutting internals are shared**).
- **Verify subagent output with `git status` after every invocation.** Subagent descriptions (`Read, Grep, Bash`, "never edits source code", etc.) are advisory — the harness does *not* enforce them. A read-only-declared agent can still call `Edit` / `Write` if its prompt nudges it that direction, and the only signal back to the main agent is the structured result it chooses to report. After any `Agent` call that returned, run `git status` once and confirm the only modified files are the ones the agent's task scope justifies. **Add `git -C .claude status`** — the superproject's status is blind to the corpus (`submodule.ignore = all`), and unprompted `.claude/` edits are a documented subagent failure (`test-runner` has done it), so a single clean `git status` is not evidence the corpus was untouched. Spell that second path **absolutely** (`git -C <primary-clone>/.claude status`): `-C` resolves against the shell's working directory, which drifts — a `Set-Location` issued through the PowerShell tool also moves the Bash tool's cwd — and the relative form then fails with `fatal: cannot change to '.claude': No such file or directory`, which at a glance is indistinguishable from the corpus directory having been destroyed. Particularly load-bearing for `test-runner` (declares no file writes), `code-reviewer` / `baselines-reviewer` (declare read-only), and any `Explore` agent. If unexpected files appear, treat the agent's result as suspect, restore the files (`git restore <path>`), and either re-invoke with a tighter prompt or do the work yourself.
- **A subagent's reported result is a claim, not evidence — verify it against an artifact.** The `git status` check above catches unauthorized *side effects*; it says nothing about whether the agent's summary is true. A subagent can report a clean pass it never observed: on 6.4.0 `test-runner` reported *"all four databases seeded successfully… passed: 1, failed: 0"* for a run that had actually failed on two of them — the numbers came from a stale heartbeat file it read instead of the run it launched. Before acting on a pass/fail summary that gates a decision, confirm it against something the agent didn't author: the test-progress JSON, the baselines diff, the build log, or re-running the narrow case yourself. **Implausible metrics are the tell** — a test count, duration, or file count that can't match the work described (1 test in 3.066 s across four databases; a "full sweep" that read three files) means the agent measured something other than what it claims. Treat the whole result as suspect and re-derive it, rather than reconciling the one number that looks off. Pairs with *Frame subagent prompts to allow failure* below (reduces fabrication) and the `git status` rule above (catches side effects); this one catches a plausible-looking answer that is simply wrong.

  **"Still running, let me wait" is a claim as well — and a worse one, because it invites you to wait forever.** An agent can return having launched nothing, reporting work as in flight. Verify *liveness*, not just results: no `dotnet`/`testhost` (or equivalent) process, and no heartbeat file such as `.build/.agents/test-progress.<tfm>.<pid>.json`, means nothing is running no matter what the agent said. Check before you settle in to wait, and again before re-invoking — a redundant second launch is the usual consequence of trusting the first claim. When you do resume the agent, say plainly what you verified and require it to run in the foreground (or to poll the heartbeat itself) rather than returning mid-flight. (On 6.4.0 `test-runner` returned *"The net9.0 run is executing in the background. Let me wait for it to complete."* with no process and no heartbeat; a `Get-Process` plus a `test-status.ps1` check settled it in two calls.)
- **Frame subagent prompts to allow failure.** When you write the invocation prompt for a subagent (`test-writer`, `code-reviewer`, `test-runner`, an `Explore`/`general-purpose` reader, etc.), make "report what's missing / blocked" an explicit, valid outcome — e.g. *"if you can't reproduce / locate / verify X, return what's missing rather than producing a plausible-looking result."* An open-ended "do X and report success" prompt rewards an agent for *demonstrating* completion over reporting honestly — the "obliging clerk" failure mode where it fabricates a green result (a vacuous test, a confident-but-wrong finding) rather than admitting the task didn't pan out. The repo's agents already have structured `blocked` / `needDisambiguation` outputs for this; the caller's prompt has to actually invite them. Pairs with the `git status` verification above — framing reduces fabrication, verification catches what slips through.
- **Don't let progress artifacts outpace real work.** Advancing a `TaskUpdate` status, checking off a plan item, or reporting a step "done" must track an actual applied change or a verified result — never mark progress you haven't produced. The failure mode (documented in autonomous-agent write-ups): an agent drifts into updating status/checklist artifacts to *look* productive while the underlying code and tests stand still. Same root as the *obliging clerk* above — rewarding the appearance of completion over the fact of it. Self-check: in a given turn, the process artifacts you touch shouldn't exceed the substantive changes you actually made.
- **Never hand-edit API baseline files.** `Source/**/CompatibilitySuppressions.xml` is generated output owned by the ApiCompat tool. Do not use `Edit`, `Write`, `sed`, or any other direct mutation on these files — not to add/remove a single suppression, not to "fix up" formatting, not to resolve a merge conflict. The only supported way to change them is the `api-baselines` skill (`.claude/skills/api-baselines/SKILL.md`), which regenerates them via `dotnet pack -p:ApiCompatGenerateSuppressionFile=true` and applies the `LinqToDB.Internal.*` policy check. If a task seems to require editing these files directly (for example, an existing PR's baseline conflicts with `master`), stop and invoke `api-baselines` instead. Applies equally to the main agent, subagents, and any generated scripts.
