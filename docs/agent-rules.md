## Working in this repo — Claude Code operational overlay

The **Claude-Code operational overlay**, auto-imported by `CLAUDE.md` alongside [`AGENTS.md`](../AGENTS.md) — both always-loaded. It carries only Claude Code harness mechanics (shell/tool rules, permission patterns, worktrees, corpus/submodule mechanics, subagent verification, skill workflows) and **does not restate agent-agnostic rules canonical in `AGENTS.md`**: where a topic is owned there, this file keeps a one-line pointer, never a second always-loaded copy. Detail lives in the focused docs under `.claude/docs/`, loaded on demand by any agent. Nothing here may contradict `AGENTS.md`.

### Creating a new branch

- **Name, base and dirty-tree handling are canonical in [`AGENTS.md`](../AGENTS.md) → *Creating a new branch*.** They bind every skill that creates a branch — `/fix-issue`, `/review-pr` checkouts of new branches, `/create-issue`'s follow-up suggestion — as well as ad-hoc branching.
- **Blocked `git checkout` / `gh pr checkout`.** If the switch fails because uncommitted changes would be overwritten, stop and ask how to proceed (stash, commit, discard), naming the blocking files. Do **not** silently `git worktree add` as a workaround.
- **Worktrees are the default for branch-based task work** — `git worktree add <worktrees-root>/<slug> <base>`, leaving the primary clone untouched; switching it disturbs its branch and whatever work sits there, and the user keeps a worktree per open PR. **`<worktrees-root>` is an environment convention, not a corpus constant**: take it from auto-memory or ask, and never assume the worktree is an ancestor *or* a descendant of the primary clone. Bootstrapping `.claude/`, `worktree remove --force`, `UserDataProviders.json` placement: [`worktree.md`](worktree.md). (`/review-pr` needs no checkout — it reads `origin/pr/<n>` via `diff-reader.ps1`.)
- **A separable shared-engine fix gets its own branch/PR** ([`AGENTS.md`](../AGENTS.md) → *Creating a new branch*). Claude addendum: don't *offer* to split a tightly-**coupled** enabling fix either — that needs an explicit user request. (#5659)
- **A structural migration an audit surfaces gets a filed issue, not a widened PR.** The rule above splits a *fix* onto its own branch; here the right answer is not to do the work yet at all. An audit — inventorying what ships, sweeping for a pattern, cataloguing dependencies — turns up adjacent structural work that is obviously correct and obviously not what the branch is for: a hand-copied binary that should come from a package, a folder that should be retired. The tell is that the finding is about *how something is obtained or organised* rather than about the defect the branch exists to fix, and that acting on it would touch artifacts the branch's own anti-goals exclude. File it with the evidence the audit already produced — that evidence is the expensive part and it is in hand right now — pick a later milestone, and cross-link it from the code. (#5731, #5861, #5862)
- **Don't switch to a recovery branch mid-rebase.** When an in-flight task surfaces an *unrelated* master breakage (usually a CI failure from a merge race), finish the in-flight branch first: resolve the conflict → force-push → `git switch -c <recovery-branch> origin/master` → open the recovery PR, which can run CI in parallel. Switching mid-rebase strands the in-flight branch rebased-but-unpushed and costs context.

### The corpus is a submodule — corpus edits go to the agents repo

`.claude/` is a git submodule ([linq2db/agents](https://github.com/linq2db/agents), branch `master`), so the corpus is identical on every linq2db branch and never needs carrying across a branch switch. What follows from that:

- **Commit corpus edits inside the submodule and push them to its `master`** — `git -C .claude add <pathspec>` / `commit` / `push` — each still gated by the *Git commit rules* below. They never land on a linq2db branch, and the `.claude` gitlink is left alone: it is a bootstrap pointer, not a version pin (`.githooks/pre-commit` refuses a staged bump, and `submodule.ignore = all` stops `git add .` from staging one). The one corpus change that *also* needs a linq2db commit is extending the root `CLAUDE.md` trampoline's import list.
- **The superproject's `git status` is blind to the corpus.** `ignore = all` hides uncommitted corpus edits *and* the submodule being ahead of the gitlink, so "clean tree" in linq2db says nothing about `.claude/`. Run `git -C .claude status` before asserting a clean tree, and after any subagent invocation that could have written there.
- **The corpus moves under you in both directions.** The user curates it from other sessions, so an *uncommitted* edit you apply can be silently wiped by their commit or working-tree reset — commit it in the same turn (when asked to) or re-verify it survived; while they are actively curating, prefer *proposing* the edit. The reverse also bites: the checkout **advances**, so a script's contract can gain the capability you are working around, with nothing in your own transcript marking it (the tell is a push reporting a range that starts from a commit you never fetched). An earlier read of a script header is evidence about *when you read it*, not about what the script does now — re-read it, or `git -C .claude log -1 -- <script>`, before hand-rolling a workaround; a third repetition of the same multi-step workaround is the signal to re-check. (#5880)
- **A fresh worktree gets its corpus from `post-checkout`, not from git.** `git worktree add` cannot populate a submodule itself, and an empty `.claude/` reads as a *clean* tree — so the failure mode is an agent running with zero project rules and nothing saying so. Since [#5820](https://github.com/linq2db/linq2db/pull/5820) the hook bootstraps it at checkout time, but the hook that runs is the **primary clone's** copy: a primary clone on a pre-#5820 branch still yields an empty `.claude/`, silently. Confirm the corpus is there before working, and note the bootstrapped submodule lands on a **detached HEAD**, so a corpus push from the worktree needs `git -C <worktree>/.claude switch master` first: [`worktree.md`](worktree.md) → *Bootstrapping `.claude/` in a worktree*.

### Bash command rules

Each Bash tool call must be a single command — the user may have a PreToolUse hook that rejects compound calls, and the permission system evaluates them as one opaque string anyway:

- No `&&` / `||` / `;` chaining; no shell control flow (`for`, `while`, `until`, `case`, `if`, `function`); no nested chains inside `$(...)` (plain `$(cmd)` is fine).
- Pipes (`|`) and heredocs are allowed, but every pipe / `>` redirect creates a novel command string that misses allowlist matching — prefer the command's own flag (`git log -n N`, `gh api --jq`, `Grep head_limit`) or persist raw output to the tool-result store and `Read` the path.

Split chained work into separate tool calls — parallel when independent, sequential when dependent.

#### Dedicated tools over raw CLI

`grep`, `rg`, `find`, `cat`, `head`, `tail`, `sed`, `awk` aren't allowlisted and prompt every time. Use the dedicated Claude Code tool:

| Want to… | Use | Not |
|---|---|---|
| Search file contents | `Grep` (`pattern`, `-n`, `-i`, `-A`/`-B`/`-C`, `head_limit`, `multiline`, `glob`, `type`; note `offset`/`head_limit` paginate *result* lines, not file lines) | `grep`, `rg`, `ack`, `ag` |
| Read a file (full or sliced) | `Read` (`offset` / `limit`) | `cat`, `head`, `tail`, `less` |
| Find files by name / glob | `Glob` | `find`, `ls -R`, `fd` |
| Edit a file | `Edit` / `Write` | `sed -i`, `awk -i`, redirect-into-file |
| Check-and-read a possibly-absent file | `Read` (returns a clean "does not exist" error you can branch on) | `test -f X && cat X` (compound → hook-rejected; recurred on the `docker-session-started.txt` check) |
| Search **with surrounding lines** | `Grep` (`-A` / `-B` / `-C` + `output_mode: "content"`) | `git grep -n "x" -A 20` — `git grep` reads a bare `-A` in that position as a **revision** and dies with `fatal: unable to resolve revision: -A`, so the miss looks like a different class of error than "unknown option" (hit twice in one session out of habit). Reserve `git grep` for plain which-files-contain-X sweeps and for searching a **non-checked-out ref** (`git grep <pattern> <ref> -- <path>`), which `Grep` cannot do. |

Reserve Bash for `git`, `gh`, `dotnet`, `pwsh`, helper scripts under `.claude/scripts/`. Four traps on that table:

- **It applies to a background task's output file too — the single most-violated case.** A completion notification hands you an absolute path, and `grep -n "error" <path>` / `tail -30 <path>` / `sed -n '117,200p' <path>` feels like shell work because the path came from the harness rather than from a tool. It isn't: `Grep` with a pattern plus `head_limit` extracts a failure summary from a 600-line log in one call, and `Read` with `offset`/`limit` replaces every `sed`/`tail` slice. (#5643)
- **A working-tree search is evidence about *your checkout*, not about the repo.** The primary clone is routinely many commits behind `origin/master` — 47 on one measured session — so a symbol a recent master commit added is simply absent, and the search returns a clean "no matches" rather than anything that looks like staleness. When something you have independent reason to believe exists comes back empty, read it as *"not in this checkout"* and re-ask against a ref: `git grep <pattern> <ref> -- <path>`, the `diff-reader.ps1` cache, or `git ls-files <ref>`. Same shape as the `git ls-tree` pathspec trap below — an empty result indistinguishable from absence. (#5737) **The mirror bites harder, because it produces an answer rather than a blank:** a `<path>:<line>` you read out of the stale clone is *wrong* in the worktree you are actually changing, and it looks authoritative wherever you paste it — a work plan, a PR body, a commit message, a review comment. Nothing in the citation says which tree it came from, and the drift is silent for any file master has touched since. Cite line numbers from the branch's own checkout, or re-derive them there before the text ships. (#5936: `SelectQueryOptimizerVisitor.cs:1373-1445` from the 93-commits-behind clone was `:1486`/`:1602` on the branch; `plan-critic` caught it in the plan, not a reader.)
- **When an `Edit` fails "string not found" on a line you just read, re-anchor — don't re-guess the indentation.** `Read` prefixes every line with a number and a tab, so the leading whitespace you see is not the file's, and counting tabs off that display is a coin flip in a tab-indented codebase. The tell is that the failure is *only* about whitespace — the code text is verbatim correct. Trim `old_string` to start at the first non-whitespace character and let the match float; uniqueness almost always survives it. (#5877)
- **Finding the newest test heartbeat is `test-status.ps1`, not `ls -t`.** It reads the latest `.build/.agents/test-progress.<tfm>.<pid>.json` and relays the one-line status in one call. The directory accumulates heartbeats from prior sessions and concurrent runs, so "newest by mtime" is a guess about whose run you are looking at. `/test-progress` wraps the same script.

#### Permission-friendly patterns

Patterns that triggered prompts in real sessions — full table in [`windows-gotchas.md`](windows-gotchas.md) → *Permission-friendly Bash patterns*. The highest-impact:

- **`>` redirect** (`gh api … > path`) misses `Bash(gh api *)` — prefer `gh api … --jq '…'` or let raw output persist + `Read`.
- **Inline `pwsh -NoProfile -Command "…"`** is never allowlisted safely — use `Grep` / `Read` instead.
- **`gh … --body @-` / `-f body=@<file>`** sets the body to the literal string `@-` or `@<file>` — use `--body-file <path>` (or `--input <json>` for PATCH).
- **Scratch scripts** must live under `.build/.agents/*.ps1` — only that path is allowlisted for ad-hoc invocations.
- **When the data is already on disk** (e.g. `diff-reader.ps1`'s `writeDir` cache at `.build/.agents/pr<n>/`), `Read` or `Grep` it rather than re-fetching via `git show …` pipelines — `Read` preserves tabs and trailing whitespace literally for byte inspection.

### Windows Git Bash gotchas

MSYS path-mangling and stdout-decoding bite well-formed `gh` / `git` / `docker` calls. Full reference: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) (tool-neutral git/gh/docker/dotnet/PowerShell); the Claude-tool-specific `Glob` + permission-allowlist gotchas are in [`windows-gotchas.md`](windows-gotchas.md). One-line triggers — when you hit one, read the relevant doc:

- `gh api` rejects a leading-slash endpoint (use `gh api user`, never `gh api /user`).
- `git show <ref>:<path>` fails with `ambiguous argument` when `<ref>` contains `/` — use `git ls-tree` + `git cat-file -p` instead.
- **`git ls-tree … -- '<glob>'` does not glob, and an empty result is not absence.** The pathspec matches literal paths / directory prefixes, so `-- '*Foo*'` exits **0 with no output** even when matching files exist. Enumerate with `git diff --name-only <base>...<ref>` or `git ls-files`, then filter with `Grep`. This bites hardest right after the rule above sends you to `ls-tree`: on #5764 both review subagents hit it in one session, and one concluded "no baseline files exist for either new test" — abandoning an empirical probe — while 100 such files were on the branch.
- **`gh … --body` is banned.** Always `--body-file <path>` or `--body-file -`; for `/azp run …` use `.claude/scripts/azp-run.ps1`. (`gh … --body @-` is *not* stdin — it sets the body to the literal string `@-`.)
- `git fetch <headRefName>` may produce no usable ref — or **delete** the tracking ref it just created, reporting `- [deleted] (none) -> origin/<branch>` and then failing `git rev-parse` with `unknown revision`. Spell **both** sides of the refspec in full: `+refs/pull/<n>/head:refs/remotes/origin/pr/<n>` to read a PR (incl. every fork PR), `+refs/heads/<branch>:refs/remotes/origin/<branch>` when you need a checkout to commit to. The short form's failure reads as "the branch is gone from origin"; `git ls-remote --heads origin 'refs/heads/*<id>*'` settles that in one call. Full write-up: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *Fetch a PR head via `refs/pull/<n>/head` into `origin/pr/<n>`*.
- Transient `fatal error — add_item (… errno 1)`: retry once, then treat the Bash tool as unavailable for `git` / `gh` **for the rest of the session** rather than re-testing it per call. It is not correlated with the command — on the 6.5.0 merge session it killed four separately-issued, well-formed calls spread over two hours while every PowerShell-tool equivalent succeeded first try, so each Bash retry was a round-trip spent re-discovering the same thing.
- `docker exec <container> /<path>` mangles the path: prefix with `MSYS_NO_PATHCONV=1` and wrap in `bash -c '…'`.
- Captured `gh` / `git` stdout decodes via the console code page, not UTF-8 — non-ASCII (emoji, em-dash) gets mangled. Don't capture body-ish output into a pwsh variable; use `Invoke-Gh` helpers, a file roundtrip, or ASCII-only anchors.
- `Glob` returns "No files found" for a path documented in CLAUDE.md / a SKILL / `agent-rules.md` — `Read` the documented path directly before concluding it's missing or reimplementing the helper.
- A tracked file stays `M` after `git restore` / `git stash`, with a diff whose two sides look identical — a lone CRLF in the *committed blob* under `core.autocrlf=true`, which no working-tree state can reproduce. Don't chase it: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *A file that stays dirty after `git restore`* (and read its merge-blocked case before reaching for `git update-index --assume-unchanged`, which does **not** get a merge past it).

### Batching and user interaction

Reduce round-trips and preserve the user's attention span. The rules that fire less often, and the cases behind these: [`turn-conduct.md`](turn-conduct.md).

- **Batch independent tool calls.** When multiple reads, searches, or shell commands don't depend on each other's output, issue them in a single assistant turn. Sequential calls are for true dependencies only.
- **Ask-ask-do-all, not ask-do-ask-do.** Front-load every question you can anticipate into one turn (numbered so the user can reply by number), wait for all answers, then execute in one batch. Interleave only when a later question genuinely depends on an earlier action's outcome.
  - **One label space per turn.** If the user replies by picking a label, nothing else in that turn may carry letters or numbers — sub-parts of a finding, halves of a defect, steps of a fix. Fold them into the option text instead.
- **Do not batch code-change reviews.** Each unrelated change gets its own review turn, even at the cost of round-trips: mixing unrelated diffs into one confirmation forces the user to context-switch and makes partial approval awkward. Group only what belongs to one logical change.
- **Interactive review of findings/comments: one at a time, with context.** When walking review comments, findings, or any list of substantive decisions the user must adjudicate item-by-item, present **one item per turn** — the finding, its context, your recommendation — and resolve it before the next. Do **not** collect several into one `AskUserQuestion` or a numbered multi-question prompt: the user needs room to weigh each decision. This is the decision-review counterpart to the rule above, and it **overrides** *Ask-ask-do-all*, which covers anticipatable setup/parameter choices, not judgment calls.
- **On a surprising failure, stop and wait.** When a command, test run or agent invocation fails in a way the plan didn't anticipate, report what happened in a sentence or two and wait for direction — workarounds invented mid-failure mask a real signal (wrong premise, wrong tool, wrong target). But **"surprising" means the *cause* is unknown, not that something went red**: a failure you predicted, a red test you wrote to be red, a probe that refuted its own hypothesis, or a build error whose fix is obvious from the message are expected outcomes of the work — keep going and report what they showed. Stopping on those turns the rule into a per-step permission loop.
- **Cap same-failure retry loops with a hard count, not just judgment** — roughly 3 local fix-and-retest attempts, 1–2 for a full CI round-trip, then stop and reconsider. At the cap, ask for a *budget* rather than deciding alone: say what the next attempt would test, what it costs, and what you'd conclude either way.
- **After launching a background task, await its completion notification — don't poll the output file.** This covers any file the task writes (including your own `>` redirect target) and any tool you inspect it with: the harness's *"Wasted call — file unchanged"* guard only fires for `Read`, so `Grep`-polling a redirect log draws no pushback, and the absence of a warning is not permission. `ListAgents` and `sleep` on a subagent are the same waste. If a turn's only content would be "still waiting", don't emit it.
  - **A CI wait has its own mechanics** — [`ci-tests.md`](ci-tests.md) → *Waiting for a run to finish*. GitHub Actions has a blocking form (`gh run watch <id> --exit-status` under `run_in_background`) with two traps that bite on a long run; Azure DevOps has none. Both have a helper script ([`wait-pr-checks.ps1`](../scripts/wait-pr-checks.ps1), [`azp-wait.ps1`](../scripts/azp-wait.ps1)). Never loop on `gh pr checks`.
- **Spend context deliberately** — fetch an external binary document (`.docx` / `.pdf`) **once** into `.build/.agents/` and `Grep` it thereafter; project the fields you need out of a script's JSON instead of `ConvertTo-Json`-ing a whole sub-object.
- **Batch edits on a single config file.** Reshaping several sections of one file (providers across TFMs in `UserDataProviders.json`, versions in `Directory.Build.props`): read it once, plan the full edit set, apply as one `Edit`. Incremental nibbles burn permission surface and miss cross-section invariants.
- **Offering a narrow fix beside a systemic one? State how their *exposure* differs, not just the mechanism they share** — the user is choosing scope, and two sites sharing a mechanism can be orders of magnitude apart in how often it fires.
- **Two-correction rule — stop repeating, reframe.** After the same correction misses twice, don't fire a third near-identical attempt: state in one line what you believe the goal is.
- **Two rules govern how wide the change gets, not how you ask.** "Hotfix" is a scope instruction, not just urgency: ship only what unblocks, and offer the virtuous extras (the stale doc table, the neighbouring comment) as follow-ups. And write **exactly** the list you got approval for — widening it inside shared infrastructure (a CI template every job runs, `Directory.Packages.props`, a hook) needs its own ask.

### Capability self-assessment

Before reporting a task as infeasible ("can't bisect", "can't build", "runtime test outside my reach"), do a one-pass environment check:

- `docker ps -a --filter name=<container>` for provider containers — use the **container name** from `test-databases.md` (`pgsql19`, `sql2022`, `firebird50`), **not** the engine/provider name; `--filter name=postgres` returns nothing even when `pgsql19` exists. When unsure, run `docker ps -a` unfiltered.
- `Glob` under `.claude/scripts/` for helper scripts wrapping multi-step sequences.
- `UserDataProviders.json` (root) and a sibling `linq2db` clone's copy (e.g. `../linq2db/UserDataProviders.json`) for connection strings.
- Existing skills (`/test`, `/test-providers`) for workflow coverage.
- `/kb-ask` or `areas/<AREA>/` for prior context on the subsystem — known issues, decisions, patterns — before declaring something unknown or infeasible.
- **Query-build performance** → [`measuring-query-build.md`](measuring-query-build.md) (BenchmarkDotNet's child-process toolchain fails in this repo — use the manual-runner pattern; `dotnet-trace` is installed and [`../scripts/speedscope-top.csx`](../scripts/speedscope-top.csx) reads its output). A work count is not a time measurement: [`bug-investigation.md`](bug-investigation.md) → *Perf work*.
- **CI investigation has a script per question** (scripts under `.claude/scripts/`, detail in [`ci-tests.md`](ci-tests.md)): a red Azure run's per-test failures → `azp-build-failures.ps1 -BuildId <n>`; a red *GitHub Actions* leg → `gh-run-logs.ps1 -RunId <id>` then `ci-test-verdicts.ps1 -Dir <logsDir>`; any single step's log, incl. a succeeded one → `azp-step-log.ps1 -BuildId <n> -StepName '<substring>'`; a timing / ordering claim → `azp-job-durations.ps1` (`-Definition -JobFilter`, or `-BuildId -Offsets`); build metadata (commit built, recent runs, repo-wide red) → the `gh api … --jq` recipes in *Is a CI failure PR-introduced or pre-existing?*. A case that seems uncovered — a green build, a succeeded step, a GitHub leg — is not a licence to hand-roll `/timeline`, `/logs` or `/_apis/build/builds`; each script was added after exactly that misreading (#5819, #5828, #5841, #5882).
- When the capability exists but the runtime cost is real, surface the cost and let the user decide.
- **Diagnose "stuck" as effort vs. capability before escalating.** Skipped verification, abandoned steps, shallow searches, not reading the whole file/log → an *effort* shortfall: do the missing work. Genuine inability to reason about the domain or a subtle bug → a *capability* shortfall, where a larger model is the lever. Reach for effort first — it is the cheaper fix — but note it costs materially more tokens (a multiple of the tokens, model-dependent), so it is a real trade-off, not a free default.

### Inferring rules from user input

When the user gives a rule that names a specific package / file / case, treat it as scoped to that case unless they explicitly generalize ("for all X…", "every Y in this family…"). Don't extrapolate to similar-looking cases without asking — "you gave rule X for P; case Q looks similar — same rule, or different?" An extra question is cheap; silent over-generalization costs a redo of every affected case plus a doc revert.

### Comments justify decisions, not mechanics

- **Write a comment only for what the code cannot say: a non-obvious decision, a rejected alternative, a constraint that isn't visible locally.** A change that follows an established pattern in the same file gets **no** comment — the pattern is the explanation. Don't narrate what the line does, and don't turn a commit message's rationale into an inline comment; the commit message already holds it. The tell that a comment is unwanted: it explains *why this line exists* when the neighbouring code already answers that. This codebase's comment density is **low**, so the default for a small, pattern-following change is zero comments. (#5614: a one-line `_visited = null;` in a `Cleanup()` method whose sibling class already did the same got a three-line comment about pooling and retention — *"we have established visitor cleanup pattern and never comment trivial code like that"*.)
- **A warranted comment is one to three lines.** Passing the "non-obvious decision" test is not a licence to write the case for it. Keep the conclusion and the constraint a future edit could break; drop how it was diagnosed, what was tried first, why the alternatives lost, and any background theory — that belongs in the commit message and PR body, which already carry it and which nobody re-reads on every visit to the file. Two objective tells that it has gone too far: the comment needs a blank `//` line to separate paragraphs, or it is longer than the code it explains. (#5858)
- **If the rationale already lives in a tracked artifact, the file gets the change and no comment.** The bullets above are read as bounding a comment's *length*; this one bounds its *existence*, and it is the one that survives "but it does justify a decision". When the why is already in the issue you filed, the commit message, or the PR body, an in-file restatement is a second copy of a fact with one owner — and it is the copy that silently goes stale, because nothing re-checks a comment when the issue is closed. Applies with full force to build / CI / setup scripts, whose whole content is decisions: a pinned version, a disabled setting, a skipped step gets the pin and stops. The tell is that you can name the issue number the comment is paraphrasing. Keep only what a reader of *this file* cannot get anywhere else — a structural mapping that the surrounding lines don't spell out, for instance. (#5882: a two-line comment on `mariadb:12` explaining that MariaDB 13 adds `UPDATE … RETURNING` and to unpin once #5933 lands — *"what is the value of comment talking about returning support, remove this useless comment"*. The adjacent `# mariadb:12 -> MariaDB.11 (port 3316)` stayed: it maps an image to a provider config, which nothing else in the file says.)

### Consult the knowledge base before investigating, designing, or orienting

See [`AGENTS.md`](../AGENTS.md) → *Consult the knowledge base first*. `kb-search.ps1` (keyword sweep) takes a manifest JSON on stdin or `-ManifestFile <path>` and has **no** `-Query` / `-Top` parameters; reserve `/kb-ask` for cross-area synthesis. Skip silently when the KB isn't built.

- **Map a changed path or topic to its area code by `Grep`-ing [`kb-areas.md`](kb-areas.md) for a path fragment, area code, or Tier-1 file name — never `Read` it.** Its rows are individually enormous (~37 k tokens total), so a whole-file `Read` blows the tool's output cap *and* returns a truncated table, after which you still have to `Grep`. The warning is stated inside `kb-areas.md` itself, which is one read too late, and the skills that send you there (`/review-pr` step 3c, `/fix-issue`, `/create-issue`, `/find-issues`, `/kb-refresh`) don't repeat it.

### Before coding a fix or feature

See [`AGENTS.md`](../AGENTS.md) → *Working discipline*. Claude addenda: enumerate existing tests before invoking `test-writer`; once the user picks "fix" over "gate", don't resurface "just gate it?" or offer to hand off to "the author" while they're driving — build a baseline worktree, instrument, attempt-then-test; un-gate verification includes the locally-runnable netfx/file-DB providers (SqlCe, Access).

- **Non-trivial work starts with `/work-plan`, before the first source edit.** [`AGENTS.md`](../AGENTS.md) → *Working discipline* for the rule, [`work-plan.md`](work-plan.md) for the schema. Claude mechanics: the plan is a **corpus** artifact (`.claude/plans/<key>/plan.md`), committed inside the submodule and never on a linq2db branch; in a worktree it goes to that worktree's own bootstrapped `.claude/`, which sits on a detached HEAD until you `git -C <worktree>/.claude switch master`. The critic runs on a **different model** from the author, passed explicitly on the `Agent` dispatch rather than left to frontmatter — the model difference *is* the mechanism, and the one place [`agent-guardrails.md`](agent-guardrails.md) → *Distinct lenses for parallel reviewers* is satisfied by construction rather than by prompt wording.
- **When repairing dead or broken code, its payload and its conditions are in scope — don't treat them as fixed points.** Finding a guard that cannot fire, the instinct is to frame the choice as *delete it* or *restore it as written*, then argue against restoring because the code as written would do something undesirable. That is a false dichotomy, and it hides the option that is usually correct: fix the **payload** too. The tell is catching yourself arguing that a repair is unsafe — if restoring the block as written is wrong, that is an argument about the block's body, not an argument for deletion. The same applies to the condition: a broken predicate is often also a redundant one, and carrying its clauses forward verbatim while fixing the bug ships the redundancy with your name on it. Read what the block was *for*, then write the version that does that. (#5841)
- **Do a blind-spot pass before coding in an unfamiliar subsystem.** Surface what you might be missing — the unknown-unknowns the change could hit (edge cases, provider quirks, cross-cutting invariants), or the assumptions the plan rests on — rather than coding straight from the first read. Cheap insurance against being confidently wrong on unfamiliar ground.
- **Offer the root-cause alternative even when the user prescribes a mechanical fix.** Present their approach first, respecting intent, then the simpler root-cause option with its trade-offs, and let them pick — rather than just executing the prescription. (#5715)
- **Handling a review finding — yours or someone else's — is [`acting-on-findings.md`](acting-on-findings.md).** Read it before proving, disputing, accepting or dispositioning one. Triggers: write the **red test first**; a finding's *mechanism* and its *stated consequence* fail independently, so verify both; a suggestion you are about to **accept** is a claim too — as is an example a reviewer supplies for a doc fix, and the rationale you write for your own design choice; a decline whose premise your own later work invalidated gets re-raised once; an incidentally observed failure is not coverage; an adjacent shape you noticed gets a test written, not offered; check a deliberate-looking element's **provenance** before flagging it; and once a finding is reproduced, **"fix it here"** is the default disposition — track-it-separately is for what the PR structurally cannot fix.
- **Building the probe that settles any of that is [`evidence-discipline.md`](evidence-discipline.md).** Read it before writing up a defect, down-scoping a fix, or reporting a measurement. Triggers: **reachability precedes reproduction** — for an input shape, a host platform and an API signature alike, and the same evidential burden falls on an argument for doing *less*; absence from a corpus sweep is not absence from the program; **instrument the code and let the existing corpus enumerate its real inputs** rather than constructing the one shape you thought of; every probe write needs a lock, because provider lanes run in parallel; a control has to be able to **disagree**, its expected value has to be *measured* rather than reasoned out, and a red that failed for the wrong reason is not a red; and mutation / revert carry documented traps — `git apply` stages, a `Copy-Item` restore skips the rebuild, `if (false)` is `CS0162`, removing a guard orphans the field it guarded. It also owns the three rules for the measurement itself — a new runtime guard's false-positive set is what grep cannot see so run the affected suite before pushing; an acceptance measurement is void the moment you edit the surface it measured; and verify a fix by the **same path that surfaced the bug**, not only a fresh unit test.
- **Repro blocked by a separate, known engine bug → gate the test, defer the fix.** A third case beyond *reproducible* and *can't-reproduce*: the finding's mechanism is verified against core code, but you can't drive an end-to-end red repro because an *unrelated, independently-tracked* engine bug blocks the only path to it. Then commit the regression test `[ActiveIssue]`-gated on the **blocker's** issue and defer the actual fix until the blocker merges — so the fix is verified over the real path once un-gated (per [`evidence-discipline.md`](evidence-discipline.md) → *Verify a fix by the same path that surfaced the bug*), rather than applying a speculative fix that can't yet be exercised. (#5704, #1813, #5701)
- **A fix in cross-cutting core gets a core-layer regression test, not only the consumer-level one.** When a bug surfaces through one consumer (e.g. `linq2db.EntityFrameworkCore`) but the defect lives in shared engine code (SQL AST, `ProviderDetectorBase`, an `IDataProvider` seam), add a provider/consumer-agnostic test at the core layer *in addition to* the consumer repro — the core test pins the general contract the fix restores, and proves the bug was never consumer-specific. (#5296: the EF `Issue5296Test` proved the `EnsureCreated` symptom, but the leak was in `ProviderDetectorBase`'s `AutoDetect` path; `ProviderDetectionDoesNotLeakConnection` in `DataConnectionTests` pins it directly — red across net462/8/9/10 pre-fix.) To prove the core test is genuinely red once the fix is already committed, see [`bug-investigation.md`](bug-investigation.md) → *Proving a red test after the fix is committed*.
- **A statically decidable invariant wants an analyzer, not a reflection guard test** — and an internal invariant an internal rule: [`authoring-analyzers.md`](authoring-analyzers.md) → *A statically decidable invariant wants an analyzer*.
- **Proposing a new cross-cutting core capability? Include a beneficiary survey.** When a task leads to proposing a new core seam (interface, hook, extension point), don't justify it by the driving case alone — sweep for existing code exhibiting the same gap (grep for the workaround pattern, e.g. `MappingSchema.Default` fallbacks) and existing/potential issues it addresses (KB github indexes + `gh search issues`), and fold that adoption analysis into the design artifact. A core change justified only by one consumer is a workaround wearing a design's coat. (#5675)

### Investigating & fixing bugs

- **Start from the KB and recorded dead-ends.** Before reproducing, check the area's `areas/<AREA>/issues.md` / `tech-debt.md` / `detected-issues/` *and* [`dead-ends.md`](dead-ends.md) — the symptom may be a known issue, a prior fix, or a `Don't re-attempt:` dead-end a past session already paid for. Capture *new* dead-ends via `/session-reflect`. Orientation only; re-verify against current source.
- **Situational triggers** — fix-or-disable batches, "regression after switching package X→Y", reproducing a regression (HEAD-contains check), tracing a token via `git log -S "<token>" --all -- "*<File>"`, `[ActiveIssue]` enable, provider-limitation flags (find the flag before gating, regress wide), non-deterministic failures (assert all valid outcomes), don't-weaken-the-test — full detail and the war-stories behind each: [`bug-investigation.md`](bug-investigation.md). Read it when one fires.
- **Attribute a failure to the right layer before working around it.** When a task fails through an external tool (a formatter, driver, build step, SDK), prove the defect isn't in *our* code before accepting "the tool is limited" — isolate it in the tool's underlying SDK or a minimal harness. (A `dotnet format` under-application looked like a tool limitation but was our `WellKnownFixAllProviders.BatchFixer` choice; the fix was a custom `FixAllProvider`.)
- **Explain the mechanism before proposing the fix — and certainly before offering a choice between fixes.** A remedy chosen from a symptom encodes whatever the symptom suggested, and a fix menu built that way asks the user to pick between options that may all answer the wrong question. Write the causal chain out first — what ran, in what order, in which process, and why that made the operation fail — then let the scope of the fix fall out of it. The same explanation that justifies a fix usually deletes half the candidates. (#5786)

### Issue-proposed fix details are written from memory — verify them

See [`AGENTS.md`](../AGENTS.md) → *Issue-proposed fix details*.

**Every claim you did not run is a hypothesis** — a comment your change falsified, a cited external precedent, a CLI flag's existence, a `WebFetch` answer, a negative about external code. Each has a cheap check and a documented way it bites: [`evidence-discipline.md`](evidence-discipline.md) → *Claims you have not run*. The one that most often passes for a doc nit: a comment your diff made untrue is usually the **symptom of a mis-scoped change**, not a wording problem — and the mirror is your own behaviour change falsifying prose in another file, which nothing in the diff points at.

### Reviewing a PR

When the user asks to review a PR, **invoke `Skill(review-pr)`**. Its finding-classification rules — most importantly the *suppression list* — live in [`api-surface-classification.md`](api-surface-classification.md) and [`code-reviewer.md`](../agents/code-reviewer.md), which the main agent does not load on its own. When the ask is broader than a review and you handle it inline, read those two suppression sections **first**; the one that leaks is the categorical `PublicAPI.Shipped.txt` / `PublicAPI.Unshipped.txt` drift ban, which an inline review of [#5804](https://github.com/linq2db/linq2db/pull/5804) violated by asking the author for `Unshipped` entries — authors add them, but a missing one is reconciled at release (`/release-publicapi`) and is never a review finding.
- **`code-reviewer.md` is 58 k tokens — `Grep` it, never `Read` it.** At ~200 KB it blows the `Read` tool's output cap and returns a truncated first third, after which you still have to `Grep`. The main agent almost never needs the whole spec: the subagent loads it itself, and what an orchestrating skill wants — the output-schema field list, the focus-scoping table, one suppression rule — is a single `Grep` away. Same trap as [`kb-areas.md`](kb-areas.md), and the pointer above is what walks you into it. (#5828)
- **An inline review still owes the user the interactive walk.** `/review-pr`'s per-finding walk is not a property of the skill — it is how review findings get delivered on this repo, so it applies equally to a review you run inline. Present **one finding per turn** — the finding, its evidence, your recommendation, the disposition options — and resolve it before the next. Do **not** substitute a consolidated severity table: it forces the user to adjudicate every item in parallel, the per-item dispositions that matter (`post` / `fix here` / `add comment` / `drop`) never get asked, and the findings strand in the transcript instead of landing on the PR — the tell is the user asking *"where is review results?"*. (#5737)

### Running tests

When the user asks to run tests, **invoke `Skill(test)`**. Don't call `Agent(test-runner)` directly, and don't run `dotnet build` first — `dotnet test` rebuilds inside the skill, and bypassing it silently skips `CreateDatabase` filter injection and the baselines diff. Project selection (Playground vs Linq), multi-TFM gating and `playgroundLink` are the skill's responsibility.

- **Every hand-run `dotnet test` / test-exe invocation carries `--test-progress`.** `/test` and `test-runner` pass it for you; the runs that lose it are ad-hoc ones — a worktree repro, a bisect step, a quick filtered check. Without it there is no heartbeat at `.build/.agents/test-progress.<tfm>.<pid>.json`, so a long run is unobservable and — worse — the *absence* of a heartbeat is the corpus's own evidence that a run never started (see *Agent guardrails* → liveness), making a flagless run indistinguishable from a dead one.
- **Except the bare-NUnit hosts** (`Tests.Analyzers*`, the CLI tests): there the flag exits 5 as `Zero tests ran`, byte-identical to a bad `--filter`. **`Zero tests ran` after a flag change means the flag, not the filter.** Detail, and the `require-test-progress` hook that enforces the rule: [`testing.md`](testing.md) → *Running the analyzer tests* / *Monitoring a long run*.

For a **worktree** target, `/test` still owns the run: pass `run <filter> worktree <abs-worktree-path>` so it forwards `repoRoot` to `test-runner`. Don't hand-run `dotnet test` against a worktree — you'll miss the custom `--provider` arg, `--settings .runsettings` and the `CreateData.CreateDatabase` prefix, and burn calls on .NET 10 MTP CLI quirks (`dotnet test` needs `--project`; without `--provider`, `[IncludeDataSources]` tests resolve zero providers → "0 tests"). Recipe: [`worktree.md`](worktree.md) → *Running tests from a worktree*.

### Build & push gotchas

Pre-push build rules are operative in [`AGENTS.md`](../AGENTS.md) → *Build gotchas that fast-iteration hides*, with full detail in the linked docs:

- **TFM API availability** — `-c Testing` builds net10.0 only and misses `net462`/`netstandard2.0` API gaps; **analyzers are Release-only**. Build a portable TFM and a Release net10.0 before pushing: [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *TFM API availability* / *Analyzers are Release-only*.
- **Iterative-build file locks / disk space** (build-server lock, `.build/bin/` accumulation): [`windows-dev-gotchas.md`](windows-dev-gotchas.md) → *Iterative-build gotchas*.
- **The `MSB4166` / dead-node recovery ladder applies to `dotnet build`, never to `dotnet test`.** `-m:2`, `-m:1` and friends are MSBuild switches, and MTP's `dotnet test` forwards anything it doesn't recognise to the *test application*: the run skips the build and ends in **`Zero tests ran` (exit 5)** with the switch named nowhere. Recover the node on an explicit `dotnet build <project> -c <cfg> -f <tfm> -m:2`, then `dotnet test … --no-build` ([`testing.md`](testing.md) → *Don't pass MSBuild switches to `dotnet test`*). **A test run too short to have compiled anything did not build — read the duration before theorising about the filter.** (#5762)
- **MSBuild override precedence** (env vars don't beat conditional `<PropertyGroup>`; only `-p:` does): [`msbuild-override.md`](msbuild-override.md). **Read it before passing `-p:` for a *list* property too** — `-p:NoWarn=<id>` does not append, it **replaces** the whole inherited list, so suppressing one rule silently drops `Directory.Build.props`'s suppressions; `-p:WarningsNotAsErrors=<id>` is no fallback when the rule's `.editorconfig` severity is already `error`. That doc carries the `%3B`-union recipe.
- **Before deleting a type or member — or removing/renaming a build or packaging concept (a NuGet package, a project's packable role, a target model) — sweep for references in XML doc-comments and inline comments, not just call sites.** A dangling `<see cref="…"/>` pointing at a removed type is a **build error** under `TreatWarningsAsErrors` (CS1574), not silent doc rot. Grep the whole worktree for the symbol (code, XML docs, comments) plus `.csproj` (an explicit `<Compile Include>`). For a build/packaging concept, extend the sweep to sibling build files (`Directory.Build.props`, sibling `.csproj`, `Directory.Packages.props`) whose comments may still describe the old model. **For a removed/renamed NuGet package id, establish whether it was ever published** — `git log --oneline --diff-filter=A -- <the .csproj>`, then `git tag --contains <sha>`: no release tag means the id only existed inside the current dev cycle and can be dropped silently; a tagged id makes the removal consumer-facing, needing a deprecation decision and a release-notes line. (#5711, #5720)

### PowerShell Core scripts for complex operations

- **When the agent would otherwise make ≥ 3 related `gh` / `git` calls whose outputs feed each other** (load → transform → post), wrap the sequence in a single **PowerShell Core script under `.claude/scripts/`**: one allowlist match instead of N, multi-step state stays inside the script, no compound-Bash friction, identical behaviour on Windows / macOS / Linux. Skip it for one-shot calls. Authoring contract, parallelism rules and pwsh-script gotchas: [`script-authoring.md`](script-authoring.md).
- **The same rule of three applies one level up:** a *procedure* hand-run 3+ times across sessions — not just a call-chain — is a candidate to codify (a script for a mechanical sequence, a skill for a multi-step workflow). Surface it to the user or route it through `/session-reflect`; don't silently keep repeating it.
- **A review finding that names a gap in a repo *procedure* the skills own** — a release / release-prep step, a maintenance workflow — rather than a defect in the PR's code, is fixed by adding the missing step **verbatim to the owning skill** (a corpus commit in `.claude/`), not by a PR code change and not by a loose "post-merge follow-up" note that gets forgotten. It is a curation task even when it surfaced while reviewing a feature PR. (#5703)
- **Prefer the PowerShell tool over `Bash(pwsh -NoProfile -File …)`** when invoking these scripts — it skips the Git-Bash / MSYS layer entirely: no path-mangling on slash-prefixed args, no `\??\C:\…` cygheap races, no quoting differences, no double allowlist hop. Use the Bash wrapper only for shell features the PowerShell tool can't express.
- **Invoking one has argument-passing traps that silently corrupt the call** — Bash expanding `$vars` out of an inline `pwsh -Command`, a nested `-Command` inside the PowerShell tool doing the same, `-File` flattening an array literal into one string, `gh` stdout arriving as a string *array*: [`script-authoring.md`](script-authoring.md) → *Invoking a script — argument-passing traps*. The same file carries the idempotency rule for a generator you might re-run — re-invoking a writer is never a verification.

### Temp files

Any skill, subagent, or ad-hoc command that writes a scratch file (JSON for `gh api --input`, generated diffs, intermediate output) must place it under **`.build/.agents/`** (gitignored) — never `%TEMP%` / `/tmp` / an absolute OS temp path. Create the directory before the first write; name files by skill + id (`.build/.agents/review-pr-1234.json`). Cleanup is optional. **The directory is shared across concurrent sessions — never delete it or its contents wholesale.** The user runs parallel sessions against the same clone, so it can hold another session's *live* diff cache, context JSON and review manifests; a #5720 cleanup pass found `pr5678-*` files written minutes earlier by a concurrent session. **And the `pr<n>*` prefix alone is not enough** — it identifies the *PR*, not the session, and the same PR is normally worked more than once: on #5762 six `pr5762-*` entries from ten days earlier sat next to nine from the current session, so a prefix-only delete would have destroyed exactly the prior-session cache this rule protects. Enumerate **with timestamps** (`Get-ChildItem … | Select-Object Name,LastWriteTime`) and remove only what this session wrote.

### Git commit rules

**Never publish without an explicit user request in the current turn** — [`AGENTS.md`](../AGENTS.md) → *Git, GitHub & publishing*.

- **Never commit playground scratch** ([`AGENTS.md`](../AGENTS.md) → *Never commit playground scratch*). Mechanics: a new `<Compile Include>` fixture ref under `Tests/Tests.Playground/` is `test-writer`'s session scratch — `git restore --staged` it before any commit/push, and if the user asks to commit one, stop and confirm.
- **Large-scale deletions are a red flag** ([`AGENTS.md`](../AGENTS.md) → *Large-scale deletions*) — check `git diff --stat <ref>..HEAD` before publishing; a regenerated-empty `CompatibilitySuppressions.xml` / `PublicAPI.*.txt` is the usual culprit.
  - **A second cause is a stale base, and it is the one that looks most alarming.** `git diff origin/master..HEAD` on a branch that is behind renders everything master gained since the branch point as *deletions*, so a one-line fix can present as tens of thousands of removed lines; `git checkout origin/master -- <path>` makes it worse by writing master's *current* file onto an old base, so the branch claims changes that are not its own. Diff against the merge base (`git diff $(git merge-base origin/master HEAD)..HEAD`), or rebase and re-check, before believing the number. (#5860: 55 368 deletions across 75 files, zero of them real.)
- **Amending a commit on a non-checked-out branch with a dirty current tree.** Don't `stash`/`switch`/`--amend`/`switch -`/`pop` — the pop can conflict on overlapping files. Use the `commit-tree` + `update-ref` recipe in [`pr-and-push.md`](pr-and-push.md) → *Amending a commit on a non-checked-out branch with a dirty current tree*.
- **`git commit --amend` takes the *whole* index — amend with `--only -- <pathspec>` whenever anything else is staged.** In the one-change-per-commit workflow the files for *later* commits sit staged while you amend the current one, and a bare `git commit --amend -F-` silently rewrites that commit to include all of them. The tell is the amend's file count; recovery is `git reset --soft HEAD~1` then re-commit with the pathspec. (#5795, #5614)
- **Multi-line commit messages: `Write` the message to a file and `git commit -F <file>`.** `@'…'@` is PowerShell here-string syntax — the **Bash** tool does *not* parse it, so `git commit -m @'…'@` passes the literal `@` through as leading/trailing message lines. Repeated `-m "para"` flags are the simplest Bash-safe multi-paragraph form, but **any body containing `;`, `&&`, `||`, or the name of a hook-banned command must go through `-F <file>`**: a PreToolUse hook sees one opaque command string and cannot tell prose from shell syntax, so a paragraph quoting `CAST(@name AS Decimal(18, 10)); …` fails with `';' chaining`, and a commit message *explaining* a build-server change is blocked by `ban-build-server-shutdown.js`. The same blind spot applies to any tool call whose command string carries prose. (#5723) Committing into *another* repo (corpus, `../linq2db.docs`, `../linq2db.baselines`) has two `-F` traps of its own: [`pr-and-push.md`](pr-and-push.md) → *Committing into another repo with `git -C`*.

### Push to remote rules

Detail-heavy mechanics live in [`pr-and-push.md`](pr-and-push.md). One-line triggers — when one fires, read the doc:

- **When several related PRs are active in one session** (a main PR + its offloads, each in its own worktree), pin an unnamed push / `/azp run` / commit instruction to the PR the user's *primary goal* concerns — not the most-recently-touched worktree. Confirm the target when the instruction is ambiguous. (#5710, #5614)
- **After every successful push, check for a PR on the branch** and diff the new commits against its body. **On a PR the user authored**, propose a body edit as a diff, never a full rewrite — append a `## Follow-up commit` subsection rather than rewriting their prose, and do it with `.claude/scripts/pr-body-edit.ps1` (anchor-based, UTF-8 file round-trip). Never hand-roll fetch-body → mutate → `gh pr edit` / `gh api`: it collapses the *existing* body's newlines onto one line. Verify the **whole** stored body afterwards, not just the appended tail — a tail-only check passes while the head is silently collapsed (#5686). **On someone else's PR, do not edit the body at all** ([`github-authoring.md`](github-authoring.md) → *Never edit content authored by other users*); use a review or a new comment. If no PR exists, propose creating one.
- **Immediately after `gh pr create`, check the diff shape** — one `gh pr view <n> --json commits,files`. A branch cut off *another* branch republishes every file the parent introduced once that parent squash-merges: [`pr-and-push.md`](pr-and-push.md) → *Immediately after `gh pr create`: check the diff shape*.
- **After every successful push, re-request Copilot review** — auto-trigger is unreliable: `gh pr edit <N> --repo linq2db/linq2db --add-reviewer copilot-pull-request-reviewer`. Don't pass the slug `Copilot` (errors); don't fall back to the REST `requested_reviewers` endpoint (silently no-ops when Copilot already reviewed an earlier commit).
- **Orphaned baselines are never an action item or a review finding; stale *keys* (a follow-up renamed / moved / deleted a test or changed its SQL) are** — close + delete via `close-stale-baselines.ps1`: [`pr-and-push.md`](pr-and-push.md) → *After test renames / moves / deletes*.

### Agent guardrails (anchor set)

The most-violated guardrails stay inline. Lower-traffic ones (Surface trade-offs, Build configurations `==` vs `!=`, Document arbitrary values, Default to script over hook, Provider / Codebase claim verification, Distinct lenses for parallel reviewers, Cross-model verification for cross-cutting core, Persona framing, Editing whitespace / control characters) live in [`agent-guardrails.md`](agent-guardrails.md). The design invariants they protect — public-API contract, cross-cutting internals, SQL AST namespace placement, column-aligned formatting — live in [`code-design.md`](code-design.md).

- **Don't reformat unrelated code; don't reshape cross-cutting internals for a local fix** — [`AGENTS.md`](../AGENTS.md) → *Load-bearing invariants*. Reviewing, the first does not suppress findings on PR-touched lines or on an untouched line the PR made inconsistent: [`review-conventions.md`](review-conventions.md) → *Formatting on PR-touched lines*.
- **Verify subagent output with `git status` after every invocation.** Subagent tool declarations are advisory — the harness does *not* enforce them, so a read-only-declared agent can still call `Edit` / `Write`, and the only signal back is the result it chooses to report. Confirm the only modified files are ones the agent's scope justifies. **Add `git -C <primary-clone>/.claude status`** — the superproject's status is blind to the corpus (`submodule.ignore = all`), and unprompted `.claude/` edits are a documented subagent failure. Spell that path **absolutely**: `-C` resolves against the shell's working directory, which drifts (a `Set-Location` in the PowerShell tool also moves the Bash tool's cwd), and the relative form then fails with `cannot change to '.claude'` — indistinguishable at a glance from the corpus having been destroyed. If unexpected files appear, treat the result as suspect and restore them.
  - **An unexpected modified file there is usually the user's parallel curation, not contamination** — read the diff and `git log` before reacting, and never `git -C .claude add -A`: [`agent-guardrails.md`](agent-guardrails.md) → *An unexpected modified file in the corpus*.
- **A subagent's reported result is a claim, not evidence — verify it against an artifact.** The `git status` check catches unauthorized *side effects*; it says nothing about whether the summary is true. A subagent can report a clean pass it never observed — `test-runner` once reported *"passed: 1, failed: 0"* for a run that had failed on two of four databases, reading a stale heartbeat instead of the run it launched. Before acting on a pass/fail summary that gates a decision, confirm it against something the agent didn't author. **Implausible metrics are the tell**: a count, duration or file count that can't match the work described (1 test in 3.066 s across four databases) means it measured something else — re-derive the whole result rather than reconciling the one number that looks off.
  - **"Still running, let me wait" is a claim as well, and a worse one — it invites you to wait forever.** Verify *liveness*: no `dotnet` / `testhost` process and no `.build/.agents/test-progress.<tfm>.<pid>.json` heartbeat means nothing is running, whatever the agent said. - **Frame subagent prompts to allow failure.** Make "report what's missing / blocked" an explicit, valid outcome — *"if you can't reproduce / locate / verify X, return what's missing rather than producing a plausible-looking result."* An open-ended "do X and report success" prompt rewards *demonstrating* completion over reporting honestly: the obliging-clerk mode where the agent fabricates a green result rather than admitting the task didn't pan out. The repo's agents have structured `blocked` / `needDisambiguation` outputs; the caller's prompt has to invite them.
- **Don't let progress artifacts outpace real work.** Advancing a `TaskUpdate`, checking off a plan item, or reporting a step "done" must track an applied change or a verified result. Same root as the obliging clerk: in a given turn, the process artifacts you touch shouldn't exceed the substantive changes you made.
