# Proving a claim — probes, controls, mutants and unverified claims

How to build a probe that actually settles the question it was built for, and how to treat a claim nobody has run.
Loaded on demand; [`agent-rules.md`](agent-rules.md) → *Before coding a fix or feature* and → *Issue-proposed fix
details* keep the triggers, this file keeps the mechanics and the cases behind them.

The rules run in sequence and each names the one before it, so read a section top to bottom rather than jumping to
a single paragraph.

## Reachability — before you reproduce anything

**Reachability precedes reproduction.** A "this code path fails for input type/shape X" finding — even one a reviewer marks *confirmed* — is only a defect if X is **reachable**: verify X is constructible and actually reaches the path (compile + run), because language/framework constraints can make it unconstructible or route it elsewhere. A code path that *could* mishandle a type it can never receive is a robustness gap for unreachable input, not a live bug — don't add untested defensive branches for it. (On #5701 a reviewer "partially confirmed" that `FSharpRewriteVisitor.CreateSentinel`/`GetUninitializedObject` silently falls back for captured `Nullable<T>` / interface / abstract free vars; empirically unreachable — `Nullable<T>.Value` on a captured local won't compile in an F# quotation (`FS3155`), and an interface-typed *local* is an ordinary closure, never a `SubstHelper` free var (those are the outer query range variables, always entity reference types). `Issue1813Test8` pins the interface-local case green; no `CreateSentinel` change made.)

  **The same test applies to a *host* — check the product ships to the configuration before writing up a platform gap.** The rule above is framed around input types, which is why it doesn't fire on its most embarrassing case: a finding of the form "on platform / OS / architecture / runtime P this would break". P has to be reachable too, and that is one lookup against the vendor's own download or support matrix — cheaper than the analysis it invalidates, and it must come *first*, because a platform-shaped finding reads as urgent and gets written up in detail before anyone asks whether P exists. (On #5786 a finding was drafted that IBM's macOS DB2 client ships arm64-only natives, so DB2/Informix would be offered and then fail to load on an Intel Mac. The maintainer's reply was *"which arch for macos linqpad support?"* — LINQPad 9 for macOS is published for Apple Silicon only, so the driver never runs on an Intel Mac and the arm64-only client is an exact match. The finding was dropped, not demoted.)

  **A reachability argument resting on a *type system* or an API signature is a claim about that signature — read it, don't recall it.** The two rules above turn on whether an input or a host exists; this one turns on whether the language even permits the shape, which feels like the one form of reachability you can settle from the armchair. It isn't, and the failure is characteristically narrow: the argument is *correct for the positions you had in mind* and false for a neighbouring position in the same grammar, because one of the APIs involved is typed more loosely than the surrounding code. Enumerate the positions the shape can occupy and check the signature governing each. (Surfaced on #5877: an unguarded enum-member reader was argued unreachable "by the type system" — sound for the accumulator, since `|=` between two enum types does not compile and a differently-typed seed breaks every later statement. But `Enum.HasFlag` takes **`Enum`**, so `flags.HasFlag(OtherEnum.Member)` compiles, and the two enums in question shared a member name — so the reader recorded a predicate as testing the wrong enum's bit. One signature lookup would have settled it; the guard was worth having and had a real fixture.)

  **Note the direction this fires in.** Both rules above use reachability to argue a finding is *not* a defect, and that is the shape the wording anticipates. The mirror — using reachability to argue for doing *less*: narrow the fix, disclose instead of fixing, guard one shape and drop the other — carries exactly the same evidential burden and gets far less scrutiny, because "we don't need to handle that" reads as scope discipline rather than as a claim. Probe it the same way before recommending it. (Same session, twice: both narrower dispositions I recommended rested on reachability arguments I had not executed, and both were wrong.)

**But absence from a corpus sweep is not proof of unreachability — and severity turns on the difference.** The rule above stops you fixing a path that genuinely cannot receive X. It does **not** license concluding "unreachable" because a sweep of the existing corpus (regenerated baselines, the test suite, a `git grep`) finds no instance: that only shows the corpus doesn't *exercise* the shape, which is exactly what you'd expect of an untested gap. When the mechanism is confirmed against source and the only open question is reachability, spend one probe **constructing** the shape before down-scoping — a playground query plus a `git worktree` at `origin/master` for attribution is usually enough. (On #5723 a marker-under-cast finding was scoped MIN because none of the 649 regenerated baselines showed the trigger shape; one probe built it from ordinary LINQ — `Sql.Convert<string, int>(Sql.AsSql(name).Length)` — and showed Firebird dropping a *declared* `VARCHAR` cast that `master` emitted. It was a MAJ, fixed in `bdbb45d93`.)

## Probes, instrumentation and controls

**Better than constructing one shape: instrument the suspect code and let the existing corpus enumerate its real inputs.** When the question is *"which types / shapes can actually reach this function?"*, a construction probe only tests the shape **you** thought of — so it confirms or refutes one hypothesis and says nothing about the rest of the input domain. Instead, temporarily log the function's actual argument at its entry (append to a file under `.build/.agents/`), run the existing test suite over the feature, then read the distinct values back. One run yields the whole reachable input set, including the members you would never have guessed, and the instrumentation comes out with the fix. (On #5701 a reviewer said a `Nullable<T>` free variable could reach `CreateSentinel`; a prior session had replied "unreachable — always entity reference types". Logging every `t.FullName` across the `Issue1813` set returned entity types, `Tuple<,>`, **`Nullable<int>`** *and* **`String`** — refuting the "always entity" claim, showing the reviewer's `Nullable<int>` was reachable but harmless, and surfacing `String` as the type that actually threw. A construction probe aimed at `Nullable<T>` would have concluded "no defect".)

  **To prove a block is dead, delete it *and* instrument its call site in the same build.** A third variant of the same one-build discipline, for the question *"does this code ever run, and is removing it safe?"* — which is two questions, and each half alone under-answers it. Logging the inputs shows the guard's combination never arrives but says nothing about whether something downstream depended on the block's side effects; deleting it and getting a green suite shows removal is safe but not *why*, so the result reads as "the tests don't cover it" rather than "the code is unreachable". Doing both in one build yields the mechanism and the safety proof together, which is what makes a delete-N-lines recommendation land instead of inviting "are you sure the tests cover that?". Log to an absolute path — a relative one follows the invoking process's cwd (see [`worktree.md`](worktree.md) → *Run artifacts follow the invoking process's working directory*). (Used on #5727 to retire 43 lines: the log recorded 1621 calls in six flag combinations with `Expand` absent from every one, while the same build ran 162/162 green with the block gone.)

  **To prove an existing test *cannot fail*, inject the defect it claims to cover and re-run it unchanged.** The variants above all probe the product; this one probes the **test**, and it is the one a coverage-gap finding needs. "This assertion could not detect X" argued from reading is a guess, and it is a guess the author will reasonably dispute, because the test is right there being green for what look like good reasons. Instead mutate the product so the guarded defect actually occurs, run the test **as authored**, and report that it stayed green — that green run *is* the finding. Then fix the test and re-run against the **same mutant**: this second half is not optional, because a mutant that was never compiled in produces exactly the same green as a test that cannot fail, and only the red proves which one you had. Finish by reverting the mutation and confirming green again, so the fix is shown not to false-positive. Cheap — three incremental runs off one build — and it converts a disputable reading into a number.

  **Restore the mutant by writing the file, never by copying a backup over it.** `Copy-Item` (and `cp -p`, and most "restore from backup" idioms) preserves the *source's* `LastWriteTime`, so the restored file is older than the mutated one MSBuild already compiled — the build is skipped, the assembly still contains the mutant, and the confirming run reports the **mutant's** result. That reads as "the fix does not work", which is the single most misleading outcome this whole rule can produce: you have just proven your fix is correct and the next run tells you it isn't. Touch the file after restoring (`(Get-Item $f).LastWriteTime = Get-Date`), or apply the revert with `Edit` / `git checkout HEAD -- <path>` instead of a copy. **The tell is duration** — a run that finishes far faster than the mutated one compiled nothing. (Surfaced on #5877: a `Copy-Item` restore of a hardened analyzer reported the same 3 failures as the mutant; touching the file and re-running returned 23/23.) (Surfaced on #5828: `MaxSqlLengthForBatchSplitsStatements` covers the splitter's rewind-and-re-add path, but the test set `ConflictAction.Ignore`, so SQLite rendered `INSERT OR IGNORE INTO` and silently swallowed a duplicated row. Suppressing the rewind left all four legs green; with `RowsCopied` asserted the same mutant reported 1003 and 1052 against 1000.)

  **A probe's *expected* value needs a control too — deriving it from first principles is a second hypothesis smuggled into the assertion.** The rules above make the probe's *observation* trustworthy; they say nothing about the number you compare it against. Reasoning that value out from semantics is exactly as fallible as the mechanism reasoning the probe exists to replace, and when it is wrong the probe reports a defect that isn't there — with a measurement attached, which makes it far more convincing than a bare claim. Get the expectation from the simplest shape that cannot exhibit the defect: the same query with the suspect element removed, the same operation over uniform types, the single-branch version. Then the comparison is between two measurements rather than between a measurement and a guess. (Surfaced on #5833: a `Union` over differing-but-assignable branches returning 9 rows was written up as "9 where 7 are due", the 7 reasoned from set semantics. linq2db's `Union` is value-dedup over projected columns while LINQ-to-Objects would use reference equality on the materialized objects, so the two disagree and neither obviously governs. The same-type control settled it empirically at 7 — the finding survived, but it had been one plausible-sounding sentence away from being wrong in public.)

  **Every probe write needs a lock — provider lanes run in parallel.** The three rules above all say "append to a file under `.build/.agents/`", which was safe when the suite was serial. Since [#5614](https://github.com/linq2db/linq2db/pull/5614) the same test method runs concurrently across provider lanes, so an unsynchronized `File.AppendAllText` throws `IOException: the process cannot access the file … because it is being used by another process` — and because the probe sits inside the code under test, that exception **fails the test it is instrumenting**. The failure reads as a product regression in whichever lane lost the race, which is the expensive part: you go looking for a bug in the change rather than in the probe. Wrap the write in a `lock` on any stable object, or give each lane its own file (`…-<context>.txt`). (Surfaced on #5737: an unlocked probe reddened `ReusesDuplicateTphConstructors("SQLite.Classic")` while `SQLite.MS` wrote fine; earlier probes in the same session happened to take a lock and were unaffected, so the difference looked like a provider-specific defect.)

  **To attribute a behaviour change to a commit, run the old implementation *beside* the new one in one build — don't revert to compare.** The rule above instruments one implementation to learn its inputs; this variant instruments two to learn which one changed the answer. Paste the pre-change version of the function in next to the current one under a throwaway name, log both results for the same input, and run once. A revert-and-rebuild cycle costs two builds, tells you only *that* the outcome flipped, and leaves the working tree in a state you have to remember to undo; the side-by-side costs one build and prints the two values, which is what identifies the mechanism. Use it when a suspect commit is already narrowed to a handful and you need to confirm which — not as a substitute for narrowing (see [`baselines-repo-layout.md`](baselines-repo-layout.md) → *Commit granularity*). (On #5750 a canonicalization fix was suspected of breaking a converter comparison. Logging the current and the pre-fix canonical forms together returned `ct1 = Convert(p, Nullable\`1).ToString()` / `ct2 = p.ToString()` against `Lt1 = Lt2 = p.ToString()` — the old form matched, the new one didn't, and no exception was thrown on either. That last part mattered: the leading hypothesis had been that the old code would *throw* on this input, and only running it proved otherwise.)

  **Exception: when the change is threaded state rather than a function, revert-and-restore is the cheaper route.** The side-by-side above assumes the old version can be pasted in *next to* the new one under a throwaway name. That fails for a change to state carried **through** a pipeline — a context object rebound in one visitor and read many frames deeper, a flag added to an options record, an ambient scope — because there is no single function whose two versions you can call for the same input; duplicating it means duplicating the whole descent. Revert the hunks, run, restore, run. The cost objection mostly evaporates in this shape: after the first build the two extra runs are **incremental** relinks of one assembly, not the two cold builds the rule warns about, and you can batch every probe question into the same pair of runs. Restore before doing anything else, and diff the tree against the PR head to prove you did. (On #5831 this compared four set operations and a nested-subquery shape across `master` and PR HEAD: two ~1-minute incremental runs after one ~2-minute cold build, and the grid showed `EXCEPT`/`INTERSECT` gaining a null check they should not have — a defect no amount of reading had surfaced.)

  **`git apply` stages, so `git checkout -- <path>` does not undo it.** The restore step above is the one that silently fails. `git apply --3way` writes the patch to the **index** as well as the worktree, and `git checkout -- <path>` restores the worktree *from the index* — so the revert is a no-op, the rebuild changes nothing, and the "control" arm measures the experimental state. Worse, the rule's own proof step doesn't catch it: a bare `git diff` also compares against the index, so it prints nothing and reads as confirmation. The tell is `git status --short` printing `M ` (staged — first column) rather than ` M`; the working revert is `git checkout HEAD -- <path>` (or `git restore --source=HEAD --staged --worktree`), and the working proof is `git diff HEAD`. (Surfaced on #5844: three consecutive probes ran on the un-reverted tree, each reported to the user as a `master` control, before the staged marker was read. The conclusions drawn from all three were wrong.)

  **Disable a probe's target by commenting it out, and restore it with `git checkout HEAD -- <path>` rather than by re-typing.** Two failure modes, both silent, both on the mechanics rather than the reasoning. `if (false) <stmt>;` is not a disabled statement where warnings are errors — it is `CS0162`, so the **build** fails and no test runs; `if (false && cond) <stmt>;` compiles, which is why the same trick works one time and not the next. The tell is the exit code, and it is easy to miss: a test failure and a build failure are both non-zero, so matching on "non-zero" logs a red that never executed a single test — the *fails-for-the-wrong-reason* trap above, in its cheapest form. And restoring by re-typing the original text duplicates whatever the probe's replacement did not remove: if the `old_string` started below a comment block, the "restore" re-adds it and the file now carries it twice. Nothing catches that — not the suite, not the build, because it is usually a comment. `git diff` before committing is the only thing that sees it. (Surfaced on #5877 round 3: an `if (false)` probe exited 1 instead of 2 and was nearly recorded as the red it was supposed to produce; separately a restored three-line comment shipped twice through 37 green fixtures and a clean census, and was caught only in the pre-commit diff read.)

  **Removing a guard orphans the field it guards — the same trap wearing a different diagnostic.** The rule above covers disabling a *statement*. Mutating a guard *away* — reverting an `if (_disposed) return;` to reach the pre-fix behaviour — leaves the flag it tested unread, and under `TreatWarningsAsErrors` an unused private field is `CS0169`. So the mutant never builds, the run exits **1**, and the arm is one glance from being logged as the exit-**2** test-failure red it was supposed to produce. Complete the mutation: take the field out with the guard, as the pre-fix code did. (Surfaced on #5893: reverting `AsyncEnumeratorAsyncWrapper.DisposeAsync` to its unguarded form, to prove a new regression test red, orphaned `_disposed` and failed the build. Reading the log rather than the exit code caught it; the completed mutant then produced the intended exit 2 with the `NullReferenceException` on both the direct and `.LinqService` legs.)

  **To decide whose fault a failure is, include a control with the suspected cause absent entirely.** The variants above vary an implementation or an input to learn a *mechanism*; this one varies the suspected *cause* to learn **whose** it is — the question every "is this in scope?", "is this a regression?" and "did the PR do this?" call actually turns on. Two cells do not settle it: showing the failure with factor X present, and with X-replaced-by-Y, still leaves "X's family is responsible" standing, and that is the shape a review write-up reaches for. The cell that settles it is X gone altogether, and it is usually the cheapest of the three to build. Put every cell in one build and read the grid rather than reasoning from the one you started with. (Surfaced on #5766: `Update(setter)` / `Delete()` throwing `Cannot find target table` on a DTO whose member was typed as a base type had been written up as the PR's own mechanism, described imprecisely. A 3×3 grid — base-typed member, exactly-typed member, and **no DTO at all**, each against `Set(…)`, `Update(setter)` and `Delete()` — showed all three shapes failing identically while `Set(…)` succeeded in all three, so it was a pre-existing routing limitation and the PR's decision to call it out of scope was right. The no-DTO control is the only cell that showed that, and it changed both the severity and what got filed.)

  **A control that passes in every arm measured nothing — make the probe prove it discriminates.** The grid above is only evidence if the cells can disagree, and a probe too blunt to separate them looks exactly like a probe that found no difference: everything green, conclusion drawn, nothing learned. Two failure shapes, both seen in one session. The probe may not exercise the mechanism — a compiled-query hint probe with no argument-dependent inner query left nothing for the suspect path to resolve, so it passed on every state. Or the arms may not differ — a fixture whose two argument values happen to select the same rows cannot show a stale reuse. Guard against both *inside the test*: assert that the arms' expected values are unequal (`Assert.That(expected1, Is.Not.EqualTo(expected2))`) before asserting the results, so a non-discriminating probe fails loudly instead of passing quietly. And when a run passes in an arm you predicted would fail, suspect the probe before revising the model. (Surfaced on #5844, where three passing runs were read as evidence about `master` — two because the probe was blunt, one because the revert above had silently not happened.)

  **The mirror shape is worse, because it looks like success: a control that fails for the *wrong reason* is not a red.** You predicted a failure, you got a failure, the arm is logged as reproduced — and the run never reached the code under test. Copying a script somewhere to run an old version is the classic trigger, because a `$PSScriptRoot`-derived default silently repoints: the copy resolves its repo root relative to the scratch directory, cannot find its inputs, and exits on *that*. Check which failure you got — the predicted exit code and the predicted message — not merely that the exit code was non-zero. A script with distinct exit codes for "violation found" and "could not read inputs" makes this checkable in one glance, which is a reason to give one those codes. (Surfaced 2026-09-03 on #5731: a red arm returned exit **2** — manifest not found — and was almost recorded as the exit **1** it was supposed to produce. Re-running it with an explicit `-RepoRoot` produced the real red.)

  **And when the thing under test is a *gate*, a green run over an input set you assembled yourself is not evidence about the set CI will hand it.** A validator, a linter, a packaging check — anything whose job is to inspect a corpus — is only as verified as the corpus you point it at, and the corpus you build by hand is made of the cases you were already thinking about. It will not contain the artifact class you forgot, and its absence is invisible: the run is green, the summary line ("inspected 17 artifacts", "0 violations") is *true*, and nothing distinguishes "asserted and held" from "had nothing to assert". Before claiming a gate verified, name the classes of input it must handle and check that at least one of each was present — or run it over the same corpus CI uses. (Surfaced 2026-09-03 on #5731, three consecutive times against the same notices gate: an *excluded* package, a *non-Windows RID*, and a *satellite* package were each absent from the hand-built directory, each produced a confident local green, and each was caught by CI one push later. The third arrived after two rounds of the same lesson.)

  **The mirror is a *threshold* you designed, and there the hand-built corpus produces a false red rather than a false green.** The rule above is about a missing input class, so it doesn't fire for a heuristic — a severity cut-off, a regression percentage, a "flag it if it exceeds N× the median" — where the worry is the opposite: not that the rule stays silent, but that it fires on everything. A fixture proves only that the threshold *can* fire, and it proves that by construction, because you chose the numbers to make it fire. It can say nothing about the false-positive rate, which is a property of the real distribution and is exactly what you don't know yet. So a threshold is not verified until it has run against **real** data and been shown to stay quiet on the ordinary case; treat the first real capture as part of designing it, not as a formality afterwards. (Surfaced 2026-09-06 authoring `/profile-analyzers rules`: a "≥ 3× the project's median analyzer time" arm passed a purpose-built fixture and then flagged `LINQ2DB0001`, which costs 0.07 % of the build, because across 565 analyzers the median is 0.058 s — most analyzers do nothing on any given project, so the arm fired on any rule that did any work at all. Replaced with a rank-based arm on the strength of that one real run.)

## Claims you have not run

**A comment a change has falsified is often the symptom, not the finding — check whether the change is mis-scoped first.** When a diff makes a neighbouring comment untrue, the tempting write-up is "stale comment, update the wording". Ask instead whether the *comment* was right and the *code* is wrong: a comment describes intent, so a change that contradicts one has, by construction, altered intent — sometimes further than intended. The highest-yield case is a `PackageReference`, `VersionOverride` or property override placed in an **unconditional** `ItemGroup` of a multi-TFM project, where it silently applies to every TFM including ones that must not have it; the falsified comment is then the only visible trace. Verify the resulting per-TFM state from the restore graph (`project.assets.json`) or the built artifact before proposing either fix. (Surfaced on #5786: a stale `System.Reflection.Metadata` resolver comment in `DriverHelper` was written up as a doc nit; the maintainer's answer was *"that's oversight. netfx too should use 5.6.0, only net8 should use downgraded version"* — an unconditional `VersionOverride` had silently downgraded the LINQPad 5 build's Roslyn. Scoping it to the intended TFM fixed the defect and made the comment true again, so the doc nit dissolved.)

  **The mirror applies to your own changes: after altering behaviour, grep the prose for statements about it.** The rule above is easy to read as being about *someone else's* comment in a diff under review, and that reading is how it gets violated — a behaviour change you make yourself falsifies a readme or doc paragraph, and nothing in the diff points at it because the prose lives in another file. So when a change alters *when* something happens, *where* it is reported, or *which* platform it applies to, search the readme, the docs and the neighbouring comments for the old claim before calling the change done; it is one `Grep` per behaviour word. (Surfaced on #5786 within one session of adding the rule above: restoring Windows message boxes left the driver readme asserting that errors outside the connection dialog are *never* shown in one — true before the change, macOS-only after it, and caught two commits later rather than in the commit that broke it.)

**A cited external precedent is a claim too — check the shipped artifact, not the source repo.** When a review / issue / doc says "project X does it this way", read what X actually *publishes* (the nupkg's nuspec, the released binary, the deployed config), not only its source tree. A repo's source can under-describe its own behaviour: shared props / imported targets / generated metadata supply what the visible file omits, so a source-only read yields a precedent that is real but incomplete — and copying it half-way ships a half-fix. (On #5720 a review cited EF Core's `EFCore.csproj` analyzer reference; `EFCore.Relational.csproj` looked like a plain `ProjectReference` that broke the chain, but the published `Microsoft.EntityFrameworkCore.Relational.nuspec` carries `exclude="Build"` — a shared props file supplies the metadata. Reading only the csprojs would have left every satellite package's hop excluding analyzers.)

  **For a NuGet package specifically, that inspection is one call: [`inspect-nupkg.ps1`](../scripts/inspect-nupkg.ps1).** `& .claude/scripts/inspect-nupkg.ps1 -Id <id> [-Version <v>] [-ScanPattern <regex>]` downloads the package, extracts it, and returns the nuspec's dependency **groups per TFM**, the `lib/` assemblies with their real assembly names, and — with `-ScanPattern` — the distinct matching strings inside those assemblies. The hand-rolled equivalent is four to six calls with two traps in it (`ExtractToFile`'s 3-argument overload is unreachable from a piped `Where-Object`; the flat-container URL needs id *and* version lowercased). Two questions it exists for: *do this version's dependency ranges fit the pins we already have* (see [`release/nuget-package-notes.md`](release/nuget-package-notes.md) → *Prefer the version whose dependencies the repo's pins already satisfy*), and *is this fork a drop-in* — a fork that renames its assembly changes what `DatabaseFacade.ProviderName` and its kin report, which is a code change and not merely a package swap. (Added 2026-09-06 after the sequence was hand-rolled on #5885 to establish exactly those two things about `Microting.EntityFrameworkCore.MySql`.)

**A flag you are about to rely on is a claim too — read `--help` before building a plan around it.** When a proposed approach's *safety* rests on a CLI option (`--dry-run`, `--check`, `--no-act`, `--what-if`), confirm the option exists on that exact subcommand and version before offering the plan, not while executing it. Tools are inconsistent about which subcommands get a dry-run, and the failure mode is silent: the flag is unrecognised or treated as a positional argument, and the "safe probe" performs the real, irreversible action. (On 6.4.0 a plan to reproduce a release-tag failure via `gh release create … --dry-run` was proposed and approved; `gh release create` has no such flag, so running it would have published a real GitHub release. Caught only by reading `gh release create --help` first.) The same caution applies to an option you *remember* existing on a neighbouring subcommand — `--dry-run` on one is no evidence for another.

**A `WebFetch` answer is a claim too — pull the raw artifact for anything load-bearing.** `WebFetch` renders the page and answers your prompt through a *small fast model*, so what comes back is a summary with summary-grade reliability: fine for orientation, not for a fact that a fix, a plan, or a review finding will rest on. When the claim is load-bearing **and** the source is a file in a public repo, fetch the bytes and inspect them yourself — `gh api repos/<owner>/<repo>/contents/<path> -H "Accept: application/vnd.github.raw"` into a file (via the PowerShell tool, which avoids the `>`-redirect prompt), then `Grep` / `Read` it. Reading the implementation also beats reading the vendor's docs, which can contradict their own code. (On PR #5756 a `WebFetch` correctly quoted YDB's `use_in_memory_pdisks_flag`, but in the same session asserted that `YDB_PDISK_SIZE` "does not appear in the provided code" when it does, and relayed a docs table that contradicted the implementation it linked to. The raw-file check settled all three.)

**A NuGet package's MSBuild logic lives in `.props` *and* `.targets` — searching one is not searching the package.** The two are separate files loaded at different points, and which one a package uses for a given piece is its own choice, so a grep of `build/<tfm>/*.targets` that comes back empty is evidence about that file, not about the package. The failure mode is confident and wrong in the deletion direction: a repo-local override that shadows a package-defined target looks like dead code, and removing it silently re-enables whatever the package was guarding. Grep the whole `build/` **and** `buildTransitive/` subtree for the target name before concluding it is unowned. (6.5.0: `SQLite.Runtime.props` disables a `CheckForAnyCPU` target for the LINQPad 5 net472 driver. `SQLitePCLRaw.lib.e_sqlite3` 3.53.3's `build/net471/*.targets` contains no AnyCPU text at all, which briefly read as "the override is a leftover from the dropped `SourceGear.sqlite3` package"; the target is defined in the sibling `SQLitePCLRaw.lib.e_sqlite3.props`, so removing the override would have broken the driver build.)

**To prove a *negative* about external code, enumerate with a repo-wide code search — one file is not the tree.** Reading the single file where a symbol is used establishes what *that file* does; it cannot establish that nothing else does it, which is the claim any "this state can only come from X" conclusion actually rests on. `gh search code --repo <org>/<repo> "<SYMBOL>"` returns every file, so "exactly one writer" becomes checkable rather than assumed — and the answer is often that the definition and the single writer are the only two hits, which is exactly the evidence you need. (On the #5757 review the conclusion turned on PostgreSQL's `DATCONNLIMIT_INVALID_DB` having one writer: reading `dbcommands.c` alone showed one assignment inside `dropdb()`, but only the repo-wide search ruled out `createdb()` / `movedb()` / recovery paths in other files and turned *"an invalid database can only follow an interrupted DROP DATABASE"* from plausible into sound. Note `WebFetch` on the vendor's own docs had already answered the same question with "the documentation does not specify" — twice.)

## Measuring the fix

**Adding a runtime guard? Its false-positive set is what grep cannot see — run the corpus before pushing.** The rules above are about finding which inputs reach code that already exists. The mirror case is a *new* assert you add to shared test infrastructure or a shared engine path: you sweep for the shapes that violate it, annotate those, and push. But a guard's cost is not the violations you found — it is every **legitimate** caller whose shape your sweep did not model, and those are invisible to a grep aimed at the shape you already have in mind. Run the affected suite once before pushing; the false positives announce themselves in a way no amount of reading will. (Surfaced on #5614: a guard requiring every remote-context creator to be classified remote was swept for by `[DataSources]`-shaped parameters, and the three matching tests were annotated. Four cases in `DataContextTests` took no context parameter at all — a shape the sweep had no way to express — and, being `[NonParallelizable]`, already satisfied the invariant by a route the classifier never sees. The guard turned 11 CI legs red on a run that cost ~40 minutes to discover what one local run would have shown.)

**An acceptance measurement is void the moment you edit the surface it measured — re-run it after the *last* edit, and name the commit it describes.** The rule above is about measuring by the right *path*; this one is about measuring at the right *time*, and it fails in the one direction nobody checks. A number taken mid-task ("0 remaining diagnostics", "all green", "N files converted") is true when taken, gets written into the summary, and then a later edit in the same session quietly invalidates it — so the figure you report describes a tree that no longer exists. Nothing goes red, because the measurement already happened. The tell is any edit landing *after* the verification run, however small or however obviously safe: a revert, a carve-out, a comment. Re-measure, or state the figure as of the commit it was taken on. (Surfaced on #5788: `0 remaining L2DB1003/L2DB1004` was measured, then one site was reverted as a deliberate fixture — restoring exactly one diagnostic — and the stale zero was reported to the user and written into the plan's amendment. The critic caught it; a second run would have.)

**Verify a fix by the same path that surfaced the bug.** When a defect was found empirically — a dogfood run, a repro, a CI leg — confirm the fix over that *same* end-to-end path, not only a fresh unit test. A green unit test proves the narrow case; it doesn't prove the fix holds on the real corpus/flow that exposed the bug. (Surfaced when a code-fix defect found by dogfooding was "verified" with a unit test alone — *"was it dogfooded?"* — the end-to-end re-run was the actual proof.)
