#### ASP.NET Core Identity provider

`linq2db.Identity` is an ASP.NET Core Identity store built on LinqToDB. It uses the standard `Microsoft.AspNetCore.Identity` entity types and the same `AspNet*` schema as the EF Core provider, so a database EF Core created works as-is.

```csharp
services.AddScoped(_ => new IdentityDataConnection(
    new DataOptions().UseConnectionString(providerName, connectionString)));

services.AddIdentity<IdentityUser, IdentityRole>()
    .AddLinqToDBStores<IdentityDataConnection>()
    .AddDefaultTokenProviders();
```

Upgrading from the standalone 6.0.0 package:

| Area | 6.0.0 (standalone) | 6.6.0 |
|---|---|---|
| Entity model | `IIdentityUser<TKey>` / `IIdentityRole<TKey>` interface family | `IdentityUser<TKey>` / `IdentityRole<TKey>` base types |
| Context wiring | `IConnectionFactory` / `DefaultConnectionFactory` | a LinqToDB `IDataContext` registered in DI |
| DI registration | `AddLinqToDBStores(new DefaultConnectionFactory())` | `AddLinqToDBStores<TContext>()` |
| Concurrency stamp | manual | automatic |
| Table names | CLR type names | `AspNet*`, as EF Core |

- Existing `AspNet*` tables need no migration. Tables created by the standalone package's `CreateTable<T>()` (`ApplicationUser`, ``IdentityUserClaim`1``, …) need renaming, or their names mapped in a `ConfigureMappings` override.
- On Oracle the text columns are now `NVARCHAR2`. An existing `VARCHAR2` table still returns correct results, but its `NormalizedUserName` / `NormalizedEmail` indexes are no longer used; convert the columns or keep `VARCHAR2` with an Oracle-scoped mapping.
- `UserManager` operations are not atomic: each store call is written when it runs, as LinqToDB has no change tracker.

The full migration guide and the per-provider mappings are in the [package readme](https://github.com/linq2db/linq2db/blob/master/Source/LinqToDB.Identity/readme.md#migrating-from-the-standalone-linq2dbidentity).
